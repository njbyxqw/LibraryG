# TileScape 资源产销统计口径

> [!warning] 验证状态
> 当前为待运行验证版本。事件名、途径值和物品 ID 已按代码及用户确认整理，但 SQL 尚未在当前 TA 环境执行。

## 1. 目标

基于现有 `report_item` 打点统计道具、货币等资源的实际产出与消耗，并按照
`change_method`、`sub_change_method` 区分具体途径。

本文以当前 TileScape 代码实际值为准：

- 累计签到使用 `total_day_sign`。
- 金牌活动使用 `GoldCard`。
- 体力相关的 `power`、`main` 本期均不纳入统计。
- 只统计物品 ID：`1, 6, 7, 8, 11, 12, 13, 14`。
- 本文记录的是静态代码口径；正式验收仍需通过运行时事件日志核对。

## 2. 事件定义

| **事件模块** | **事件名** | **事件显示名** | **事件说明** | **属性名** | **属性显示名** |
| :---: | :---: | :---: | :--- | :--- | :--- |
| 资源类 | `report_item` | 道具产销 | 资源类道具实际发生变化后上报 | 公共事件属性 | 由埋点公共参数统一补充 |
|  |  |  |  | `change_type` | 变化类型：`1` 为产出，`-1` 为消耗 |
|  |  |  |  | `report_item_type` | 物品类型 |
|  |  |  |  | `report_item_id` | 物品 ID |
|  |  |  |  | `change_num` | 实际变化值，使用正数 |
|  |  |  |  | `change_unit` | 变化值单位：`count` 为数量，`duration_seconds` 为限时时长秒数 |
|  |  |  |  | `remain` | 变化后的实际存量 |
|  |  |  |  | `change_method` | 变化途径 |
|  |  |  |  | `sub_change_method` | 副变化途径 |

### 2.1 字段口径

| 属性名 | 类型 | 统计口径 | 注意事项 |
| :--- | :--- | :--- | :--- |
| `change_type` | 整数 | `1` 为产出，`-1` 为消耗 | 不使用 `change_num` 正负判断产销方向 |
| `report_item_type` | 整数 | 取物品配置中的实际类型 | `1` 基础资源；`10` Tile 道具；`11000` 头像；`12000` 头像框 |
| `report_item_id` | 整数 | 取发生变化的实际物品 ID | 奖励配置需要先解析为实际物品后再上报 |
| `change_num` | 整数 | 本次实际变化值的绝对值 | 与 `change_unit` 一起解释，不能使用请求数量代替实际变化量 |
| `change_unit` | 字符串 | `count` 为数量；`duration_seconds` 为限时时长秒数 | 新字段；旧版空值中物品 `6/7/8` 为不可拆的历史混合口径 |
| `remain` | 整数 | 本次变化完成后的存量 | 不能累计求和；限时资源可能表示剩余秒数 |
| `change_method` | 字符串 | 一级来源 | 以第 3 节枚举为准 |
| `sub_change_method` | 字符串 | 来源下的具体关卡、商品、广告或奖励档位 | 同一 `change_method` 内保持格式稳定 |

## 3. 产销方式说明

### 3.1 购买道具的定义

使用钻石购买道具属于一笔资源兑换交易，在资源流水中拆成两条记录：

| 流水方向 | 资源 | 归属报表 | 统计分类 |
| :--- | :--- | :--- | :--- |
| 消耗 | 钻石等支付资源 | 资源消耗表 | `purchase_exchange` |
| 产出 | 玩家实际获得的道具 | 资源产出表 | `purchase_acquisition`，非免费获得 |

两条流水可以分别进入产出、消耗统计，但不能将钻石数量与道具数量直接相减。当前
`report_item` 尚无稳定的交易 ID，因此只能分别统计两侧流水，不能可靠地在数据侧逐笔配对。

“资源总流入”可以包含购买获得的道具；“免费投放”必须排除 `purchase` 和 `ads`：

```text
资源总流入 = 免费投放 + 广告获得 + 购买/兑换获得 + 返还 + 其他获得
免费投放 = is_free_source = 1 的产出
```

### 3.2 本次纳入统计

| **功能** | **change_method** | **sub_change_method** | **说明1** | **说明2** |
| :--- | :--- | :--- | :--- | :--- |
| 商业化支付/兑换 | `purchase` | 商品 ID、PurchaseId 或 OfferId | 消耗侧为购买兑换消耗；产出侧为非免费购买获得 | 局内钻石购买道具时使用所购道具 ID |
| 广告 | `ads` | 广告 `enter_id` | 广告奖励 | 广告配置不可用时当前代码会降级为 placement 字符串 |
| 关卡开始 | `level_start` | `lv_id` 或 `endless_n` | 扣除体力和开局前置道具 | 普通关卡为具体关卡 ID；无尽关为 `endless_n` |
| 关卡内使用道具 | `tile_prop_use` | `lv_id` 或 `endless_n` | 局内使用道具 | 只统计实际扣除的库存 |
| 复活 | `revive` | `lv_id` 或 `endless_n` | 复活资源消耗 | 统计实际扣除的资源及数量 |
| 关卡体力返还 | `level` | `lv_id` 或 `endless_n` | 关卡结算前返还已扣体力 | 只作为关卡流程返还，不归入体力购买 |
| 关卡结束 | `level_end` | `lv_id` 或 `endless_n` | 关卡结算产出 | 包含关卡奖励及局内结算获得的钻石 |

| 无尽免费奖励 | `endless` | `activityId_round_free_n` | 无尽活动免费档奖励 | 包含活动 ID、循环次数和奖励档位 |
| 金牌活动 | `GoldCard` | `collect_*`、`stage_*`、`consume_*` | 金牌活动收集、阶段奖励及消耗 | 大小写以当前代码实际值为准 |
| 邮件 | `mail` | 邮件标题 | 邮件附件奖励 | 当前代码未使用邮件 ID |

### 3.3 产出性质

| 产出性质 | 典型途径 | 是否计入免费投放 |
| :--- | :--- | :---: |
| `free_grant` | `daily_sign`、`total_day_sign`、`account_in`、`mail` | 是 |
| `gameplay_reward` | `level_end`、`home_chest` | 是 |
| `activity_reward` | `endless`、`GoldCard` 的奖励产出 | 是 |
| `ad_reward` | `ads` | 否，单独统计广告获得 |
| `purchase_acquisition` | `purchase` 的正向资源变化 | 否，单独统计购买/兑换获得 |
| `refund` | `level` 等返还 | 否，单独统计返还 |
| `initial_grant` | `ItemInit` | 是，但建议与常规运营投放分开展示 |

### 3.4 本次不纳入统计

| `change_method` | 原因 | 处理方式 |
| :--- | :--- | :--- |
| `power` | 体力界面购买时的钻石支付侧，本期暂不统计 | 查询侧排除，不修改代码 |
| `main` | 体力界面购买后的体力增加，本期暂不统计 | 查询侧排除，不修改代码 |
| `Trade` | 交易来源缺失时的兜底值，无法稳定映射具体业务途径 | 单独监控，不计入正式分途径结果 |
| `GM` | 开发和调试产生的资源变化 | 正式环境统计排除 |
| `ignore` | 内部回滚、试用状态等不应进入业务产销的变化 | 代码已直接禁止上报 |
| 空字符串 | 来源信息缺失 | 单独作为数据质量异常监控，不并入任何业务途径 |

## 5. 数据聚合口径

查询时间由 TA 日期控件自定义选择，默认最近 7 天。SQL 对所选完整区间直接汇总，不固定拆成每日结果；
因此人数是在整个区间内去重，而不是将每日去重人数相加。

人均指标按分析对象区分，不能混用：

- 活跃人均：使用所选区间内 `ta_app_start` 去重用户数，衡量该途径对整体资源经济的影响。
- 产出渠道参与人均：优先使用对应上游参与或完成事件；没有可靠事件时，允许回退为实际产出用户，
  但必须显式标明回退口径。
- 消耗场景参与人均：使用进入消费场景或获得消费机会的上游用户；没有可靠事件时保持为空。
- 实际消耗用户人均：只使用真正发生资源扣除的 `report_item` 用户。

### 5.1 产出

筛选：

```text
event_name = report_item
change_type = 1
report_item_id IN (1, 6, 7, 8, 11, 12, 13, 14)
change_method NOT IN (power, main, Trade, GM)
change_method != ''
```

按以下维度分组：

```text
report_item_type
report_item_id
change_method
```

主报表不按 `sub_change_method` 拆行，避免每个关卡 ID、商品 ID、广告入口或奖励档位各占一行。
需要定位具体入口时，再建立副途径下钻查询。

#### 5.1.1 数量与限时时长

`ItemReward.id` 是奖励配置行 ID，`ItemReward.itemId` 是最终目标物品 ID。奖励解析后传给 ItemSystem 的是
`itemId`，因此 `report_item.report_item_id` 上报的是目标物品 ID，而不是 Reward ID。例如 Reward ID
`17` 会解析为物品 ID `6` 的无限时长奖励，最终 `report_item_id` 仍为 `6`。

旧版 `report_item` 没有 `reward_id`、`effect_id` 或计量单位字段。物品 `6/7/8` 的普通数量与无限时长
都会落在同一个 `report_item_id` 下；无限奖励的 `change_num` 使用秒数，普通奖励使用数量。不能根据
`change_num >= 300` 或是否整除 300 猜测计量类型，否则大额数量奖励会被误分。

新版 `report_item` 增加 `change_unit = count | duration_seconds`。`count` 表示 `change_num` 的单位是个，
`duration_seconds` 表示 `change_num` 的单位是秒；产出 SQL 按该字段拆行。历史数据没有该属性，物品
`6/7/8` 仍标记为“历史混合：数量/时长秒数（不可拆）”，不伪造拆分结果。若以后还需要反查具体
奖励配置，再单独增加 `reward_id` 并从 Reward 解析链路向下透传。新字段只对上线后的事件有效，
历史数据不能无损回填。

在客户端版本上线且 TA 事件表实际出现 `change_unit` 列之前，产出 SQL 使用空字符串作为兼容占位，
保证查询可执行；确认新列入库后，再按 SQL 顶部注释切换为读取 `e.change_unit`。切换前只展示历史
混合口径，切换后新事件按“数量（个）/限时时长（秒）”分行，旧事件仍保留历史混合口径。

指标：

```text
资源总流入 = SUM(change_num)
免费投放量 = SUM(CASE WHEN is_free_source = 1 THEN change_num ELSE 0 END)
广告获得量 = SUM(CASE WHEN source_category = 'ad_reward' THEN change_num ELSE 0 END)
购买/兑换获得量 = SUM(CASE WHEN source_category = 'purchase_acquisition' THEN change_num ELSE 0 END)
产出次数 = COUNT(*)
产出人数 = COUNT(DISTINCT user_id)
活跃人均产出值 = SUM(change_num) / COUNT(DISTINCT ta_app_start.user_id)
渠道参与人均产出值 = SUM(change_num) / 渠道参与人数
产出覆盖率 = 产出人数 / 渠道参与人数
```

产出报表不再计算“渠道参与人数 / ta_app_start 用户数”。渠道参与用户与 `ta_app_start` 用户不一定是
包含关系，该比例可能超过 `100%`。`产出覆盖率`用于衡量进入渠道的用户中实际获得当前物品的比例；
没有可靠上游分母、渠道参与人数回退为实际产出人数时，该指标保持为空，不显示没有分析意义的 `100%`。

### 5.2 消耗

消耗使用负向流水，并排除体力相关的 `power`、`main`：

```text
change_type = -1
report_item_id IN (1, 6, 7, 8, 11, 12, 13, 14)
change_method NOT IN (power, main, Trade, GM)
change_method != ''
```

指标：

```text
实际消耗数量 = SUM(change_num)
消耗次数 = COUNT(*)
消耗人数 = COUNT(DISTINCT user_id)
活跃人均消耗数量 = SUM(change_num) / COUNT(DISTINCT ta_app_start.user_id)
实际消耗用户人均 = SUM(change_num) / 消耗人数
活跃消耗用户率 = 消耗人数 / COUNT(DISTINCT ta_app_start.user_id)
场景参与人均消耗数量 = SUM(change_num) / 场景参与人数
场景使用率 = 消耗人数 / 场景参与人数
```

主消耗表统一统计钻石和其他道具。钻石根据 `change_method + sub_change_method` 在主表中归入三类：
关前购买道具、局内购买道具和复活；其他道具仍按关前消耗、局内使用、活动消耗等途径统计。
`sub_change_method` 只用于分类，不作为主表分组字段。

消耗报表不再计算“场景参与人数 / ta_app_start 用户数”。两组用户不一定是包含关系，直接相除可能
超过 `100%`。没有可靠上游场景事件时，场景参与人数及其派生指标保持为空，不回退为消耗用户数。

#### 5.2.1 钻石消耗三类途径

钻石与其他道具使用同一张资源消耗主表、同一组指标字段，不新增钻石专用结果表。主表只拆三类业务途径：

- 关前购买关前道具：`purchase`，副途径为 `6/7`，分别对应魔法棒和增加收集槽位。
- 局内购买局内道具：`purchase`，副途径为 `11/12/13/14`，分别对应移出一个、风车、磁铁和手套。
- 复活消耗：`revive`，副途径为普通关卡 ID 或无尽关 `endless_n`。
- `power` 是购买体力时的钻石扣除，`main` 是购买后的体力增加；两者均按本期约定排除。

主表不按具体关卡、具体道具或商品 ID 拆行。未命中四类映射的钻石流水保留在“购买/兑换消耗”或
“其他资源消耗”中，用作数据质量排查；后续确有精细入口分析需求时，再单独建立下钻表。

### 5.3 期末存量

`remain` 是单次变化后的库存快照，不能使用 `SUM(remain)`。期末存量应按用户、物品取统计周期内
最后一次 `report_item` 的 `remain`，再根据分析目标计算人数分布、均值或总量。

### 5.4 净产出

```text
净产出 = SUM(
  CASE
    WHEN change_type = 1 THEN change_num
    WHEN change_type = -1 THEN -change_num
    ELSE 0
  END
)
```

净产出沿用产出与消耗各自的过滤口径：`power`、`main` 均不计入总产出、总消耗或净产出。

限时资源的 `change_num`、`remain` 可能表示持续时间秒数，必须与普通数量型资源分开汇总。

### 5.5 渠道参与分母

| 资源途径 | 上游分母事件 | 条件 | 当前 SQL 处理 |
| :--- | :--- | :--- | :--- |
| `ads` | `ad_result` | `ad_result = 1` | 使用完成观看的去重用户数 |
| `level_start` | `lv_start` | 无 | 使用进关去重用户数 |
| `tile_prop_use` | `lv_start` | 无 | 使用进关用户数，表示每名进关用户的道具消耗强度 |
| `revive` | `add_moves_show` | 无 | 使用复活机会展示用户数；实际复活消耗用户仍取 `report_item` |
| `level_end` | `lv_end` | `result = 'win'` | 使用关卡胜利结算去重用户数 |
| `level` | `lv_end` | 无 | 使用全部关卡结算去重用户数 |
| `daily_sign` | `day_sign_reward` | 无 | 使用成功领取签到奖励的去重用户数 |
| `account_in` | `channel_bind` | 无 | 使用绑定成功的去重用户数 |
| `GoldCard` | `lv_start` | `gold_num > 0` | 使用金牌活动覆盖的进关用户数 |
| `purchase` | 暂不统一 | IAP 与游戏内资源兑换混用同一途径 | 产出表回退实际产出用户；消耗表场景指标为空 |
| `total_day_sign` | 暂不统一 | 需按累计签到档位判断实际触发 | 回退为实际产出用户数 |
| `home_chest`、`endless`、`mail`、`ItemInit` | 暂无稳定一一对应事件 | 不使用过宽的 `home_enter` 或付费 `gift_endless` 代替 | 回退为实际产出用户数 |

分母事件只在相同查询时间、测试用户过滤及公共筛选条件下去重。主报表不按 `sub_change_method` 拆行，
因此广告入口、绑定渠道、具体关卡和活动档位只在下钻查询中进一步匹配。

`purchase` 后续必须先从逻辑层拆分 IAP 与游戏内兑换：IAP 可使用 `trackrevenue` 且
`isscalp = false`；游戏内钻石兑换不能套用支付成功用户作为分母。

### 5.6 报表展示字段

SQL 对外输出使用中文列名，同时保留原始途径字段，避免为了可读性丢失排查能力：

| 展示字段 | 用途 | 建议用法 |
| :--- | :--- | :--- |
| 物品名称 | 将物品 ID 转为中文名称 | 作为筛选器或图例 |
| 产出计量口径 | 标记数量、秒数或历史混合口径 | 物品 `6/7/8` 在新增单位字段前不得直接汇总为“个” |
| 产出性质 / 消耗性质 | 对业务途径做一级中文归类 | 作为堆叠维度 |
| 是否免费投放 | 区分免费投放与广告、购买、返还 | 作为产出报表筛选器 |
| 变化途径 | 原始 `change_method` | 用于数据核查，不建议直接作为面向业务的标题 |
| 途径说明 | `change_method` 的中文业务含义 | 作为主要图例或表格维度 |
| 产出值 / 消耗数量 | 实际资源变化量 | 产出值必须结合“产出计量口径”解释 |
| 产出次数 / 消耗次数 | 事件发生次数 | 辅助判断单次发放或消耗强度 |
| 产出人数 / 消耗人数 | 去重用户数 | 辅助判断覆盖面 |
| 区间活跃人数 | 区间内 `ta_app_start` 去重用户数 | 活跃人均指标分母 |
| 活跃人均产出值 / 消耗数量 | 区间资源变化值除以区间活跃人数 | 比较不同时间范围或活跃规模下的资源强度 |
| 渠道 / 场景参与人数 | 对应上游事件去重人数 | 产出使用渠道分母；消耗使用场景机会分母 |
| 渠道参与人均产出值 | 产出值除以渠道参与人数 | 衡量渠道参与人群的资源获得强度；数量和秒数不得跨口径相加 |
| 产出覆盖率 | 产出人数除以可靠的渠道参与人数 | 衡量渠道参与用户中实际获得当前物品的比例；回退分母时为空 |
| 实际消耗用户人均 | 消耗数量除以实际消耗人数 | 衡量实际使用资源玩家的消耗强度 |
| 场景参与人均消耗 | 消耗数量除以场景参与人数 | 衡量每名场景参与者带来的资源消耗 |
| 场景使用率 | 实际消耗人数除以场景参与人数 | 衡量进入场景后实际使用资源的比例 |
| 参与 / 场景分母口径 | 当前行实际使用的上游事件；缺失时明确标记 | 防止不同分母被误比较 |

推荐默认展示最近 7 天的区间汇总：以“物品名称”为主维度，以“产出途径 / 消耗途径”为分类，展示
产出量、消耗量、次数、实际资源用户数、参与人数及对应人均指标。关卡 ID、商品 ID 等高基数字段
不直接作为主图图例。钻石的四类消耗途径直接在主表展示；需要查询其他时间范围时，直接调整 TA 日期控件。

## 6. 数据质量检查

正式统计前至少检查：

1. `change_method` 为空的事件数量及占比。
2. `Trade` 兜底来源的事件数量、物品和触发业务。
3. `ads` 的 `sub_change_method` 是否均为广告 `enter_id`，是否仍存在 placement 字符串。
4. `purchase` 的副途径是否能稳定区分商品、礼包和局内道具购买。
5. `change_num` 是否始终大于 `0`，`change_type` 是否只出现 `1/-1`。
6. 同一用户、物品发生变化后，下一条事件的存量是否与前序变化能够衔接。
7. `power/main/GM` 是否已在正式报表查询中排除。
8. 限时道具是否被错误地与普通数量型道具相加。
9. 上游场景事件人数是否为 `0`，以及是否异常小于对应资源变动用户数。
10. `ads` 的完成用户、`daily_sign` 的领取用户、`account_in` 的绑定成功用户能否覆盖对应
    `report_item` 用户。
11. `GoldCard` 的 `lv_start.gold_num > 0` 是否只在活动有效期和符合资格的人群上报。
12. `purchase` 是否已能按 `sub_change_method` 或交易上下文拆分 IAP 与游戏内资源兑换。

## 8. 逻辑层迭代验收规则

后续新增或修改任一资源途径时，应沿同一链路检查，不能只确认 `report_item` 最终有数据：

```text
业务触发条件
  -> 上游参与/完成事件
  -> 奖励或消耗配置解析
  -> 实际库存变化
  -> report_item(change_type, item_id, change_num, remain, method, sub_method)
  -> SQL 途径分类与参与分母
```

每次迭代至少验证：

1. 上游事件与 `report_item` 使用同一用户标识、时间口径和测试用户过滤条件。
2. `change_method` 与 `sub_change_method` 能反查到唯一业务入口；不能用 UI 展示事件替代成功或领取事件。
3. 产出以实际入库量、消耗以实际扣库量为准，失败、取消、试用和回滚不得进入正式产销。
4. `change_num`、变化前后库存及 `remain` 能组成一致的库存变化链路。
5. 渠道参与人数应大于等于对应资源变化人数；否则优先检查事件漏报、成功条件或时间关联口径。
6. 没有可靠上游事件时，产出表必须明确标为“实际产出用户回退”；消耗表场景指标保持为空，不能把
   实际消耗用户或全活跃用户伪装成场景参与用户。
7. 新增途径需同步更新：代码中的途径常量、TS 打点字典、本文映射表、SQL 分类与测试验数记录。

主报表只保留 `change_method` 粒度；`sub_change_method` 继续在原始事件中保留，并用于关卡、商品、
广告入口和奖励档位的下钻验收。

## 9. 实现顺序建议

### Step1：确认数据表字段

确认数据平台中的 `report_item` 已包含第 2 节七个业务字段以及稳定用户标识、事件时间、应用版本、
平台等公共字段。

### Step2：建立基础过滤

只保留物品 ID 为 `1, 6, 7, 8, 11, 12, 13, 14`，且 `change_type` 为 `1/-1`、
`change_num > 0` 的事件。产出侧和消耗侧均排除 `power`、`main`、`GM`；将 `Trade` 和空途径
单独输出为数据质量结果。

### Step3：建立产出与消耗明细

分别建立资源产出表和资源消耗表。产出表增加 `source_category`、`is_free_source`，消耗表增加
`consumption_category`。主报表按照物品类型、物品 ID、变化途径聚合数量、次数和人数；
副变化途径仅用于需要定位关卡、商品、广告入口或奖励档位时的下钻查询。

### Step4：建立途径映射

根据第 3 节给 `change_method` 增加中文功能名。主报表不输出 `sub_change_method`，原始事件仍需保留
该值，以便下钻追查广告、付费、关卡和活动的具体入口。`purchase` 的正向流水标记为非免费购买获得，
负向流水标记为购买兑换消耗。

### Step5：接入渠道与场景参与分母

按第 5.5 节建立上游事件用户集合，并按 `change_method` 关联。产出表输出渠道参与人数和分母口径；
消耗表输出实际消耗用户人均、场景参与人均、场景使用率和场景分母口径。消耗途径没有可靠上游事件时，
场景指标保持为空，不能回退为实际消耗用户或全活跃用户。

### Step6：校验实际投放与分母链路

选择签到、关卡结算、Journey 宝箱、账号绑定、广告奖励、付费礼包各至少一个入口，在测试环境记录
操作前库存、上游参与事件、配置奖励、操作后库存和 `report_item`，验证实际变化量与分母事件覆盖一致。

### Step7：上线报表

在运行时验数通过后再建立正式产销报表；同时保留空途径、`Trade` 兜底和 placement 降级值的监控，
防止新增功能漏传来源。
