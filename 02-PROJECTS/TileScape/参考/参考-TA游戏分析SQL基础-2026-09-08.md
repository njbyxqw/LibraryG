# TA 游戏分析 SQL 基础

> 用于后续游戏数据 SQL 的共同起点。写具体需求时默认引用本文，只补充该需求特有的 cohort、窗口、指标和筛选条件。

## 使用边界

- 本文记录的是当前项目已使用、已核对过的分析口径，不是所有事件字段的完整字典。
- 表名、字段类型、事件覆盖率和 SQL 方言可能随环境变化；运行新 SQL 前先做小样本字段检查。
- 分析结果要区分“SQL 已跑通”“数据口径已核对”和“业务结论已验证”。前两者不自动证明第三者。

## 当前常用数据源

| 对象 | 当前常用来源 | 用途 | 复用前检查 |
|---|---|---|---|
| 行为事件表 | `ta.v_event_54 e` | 事件、事件时间、设备/渠道字段、关卡和时长属性 | 视图是否可用，分区时间范围是否覆盖 |
| 用户表 | `ta.v_user_54 ta_u` | 注册时间、用户属性、AB 分组、用户分群 | 用户属性是否仍为当前快照，字段类型是否变化 |
| 关联键 | `e."#account_id" = ta_u."#account_id"` | 将事件关联到用户属性 | 是否存在空值、重复用户属性行或匿名 ID 需求 |

> [!warning] 用户属性的时间性
> `active_days` 等用户属性可能是查询时的累计快照，不适合直接回推历史首日。需要历史 cohort 时，优先用注册时间与事件发生本地日计算。

## 常用事件与游戏概念

| 事件 / 字段 | 本文中的含义 | 常用用途 |
|---|---|---|
| `ta_app_start` | App 启动事件 | 新用户激活日、会话开始线索 |
| `ta_app_end` | App 结束事件 | 前台在线时长；常用字段为 `#duration` |
| `lv_start` | 开始一局关卡 | 进关人数、重开、下一关开启 |
| `lv_end` | 一局关卡结束 | 通关/失败/退出、关内时长、关卡结果 |
| `lv_id` | 关卡 ID | 关卡维度分组和筛选；使用时建议 `TRY_CAST` |
| `levelend` | 关局结果 | `1`、`6` 视为成功通关；`2` 失败；`4` 退出；`5` 崩溃。使用时建议 `TRY_CAST` |
| `lv_time` | 关内时长 | 通常由 `lv_end` 提供，单位为秒；需用小样本确认 |
| `#event_time` | 事件发生时间 | 本地日、事件顺序、观察窗口 |
| `#zone_offset` | 设备时区偏移 | 计算本地自然日时使用；空值按 0 处理 |
| `register_time` | 注册时间，毫秒时间戳 | 新用户 cohort 定义 |

### 三类时长

- **前台时长**：同一用户、同一本地日内 `ta_app_end.#duration` 的累计值。
- **关内时长**：同一用户、同一本地日内 `lv_end.lv_time` 的累计值。
- **关外时长**：按用户日计算 `GREATEST(前台时长 - 关内时长, 0)`；再在目标人群中求均值或分位数。

关外时长必须先按用户日截断为非负，再汇总。直接计算“前台均值 − 关内均值”会得到不同结果。

## 时间与新用户口径

### 本地日

当前 SQL 使用下面的本地日表达式；`#event_time` 先按设备时区偏移换算，注册时间按 `-7` 时区转换：

```sql
date(date_add(
  'minute',
  cast((-7 - if("#zone_offset" is null, 0, "#zone_offset")) * 60 as integer),
  "#event_time"
))
```

### 新用户

新用户定义为“注册本地日 = 事件发生本地日”，即下式等于 `0`：

```sql
date_diff(
  'day',
  date(from_unixtime(cast(ta_u."register_time" / 1000 as integer), '-7')),
  date(date_add(
    'minute',
    cast((-7 - if("#zone_offset" is null, 0, "#zone_offset")) * 60 as integer),
    "#event_time"
  ))
) = 0
```

不要以当前 `active_days = 0` 替代这个定义，它可能随用户之后的活跃累计而变化。

### 首次与第二实际游玩日

- **首次游玩日**：新用户第一天出现 `ta_app_end` 且累计 `#duration > 0` 的本地自然日。
- **第二次游玩日**：同一用户第二个满足上述条件的本地自然日；不要求连续次日。
- 这不是“第二个 session”。跨自然日才进入第二实际游玩日。
- 当输出按注册日期汇总时，第二次游玩人数归入用户的注册日期 cohort，而非第二次游玩的发生日期。

## 查询标准结构

```text
new_user_cohort
  └─ 定义注册首日 cohort，并放入全局筛选
base_events
  └─ 关联 cohort，读取 ta_app_end / lv_end 等所需事件
user_day
  └─ 按 用户 × 注册日 × 游玩日 聚合时长和当日最高通关关卡
play_days
  └─ 过滤有效游玩日，计算关外时长，并用 row_number 排首次/第二次
first_play / second_play
  └─ 分别取 play_order = 1 / 2
final select
  └─ 明细输出或按注册日期汇总
```

### 基础骨架

```sql
WITH new_user_cohort AS (
  SELECT DISTINCT
    e."#account_id" AS user_id,
    date(from_unixtime(cast(ta_u."register_time" / 1000 AS integer), '-7')) AS register_date
  FROM ta.v_event_54 e
  JOIN ta.v_user_54 ta_u
    ON e."#account_id" = ta_u."#account_id"
  WHERE e."#event_name" = 'ta_app_start'
    AND e.is_test = false
    AND e."#country_code" <> 'CN'
    AND /* 注册日与事件本地日的 date_diff */ = 0
),
base_events AS (
  SELECT
    c.user_id,
    c.register_date,
    /* 事件本地日 */ AS play_date,
    e."#event_name",
    TRY_CAST(e."#duration" AS double) AS foreground_sec,
    TRY_CAST(e.lv_time AS double) AS in_level_sec,
    TRY_CAST(e.lv_id AS integer) AS lv_id,
    TRY_CAST(e.levelend AS integer) AS levelend
  FROM ta.v_event_54 e
  JOIN new_user_cohort c ON e."#account_id" = c.user_id
  WHERE e."#event_name" IN ('ta_app_end', 'lv_end')
),
user_day AS (
  SELECT
    user_id, register_date, play_date,
    SUM(CASE WHEN "#event_name" = 'ta_app_end' THEN foreground_sec ELSE 0 END) AS foreground_sec,
    SUM(CASE WHEN "#event_name" = 'lv_end' THEN in_level_sec ELSE 0 END) AS in_level_sec,
    MAX(CASE WHEN "#event_name" = 'lv_end' AND levelend IN (1, 6) THEN lv_id END) AS max_clear_level
  FROM base_events
  GROUP BY 1, 2, 3
),
play_days AS (
  SELECT
    *,
    GREATEST(foreground_sec - in_level_sec, 0) AS out_level_sec,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY play_date) AS play_order
  FROM user_day
  WHERE foreground_sec > 0
)
SELECT *
FROM play_days;
```

> 上述骨架刻意省略分区条件、本地日完整表达式和业务筛选；正式运行时必须补齐，且先以小日期范围验证。

## 常用汇总指标

| 指标 | 计算方式 | 解读注意 |
|---|---|---|
| 首次有效游玩人数 | `COUNT(first_play.user_id)` | 不是所有注册人数，而是有 `ta_app_end` 且时长大于 0 的用户 |
| 第二次游玩人数 | `COUNT(second_play.user_id)` | 只计算观测到第二实际游玩日的用户 |
| 第二次游玩率 | `第二次游玩人数 / 首次有效游玩人数` | 晚近 cohort 观察期更短，不能直接横向比较 |
| 最高通关关卡 | 当日成功 `lv_end` 的 `MAX(lv_id)` | 是当天最高通关，不是生命周期累计最高关 |
| 中位数 / P75 | `APPROX_PERCENTILE(metric, 0.5 / 0.75)` | 比最大值更适合描述日常水平 |
| 最大值 | `MAX(metric)` | 用于检查极端用户或异常打点，不宜单独判断趋势 |
| 首次至第二次间隔 | `DATE_DIFF('day', first_play_date, second_play_date)` | 只在已有第二次游玩的用户中计算 |

## 常用筛选写法

全局用户筛选放在 `new_user_cohort`，使 cohort 与所有后续指标保持一致：

```sql
AND e.is_test = false
AND e."#country_code" <> 'CN'
-- AND e."#app_version" = '1.2.16'
-- AND e."#os" = 'iOS'
-- AND CONTAINS(ta_u."ab_group1", '53_2')
-- AND ta_u."ul_ad_layer" IN (1, 2, 3, 6)
-- AND ta_u."ul_user_type" <> 'Tile'
-- AND e."#carrier" <> 'Verizon Wireless'
-- AND e."#account_id" <> '43073964951502848'
```

关卡范围和关卡测试条件不能直接加到 `ta_app_start` cohort：启动事件通常没有 `lv_id` 或 `test_id`。如需限制关卡，应在 `lv_end` 分支单独筛选，并明确它是否也应影响前台时长的分母。

## 运行前检查清单

1. 确认当前可用的事件表、用户表和字段类型。
2. 补齐 `PartDate` / 时间范围，确保事件分区与观察期都覆盖。
3. 用少量用户核对 `ta_app_end.#duration` 与 `lv_end.lv_time` 的单位和空值。
4. 检查 `levelend` 成功编码仍为 `1`、`6`，并确认 `lv_id` 是否需要转换。
5. 明确分母：注册用户、启动用户、首次有效游玩用户或进关用户不能混用。
6. 对回访、流失等结果标注观察窗口；末尾日期 cohort 通常尚未成熟。
7. 先保留明细 SQL，再复制一份做汇总 SQL，便于抽样复核用户级结果。

## 已知边界

- `ta_app_end` 将整段时长归到结束事件的自然日；跨午夜会产生少量日归属偏差。
- `lv_end.lv_time` 只覆盖有结束事件的关局，未结束或缺失事件的关内时间可能被归到关外。
- 使用第二游玩日的指标天然只代表已回访用户；不能外推到全部新用户。
- 当前默认暂不处理 cohort 观察期不完整的问题；正式做趋势判断前应再制定成熟窗口规则。
