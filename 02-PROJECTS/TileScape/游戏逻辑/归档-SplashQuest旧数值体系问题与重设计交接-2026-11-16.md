# SplashQuest 旧数值体系问题与重设计交接

> [!note] 2026-11-18 后续入口已更新
> 本文保留11月16日停止旧体系的历史决定。后续“设计百人七关数值配置”已完成新三档与导表核对，当前保留2573／3720／4787基础总奖，3000候选未采用；不再处于“尚未另起对话”。当前实现仍沿用旧人数／补偿算法，并不意味着本文记录的问题已解决。新状态及适用阈值见 [[02-PROJECTS/TileScape/游戏逻辑/任务-钻石联盟每日三阶段改造#当前三档配置与发放（2026-11-18）|当前三档配置与发放]]。下文所有“当前”指原归档时点。

## 本次决定与适用范围

2026-11-16 用户决定：现有数值体系有问题，后续设计不需要沿用。本轮结束旧体系上的三档与系数调优，整理证据；用户将另起对话重新设计数值配置。

**B1、R0、R1、R2、V1、V1.1 全部降为历史方案／试算。之前“第1版确认”“按 V1.1 落表”“保护组、分组、关型权重先保留”的安排，不再约束新设计。** 不删除历史结果，也不把本次决定解释成已删除游戏内旧算法、已替换配置或已完成新方案。

本轮仅归档及同步状态，不改代码、运行配置、在线源表，不继续给出新系数。活动其他功能工作不因此被取消。多发／正常／少发、低货币用户多发的产品意图可以作为新对话输入，但不能代替目标定义与预算依据。55～104 保护组的目的、实现方式和入组条件均可重审。

## 两个根本设计问题

### 1. 按关型通关率设置难度系数的前提已不适用

用户指出：此需求建立在“一百人参与同样的七关”的旧设定上，当前活动没有必要继续沿用。此处历史动机来自用户说明，不由代码反推。

当前实现会获取玩家接下来主线关卡的类型，结合 `LevelCoefList` 和平均淘汰模型分配逐关淘汰，最后一关补足剩余差额。各组当前关型权重为 `[1,1.1,1.2,0.1,0.5]`。这段逻辑说明它怎样工作，并不能证明虚拟参与者具有对应的真实通关率，更不能证明活动奖励需要依赖这套关型权重。

影响：奖励节奏和部分取整结果被个人主线关型绑定，增加解释、调试和配置成本；旧七关同关竞争前提无法直接支撑当前阶段版经济设计。关型权重的必要性应从当前活动目的重新判断，不把“全部改为 1”当作已经决定的新方案。本次不修改主线关型或难度。

证据：TS `Assets/Module/Activity/SplashQuest/Scripts/ActSplashQuest.PeopleRule.cs`，`GetLevelTypeList`、`GetFailPeople`；活动使用 `ISplashQuestGameData.TryGetUpcomingLevelTypes` 获取当前玩家后续关型。

### 2. 只统计钻石复活不足以代表用户消耗

TS 当前仅接收 `ReviveDiamondSpent`，成功且实际付出钻石的复活才计入活动消费。有限库存道具、广告道具与广告复活没有通过该活动入口参与补偿。MT 原版虽订阅通用 `DiamondConsume`，但在活动内明确过滤 `reason != "revive"`；因此这是原模型范围，不是仅在 TS 迁移时漏接的功能。

影响：同等资源价值的复活与库存道具，可能承担同等成本却得到不同活动反馈。只提高复活系数不能解决这一口径问题。将所有扣款直接相加也不合理：购买道具与之后使用不能重复计费，广告有效回收不等于真实资产减少。

建议保留的方向是复用 DDAV3 的统一资源折算；哪些消费应影响活动、影响多少、何时生效，须在新设计中决定。DDAV3 的计价事实可以复用，其回收目标、记录门禁和活动补偿政策不能直接等同。

证据：TS `ActSplashQuest.FlowAndConfig.cs`、`ActSplashQuest.PeopleRule.cs`（均在上述 SplashQuest 脚本目录）；`Assets/Game/TileV2/Scripts/Entry/TileMatch.Props.cs`。MT `Assets/Activity/DiamondChampion/Scripts/ActDiamondChampion.PeopleRule.cs` 的 `OnDiamondConsume(string reason, int count)`，核对版本 `0c6624ba17`。

## 待原程序确认的代码／接口问题

以下保留为核对清单，尚未取得原程序结论，不以调系数掩盖，也不要求新方案继续兼容错误语义。若新算法不再经过对应路径，应复核问题是否仍适用。

| 编号 | 问题与证据级别 | 影响 | 后续确认事项 |
|---|---|---|---|
| C1 | 旧余额判定与更新口径不一致；源码及离线算例可复现 | 重试首关把旧余额 C 加入消费记录后，判定使用 `(S+C)×k+C`，更新却为 `Round((S+C)×k−奖励增量)`，可能提前触发补偿并产生负余额 | 先确认余额的单位、是否已经乘系数、全额继承还是衰减。不要只清零负值或提高系数 |
| C2 | 关中复活消费持久化风险；静态发现 | `_jewelUse` 在关卡结果时才进入活动记录；扣款后中断、恢复是否漏记尚待实测 | 核对保存时点、断线恢复、重放与消费事件去重；不能直接断言所有重启都会漏记 |
| C3 | 奖励成功契约风险；静态接口发现 | 活动把 `TryGrant` 成功作为已领奖依据，而底层部分失败／异常路径是否能正确回传需核对；可能影响到账与已领一致性 | 核对成功回执、异常分支与幂等，保留真实失败证据；不据此擅改全局奖励接口 |
| C4 | 90% 分组边界存在精度差；离线可复现 | float 的 0.9 约为 0.899999976，与 double 0.9 比较可落入较低分桶。已有 105 关、5000 钻石、倾向 0.4 的边界算例 | 明确阈值比较与统计精度；不是所有小数边界都有同一问题，0.5 不能类推 |

C1 旧模型例：第 1 层第 2 阶段，奖池 10000、下限 10、系数 0.3；期望人数 14、复活 900 后失败，得到余额 215。下一次期望人数 12、没有新消费时，判定预算 279.5 超过奖励增量约 75.76，但更新按 64.5−75.76，取整得到 −11。这里只用于说明双口径，不是新模型测试目标。

完整触发条件与原证据保留在 [[02-PROJECTS/TileScape/游戏逻辑/任务-钻石联盟每日三阶段改造#代码问题与原程序确认清单]]。本次没有联系原程序或宣称风险已确认／修复。

## 其他设计选择与配置隐患

| 分类 | 已发现的问题或行为 | 影响及处理方向 |
|---|---|---|
| 重试设计 | 免费失败重试的随机区间存在向下漂移，即使调整强度为 0 也可能下降 | 没有消费也会逐步提高奖励；是否需要失败保护应显式定义，不继承随机偏移作为保护政策 |
| 补偿设计 | `ExtraJewelCoef` 是额外淘汰预算权重，不是返还比例；严格大于门槛、每关最多额外淘汰 1 人并有下限约束 | 同总消费发生在早／晚关、同一关／分散关，效果可不同，较多复活可能不增加奖励；先定义预期反馈，再决定机制 |
| 余额设计 | 旧余额重新乘系数，失败余额大于 200 又影响下一轮基础人数 | 当前补偿与后续重试扶持互相牵制。提高系数可能使某些付费失败重试路径最终发放下降，V1.1 已出现此类反例 |
| 人数边界 | 配置下限约束基础期望及额外淘汰判断，不能保证实际最终人数硬下限 | 用户此前已接受旧行为，不能重新归类为已确认 bug；新设计自行决定奖励边界，不自动继承硬下限或原实现 |
| 分组设计 | 当前按裸钻石、连胜表现、复活倾向共同选组，低余额并不总是多发 | 分组目标与映射应重新对齐。裸钻石 4000／10000 阈值不能直接移植到含库存道具的总资产口径 |
| 统计设计 | 最近 30 条每日记录不等于最近 30 个自然日，缺分母返回 0 | 活跃间隔、缺数据与真实低倾向可能混为一组；需要明确定义样本窗口和未知值 |
| 前期保护 | 活动通常 55 关开启，规则 50～104 统一第 5 层，参数与第 3 层相同 | “保护组”名称不证明实际保护效果；保护目标及参数需要新设计评估 |
| 分组配置 | 空兜底规则、层 0 可配置但就绪条件要求大于 0、缺属性默认 0 | 可能未正常兜底或静默落错组；需结合真实加载与账号样本确认，不把静态风险写成线上事故 |
| 奖励尾部 | 当前不同组共享部分人数下限，多次重试／高消费后可能趋同 | 首次无消费均值不同不保证高消费、失败路径仍有稳定档位差异 |
| 配置覆盖 | 多条 Main 共用 id，活动按 id+层选择，通用增量覆盖若只按 id 则有歧义 | 尚无实际覆盖事故证据；新方案导出时验证多层完整性，不仅看编辑表 |
| 配置生命周期 | 当前锁定层号不等于冻结全部参数；期中配置变化可能影响进行中的活动 | 新配置设计需要明确读取和生效时点 |
| 数组与源表 | 7／7／15 长度取实际 5／7／10 前缀；旧在线表与本地导出的关数、奖池版本曾有差异 | 尾项冗余不等于越界；下次设计／导出前重新核对真实源表版本，本次不推断线上状态 |
| 评估方法 | 试算按入口关卡等权、给定消费和最终完成路径，没有线上参与／完成／流失分布 | 结果是条件场景发放，不是参与玩家日均。道具提升通关概率及 DDA 反馈没有被完整建模 |
| 旧校准假设 | V1.1 用“最小 500 价值消耗跨首次额外淘汰门槛”校准 | 这是上轮试算假设，没有已确认的产品目标依据；撤下为设计标准，不作为新方案约束 |

## DDAV3 可复用事实与边界

本轮源码核对的有限道具单位价值：撤回 500、移出 900、自动配对 900、洗牌 1300。库存及广告来源回收比例当前均为 100%；有效记录还受 V3 循环、游戏状态、恢复／重放等条件控制。成功付费复活通常以实际金额折算；广告复活按报价折算。未来使用前应核对当时配置，不能把本表当作永久常数。

分析必须分清：**真实钻石与库存变动、DDAV3 有效回收、活动奖励／补偿**。广告有效回收并不直接减少原有资产；购买和使用道具不能重复计算同一成本；未消耗有限库存的无限道具不能直接按库存扣减记账。

源码定位：

- `Assets/Game/TileV2/Scripts/DataCenter/TileMatchDataCenter.Recovery.cs`：资产折算、有效消费解析与提交。
- `Assets/Game/TileV2/Scripts/Entry/TileMatch.Recovery.cs`：成功消费至回收处理的接入。
- `Assets/Game/TileV2/Config/TableConfigLevelControlV3/ddav3consumeconfig.json~`、`Assets/Game/TileV2/Config/TableConfig/tilepropbuycfg.json~`：折算比例与购买单价依据。
- 判断链：V3 开关 → 新循环默认策略／Coins 覆盖、已有循环沿用 → 回收缺口 → Retry 修改 → 局内保护。目前没有 SplashQuest 专属策略已接入的证据。

保留统一估值、后续在 DDAV3 判断链研究活动策略的方向，不建设另一套独立 DDA。具体覆盖时点、已有循环与回收量如何承接，仍未设计。详见 [[02-PROJECTS/TileScape/游戏逻辑/任务-DDAV3逻辑策略持续研究#活动策略接入边界]]。

## 新对话交接

先读本归档，重新确定活动的目标、发放预算、资源口径与失败／消费反馈，再设计用户分组、配置结构和模拟。旧均值、系数、关型权重、补偿余额、200 阈值、单关额外淘汰上限以及 500 触发标准均不是必须继承的约束。

可沿用的是已经查明的源码入口、DDAV3 估值事实、旧模型反例与产品背景。需要重新论证的是奖励怎样产生、为什么随这些行为改变，以及如何验证人群和阶段效果。无需为了保留旧实现而先做局部修补；也不能在没有新设计时把本次归档直接变成改代码指令。

本次交接完成，不继续设计新数值；代码问题继续保留待原程序确认。
