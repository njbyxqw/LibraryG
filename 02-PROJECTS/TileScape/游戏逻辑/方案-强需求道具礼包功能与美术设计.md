# TS 强需求道具礼包：功能与美术设计

> 2026-11-19：按用户要求，功能已单独收拢为[[02-PROJECTS/TileScape/游戏逻辑/方案-道具礼包功能逻辑|道具礼包功能逻辑]]，仅描述触发、展示、购买及回流。功能评审以该稿为入口；本文保留前序数值、美术及综合讨论，不将其中提案视为已确认规则。

**玩家在局内缺少某种道具，主动点击货币购买但余额不足时，跳转商城，并立即看到顶部 Banner 第一位的对应道具礼包。礼包支付成功并完成奖励入账后，通过界面回调关闭商城，刷新局内道具数量，由玩家再次点击使用。**

这是 TS 功能设计稿。核心入口、首位展示、买后关闭商城与刷新库存来自2026-11-18用户要求；其余标为“建议”的内容为本稿提案。具体售价、奖励数量、分档参数尚未定版。TF 调研正文、HTML及拼装图继续保留为独立原始资料，本稿不覆盖它们。

阅读版与四类 Banner 结构示意：[[02-PROJECTS/TileScape/游戏逻辑/TS_Prop_Offer_Design.html|打开设计文档]]。代码依据单独存放于[[02-PROJECTS/TileScape/参考/核对-道具购买缺货跳商店与支付回流-2026-11-18|入口与回流核对]]。

## 1. 定位与本期范围

礼包解决的是“现在就需要该道具，但既没有可用库存，也没有足够购买货币”的强需求。玩家已经主动表达购买意愿，因此先保证对应商品在商店首屏可见，再讨论促销包装与客单价。

| 项目 | 本期设计 |
|---|---|
| 展示入口 | 局内道具货币购买失败后，点击跳转独立商城页 |
| 展示位置 | 商城顶部 Banner 区的第一个轮播项，首次打开直接停在该项 |
| 定向依据 | 本次被点击购买的道具，不按“所有零库存道具”随机选择 |
| 商品形态 | 现金 IAP 礼包；目标道具为主，附带购买货币及其他局内道具 |
| 首批道具建议 | 撤回、手套、磁铁、风车四种，与 TS 当前局内按钮一致 |
| 购买后 | 奖励入账 → 成功界面回调 → 关闭商城及本次遗留购买弹窗 → 刷新道具/货币 → 回到原关卡 |
| 使用行为 | 不自动使用道具，不补扣跳转前未付出的货币；玩家再次点击道具 |
| 本期暂不扩展 | 失败N次强弹、Home登录强弹、另建礼包入口、限时道具售卖、TF加格礼包直接移植 |
| 尚未定版 | 具体售价、正式奖励、档位数量、选档窗口、独立开放关卡、促销标签 |

说明：用户描述中的“金币”在本机 TS 实现里对应道具购买货币 **DIAMOND（ID=1，钻石）**。本稿统一称“购买货币（当前代码为钻石）”；代码枚举不等于图形。11月19日用户TS截图中货币以星形金币呈现，美术沿用该形象，接入时核对ID对应资源，不因DIAMOND命名改画蓝钻。TF金币与TS钻石不存在已确认的1∶1兑换关系。

## 2. 当前链路核对与需要补齐的部分

核对对象为本机 `D:/TileScape_fresh` 可读源码，非线上实测。当前仓库已改用 `.cursor/rules` 入口，旧 `Docs/Knowledge` 三文件在本机不存在；本次依据项目AGENTS、LG索引和实际源码定位。Git提交身份未能读取，不能断言本机代码与正在测试的直购版本完全一致。

| 用户关注点 | 本机代码事实 | 本方案处理 |
|---|---|---|
| 普通库存不足且无可用限时道具 | 已有。`CanUse(itemId,1)`统一覆盖有效限时无限效果和可消费数量堆栈；道具按钮按`CanConsume`选择使用或获取入口 | 复用统一“可用库存”判定，不只检查普通数量=0 |
| 点击购买且货币不足跳商城 | 已有。购买服务扣货币失败后，若货币为DIAMOND，路由至`ShopPanel` | 在这一具体失败原因处携带本次目标道具及来源 |
| 单次点击直购 | 本机控制器先开`UIPropBuyPanel`，再由弹窗购买按钮调用购买服务；未核到用户描述版本的单击直接扣款路径 | 以“实际尝试货币购买且余额不足”为统一接入点；最终分支若是直接购买，也走同一语义入口 |
| 商城知道缺哪个道具 | 尚无。现有跳转参数为null；`ShopOpenContext`仅有Home/Match来源 | 增加本次目标道具与进入原因，不能只凭Match判断 |
| Banner首个展示 | 已有排序和从索引0展示能力，候选按Priority降序排序 | 本次定向礼包明确放到首位，且只插入一次 |
| 支付后关闭商城 | 已有局内奖励展示结束后关闭独立商城的回调；全局购买成功通知本身主要用于标记和刷新 | 复用成功回流能力，核对新Banner实际接入交易链和旧购买弹窗清理 |
| 道具数量刷新 | 控制器已订阅对应道具库存变化事件 | 回流后再同步当前状态，避免隐藏期间显示残留 |

特别注意：现有金币/钻石不足跳转基于“扣款失败”，不是专门的错误码。接入礼包时要区分**余额不足**与服务/配置异常；后者不得被当作强需求曝光。

## 3. 展示条件与玩家流程

**完整触发条件：** 道具已解锁且入口可交互 → 玩家主动点击该道具的货币购买按钮 → 当前没有足够使用一次的可用道具（包括普通、有效限时数量、有效限时无限）→ 当前购买货币余额低于本次购买费用 → 对应现金礼包配置及IAP可售资格有效。

前四项决定进入“道具缺货、货币不足”的商城场景；最后一项决定是否在商城展示该礼包。没有可售礼包时，仍进入正常商城，不能卡住购买流程。

| 点击时状态 | 处理 | 定向礼包 |
|---|---|---|
| 未解锁、教学锁定或当前输入被阻塞 | 保持现有入口限制 | 不触发 |
| 有普通库存，可使用一次 | 走现有使用逻辑 | 不触发 |
| 普通库存为0，但有限时数量或限时无限可用 | 走对应道具使用逻辑 | 不触发 |
| 无可用库存，但未点击购买 | 只显示购买入口 | 不自动弹出 |
| 无可用库存，点击购买，货币足够或恰好等于费用 | 走原有货币购买流程 | 不触发 |
| 无可用库存，点击购买，货币不足（含余额0） | 打开独立商城，携带目标道具 | 有有效商品则首位展示 |
| 商品不可售、配置缺失、定向图资源加载失败 | 正常商城兜底；不显示空白礼包或错误购买按钮 | 本次不展示 |
| 从Home、复活、货币栏“＋”等其他入口进商城 | 保持各自原流程 | 建议不展示本场景专属礼包 |

**点击时重查。** 展示为“购买”不代表点击时仍然缺道具。奖励可能刚到账，限时道具也可能刚生效；实际跳转前需按当前库存和余额重查。道具在棋盘上的使用条件继续由现有玩法判断，本礼包不额外引入“必须死局”条件。

**正常路径：** 点击购买 → 余额不足 → 商城打开并定位到顶部 → 对应道具礼包位于Banner第0项 → 点击礼包价格按钮 → 支付与发奖 → 成功回调关闭商城 → 原关卡显示最新库存 → 玩家决定何时使用。

如果实际版本还保留`UIPropBuyPanel`，它不能在商城关闭后继续遮住关卡。建议将它纳入本次跳转链的清理范围：成功回流关闭本次旧购买弹窗；主动取消商城时可返回该弹窗，沿用原有操作层级。单击直购版本没有这一层，无需新增。

## 4. 商城首屏与Banner规则

| 规则 | 设计要求 |
|---|---|
| 首屏位置 | 打开后纵向列表位于顶部；目标礼包横向索引为0，两项需同时满足 |
| 首次显示 | 页面第一次可见时就是目标礼包，避免先显示常规活动再切换造成闪动 |
| 目标唯一 | 同一次打开只展示本次需求道具的一档礼包；不同时塞入四个定向礼包 |
| 其他Banner | 保留其他合格Banner的相对顺序，目标礼包插入后避免重复 |
| 上下文有效期 | 仅本次商城会话有效；手动关闭、购买完成或场景离开后清理。下次普通进店不继承 |
| 点击连续发生 | 打开中防重复；已有商城时不叠加第二个窗口，避免支付来源串道具 |
| 页面刷新 | 在同次会话内锁定目标道具与已展示商品，不能因后台分层刷新无提示换价 |
| 轮播建议 | 强需求首项默认停留，允许手动滑动；首次自动轮播暂缓，避免用户刚进店3秒即失去目标。属于建议待评审，不影响“首位展示”核心要求 |
| 无效兜底 | 请求目标商品失败时使用正常商城；不展示伪价格、无奖励商品或空位 |

现有商城Banner默认3秒轮播、0.45秒切换。若保留自动轮播，至少保证首屏先展示目标礼包，并在触摸、支付准备、系统支付中暂停；最终选择“停留到手动切换”或“延长首项停留”在评审时确认，不直接照抄TF的5秒。

## 5. 奖励结构与配置参考

建议采用 **目标道具补给 + 购买货币 + 其他三种道具**。每种目标道具有独立奖励组，展示模板共用。以TF的道具偏重结构为起点，但不把TF金币量和美元档位直接变成TS正式数值。

| TF资源 | TS对应 | 迁移方式 |
|---|---|---|
| 撤回 | 撤回（11） | 对应使用需求，沿用TS图标与实际效果描述 |
| 抓钩 | 手套（14） | 对应移牌/开路需求，不沿用抓钩图标或英文propeller |
| 磁铁 | 磁铁（13） | 对应凑消需求 |
| 洗牌 | 风车（12） | 对应重排需求，使用TS现有名称与美术 |
| 加格 | 本期不纳入四类入口 | TS存在ADD_SLOT常量不等于已具备本次完整局内购买入口 |
| 金币 | 购买货币（当前钻石ID=1） | 数量需按TS经济重新配置，不能1∶1搬运 |

下表为**奖励数量讨论稿**：取TF四类目标道具的“合计到账量”作为TS评估起点。A/B/C/D只是参考层级，是否全部启用待定；全部数量与货币均未批准上线。

| 目标道具 | 参考层级 | 目标道具总数 | 其他三种各 | TS购买货币 | 售价 |
|---|---|---:|---:|---|---|
| 撤回 | A / B / C / D | 8 / 10 / 15 / 31 | 2 / 2 / 3 / 6 | 各档待定 | 后续讨论 |
| 手套 | A / B / C / D | 5 / 8 / 11 / 22 | 1 / 2 / 3 / 6 | 各档待定 | 后续讨论 |
| 磁铁 | A / B / C / D | 4 / 6 / 9 / 18 | 1 / 2 / 3 / 6 | 各档待定 | 后续讨论 |
| 风车 | A / B / C / D | 5 / 8 / 11 / 22 | 1 / 2 / 3 / 6 | 各档待定 | 后续讨论 |

**显示与到账统一。** 建议TS把重复道具先合并成一个奖励项：例如手套A档大图显示“手套×5”，侧面显示钻石及撤回/磁铁/风车各×1。不要大图×5后又在小图补一个手套；也不要将礼包本体内的奖励标成额外赠品。若后续坚持TF的“主奖励×4 + 基础包内×1”表现，必须清楚标总计5，并从同一份最终奖励数据生成UI和发奖，二者不能各填一份。

奖励建议为普通可累计数量道具。限时无限道具、体力、章节物品不纳入首版，避免稀释“补充当下缺少的道具”的信息。礼包至少能补充一次目标道具；正式量还需结合TS当前单次购买价、单局消耗、直购/复活关系和已有商店包价值校准。

## 6. 定价方向与配置需求

**本轮不确定价格。** 可参考TF“近期成功付费的单笔中位价 → 对应道具组候选档”的方法：无有效记录用默认入门档，有记录则在该道具候选档内选择接近玩家既有付费习惯的一档。窗口长度、是否跨商品组、等距选高还是低、档位上限均待讨论，不默认继承TF全部参数。

TS现有商店已经有用户分层控制器。后续定价评审应先比较“复用现有分层”与“本礼包独立中位价选档”，再决定是否新增策略；本期只要求展示模块能接收一个确定SKU，在同次展示/支付期间保持一致。展示价格取实际商店本地化报价，未取得报价时不允许发起该商品购买。

| 配置概念（名称示意） | 用途 | 当前状态 |
|---|---|---|
| 功能开关、目标道具ID | 控制是否启用及四类映射 | 功能需要 |
| 触发来源 | 仅“道具货币购买不足”的定向场景 | 核心要求 |
| 道具组 → 候选SKU | 在正确组内选择商品 | 功能需要；实际SKU待定 |
| SKU → 完整奖励清单 | 目标总数、货币、其他道具 | 结构确定；正式数量待定 |
| 价格/选档策略/默认档 | 产生本次确定商品 | 后续讨论 |
| 标题、图标、Banner模板 | 同一模板展示四类内容 | 见美术需求 |
| 本次来源与回流信息 | 缺货道具、进入原因、原关卡/页面、本次打开标识 | 需要补齐；不是长期库存或玩家偏好 |

不照搬TF的30关、商品限购、冷却或限时促销。首版建议遵从TS道具解锁与IAP基础资格，不另加未讨论的强制关卡门槛或倒计时；如果后续需要投放限制，再补规则。

## 7. 支付成功后的界面回调

| 结果 | 界面处理 | 库存与行为 |
|---|---|---|
| 本次礼包交易成功且奖励已入账 | 完成必要奖励反馈后关闭本次商城；处理遗留购买弹窗，回到原关卡 | 刷新四种道具及货币；不自动使用、不补扣直购费用 |
| 支付取消或明确失败 | 留在商城当前礼包位置，恢复购买按钮 | 不关闭关卡，不生成成功反馈 |
| 支付处理中/待恢复 | 保留处理中提示，防重复提交 | 未完成入账前不冒充成功，不预加显示数量 |
| 已扣费但发奖异常 | 走既有交易恢复/补发路径 | 不把SDK支付成功直接当作礼包已完成 |
| 玩家主动关商城 | 按原页面栈返回；清理本次定向来源 | 不自动扣款或用道具 |
| 延迟成功时原关卡/窗口已不存在 | 奖励通过正常账户系统入账 | 不强开已离开的关卡、不关闭另一轮新商城 |

这里的“支付成功后的界面回调”以**交易成功、奖励完成入账**为条件，不能仅监听系统支付页关闭。TS已有奖励入账与展示分离的流程，应复用，不在UI另发一遍奖励。

本机常规局内商店当前为“奖励展示结束后关闭商城”。首版建议沿用这条短回流，不新增独立领取页；回调、库存变化通知、商城关闭三者需协调，做到返回关卡时可见数量已是最新值。若要求改成入账后立即关商城、奖励飞向局内按钮，可作为后续表现调整。

从此入口进入商城后，如果玩家改买其他常规商品，建议继续沿用现有局内商城购买回流。定向礼包回调只处理本次会话的UI清理，不能把其他全局购买成功误认成这张礼包成交。

## 8. 美术与交互设计

**2026-11-19美术需求细化：** 根据用户新增的Booster Pack与Prop Favor两张截图，形成独立交付稿[[02-PROJECTS/TileScape/游戏逻辑/需求-道具礼包BannerUI美术|道具礼包Banner UI美术需求]]，图文优先阅读[[02-PROJECTS/TileScape/游戏逻辑/TS_Prop_Banner_Art.html|UI美术需求网页]]（四道具切换与分区示意）。用户随后明确样式参考TS商城截图，当前V2主稿改为奶油圆框、浅米灰奖励分组、红色底栏、绿色购买按钮，并提供TS顶部蓝框／橙底栏对照；原V1竞品金边方向已被替代。三组奖励分区，右侧其他三道具按上二下一居中排列。属于待评审美术提案。原HTML中的蓝色交互草图保留作早期结构参考，其配色和右侧横排不作为本版美术要求。

**制作目标：一眼看见“正缺的那个道具”，其次看清购买所得与价格。** 使用TS现有欧卡休闲风格、道具图标、货币图标、按钮和字体。TS现有商城礼包样式作为视觉依据，默认不增加竞品Popular或TS促销90%OFF角标；TF原图不直接作为TS交付资产。

## 9. 关键检查点与轻量监控

| 场景 | 预期 |
|---|---|
| 库存0、无有效限时道具、货币不足 | 点击购买才进店；对应礼包首次可见且在首位 |
| 库存0但限时无限仍有效 / 有限时数量 | 不误进本场景 |
| 余额=费用 / 余额=0 | 前者走原购买，后者可触发缺货礼包 |
| 连续点、关闭重开、切另一道具 | 不叠窗，不继承上一次目标，不展示错包 |
| 商品缺失或不可售 | 正常商城兜底，无空卡/伪价格 |
| 多Banner和商城刷新 | 首次位置正确；本次SKU不无提示改变 |
| 礼包成功 | 原关卡恢复，库存与奖励一致，不自动用一个，不补扣原直购费用 |
| 取消/失败/待恢复/晚到回调 | 不伪成功，不重复入账，不误关闭后开的窗口 |

监控先覆盖这条漏斗：货币不足触发 → 商城打开 → 定向Banner实际可见 → 购买点击 → 交易成功 → 关闭回流 → 玩家再次使用目标道具。记录本次来源、目标道具、SKU/档位、展示位置与失败原因，订单使用既有标识关联。后续观察定向礼包转化、成功回流率、买后目标道具使用，以及对原直购/复活和整体收入的影响。事件正式名称与报表字段后续对齐现有打点，不在本轮另建分析平台方案。
