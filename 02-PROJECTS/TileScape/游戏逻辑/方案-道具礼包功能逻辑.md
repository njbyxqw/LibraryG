# TS 道具礼包功能逻辑

**当玩家在关卡内需要某个道具、没有可用库存，并主动尝试用金币购买但金币不足时，打开商城，优先展示该道具的礼包。礼包购买成功且奖励到账后，关闭商城，返回原关卡并刷新道具数量。**

本稿作为本功能的独立逻辑评审入口，仅描述条件、行为、状态和回流，不包含奖励数值、定价策略及美术设计。用户已明确“缺货购买时金币不足进入商城、顶部Banner首位展示、成功回调关闭商城并刷新道具数量”；下文补充的是本版逻辑设计，不表示均已获得确认或已经实现。金币在本文指玩家实际用于购买道具的货币。

## 1. 触发条件

目标道具为玩家本次点击购买的道具。触发需同时满足：

| 条件 | 判定口径 |
|---|---|
| 正在关卡内，目标道具购买入口可操作 | 沿用道具解锁、教学及输入限制，不新增解锁体系 |
| 目标道具当前不可从库存中使用 | 普通库存不足，且没有能够支持本次使用的有效限时道具；有效限时数量及限时无限均计入可用状态 |
| 玩家主动发起该道具的金币购买 | 必须发生购买操作，仅库存不足、金币不足或停留在关卡中均不触发 |
| 本次购买因金币余额不足而无法完成 | 必须确定是余额不足，不能将配置缺失、服务错误等购买失败统一当成此场景 |

**“进入商城”与“展示礼包”分开判断。** 前述条件满足时走现有金币不足跳商城流程；商城再检查功能是否启用、目标道具是否有对应礼包、商品是否可购买。符合才展示定向礼包，否则正常打开商城。

在实际购买点击时重查道具可用性和余额，使用同一套库存判定。若道具刚到账或限时效果刚生效，交回现有道具逻辑处理，不再以旧状态触发礼包；若金币已经足够，走原金币购买流程。礼包功能不额外要求死局、失败次数或其他付费压力条件。

## 2. 进入商城与展示规则

本次跳转保留“为什么进店、缺哪个道具、从哪个关卡或页面返回”的信息，商城据此生成对应礼包。不能仅凭“从关卡打开商城”判断，因为复活、金币栏等入口也可能来自关卡。

| 规则 | 处理 |
|---|---|
| 对应关系 | 本次点击哪种道具，就展示哪种道具的礼包，不随机选择其他缺货道具 |
| 展示位置 | 商城纵向打开在顶部，目标礼包位于顶部Banner的首个展示位，页面首次可见时就展示它 |
| 展示数量 | 本次只确定一个目标礼包，不同时加入所有缺货道具的礼包 |
| 与现有Banner共存 | 目标礼包置于首位，其余有效Banner按原相对顺序排列；同一商品不重复插入 |
| 会话内刷新 | 保持本次目标及商品一致，不因页面刷新悄悄换成其他道具或商品；商品失效则停止该商品购买并走兜底 |
| 本次信息的有效期 | 仅用于本次打开商城；退出商城或离开原场景后清理，下次打开重新根据入口判断 |
| 连续点击 | 同一次跳转只打开一个商城，不重复叠加窗口或替换正在支付的目标 |

首次是否暂停自动轮播仍待确认；无论选择哪种轮播行为，都必须保证目标礼包在商城第一次显示时处于首位。

从Home、复活、金币栏等其他入口进入商城，保持各入口原有规则，不继承上一次的定向礼包。本稿不新增这些入口的主动推荐规则。

## 3. 购买与成功回流

玩家在商城点击礼包的购买入口，进入现有支付与发奖流程。礼包展示、购买和发奖必须对应同一个商品，不在界面层单独发奖励。

成功顺序为：**确认交易完成及奖励入账，完成现有必要的奖励反馈，通过本次界面回调关闭商城，回到原关卡并同步最新道具和金币状态。** 实际入账可以早于界面关闭，但玩家看到关卡时，库存显示必须已更新。

本版默认购买只补充库存：不补扣跳转前未完成的金币购买，不自动消耗刚获得的道具，由玩家回到关卡后自行点击使用。这属于本次补充的行为规则，避免将“礼包购买”误执行成“继续之前的金币直购”。

若实际版本仍有道具购买弹窗，成功回流需一并关闭本次操作遗留的该弹窗，避免关闭商城后仍被遮挡。若实际版本已是单击直购，则无需增加这层界面。

## 4. 各结果的处理

| 结果或操作 | 商城及返回处理 | 库存与后续行为 |
|---|---|---|
| 礼包购买成功、奖励已到账 | 完成现有成功回调，关闭本次商城，返回原关卡 | 刷新最新库存及金币，不自动使用 |
| 玩家取消支付或支付明确失败 | 留在当前商城，恢复可操作状态 | 不新增奖励，不触发成功回流 |
| 支付处理中或订单结果未定 | 走现有处理中／订单恢复流程，避免重复提交该交易 | 不预加数量，不提前视为成功 |
| 支付已成功，但奖励尚未确认到账 | 交由现有交易恢复与补发流程处理；不能走“已完成”回流 | 不重复发奖，也不让界面假装已获得道具 |
| 玩家未购买，手动关闭商城 | 按原页面层级返回，清理本次定向信息；若保留旧购买弹窗，取消时沿用原返回层级 | 不扣金币、不用道具；重新点击时重新判断条件 |
| 对应礼包缺失或不可购买 | 展示正常商城，不出现空白礼包或无效购买入口 | 原金币不足跳商城能力继续可用 |
| 回调到达前，玩家已离开原关卡或打开另一轮商城 | 只让正常订单流程完成奖励处理，不强行拉回旧关卡，也不关闭新窗口 | 账户数据正常更新；后续界面显示最新库存 |

玩家进店后可以滑动并购买其他常规商品。其购买与返回沿用现有商城规则，不将其他商品的成功错误识别为本礼包成功；是否统一修改所有局内购买回流不属于本次新增范围。

## 5. 需要接入的逻辑与现有依据

以下依据来自11月18日的本机静态核对，并非本轮重新检查的当前分支事实。

| 环节 | 已有依据 | 本功能需补齐或核对 |
|---|---|---|
| 无可用道具判断 | 已有统一库存判断，覆盖有效限时效果 | 购买点击时复用并重查，避免只看普通数量 |
| 金币不足跳商城 | 已有购买失败后跳商城路径 | 明确区分余额不足与其他失败原因 |
| 目标信息传递 | 当时商城仅知道Home／Match来源 | 补本次缺货道具、进入原因与返回关联 |
| Banner首位显示 | 已有排序、横向首项与纵向回顶部能力 | 确保本次目标优先、首次即显示、不会重复或带到下一次进店 |
| 支付与回流 | 已有奖励展示结束后关闭局内独立商城、库存变化刷新 | 新礼包接入统一交易；回调只处理本次页面；处理遗留道具购买弹窗 |

**实施前必须确认的现状差异：** 用户描述为道具单击直购金币不足后跳商城；11月18日本机代码仍先打开道具购买弹窗，再由弹窗购买按钮尝试扣款。两者不影响本方案的业务条件，但实际接入点和返回层级不同，需要在执行分支核对，不能直接宣称完整条件已经存在。

本轮没有新增代码实现，也未重新运行关卡、商城或支付流程。完整代码定位见[[02-PROJECTS/TileScape/参考/核对-道具购买缺货跳商店与支付回流-2026-11-18|入口与回流静态核对]]。

## 6. 逻辑验收

| 场景 | 应得到的结果 |
|---|---|
| 有可用普通库存，或普通库存不足但限时道具仍可用 | 不进入本礼包触发流程 |
| 无可用道具，但没有点击金币购买 | 不自动打开商城或礼包 |
| 点击金币购买且余额足够 | 走原金币购买流程 |
| 点击金币购买且余额不足，有对应可售礼包 | 打开商城，首次显示对应礼包且处于Banner首位 |
| 相同条件但无有效礼包 | 正常打开商城，玩家仍可购买其他商品 |
| 关闭后换一种道具再次触发 | 显示新目标，不继承旧目标 |
| 支付成功且奖励到账 | 回原关卡，数量正确，无补扣、无自动使用、无遗留遮挡 |
| 取消、失败、重复点击、延迟回调 | 不重复购买／发奖，不误回流，不误关另一轮商城 |

**评审只需聚焦：** 首次展示后是否暂停自动轮播，以及本版默认的“购买只补库存、不自动使用”是否采用。实际分支入口和旧购买弹窗层级属于实施核对项，不与业务方向混为一谈。
