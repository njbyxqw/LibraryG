# 买量承接与章节拆分长期任务

> [!abstract] 当前定位
> 买量承接是从广告创意到首局、再到章节剧情与关卡体验的一条长期设计链路。片头视频是第一步：用户负责提出与迭代方案，交由程序开发；本地实现用于确认技术边界、提前发现问题并反哺需求，不替代后续 Chapter0 内容、章节拆分或正式移动端验收。

## 1. 目标、边界与协作方式

### 长期目标

让买量素材中呈现的剧情问题、场景和 Tile 玩法，在玩家首次进入游戏、首关操作及后续章节节奏中形成连续承接；效果通过对照与数据评估，而不预设视频必然提升留存。

### 当前工作分工

| 角色 / 路径 | 职责 | 当前边界 |
|---|---|---|
| 用户（方案 owner） | 定义买量素材承诺、首关语义、章节拆分、体验规则、数据目标和验收口径；将需求交给程序开发。 | 需求可因实现事实调整；不以早期设想强行要求代码回退。 |
| 程序开发 | 按已确认方案完成正式功能、配置、资源接入、测试和提测。 | 以研发分支、CI、Unity/设备验证为交付证据。 |
| 本地探索实现 | 试做首播视频和相关链路，定位启动、存档、资源、播放器、打点和 UI 风险。 | 用于完善需求与技术沟通；用户已确认本轮分支为验收通过状态。 |

### 决策层级

1. 用户确认的产品目标、素材承诺、首关语义和章节节奏决定需求方向。
2. 当前代码、配置和测试结果只提供实现约束与已验证行为；实现方式可校准需求，但不替代未拍板的内容决策。
3. 固定 L1/L2 剧情、临时 Prefab 和局部试做是历史/试验材料；不得因其已存在而固化当前视频映射或要求继续执行。

### 不做的事

- 不将本地探索记录等同于线上发布或正式研发验收。
- 不以片头视频替代后续章节剧情、关卡花色或章节拆分的内容决策。
- 不在本任务中固定未确定的剧情、首关场景、前 N 关花色或 AB 策略。

## 2. 第一阶段：片头视频（已形成可用基线）

### 状态

- **用户确认**：需求以已实现的启动/Loading/跳过方式校准，不要求复原早期草案；“首播完成”仍只允许自然播完或有效跳过写入。
- **代码事实（2026-09-23 只读快照）**：当前工作目录为 `dev@94e8d7899`，其合入 `feat-cg@7bd9d435c`；`OnStarted` 只保存待播 session 并释放 Loading，`OnCompleted` / `OnSkipped` 才调用完成写入。
- **验证边界**：当前项目验证记录报告 Video/VideoFirst Unity 回归 142/142 通过及相关受控编译通过；本轮只读取其证据与源码，未重新执行测试。BI 后台入库、Android/iOS 真机、实际素材替换与完整买量效果仍未验收。

### 已确认的实现链路

```text
TileMatch.StartGame
  → VideoFirstModule.TryEnter
  → VideoFirstState
  → IVideoService / VideoModule
  → DefaultVideoPlayer / UnityVideoMedia / UIVideoDefault
  → 原 HomeScene 或 LevelScene 入口
```

| 项目 | 当前事实 |
|---|---|
| 视频配置 | `Assets/Module/Video/Config/Data/video.bytes`，ID 为 `VideoFirst`，路径为 `Assets/Module/VideoFirst/Res/Cg/First.mp4`。 |
| 资源 | `Assets/Module/VideoFirst/Res/Cg/First.mp4`；本轮核查约 16 MB。 |
| 完成状态 | 仅自然完成或有效跳过写 `video_first.played`；未完成通过 `PlayFirstVideo` / `video_first.session` 支持下次启动重播与中断补报。 |
| 通用视频打点 | `video_start`、`video_skip`、`video_end`；结束结果：1 自然完成、2 跳过、3 失败，`reason` 为稳定数值原因码。 |
| 首播专用历史事件 | `VideoFirstState` 仍会发送 `video_first_*` 会话事件；与通用事件并存。 |

### 本轮发现的问题与处理边界

| 问题 | 状态 | 结论 / 后续处理 |
|---|---|---|
| `Video` 与 `VideoFirst` XAsset 组均收录同一 `Res` 目录 | 已定位，非阻断 | XAsset `CheckAssets` 会按收集顺序去重，当前由 `Video` 组保留资源；配置冗余且依赖分组顺序。后续资源归属调整时应只保留一个 owner。 |
| 早期 .NET / Unity 生成资产阻断 | 已由后续验证记录覆盖 | 2026-09-23 当前项目记录报告相关程序集编译与 Unity 回归通过；本长期任务不把旧阻断继续列为当前状态。 |
| 通用 `video_*` 与 `video_first_*` 同时上报 | 待数据口径确认 | 看板/数仓必须明确是否保留首播专用事件，避免将两套事件混作同一漏斗分母。 |
| 真机音视频、后台、杀端和平台存储 | 待专项验证 | 当前不据静态审查宣称 Android/iOS 已验收；在研发提测或素材替换时作为回归项。 |

## 5. 长期推进主线

### A. 方案与内容

- 明确每支买量素材的剧情问题、末帧、对应首关 Tile/场景/任务语义，以及不适用时的降级路径。
- 以章节拆分方案决定首关前视频与关后剧情视频的触发节点；所有节点通过配置保持可替换，不固化当前临时映射。
- 明确视频时长、跳过时机、音频策略、素材标识、AB 对照和成功指标；当前不设计“换素材后自动重播”的版本策略。

### B. 正式研发与交付

- 将已确认方案拆为程序、美术、关卡、数据任务；研发侧明确资源 owner、包体预算、配置字段和回滚条件。
- 用 Unity TestRunner、目标平台真机和构建产物验证，不以本机静态审查替代。
- 素材或章节配置变更时，复核视频路径、XAsset/DLC 归属、首关目标、完成状态和打点口径。

### C. 本地探索与需求反哺

- 保持小范围、可回退的技术试验，优先回答“会不会阻断首关”“会不会重复播放”“资源如何归属”“事件如何统计”。
- 将发现写入本任务的“问题与边界”，由用户决定是否升格为需求、研发任务或仅保留为风险。
- 不从本地提交、文件修改时间或他人提交推断个人工作量或正式上线状态。
