# 死局拓展及应用

## 1. 功能目标与范围

建立覆盖关卡失败前后的死局识别与行为统计能力：每步判断当前可见牌是否存在消除路径，识别玩家使用道具时的无解压力，并持续观察该局面最终通过道具、复活、正常操作解除，还是以退出结束。

核心产出是三个问题的答案：

1. **当前是否可见无解，还剩多少操作空间？**
2. **玩家遇到无解后如何应对，是否购买或使用救助手段？**
3. **救助是否解除当前无解，最终是否继续或完成关卡？**

| 功能 | 本期交付 |
|---|---|
| 可见死局识别 | n 随当前有效剩余格数变化，检查最多 n 步内的首次消除路径 |
| 道具使用归因 | 固定使用前是否无解、剩余 n，记录使用后是否解困 |
| 死局后行为监控 | 道具解困、购买并使用解困、死亡与复活弹窗、主动退出、后台离开及返回 |
| 广义复活转化 | 把死局内的主动道具使用和传统复活统一计入自救转化 |
| 兼容现有系统 | 保留旧死局字段、原复活指标和 DDA 行为，新口径独立版本化 |

本期用于观察与分析，不自动改变难度、提示、道具推荐或失败判定；不求解整关，不预测未揭暗牌的最终花色。本文包含功能目标及分阶段实现，现有代码基础见第 8 节，实施范围与发布边界见第 9 节。

## 2. 核心定义

### 2.1 可见死局

**在一个已经结算稳定的局面中，手牌剩 n 格；只使用此刻花色可见的牌并遵守合法操作顺序，若不存在最多 n 步内触发第一次消除的路径，则判定为可见死局。**

- n 根据当前局面计算，不固定为 1、2 或 3。
- 任意一条路径可消除即为有解。第 n 步恰好消除仍为有解。
- 判断是“有没有路径”，不要求玩家实际选到该路径。
- 可见死局是信息范围受限的无解状态，不等于实际必死。后续揭牌或 DDA 可以解除它。
- 解除表示当前重新存在消除路径，或直接完成关卡；不要求玩家已经执行那次消除，也不保证最终通关。

### 2.2 可见牌与合法路径

| 对象 | 处理规则 |
|---|---|
| 花色可见、当前可点击 | 可以作为当前动作 |
| 花色可见、目前被遮挡 | 可以在前序已知牌移除后作为后续动作 |
| 当前花色不可见的暗牌 | 不读取内部花色来证明有解；实际揭开后才参与新一轮判断 |
| 弃牌区花色可见的牌 | 纳入范围，但必须遵守实际取牌顺序 |
| 曾经看过、当前完全不可见的牌 | 本期不按玩家记忆纳入；当前可见性与 HasSeen 不混用 |
| 特殊障碍或连带取牌 | 使用经过验证的合法性与效果规则；不支持时返回技术未知 |

单次评估冻结起点可见牌集合。模拟中揭开的暗牌不会自动加入该集合；它仍保留位置和遮挡作用，不能当作空位移除。**暗牌存在本身不导致“未知”：所有已知路径均无解时，仍判可见死局。**

### 2.3 n 与结果状态

普通单牌入手模型：`n = CurrentCapacity - UnmatchedCount`，即匹配与入手结算后的有效剩余格数。当前 `Bar.RemainingCapacity = MaxCapacity - Tiles.Count`，不能直接当成同一口径。

| 结果 | 含义 | 剩余步数上报 |
|---|---|---|
| 有解 | 找到合法首次消除路径 | 无解剩余步数字段为 null；有效空位仍记录 |
| 可见无解 | 已完整检查受支持的已知路径，均不能消除 | 填写当前 n |
| 技术未知 | 搜索超预算、规则不支持或快照不稳定 | 为 null，并记录原因；不当作有解或死局 |

字段业务名称采用“可见无解时剩余步数”，不称为“必死倒计时”。普通模型的一步等于入手一张牌；连带入手或自动释放空间时，必须按真实状态模拟，不把空位数直接解释成真实剩余点击次数。未支持的特殊模型保留空位数，步数含义标记不适用。

成功关卡不产生死局。实际死亡时转入失败阶段，记录 n=0 和失败原因，保留死亡前最后一次稳定 n。无合法动作但未满的局面须等自动保底执行后再判断，另记无操作原因。

## 3. 判定时机与 DDAV3 协作

### 3.1 稳定局面采样

首次可操作，以及每次点击、道具、复活、扩容或自动效果引起的逻辑变化完成后，统一重判。采样须晚于入手、匹配、揭牌、DDA 以及相关自动效果的逻辑结算；纯视觉动画是否结束不是唯一依据。

道具执行前检查快照版本：版本有效则复用，过期则重判。固定使用前结果、n、死局 ID；使用后另采结果，不用后态覆盖前态。若操作仍在结算，不强行提交一个确定判断。

### 3.2 DDAV3 的职责边界

DDAV3 当前使用最小路线估算成本 `FastNcd` 与 `HardSlack = 有效空位 - FastNcd` 调控压力。无可见路线时成本和 Slack 为 null；负 Slack 表示估算成本超过空位。它包含可见深度范围、共享前置及部分障碍修正，不能等同于完整合法路径搜索。

| 能力 | 用途 | 与新功能关系 |
|---|---|---|
| 旧死局判定 | 近满手牌判断、累计次数，且被 V1 DDA 使用 | 保留原行为；不直接扩大其入口影响旧 DDA |
| DDAV3 路线成本 | 压力评估与换牌决策 | 作为对照指标，不直接充当无解标签或决定分母 |
| 新可见死局判定 | 当前可见范围内是否存在 n 步消除路径 | 为自救归因和行为监控提供结果 |

普通取牌链路是：移出棋盘并更新可见性 → 加入手牌 → 对露出的目标执行 DDA。DDAV3 对未曾看见、从 NotVisible 首次变为 Visible／Highlight 且真实花色可见的牌可能调控；不必等到可点击，也不保证一定换牌。

新评估器只读取结算后的真实局面，不提前调用 DDA，不消耗正式随机数，不预测暗牌换色。

### 3.3 暗牌变化示例

剩 2 格，已知可见牌两步无解，即进入死局。随后：

| 行为 | 处理 |
|---|---|
| 立即使用道具 | 按无解、n=2 记录主动自救 |
| 正常拿一张，揭牌并经 DDA 后一步可消 | 正常操作解除，不计自救转化 |
| 正常拿一张，揭牌并经 DDA 后一步仍无解 | 同一死局延续，当前 n 更新为 1 |

后续自然解除不撤销先前的可见死局记录。道具引发的整次操作结算后解除，记“道具使用后解困”；不能仅凭结果把其中作用细分归因给道具或 DDA。

### 3.4 DDAV3 对照结论与结合方式

已在 `feat_deadlock` 使用 Unity EditMode 完成 14 项对照测试。其中 7 项枚举四张可点击普通牌、三种花色、n=1..7，共 567 个组合，默认成本下 DDAV3 风险分类与新判定一致；手牌补齐、第 n 步消除、单层遮挡、暗牌实际揭开案例也一致。此为构造局面验证，不是全部关卡或线上覆盖率结论。

**默认成本下存在明确差异：部分共享遮挡会重复计费。**

- 手牌有一张 A，剩余 5 格。可见下层有 A1、A2。
- A1 被 B、C 遮挡；A2 被 B、D 遮挡。B 是两条路线共用的前置，B／C／D 为不同花色。
- 标准尺寸、错位半遮挡构造中，A1／A2 自然为 Visible，无须强制修改可见状态。
- 实际路线可以为 B → C → A1 → D → A2，第 5 步完成 AAA。
- DDAV3 当前给出 FastNcd=6、HardSlack=-1；新判定为 solvable。其共享成本修正合并相同前置集合，但本例 `{B,C}` 与 `{B,D}` 只部分重叠，B 被重复计入。

因此，即使当前新局使用默认 1／2／3 成本，也不能把 `HardSlack<0` 直接作为“确定 n 步无解”。另一个参数边界测试将 HighlightCost 改为 2 后，三张直接可点击同色牌的 FastNcd 为 6，而实际仍是 3 步；该参数案例仅验证口径边界，当前普通／回收新局构造代码的 HighlightCost 均为 1，不代表线上正在使用 2。

DDAV3 的安全候选与 UnsafeFallback 属于调控风险判断。实际取牌死亡由 `BarActions` 在更新手牌状态后检查 `Bar.IsFull` 并发布 `LevelFailed`；不会因 Slack 负值直接判玩家死亡。

**结合方案：统一观察入口和数据，保留压力与确证状态的区别。**

1. 复用 DDAV3 已有操作批次、事件派发结束及 ApplicationPendingEnd 的采样边界，同时检查整次动作是否仍在 Pending；在同一稳定局面取得新判定与压力信息。
2. DDAV3 的 `GetSnapshot()` 读取已发布快照，不自动刷新。两种结果需关联共同的操作／锁定版本，不能只因为在同一帧读取就认为对应同一局面，也不能比较两者各自独立的版本号。
3. 压力曲线仅在棋盘牌数变化等条件下追加点，不足以充当每一步的死局状态流；洗牌等牌数不变的变化仍需读取当前有效快照。
4. 道具前态固定 n、可见有解状态、FastNcd、HardSlack、目标压力；后态记录是否解除和期间实际换牌变化。普通揭牌／DDA 自然解除不计道具转化；道具引发的整次操作解除计使用后解困，不分拆未经验证的因果贡献。
5. 普通牌已支持范围内，以新判定决定死局统计，DDAV3 压力作为并列诊断字段；两者不一致保留差异。新判定 unknown 时不以负 Slack 或 null 代替确证死局。
6. 特殊机制先复用 DDAV3 的规则识别与专项成本知识作对照，逐类验证合法路径及失败边界后再扩大确证范围；本轮未修改 DDAV3 调控算法。

对照代码：`Tests/EditMode/DataCenter/MoveToOverBarPropTests.DdaDeadlockComparison.cs`（相对 TileV2 根目录）。验证附件：TileScape `Docs/Knowledge/Local/Deadlock/dda-comparison.xml`。下一实施点为共同稳定快照与差异字段接入；共享遮挡成本修正另作明确改动，避免分析统计接入顺带改变难度。

## 4. 死局记录与五类行为监控

### 4.1 一次死局的记录单位

连续处于可见无解的过程称为一个“死局段”，使用挑战 ID、判定版本、段 ID 唯一标识。每步重判不等于每步新建一段。

| 状态变化 | 处理 |
|---|---|
| 非死局 → 可见无解 | 创建段，记录进入时 n |
| 无解 → 仍无解，n 变化 | 延续同段，更新当前 n |
| 使用道具但仍无解 | 记录救助，延续同段 |
| 无解 → 有解或通关 | 结束段，记录解除来源 |
| 死亡并展示复活界面 | 进入失败阶段，段继续等待复活或退出 |
| 主动退出／挑战确认终止 | 结束段，保留之前全部行为 |
| 后台挂起 → 返回同一挑战 | 延续同段，后台时间单列 |
| 技术未知或恢复信息缺失 | 标记观察缺口，不伪造解除；该段不纳入完整观察分母 |

未知期间不能证明连续性，恢复后的记录携带不完整标记，不追溯补造段。没有前置可见死局记录却发生失败时，保留传统失败／复活统计，并记录“无可关联死局／观察缺口”；不把该失败回填成先前的可见死局。

### 4.2 五类行为

| 类别 | 成立条件 | 后续处理 |
|---|---|---|
| 道具解决当前死局 | 使用前无解，非本段关联购买的有效道具使用后变为有解或通关 | 记录解困，结束段；注明库存、广告等来源 |
| 购买并使用道具解决 | 本段内购买成功、关联具体使用、该使用后解困 | 保存购买→使用→解除关联，结束段 |
| 持续操作后死亡并弹出复活 | 实际失败且复活界面实际展示 | 分别记录失败与展示，继续监控复活或放弃 |
| 主动退出 | 玩家确认退出关卡或放弃复活，业务结算完成 | 结束段；区分局内退出和复活界面放弃 |
| 后台退出 | 挂起后挑战确认终止，或观察窗口内未返回 | 确认终止与推断未返回分开；返回可修正推断 |

五类是行为监控维度，不是互斥最终分类。例如“道具未解困 → 死亡弹窗 → 放弃复活”属于同一段的连续行为。原始发生率不能相加当作 100%。

段结束结果另外使用互斥分类：道具后解除、购买关联道具后解除、复活后解除、正常操作解除、主动退出、后台后确认终止、其他／观察不完整。后台未返回推断及仍进行中作为观察状态单列。归因不明的道具解困保留独立标记，不强塞入购买或非购买分类。

正常揭牌解除、购买未使用、有效使用但未解困、执行失败均保留记录。自动系统保底不算玩家主动自救。

### 4.3 购买归因

购买成功携带挑战 ID、段 ID、道具 ID、数量、币种、消耗和购买关联 ID；只有实际绑定到该购买的使用才能归为“购买并使用”。优先接入购买后立即使用链路。

以前购买的库存本次使用归库存使用。多件购买与旧库存混用、无法绑定时标记关联不明；不以时间相近推断。只购买不使用不算完成转化；钻石购买与真实货币交易分开。

### 4.4 后台监控

进入后台时持久化活动段及最后稳定快照，记录挂起时间。返回同一挑战则恢复；后续确有挑战放弃或替换证据才确认结束。退出回调不能替代完整终止证据。

没有返回也没有终止证据时，在数据侧按统一观察窗口标记“后台未返回／疑似退出”；窗口长度为发布前需要确定的报表参数，不写成客户端确定事实。迟到返回修正推断，保持同一段去重。不能把崩溃、断网或系统回收推断为玩家主动退出。

## 5. 数据应用与指标口径

### 5.1 三层指标

| 层级 | 指标 | 计算口径 |
|---|---|---|
| 使用行为 | 道具使用中的自救占比 | 使用前可见无解的有效主动道具使用次数 / 使用前判定有效的全部局内主动道具使用次数 |
| 继续投入 | 广义复活转化率 | 至少一次有效主动道具使用或传统复活的死局段数 / 完整观察的死局段总数 |
| 救助效果 | 自救段解困率 | 由某次有效救助操作结算后解除的死局段数 / 发生有效救助且结果可判定的死局段数 |

有效使用指道具或复活实际成功执行，不要求解困。打开商店、仅购买、仅显示复活界面、取消广告、执行失败不算完成转化；执行失败但消耗资源另外记录。使用行为指标按次数，转化指标按段，不能混用。

同段多道具再复活，转化只计一次；渠道用“仅道具／仅复活／道具加复活”去重分组。正常操作解除但未救助的完整段仍在转化分母中。

### 5.2 报表设计

| 报表 | 核心维度和结果 | 支持的决策 |
|---|---|---|
| 道具使用压力分布 | 使用前有解／无解、无解时 n、道具类型、来源、使用后解除情况 | 道具更多用于提前自救还是普通推进；何种压力下使用与效果更突出 |
| 死局行为路径 | 进入 n、首次行为、行为序列、五类节点、最终结果 | 玩家倾向救助、继续操作还是离开；在哪个环节流失 |
| 购买救助漏斗 | 死局段→购买成功→关联使用→解困，旁列未使用／未解困／退出 | 区分购买意愿、使用完成和救助效果，避免只看成交 |
| 复活衔接 | 死亡、弹窗展示、复活成功、放弃；是否先用过道具 | 道具与复活的衔接及重复投入 |
| 后台行为 | 挂起、返回、确认终止、窗口未返回 | 区分短暂离开与可能流失 |

按关卡、玩家阶段、进入时 n、使用时 n、道具库存、DDA 类型／配置版本分层。DDAV3 Slack 及实际换牌记录可作为诊断维度，但相关性不等于难度调控或收入的因果收益。

### 5.3 分母和可比性

- 新口径不覆盖旧 `is_deadlock`、`deadlock_times`，保留传统复活弹窗转化指标。
- 同一报表固定判定版本、支持的机制范围与观察窗口。正在进行、技术未知、缺失重连数据、后台未返回推断单列，展示排除数量和覆盖率。
- 完整观察转化率是该有效样本的结果，不代表全量玩家；单独报告退出证据缺失造成的选择偏差。
- 未使用道具的死局也必须有进入及结束记录，否则不能形成广义转化分母。
- 扩大死局识别范围会同时改变分子和分母，不能直接解释为转化提升。

## 6. 数据采集契约

以下是字段语义建议；正式事件名、类型和枚举值在实施时对照打点字典确认。

| 数据 | 最小字段 |
|---|---|
| 判定快照 | 挑战 ID、快照版本、判定版本、有解／无解／未知、有效空位、无解时 n、规则支持状态 |
| 死局段 | 段 ID、进入时 n、开始／结束时间、阶段、结束原因、是否已转化、观察完整性 |
| 救助行为 | 操作 ID、段 ID、类型／来源、购买关联、执行结果、消耗、使用前状态与 n、结算后状态、是否解除 |
| 后续节点 | 购买、实际失败、弹窗展示、退出、挂起、返回；节点时刻、阶段、最后稳定 n、确认／推断来源 |

关键顺序：

1. 稳定局面评估并更新段。
2. 道具使用前冻结状态、n、段 ID、操作 ID。
3. 实际执行并记录成功或失败。
4. 效果及 DDA 结算稳定后，补对应操作的解除结果，再更新段。

当前 `prop_used` 可扩展前态字段；异步后态应另行关联回传，不要求使用事件发送时就已解困。不得把后来的正常点击解除归到上一次道具。

购买、使用和后态使用明确关联 ID；事件重发幂等。持久化活动段以支持重连，旧存档缺字段时标记未知／不完整。回放及 Bot 测试不写生产行为统计。每步本地评估，但不要求每步上传全量棋盘；只上报必要状态转移与行为，诊断按需采样。

## 7. 技术方案

### 7.1 组件职责

| 层次 | 职责与状态所有权 |
|---|---|
| GameLogic 评估器 | 从稳定快照计算只读结果；独占派生缓存，不修改正式牌局或 DDA |
| GameLogic 操作协调 | 提供版本及稳定采样边界，执行后显式触发重判 |
| DataCenter 会话层 | 唯一维护段 ID、转化标记、行为关联及结束状态 |
| UI／购买／应用生命周期桥接 | 传递真实展示、确认、购买、挂起和返回信号；不自行决定是否死局 |
| 会话存储与分析层 | 持久化、幂等上报、报表窗口与推断分类；不回写玩法 |

只采用已有层次与显式调用，不为本功能新建通用事件框架。运行时状态属于当前挑战，派生缓存按局面版本失效；持久化新增字段默认兼容旧数据。

### 7.2 搜索方法

候选实现为独立的 `VisibleDeadlockEvaluator`：冻结可见牌集合，枚举当前合法动作，模拟入手与确定性效果；出现首次消除即返回有解，否则继续至容量边界并回退。普通单牌模型最多搜索 n 步。

复杂规则按真实占格与失败过程处理。分支尚有未支持变化时不能依据其失败返回确定无解；找到一条完全可验证路径可直接返回有解。所有受支持路径穷尽才返回可见无解，预算耗尽返回未知。

现有 Bot 模拟／回退能力优先评估复用；必须验证不读取未知牌花色、不触发正式 DDA、能恢复障碍与锁定状态。不能直接套用关闭障碍模拟的 SolutionHint 选项并声称完整支持。

最坏约 `O(b^n)`：找到路径即停、按完整状态去重、复用缓存与容器、设节点预算，避免逐帧计算。相同花色但位置不同不能随意合并。具体设备耗时与覆盖目标以基准测试确定。

### 9.2 已接入的事件协议

新增事件 `visible_deadlock`，通过 `phase` 区分节点：

| phase | 含义 |
|---|---|
| enter | 新可见死局段，保存 entry_free_slots |
| rescue_used | 死局前态下成功使用道具，或活动死局段内复活成功 |
| prop_used | 使用成功但前态不满足已确认死局；不据此计死局转化 |
| rescue_result | 同一 action_id 的后态，reason 为 resolved／unresolved／unknown／not_observed |
| purchase | 活动段内购买完成，尚不能据此认定使用或解困 |
| death / revive_show | 实际进入等待复活／复活窗口实际打开 |
| background / foreground | 应用挂起／返回，同一段继续；后台未返回由分析窗口推断 |
| unknown | 当前无法可靠判断，同时标记 observation_complete=false |
| end | 结束原因：prop／revive／normal_play／win／quit／give_up_revive／session_cancelled |

公共关联键为 `attempt_id + deadlock_id + sequence`，操作关联使用 `action_id`，版本为 `judge_version=1`。`visible_deadlock_steps` 仅在当前记录的判定为 deadlock 时有值；使用事件取冻结的使用前 n。分析端按关联键去重，不把客户端发出事件等同于服务端已收到。

`purchase_attribution=same_episode_same_item` 表示存在明确的同段、同道具购买记录；其他情况为 unconfirmed。`converted` 表示发生过成功救助使用，`observation_complete` 表示该段观察是否完整。不能用 converted 替代 resolved，也不能将多个行为节点相加作为互斥占比。

旧 `prop_used` 保留原字段，新增 `visible_solution_state`、`visible_deadlock_steps_before`、`visible_judge_version`；旧 `prop_purchase` 增加 `purchase_id`。

### 9.3 后续实施与发布条件

1. **规则覆盖与性能**：扩展特殊元素、序列／批次和多牌动作；用真实普通关卡和大棋盘确认可见有解覆盖率、unknown 比例及设备耗时，再确定正式预算。
2. **时序验收**：真实道具异步结算、紧接普通点击、死亡与复活、进后台及重连均需 PlayMode／设备验证；当前稳定采样与前态冻结已有代码，不能仅凭 EditMode 测试宣称全链路通过。
3. **存档源同步**：新增字段目前已在客户端生成类接入；仓库未找到其配置源表，发布前需将 `VisibleDeadlockJson:string` 同步至 Profile 源表并重新生成，防止后续覆盖丢失。不得把客户端编辑视为源表已更新。
4. **埋点与分析**：确认正式事件字典、后台未返回窗口、无存档返回的归类；后台终止无证据时保持观察未闭合。数据平台建表、报表和上传实测尚未完成。
5. **未成功使用**：当前转换只接既有成功使用链路；点击不可用、执行失败及异常退款若需完整尝试漏斗，应补独立尝试结果，不计成功转化。

第一阶段可用于开发验证；完整发布以这些条件及下列验收矩阵为准。

验证证据：Unity 6000.0.60f1 下 15 项专项 EditMode 测试通过；相关流程回归 523 项中 392 通过、131 失败，与原始代码 509 项中 378 通过、131 失败相比，失败名称和消息完全一致，无新增失败。回归批次包含当时的 14 项新测试，最后追加的遮挡路线用例在专项批次验证。完整 dotnet 构建仍受第三方 BouncyCastle 错误影响；不宣称全项目构建通过。详细结果保存在 TileScape 的 `Docs/Knowledge/Local/Deadlock/`。
