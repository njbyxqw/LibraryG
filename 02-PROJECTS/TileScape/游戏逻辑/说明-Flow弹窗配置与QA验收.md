# TS Flow 弹窗流程、配置与验收说明

图文说明见 [《弹窗流程与名额规则》](说明-Flow弹窗流程与名额规则.html)，包含四表关系图、五类场景流程和可交互的名额计算示例。

本文定义登录进入首页、关卡胜利、关卡失败、主引导和新邮件的弹窗执行顺序、配置含义及验收标准。配置基线为 2026-11-25 读取的正式 Flow 表，包含 6 个 Trigger、12 个 Group、34 个 FlowItems 和 2 个 Condition 声明。五个 Trigger 用于正式业务，一个用于框架样例。

测试前记录客户端版本、资源／配置版本和账号状态。云端表需要经导表、资源构建与发布才交付客户端，编辑云端单元格后，已运行的客户端不会立即取得新规则。此前四表快照已与 dev@9527c15fa 导出逐字段核对一致。本次已提交的配置将首页额度改为 4，胜败组额度改为 0（不限），三处线上值已读回确认。验收记录应包含设备实际加载的配置版本。[正式 Flow 表](https://docs.google.com/spreadsheets/d/1QolcRqCcaq4J5rA9SyccCqjCUDc4cOda6GIKccf_gjo/edit)

成长礼包在本版仍按 `220` 现有行为参与礼包组。本版验收范围包括通用调度、BP 和关卡胜败流程。成长礼包开启／结算拆分处于暂缓状态。

## 1. 弹窗执行顺序

弹窗按配置优先级依次判断展示资格。无可领取奖励、活动未开放、已展示、已购买或广告不可播放等状态，可能使相应条目被跳过。结算内的领奖、挽留和确认流程全部结束后，才执行下一个 Flow 根弹窗。验收预期应依据账号当时的业务状态确定。

### 1.1 登录或返回首页

首页首先处理待展示的关卡进度，包括关卡按钮、奖励飞入、活动入口表现、宝箱和地图聚焦。上述动作与章节提示按组 1001 的配置顺序执行，完成后进入运营弹窗阶段。

| 顺序 | 展示内容 | FlowItems ID | 展示条件与接续规则 |
| --- | --- | --- | --- |
| 前置 | 退出无尽后的新章节提示 → 章节解锁／进入无尽提示 → 待办主引导 | `204 → 205 → 208/209` | 各自有业务资格。208 是通知步骤，实际引导由 209 执行。中间还穿插地图和宝箱动作 |
| 1 | 每日奖励领取页 | `219` | 当前配置排在所有活动结果前 |
| 2 | 射箭结果／特定主界面展示 | `2` | 按当前活动状态选择页面 |
| 3 | 浪花夺宝恢复／结果处理 | `3` | 成功、失败、到期、待领奖等由业务状态决定 |
| 4 | BP 赛季结算及其后续 | `233` | 领奖、挽留和确认跟随本次结算链 |
| 5 | 金牌活动开启页 | `1` | 开启提示，包含当前进度和目标 |
| 6 | BP 新期开启／进行期购买奖励补展示 | `221` | 旧期已结束且新期符合条件时才进入新期开启 |
| 7 | 射箭开局提示 | `223` | 符合开局资格时出现 |
| 8 | 浪花夺宝下一阶段／新期开场 | `224` | 后续匹配按活动业务接续 |
| 9 | 首充礼包 | `4` | 以下礼包各自判断购买资格、周期和频控 |
| 10 | 破冰礼包 | `5` | 合格时按此位置展示 |
| 11 | 无尽礼包 | `6` | 合格时按此位置展示 |
| 12 | 天选礼包 | `218` | 合格时按此位置展示 |
| 13 | 成长礼包现有页面 | `220` | 本版保留现状，专题拆分暂缓 |
| 14 | 去广告礼包 | `222` | 还受插屏启用、广告次数、冷却和购买资格等条件限制 |
| 15 | 待弹邮件详情 | `210` | 一封结束后，若本轮还有名额，可继续处理其他待弹邮件 |

**一次 Home 流程最多实际展示 4 个根弹窗。上表为候选条目的配置优先级。** 章节提示也计入这 4 个，引导、飞奖和入口表现不计入。达到 4 个名额后，本轮后续礼包或邮件将受额度限制而跳过。

弹窗链完成后，从根组重新判断候选资格。例如 BP 旧期结算完成使新期可以开启，随后会先判断位置更靠前的金牌，再判断 BP 开启。如果金牌不合格，可能直接出现 BP 新期开启。应结合该时刻的资格判断先后。

### 1.2 普通关卡胜利

**过关祝贺 `227` → 过关插屏 `228` → 胜利结算 `229` → 浪花夺宝结果／领奖 `225` → 返回首页 → 执行首页流程（1.1 节）。**

- 祝贺、广告、浪花夺宝结果各有触发条件，条件不满足时继续后项。
- 胜利结算关闭并完成本局处理后，仍需先完成合格的浪花夺宝结果，再正常返回首页。
- 胜利组当前不限额，228 属于动作，其余三项为根弹窗。进入首页后独立启动 Home，每轮最多展示 4 个根弹窗。
- 新手连关中间关和试用关可能采用专门流程，本节预期适用于常规关卡。

`225` 对应关卡胜利后的活动结果入口。浪花夺宝实际展示的页面由活动状态决定。AB 未命中、资源未就绪或没有待处理结果时，该项可能不展示。

### 1.3 关卡失败、放弃与重试

关卡失败后首先展示复活页。复活成功后继续本局。放弃复活或确认主动退出后，进入以下失败处理流程。

```text
浪花夺宝失败后结果 226（符合条件时）
  → TryAgain 重试页 232
      → 点重试、条件满足：重新进入本关
      → 体力不足：打开体力处理子窗，处理后继续重试操作
      → 关闭重试页：返回首页，执行首页流程（1.1 节）
```

失败组当前不限额，两项根弹窗都有自己的条件。普通失败处理和 TryAgain 重试这条链没有插屏步骤。主动退出在确认后进入同一失败处理链。复活页和退出确认属于之前的业务入口，发生在 226／232 之前。

返回首页后，由 Home 独立启动组 1000，最多展示 4 个根弹窗。当前采用关卡不限额、首页独立限额，跨场景共享剩余额度尚未实现。胜败组当前均未引用 `-1000`。普通 LevelEntry 开始按钮另有开局插屏资格检查，激励广告复活按激励广告规则执行。

### 1.4 BP 结算内部接续

| 测试状态 | 预期接续 |
| --- | --- |
| 旧期有可领取奖励 | 赛季结束页 → 结算领奖页 → 未购买且仍处结算阶段时进入挽留 |
| 旧期无可领取奖励且未购买 | 赛季结束页 → 挽留页 |
| 旧期无可领取奖励且已购买 | 赛季结束页 → 完成旧期处理 |
| 关闭挽留页 | 打开放弃确认。取消放弃回到挽留，确认放弃完成旧期处理 |
| 在挽留页购买成功 | 购买成功页 → 对应结算奖励处理 → 完成本链 |
| 存在购买奖励补展示 | 按活动阶段，由 221 或 233 从购买成功页承接后续奖励 |

各分支根据实际业务状态执行。奖励动画完成后，对应操作才进入可交互状态。结算链完整退出之前，金牌、新期 BP 或礼包等其他根项应等待。链结束后，从根组重查候选和剩余额度，下一期开启服从 221 的位置和资格。

### 1.5 首页停留期间的补充触发

- **新邮件**通过 `1003 → 210` 在流程空闲后补弹。当前 Home 已包含邮件项时，交由该轮处理。真正的新邮件事件可启动独立轮次，列表中有积压本身不会反复启动新轮。
- **待办主引导**通过当前 Home 的 209 或独立 `1002 → 209` 承接。在完整 Home 中，209 排在运营弹窗之前。

### 1.6 顺序异常记录要求

预期顺序与实际顺序均使用“页面名称＋FlowItems ID”记录。例如“预期 BP 结算 233 完整退出后再显示金牌 1，实际在 BP 挽留页仍未关闭时出现金牌”。同时记录业务状态、本轮已展示的根弹窗数及完整录屏，便于判断是资格变化、名额限制、正常重扫还是交接异常。

## 2. 配置表职责与关联

| 表格 | 作用 | 核对依据 |
| --- | --- | --- |
| Trigger | 把业务触发时机对应到一个根组 | 业务操作对应的 Timing 及根组 ID |
| Group | 定义组内顺序、子组和弹窗名额 | 按 Members 从左往右展开，逐层检查条件和限额 |
| FlowItems | 将条目 ID 对应到业务行为，定义是否占弹窗名额及条件模式 | 条目 ID 对应的弹窗／动作、计数类型及业务资格 |
| Condition | 声明可在表内使用的条件名称和参数类型 | 核对条件 JSON 的名称、参数个数和类型，确认条件模式是否会执行这些条件 |

读取关系为 `Trigger → 根 Group → 子 Group／FlowItems → 实际业务`。Group 和 FlowItems 都可以填写 Conditions。表内的 `note` 是阅读说明，字段类型为 `note` 时不导出为业务字段。

前三行为字段名、字段类型和说明，第 4 行开始是数据。定位配置时优先使用 ID／Timing，避免人工排序后引用错误行号。

### 2.1 Trigger 触发映射

| Timing | 根组 | 触发条件 |
| --- | --- | --- |
| Home | 1000 | 实际进入首页，首页入场准备完成 |
| Home.Tutorial | 1002 | 首页就绪、有待处理主引导，当前流程没有承接该项时尝试执行 |
| Home.Mail | 1003 | 首页收到新待弹邮件，流程空闲后执行 |
| TileV2.LevelSuccess | 2000 | 正常关卡胜利结算 |
| TileV2.LevelFailed | 2001 | 放弃复活或确认退出后进入失败处理 |
| Flow.Step1.Sample | 1 | 框架样例入口，正式体验验收使用上面五个时机 |

新建 Trigger 行还需要程序在对应事件处调用。仅填写名字不会自动监听事件。忙碌时调用可能未受理，是否再次尝试由业务负责。

## 4. 调度、计数与条件规则

### 4.1 候选优先级与重新扫描

Flow 按 Members 扫描，当前不满足资格的条目会被跳过。根弹窗实际展示且整条 UI 链结束、界面稳定后，会从根组重新扫描。因此前面刚变为可执行的内容，可能先于原来后面的条目出现。普通失败继续检查后项。BP 起始项在排队期间到期取消时，有专门的重扫逻辑让结算得到处理。

例如每日奖励和首充都符合条件，当前优先每日奖励。若每日奖励已领取，直接跳过。顺序验收记录需包含各条目在本次触发时的资格状态。

### 4.2 PopupLimit 计数规则

- `Kind=0` 为 Popup，根窗口实际显示后计 1 次。同一个展示请求重复通知只计一次。
- `Kind=1` 为 Action，不占弹窗名额，仍需等待其动作完成。引导、飞奖、插屏广告都在此类。
- 组的 PopupLimit 为正数时限额，空、0、负数均为不限。
- 一个弹窗同时计入所在组及所有祖先组。`1011/1012/1013` 的额度为空，仍受根组 `1000=4` 限制。
- 子组达到额度后，该路径上的 Popup 被跳过，Action 仍可执行。
- 额度每轮重置。同一轮多次引用同一 Group ID 时共享该组额度。
- 前窗加载失败或取消且未实际展示，不占名额。已经展示再关闭，仍计一次。
- BP 结算内的领奖、挽留和确认由业务连续承接，共用结算根项的名额。它们出现期间，其他 Flow 项等待链路结束。

**当前首页最多 4 个根弹窗，范围包含章节提示、活动、礼包和邮件。** 若本轮展示了 1 个章节提示，再展示 3 个运营根弹窗，队尾邮件已没有本轮额度。进入下一次正常 Home 会重新判断剩余业务。

`1003` 是独立新一轮，当前不限额。停在首页真正收到新邮件后可以唤起它。同一通知不能因为仍有积压邮件就不断自启新轮。测试邮件要区分“只关闭未领取”“已经领取”和“真正新到达”。

### 4.3 ConditionMode 与 Conditions

| ConditionMode | 判断方式 | 当前用法 |
| --- | --- | --- |
| 0 | 只看表内 Conditions | `101` 框架样例采用此模式。空条件会直接通过表条件判断 |
| 1 | 只看业务代码资格 | 当前正式业务项全部使用此模式 |
| 2 | 表条件与业务资格都满足 | 将来增加策划门槛时通常采用此模式 |

当前正式组的 Conditions 都为空，正式 FlowItems 的 Conditions 也为空。当前排序依赖 Group，资格依赖业务代码。

Condition 表的 `LevelPass` 参数类型是 `int`。写在条目或组内的 `[ ["LevelPass",60] ]` 表示已通关至少 60 关。60 必须是数字。多项条件按 AND 判断，即全部满足才通过。

若在隔离测试配置中把首充 `4` 改为模式 2 并填写 `[["LevelPass",60]]`，应准备已通关 59／60／61 关且其余首充资格一致的账号进行边界测试。模式 1 下填写条件不会启用额外门槛，但内容仍需要通过格式和签名校验。此例是字段测试示例，当前正式表未配置该门槛。
