# Chuzzle 设计合同与当前代码差异清单

## 结论

以下是“文档表达”与“当前源码 / 配置合同”的静态差异，不自动等于实现缺陷。后续需由产品或负责人决定：更新文档、迁移配置，或调整代码。

| ID | 文档合同 | 当前代码 / 配置事实 | 状态与建议 |
|---|---|---|---|
| D-C01 | `00-产品范围与玩家规则` 以通用 `ElementType.Booster` 描述 Booster | `ChuzzleElementConfigCatalog` 明确拒绝旧 `ElementType.Booster (201)`，要求 202–205 的具体 Booster；当前规则配置也直接产出具体类型 | `needs-review`：统一产品术语，确认旧枚举是否只保留兼容含义 |
| D-C02 | 目标为 `EliminateObjective(ObjectiveId, TargetElementTypes[], RequiredCount)`，支持目标类型 OR 集合 | `LevelConfig.ObjectiveConfig` 只有 `ObjectiveId`、单个 `ObjectiveType`、`RequiredCount` | `needs-review`：明确首版是否已收敛为单目标，或需补充组合目标模型 |
| D-C03 | Booster 创建描述为“同色组达到 4 个或以上即可创建” | 当前 `BoosterGenerationConfig.json` 使用 CountRules 与 ShapeRules：4→PaperPlane、5/6→Tnt、四连线→Rocket，且由编译器校验 | `needs-review`：文档应描述规则可配置性和形状优先关系，或确认代码规则超出当前产品合同 |
| D-C04 | 运行时结构文档的目录示例为 `Scripts/Logic`、`Application`、`View`、`Game` 平级 | 当前源码是 `Scripts/Entry/` 与 `Scripts/GameCore/{Application,Game,Logic,View}`，生成 `.csproj` 还残留旧 `Scripts/Game/` 条目 | `needs-review`：更新导航；Unity 刷新前不把生成项目路径问题判为编译故障 |
| D-C05 | `ChuzzleApplication` 被描述为可选的输入 / 表现用例层 | 当前 `ChuzzleGame` 初始化时构造 `ChuzzleGameplaySession` 与 `ChuzzleApplication`；View 可选，Application 负责持有 / 释放 Session、Logic、LevelLogic | `needs-review`：区分“可选 View”与“当前实现中始终存在的 Application” |

## 已保持一致的核心边界（静态）

- `ChuzzleModule → ChuzzleGame.Update → Timer / GameLogic.Update` 的主要生命周期可在当前 `Entry`、`Game` 代码中找到。
- `ChuzzleGameLogic` 与 `ChuzzleLevelLogic` 仍分别承担玩法状态与关卡状态；`ChuzzleGameplaySession` 是玩家 / 窗口动作的窄入口。
- View 的 Board / HUD / Preview 协作者只处理表现投影，正式结果由 Game / Application 链路投递。

## 验证边界

本表没有验证产品期望、关卡配置迁移、Unity 场景行为或编译结果。每个差异在进入修复前都应补充负责人决策、受影响关卡 / 资源范围与 Unity 回归证据。
