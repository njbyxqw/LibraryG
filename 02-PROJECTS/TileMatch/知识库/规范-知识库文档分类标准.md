# 知识库文档分类标准

> TileMatch 知识库的文档命名、分类、frontmatter 规范。所有文档必须遵循此标准。

---

## 一、文档分类

所有文档通过 frontmatter `type` 字段分类，共 6 种：

| type | 定位 | 命名前缀 | 示例 |
|------|------|---------|------|
| `spec` | 必须遵守的规则 | `规范-{主题}` | `规范-知识库文档分类标准` |
| `analysis` | 代码/逻辑深度梳理 | `分析-{主题}-v{版本}` | `分析-RocketV2完整逻辑-v2` |
| `report` | 工作成果总结 | `报告-{主题}` | `报告-关卡文件追踪工具` |
| `reference` | 属性速查/清单 | `{主题}-类型全览` 等 | `障碍牌-类型全览`、`Effect-Ice` |
| `note` | 杂项记录/复盘 | `记录-{主题}`、`复盘-{主题}` | `记录-gitignore本地忽略配置` |
| `index` | 导航/索引 | `_MOC`、`知识库文档顺序索引` | `_MOC.md` |

> 详见下方「type 类型定义」。 |

---

## 二、Frontmatter 标准

所有文档必须包含以下字段：

```yaml
---
title: "显示标题"
date: YYYY-MM-DD
type: spec | report | analysis | reference | note | index
status: draft | finalized
cat_order: NNN  # 三位补零，分类内从 001 起连续编号
tags: [TileMatch, 子模块]
---
```

### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | ✅ | 文档显示标题 |
| `date` | ✅ | 创建或最后更新日期 |
| `type` | ✅ | 文档类型（见下方类型定义） |
| `status` | ✅ | 完成状态（`draft`=草稿/待完善 / `finalized`=终稿/可引用） |
| `cat_order` | ✅ | 分类内序号（三位补零，如 `001`）。文件夹内从 001 起连续。编号规则：总/规范/全面排前，特殊/业务/专门排后 |
| `tags` | ✅ | 标签数组，至少包含 `TileMatch` |
| `aliases` | ⚠️ | 旧名称向后兼容（如 `_MOC` 加 `aliases: [TileMatch 知识库_MOC]`） |

### type 类型定义

| type | 用途 | 典型文件 |
|------|------|---------|
| `spec` | 规范/标准 | 知识库文档分类标准、健康检查规范 |
| `analysis` | 技术分析/代码逻辑梳理 | RocketV2 完整逻辑、死局分析、编辑器架构 |
| `report` | 工作报告/总结 | 打点事件梳理、关卡文件管理工具、SQL 分析 |
| `reference` | 参考资料/属性速查表 | 障碍牌类型全览、Effect 类型全览 |
| `note` | 笔记/记录 | gitignore 配置记录、复盘 |
| `index` | 索引/导航页 | MOC、知识库文档顺序索引 |

### status 取值说明

| 值 | 含义 | 何时使用 |
|----|------|---------|
| `draft` | 草稿 | 内容待补充、待验证 |
| `finalized` | 终稿 | 内容完整、可放心引用 |

> ⚠️ **禁止使用中文值**（如 `已完成`、`完成`）——会导致仪表盘过滤漏掉。所有字段统一英文。

## 三、Wikilink 规范

### 核心规则

| 场景 | 链接格式 | 示例 |
|------|---------|------|
| TileMatch 内部引用 | **基名**（仅文件名） | `[[分析-死局逻辑与改进方案-v1\|死局逻辑]]` |
| 跨项目引用（如 03-KNOWLEDGE） | vault-root 全路径 | `[[03-KNOWLEDGE/Game-Logic/游戏逻辑分析\|游戏逻辑分析]]` |
| 指向 MOC | 基名 + 别名 | `[[02-PROJECTS/TileMatch/_MOC\|TileMatch 知识库 MOC]]` |

> **禁止**在 TileMatch 内部使用缺 `02-PROJECTS/TileMatch/` 前缀的路径链接（如 `[[游戏逻辑/Rocket/xxx]]`）—— Obsidian 按 vault-root 解析，会指向不存在的路径。

### 关联章节规范

- 所有文档末尾必须有 `## 关联` 章节，列出相关文档
- 关联链接必须有简要说明（用 `—` 分隔）
- 末尾链接统一指向 `[[02-PROJECTS/TileMatch/_MOC\|TileMatch 知识库 MOC]]` 作为返回入口

正确示例：
```markdown
## 关联

- [[02-PROJECTS/TileMatch/_MOC|TileMatch 知识库 MOC]] — 返回项目总入口
- [[分析-死局逻辑与改进方案-v1|死局逻辑]] — 相关：死局触发条件
```

## 四、MOC 层级与导航

```
HOME.md（vault 级主 MOC，D:\LibraryG\HOME.md）
  └─ _MOC.md（TileMatch 项目 MOC）
       ├─ 局内障碍知识库_MOC.md（障碍系统子 MOC）
       └─ 知识库文档顺序索引.md（按 cat_order 全量排序）
```

| MOC | 位置 | 职责 |
|-----|------|------|
| `HOME.md` | vault 根 | 全库入口，指向所有项目/知识领域的各级 MOC |
| `_MOC.md` | `02-PROJECTS/TileMatch/` | TileMatch 导航中心，覆盖 100% 项目文档 |
| `局内障碍知识库_MOC.md` | `游戏逻辑/局内障碍/` | 障碍系统子入口 |
| `知识库文档顺序索引.md` | `知识库/` | cat_order 全量排序（不参与 MOC 导航） |

规则：
- 每个 MOC 用 `aliases` 提供唯一别名（如 `aliases: [TileMatch 知识库_MOC]`）
- vault 内禁止两个 MOC 同名（已统一：WorkBuddy MOC 更名为 `WB-MEMORY_MOC.md`）
- HOME.md 为**重点维护对象**，新增项目/MOC 时必须在 HOME.md 登记

## 五、版本管理

- `analysis` 类文档使用版本号：`v1`, `v2`, ...
- 重大重构时版本号+1，同时在文档开头注明「依据版本」

## 六、操作流程

### 新建文档
1. 确定类型和文件夹
2. 按命名规则生成文件名
3. **分配 `cat_order`**：找到目标文件夹中现有的最大 `cat_order`，新文件取 N+1（三位补零）
4. 生成 frontmatter（含 `cat_order`）
5. 写入内容，末尾加 `## 关联`
6. **更新 `_MOC.md`**：在对应章节添加 `[[基名|显示名]]`
7. **更新 `知识库文档顺序索引.md`**：在对应分类下追加新条目

### 更新文档
1. 更新 `date` 字段
2. 如果用旧名、移动位置等导致链接变更 → 检查并更新所有引用该文档的 wikilink
3. 更新 `## 关联` 章节
