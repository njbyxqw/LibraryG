# 项目知识库维护总纲

> 本文档汇总 TileMatch 项目知识库的管理与维护规则。它只整理已存在规范文件中的内容；对来源为草稿、待确认或历史方案的内容，统一标注为建议或待确认，不提升为正式规则。

---

## 使用范围

| 范围 | 说明 |
|---|---|
| 适用对象 | `02-PROJECTS/TileMatch/` 下的项目知识库文档 |
| 上层入口 | `HOME.md`、`工作空间总纲.md`、`02-PROJECTS/TileMatch/_MOC.md` |
| 跨项目规则 | MOC 命名、Daily、INBOX、MT / TS 复现流程按 `02-PROJECTS/Agent/工作流/` 中规范执行 |
| 不包含 | 具体关卡设计、玩法数值、聊天中未被规范文件确认的内容 |

## 已确认规则

### 检索与导航

| 规则 | 来源 |
|---|---|
| 查知识库时从 `HOME.md`、`工作空间总纲.md`、项目 `_MOC.md`、MEMORY 逐级进入，不默认全盘搜索。 | `HOME.md`、`02-PROJECTS/Agent/Memory.md`、`规范-MOC命名与导航层级.md` |
| `HOME.md` 是全库主路由，只放项目入口和高价值入口；项目 `_MOC.md` 做模块导航，不承载长篇正文。 | `规范-MOC命名与导航层级.md` |
| 从 `HOME.md` 指向项目 MOC 时使用 vault-root 完整路径；项目内部返回本项目 MOC 可用 `[[02-PROJECTS/TileMatch/_MOC|项目 MOC]]`。 | `规范-MOC命名与导航层级.md` |
| 新增项目文档后必须更新对应 `_MOC.md`，并在文档末尾保留 `## 关联`。 | `规范-知识库文档分类标准.md` |

### 文档结构

| 规则 | 来源 |
|---|---|
| 文档通过 frontmatter `type` 分类：`spec`、`analysis`、`report`、`reference`、`note`、`index`。 | `规范-知识库文档分类标准.md` |
| `spec`、`analysis`、`report`、`note` 必填 `title`、`date`、`type`、`status`、`tags`、`cat_order`。 | `规范-知识库健康检查.md` |
| `reference` 必填 `type`、`tags`、`cat_order`；`index` 必填 `title`、`type`、`tags`。 | `规范-知识库健康检查.md` |
| `status` 使用英文值，核心规范中明确禁止用中文状态值替代。 | `规范-知识库文档分类标准.md` |
| `analysis` 类文档使用版本号；重大重构时版本号加一，并在文档开头注明依据版本。 | `规范-知识库文档分类标准.md` |

### 维护检查

| 规则 | 来源 |
|---|---|
| 知识库健康检查按“导航可用性 60% + 规范合规 40%”评分。 | `规范-知识库健康检查.md`、`规范-自动化任务设计-v1.md` |
| 导航可用性包括断链扫描、MOC 导航闭环、链接风格。 | `规范-知识库健康检查.md` |
| 规范合规包括 Frontmatter、`cat_order`、文件命名、零污染。 | `规范-知识库健康检查.md` |
| 自动化维护禁止替换已有文件、未确认移动源文件、自动 git commit/push。 | `规范-自动化任务设计-v1.md` |

### 产物与日志

| 规则 | 来源 |
|---|---|
| `00-INBOX/` 是对话工作区，不做最终分类判断；整理阶段再归位。 | `INBOX对话工作区工作流.md` |
| 规范类和流程类产物形成后，应移动到稳定目录，不长期留在 INBOX。 | `INBOX对话工作区工作流.md` |
| DAILY 记录“做了什么 + 结论是什么”，不存放具体产物文件。 | `工作内容日志同步规范.md` |
| 同一天不同项目日志合并到同一 `01-DAILY/YYYY-MM-DD.md`，按项目分节。 | `工作内容日志同步规范.md` |

## 后续维护规范

1. LibraryG 全局入库流程优先按 [[02-PROJECTS/Agent/工作流/规范-任务产出入库与维护|任务产出入库与维护规范]] 执行；本文只补充 TileMatch 项目内规则。
2. 新增或整理知识库文档前，先从 `HOME.md` 或项目 `_MOC.md` 进入目标目录，再在该目录内做局部检索。
3. 新文档先判断 `type` 和目标目录，再补齐 frontmatter、`cat_order`、`## 关联`。
4. 新文档落库后同步更新 `_MOC.md`；如果参与顺序管理，再更新 `知识库文档顺序索引.md` 的静态备份。
5. 若来源是草稿、聊天结论、历史方案或待验证内容，在正文中明确标为“建议”或“待确认”。
6. 不确定的历史材料优先标注 `historical`、`deprecated` 或 `needs-review`，不要直接删除。
7. 自动化或批量维护只生成报告和建议；涉及移动、覆盖、删除、git commit/push 时必须另行确认。
