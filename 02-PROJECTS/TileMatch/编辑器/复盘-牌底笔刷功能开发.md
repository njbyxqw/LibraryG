# 牌底笔刷功能开发复盘

## 一、需求

在编辑器中，给关卡内**每张牌块独立配置底板资源**（当前统一用 block_bg2）。

- 操作方式：和花色/障碍一样，右侧选一个底板 → 点棋盘上的牌 → 那张牌换底板
- 效果：同一关内多张牌可以显示不同底板
- 目标：编辑后进 Play 验证

## 二、三次尝试

### v1 — LevelConfigView 下拉

**做法**：在关卡属性面板（Theme 旁边）加一个"牌块底板"下拉

**废弃原因**：交互位置不对。用户要的是和花色一样的侧栏点选方式，不是属性面板下拉。

### v2 — TileSelectionView 分类 + 映射文件

**做法**：
- 在 TileSelectionView 新增"Block_bg"分类（和 Tile/Element/TileType 并列）
- 选底板 → 点棋盘牌块 → 写 `{关卡名}.blockbg.json` 映射文件
- 反射更新场景 SpriteRenderer
- Play 模式用 `EditorApplication.update` 持续扫描覆盖

**技术和交互都走通了，但 Play 模式不生效。**

**失败原因**：

| 问题 | 表现 | 根因 |
|------|------|------|
| 位置匹配 | Play 模式找不到对应牌块 | `transform.localPosition` ≠ 棋盘坐标（有 Scale/Offset），后来用反射读 `TileData.Position` 修复 |
| 时序 | `EnteredPlayMode` 触发时牌块还没创建 | tile 在游戏初始化过程中动态创建，晚于 playModeStateChanged |
| **根本原因** | 数据不在关卡 JSON 里 | 映射文件是外部数据，运行时不走这个路径。要想 Play 生效必须 hack 进去覆盖，脆弱且不通用 |

### v3 — 关卡数据模型加字段

**做法**：在 `LevelTileConfig` 加 `BlockBg` 字段（string），改 `TileData`、`TileViewBackgroundAb`，编辑器直接写回关卡文件。

**废弃原因**：编译反复报错（`Data` 是 `protected`、asmdef 缺引用、命名冲突），更关键的是——同事已经在同一个分支上提交了完整实现。

## 三、同事的实现（commit `0f0b335519` "牌底笔刷"）

### 架构

```
数据层
  LevelTileConfig.BgId (int, 0=默认)
    → TileData.BgId
    → LevelConfigWriter: BgId != 0 时写 JSON

编辑器交互
  TileSelectionView 内置 "TileBG" 分类（非本地扩展）
    → TileSelectionBg 组件（镜像 TileSelectionObstacle）
    → SetCurrentTileBg(bgId)
    → MessageDispatch(TileBgChange)

  点棋盘 → BoardBlock.OnTileBtnClick()
    → else if (CurrentTileBg > 0) 分支
    → ModifyTileBgCommand(tile, newBgId)
    → BgIdModification（命令模式，支持 Undo/Redo）

运行时渲染
  TileView.ApplyTileBg()
    → if Data.BgId > 0:
        background.sprite = 加载 block_bg/block_bg{N}.png
    （直接覆写，不走 TileViewBackgroundAb）
```

### 关键设计决策

| 决策 | 理由 |
|------|------|
| `BgId` 用 int 而非 string | 和资源编号天然对应，比字符串名更稳定 |
| 渲染在 `TileView.ApplyTileBg()` 而非 `TileViewBackgroundAb` | `Data` 是 `protected`，`TileView` 自身能访问，`TileViewBackgroundAb` 不能 |
| 交互走 `BoardBlock.OnTileBtnClick` 内部分支 | 不需要额外的事件监听，复用现有的 tile 点击分发逻辑 |
| 命令模式 `BgIdModification` | 支持 Undo/Redo，和现有 `ModifyTile` 体系一致 |
| 默认底板 `block_bg3` | 新放置的牌块默认用 block_bg3，不是空或全局配置 |

### 改动量

27 个文件，1065+ 行。涉及数据层、编辑器交互、命令、UI、运行时渲染全链路。

## 四、真正的卡点分析

### 卡点不是技术，是策略

**问题 1：选了本地扩展的路，但没有先判断边界**

本地扩展的适用场景：
- ✅ 快捷键绑定、UI 辅助、编辑器工具（不涉及数据模型变更）
- ❌ 需要关卡 JSON 加新字段、运行时渲染逻辑变更

牌底笔刷需要 `LevelTileConfig` 加字段 + `TileView` 改渲染，**已经跨过了本地扩展的能力边界**。

**问题 2：没有先看分支已有提交**

同事 12:04 提交了完整实现，我们是下午开始做的。如果一开始 `git log --oneline -5` 看一眼，全程不用写一行代码。

**问题 3：反复修补，没有停下来诊断根因**

v2 的 Play 模式不生效——正确做法是先诊断 "为什么数据到不了运行时"，而不是接着用映射文件修补、再用 `EditorApplication.update` 修补、再用反射修补。一层层补丁上去，离正确方案越来越远。

## 五、教训

1. **动手前先确认三件事**：
   - 分支上有没有人已经做了？（`git log`）
   - 这功能要不要提交 git？（决定走源码还是本地扩展）
   - 涉及数据模型变更吗？（涉及 → 必须走源码，不涉及 → 可以走本地扩展）

2. **本地扩展有明确边界**：数据模型不变、纯编辑器辅助。一旦需要改 LevelConfig 字段或运行时渲染逻辑，必须在源码里做。

3. **遇到阻塞先诊断，不要修补**：v2 Play 不生效 → 根因是数据不在 JSON 里。修补映射文件、修补时序、修补位置匹配都不对。

4. **同事的代码是最好的设计参考**：
   - 用 `int BgId` 而非 `string BlockBg`
   - 渲染放在 `TileView.ApplyTileBg()` 而非 `TileViewBackgroundAb`
   - 命令模式 `BgIdModification` 支持 Undo/Redo
   - 交互走 `BoardBlock` 内部分支，不额外监听事件
1. **对规则的判断是我的责任**：过程中用户问"现有规则中有没有限制此次功能开发的规则"，我回答没有。这是错的。本地扩展的规则里隐含了一个硬边界——"不修改游戏/编辑器核心代码"。牌底笔刷需要改 `LevelTileConfig` 数据模型和 `TileView` 运行时渲染，已经越界了。我应该识别出来并反馈："这个功能超出了本地扩展的能力范围，需要在源码里做。"

2. **遇到编译错误反复修补，没有停下来问：这条路对不对**：v2 Play 不生效，根因是数据不在 JSON 里。我加了映射文件、加了 PlayMode 重试、加了反射位置匹配，全是在错误路线上打补丁。正确做法是回到出发点：本地扩展做不了数据模型变更，必须走源码。

3. **别人做了不是我失败的理由**：能不能做出来是我的问题。本地扩展选错了路线、规则边界判断错误、编译报错后没有反思路线，这些才是真正的失败原因。

## 六、重做提示词模板

如果重新做这个需求，提示词应该这样写，把踩过的坑变成硬约束：

```markdown
## 需求：关卡编辑器 — 单牌块牌底配置

### 功能描述
在关卡编辑器中，支持为每个牌块单独配置牌底背景资源。
操作流程：侧栏选择牌底 → 点击棋盘牌块 → 该牌块背景切换为所选资源。
与花色/障碍的选牌流程一致，复用 TileSelectionView 的分类机制。

### 技术约束（必须遵守）
1. 此功能涉及数据模型变更（LevelTileConfig 新字段）和运行时渲染变更（TileView），必须直接修改源代码，不能用本地扩展方案
2. 字段类型用 `string BlockBg`（对齐资源命名 `block_bg*.png`），不用 `int BgId`
3. 资源路径统一为 `Tiles/` 根目录下的 `block_bg*.png`，不用 `block_bg/` 子目录
4. 不新增 MessageDispatch 消息类型，牌底变更走 ModifyTile 命令（支持 Undo/Redo）
5. 不硬编码默认值（如 block_bg3），null 表示使用全局牌底配置

### 设计要求
- 有效且优美，不是精简版：改动范围最小化，但不以牺牲合理性为代价
- 数据流必须闭环：LevelTileConfig → TileData → TileView.ApplyTileBg() 全链路打通
- 新增牌底资源只需往 `Tiles/` 目录放入 `block_bg*.png` 文件，无需任何代码变更
- EditorUtils 扫描 `block_bg*.png` 自动发现所有可用牌底

### 执行前必须完成
1. 先看当前分支最近提交，确认是否有相关功能已存在
2. 列出所有需要修改的文件和改动点，评估改动合理性后再执行
3. 每次改动说明"为什么这样改"，而不是"改了什么"

### 验收标准
- 编辑器：选择牌底 → 点击牌块 → 牌块背景即时切换
- 运行时：编辑后进入关卡，牌块背景与编辑时一致
- Undo/Redo：牌底操作可撤销/重做
- 新增资源：放入 block_bg*.png → 侧栏自动出现新选项
- 兼容性：BlockBg 为 null 的牌块使用全局牌底，老关卡无影响
```

### 提示词设计逻辑

| 踩坑点 | 提示词如何规避 |
|---|---|
| 我说"本地扩展没问题"结果做不出来 | **约束第1条**直接锁定源代码方案 |
| 用了 int BgId 而非 string | **约束第2条**明确用 string BlockBg |
| 没检查现有提交就闭门造车 | **执行前第1条**强制先看分支 |
| 改动太大（14文件/新增消息类型） | **约束第4-5条**砍掉不必要的复杂度 |
| 数据流没闭环（v2运行时不生效） | **设计要求**明确全链路打通 |
| 只做精简版而非好版本 | **设计要求**写明"有效且优美" |

**核心原则**：把踩过的坑变成硬约束写进提示词，让 AI 在执行前就被限制在正确轨道上，而不是靠它自己"领悟"教训。
