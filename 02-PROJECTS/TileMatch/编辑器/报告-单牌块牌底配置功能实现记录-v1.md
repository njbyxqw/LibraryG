# 单牌块牌底配置功能 — 完整实现记录

## 一、功能概述

在关卡编辑器中为每张牌块**独立配置牌底背景资源**，覆盖全局 `GlobalConstCfg.BlockBgConfig`（当前 `block_bg2`）。

- `BlockBgConfig = null` → 回退全局配置（老关卡零影响）
- `BlockBgConfig = "block_bg3"` → 该牌块显示 block_bg3
- 操作流程：侧栏选牌底 → 点棋盘牌块 → 该牌块底板即时切换
- Undo/Redo 支持，新增资源零代码改动

## 二、核心数据流（必须闭环）

```
LevelTileConfig.BlockBgConfig  (JSON 持久化, string, null=全局)
  ↓ 构造函数读取
TileData.BlockBgConfig  (运行时数据)
  ↓ 运行时: TileBase.Initialize() → TileViewBackgroundAb.SetBlockBg()
  ↓ 编辑器: BoardBlock.RefreshBaseInfo() → _blockBgImage.sprite
```

## 三、资源目录

- **新建子目录**: `Assets/Game/TileV2/Res/Game/GameCore/Texture/Tiles/BlockBg/`
- **复制现有牌底**: `block_bg.png` + `block_bg2.png` 复制（非移动）到 BlockBg/
  - 根目录原件保留 → 全局配置仍从 `Tiles/{bgConfig}.png` 加载
  - 子目录副本 → 出现在单牌底选择器列表中
- EditorUtils 只扫描 `BlockBg/` 下 `block_bg*.png`
- 列表首项固定为「默认(全局)」（`__DEFAULT__` 常量），选中后点牌块 = 清除单牌底

#### 3. `Scripts/GameCore/View/GameView/Views/Tile/TileViewBackgroundAb.cs` — 新增 SetBlockBg

在 `ApplyBlockBackground(GlobalConstCfg)` 方法后新增：
```csharp
private const string BlockBgSubDir = "Assets/Game/TileV2/Res/Game/GameCore/Texture/Tiles/BlockBg";

/// <summary>
/// 设置单牌块牌底配置。bgConfig 为 null/空时保持 Awake 加载的全局牌底不变。
/// 资源从 BlockBg/ 子目录加载（与全局牌底的 Tiles/ 根目录区分）。
/// </summary>
public void SetBlockBg(string bgConfig)
{
    if (string.IsNullOrEmpty(bgConfig)) return;

    Sprite sprite = null;
#if UNITY_EDITOR
    sprite = AssetDatabase.LoadAssetAtPath<Sprite>($"{BlockBgSubDir}/{bgConfig}.png");
#endif
    if (sprite == null)
    {
        sprite = TileResourceHub.LoadAsset<Sprite>(
            $"{BlockBgSubDir}/{bgConfig}.png", gameObject);
    }

    if (sprite == null)
    {
        UtilsLog.E($"TileViewBackgroundAb.SetBlockBg: bgConfig:{bgConfig} cannot be loaded from BlockBg dir");
    }
    else
    {
        spriteRenderer.sprite = sprite;
    }
}
```
**关键**: 加载路径用 `BlockBgSubDir`（子目录），**不复用** `ApplyBlockBackground` 的根目录路径。

#### 4. `Scripts/GameCore/View/GameView/Views/Tile/TileBase.cs` — Initialize 后刷新

```csharp
public class BlockBgModification
{
    public string OldBgConfig { get; }
    public string NewBgConfig { get; }

    public BlockBgModification(string oldBgConfig, string newBgConfig)
    {
        OldBgConfig = oldBgConfig;
        NewBgConfig = newBgConfig;

    public bool IsValid => OldBgConfig != NewBgConfig;
}
```

```csharp
public static ModifyTile CreateBlockBgModification(LevelTileConfig levelTileConfig,
```

## 五、遇到的问题及解决方案

### 问题 1: CS1503 — SetCurCategoryTypeTile 类型不匹配

**现象**: `TileSelectionBlockBg.cs(46)`: `SetCurCategoryTypeTile` 第二个参数期望 `TileSelectionTile`，但传入 `TileSelectionBlockBg`。

**原因**: `SetCurCategoryTypeTile(string, TileSelectionTile)` 只接受 TileSelectionTile 类型。TileSelectionBlockBg 不继承 TileSelectionTile。

**解决**: 去掉 `SetCurCategoryTypeTile` 调用。该方法只用于选中状态管理（CurCategoryTile 字典），牌底选择不需要此功能。

### 问题 2: CS0103 — LevelEditorConfigDataManager 不在作用域

**现象**: `TileSelectionBlockBg.cs(63)`: `LevelEditorConfigDataManager` 未找到。

**原因**: 命名空间未引入，且该类用于配表查询，牌底预览不需要。

**解决**: 去掉 `LevelEditorConfigDataManager` 引用，直接用 `EditorUtils.SetSprite` 加载全局 block_bg2 预览图。

### 问题 3: CS0165 — targetBoard 未赋值

**现象**: `BoardView.Tile.cs(192)`: `targetBoard` 未赋值就使用。

**原因**: `targetBoard` 在 `if (blockList.TryGetValue(oldPos, out var targetBoard))` 块内赋值。我在 if 块**外面**加了独立的 BlockBg 分支引用 targetBoard，当 TryGetValue 失败时 targetBoard 未赋值。

**解决**: 删掉独立的 BlockBg 分支。if 块内已有 `targetBoard.RefreshUI()`（第187行），BlockBg 修改时牌块在原位，TryGetValue 成功，RefreshUI 会触发 RefreshBaseInfo 刷新牌底。

### 问题 4: 右侧栏牌底图片不对

**现象**: 右侧栏"牌底"分类显示的图片不是 BlockBg/ 目录下的资源，而是预制体默认图标。

**原因**: 复制到 BlockBg/ 子目录的 png 文件被 Unity 默认 import 为 **Texture 类型**（`textureType: 0`），而非 **Sprite 类型**（`textureType: 8`）。`AssetDatabase.LoadAssetAtPath<Sprite>` 对非 Sprite 类型返回 null。

**根因对比**:
| 字段 | 根目录原版 | 子目录复制版 |
|------|-----------|-------------|
| textureType | 8 (Sprite) | 0 (Default) |
| spriteMode | 1 | 0 |
| enableMipMap | 0 | 1 |

**解决**: 修改 BlockBg/ 下所有 .meta 文件:
```
textureType: 0 → 8
spriteMode: 0 → 1
enableMipMap: 1 → 0
```
用 sed 批量修改:
```bash
sed -i 's/enableMipMap: 1/enableMipMap: 0/' block_bg.png.meta block_bg2.png.meta
sed -i 's/spriteMode: 0/spriteMode: 1/' block_bg.png.meta block_bg2.png.meta
sed -i 's/textureType: 0/textureType: 8/' block_bg.png.meta block_bg2.png.meta
```

**预防**: 新增 png 文件时，复制现有 Sprite 的 .meta 并替换 GUID:
```python
import uuid, re
# 复制 .meta，替换 GUID
content = re.sub(r'guid: [a-f0-9]+', f'guid: {uuid.uuid4().hex}', content)
```

### 问题 5: ModifyTile 构造函数参数扩展

**现象**: ModifyTile 构造函数有 9 个参数，新增 BlockBgMod 参数后所有 8 个 `Create*Modification` 工厂方法都需补 null。

**解决**: 用 **C# 可选参数** `BlockBgModification blockBgMod = null`，避免改动任何现有工厂方法。编译器自动用默认值 null。

## 八、前置失败复盘

> 本功能经历三次失败尝试后独立完成实现。完整复盘见 [[复盘-牌底笔刷功能开发|牌底笔刷复盘]]。

### 失败路线

**v1 — LevelConfigView 下拉**：交互位置选错——应该和花色一样用侧栏点选。废弃。

**v2 — TileSelectionView + 外部映射文件**：选牌底后写 `{关卡名}.blockbg.json` 映射文件。交互和技术都通了，但 Play 模式不生效。根本原因：数据不在关卡 JSON 里，运行时走不到映射文件。接着打了三层补丁——反射修位置、`EditorApplication.update` 修时序、hack 覆盖渲染——全部在错误路线上打补丁。

**v3 — 关卡数据模型加字段**：在 `LevelTileConfig` 加 `BlockBg`（string），方向终于对了。但编译反复报错：`Data` 是 `protected`（`TileViewBackgroundAb` 拿不到）、asmdef 缺引用、命名冲突。

### 根本原因

| 错误 | 后果 |
|------|------|
| 本地扩展路线边界判断错误 | 牌底笔刷需要改 `LevelTileConfig` 和 `TileView` 运行时渲染，已跨过本地扩展能力边界 |
| v2 反复修补不停下诊断 | Play 不生效的根因是数据不在 JSON 里，不是位置、时序、渲染的任何技术细节 |
| v3 编译报错后没反思架构 | `protected` 限制不是语法问题——是调用点选错了，`TileView.ApplyTileBg` 才是正确入口 |

### 教训

**1. AI 对规则的误判是起点**

过程中用户问"现有规则中有没有限制此次功能开发的规则"，AI 回答没有。这是错的。本地扩展的规则里隐含了一个硬边界——不修改游戏/编辑器核心代码。牌底笔刷需要改 `LevelTileConfig` 数据模型和 `TileView` 运行时渲染，已经越界了。AI 应该识别出来并反馈：这个功能超出了本地扩展的能力范围，需要在源码里做。

**2. 动手前确认三件事**

- 这功能要不要提交 git？（决定走源码还是本地扩展）
- 涉及数据模型变更吗？（涉及 → 必须走源码，不涉及 → 可以本地扩展）
- 涉及运行时渲染逻辑吗？（涉及 → 必须走源码）

**3. 本地扩展有明确边界**

数据模型不变、纯编辑器辅助。一旦需要改 `LevelConfig` 字段或运行时渲染逻辑，必须在源码里做。不要试图在本地扩展路线上修补边界的破口。

**4. 遇到阻塞先诊断根因，不要在错误路线上打补丁**

v2 Play 不生效 → 该问的不是"怎么让映射文件生效"，而是"数据为什么到不了运行时"。反射修位置、`EditorApplication.update` 修时序、hack 覆盖渲染——每一层补丁都是对错误路线的加固，离正确方案越来越远。

**5. 编译报错反复修补，应该停下来问：这条路对不对**

v3 编译报 `protected` 访问限制 → 不是语法没写对，是架构选错了调用点。`TileViewBackgroundAb` 不适合做牌底逻辑的入口，`TileView` 自身才是。到这一步该停下来反思，而不是继续报错继续补。

**6. 同事的代码是设计参考，不是替代品**

目标是自己独立做出来。但同事实现里的设计决策可以反向验证自己的方案：`int BgId`（对应资源编号）vs `string BlockBg`（对应文件名），`TileView.ApplyTileBg()` vs `TileViewBackgroundAb`，命令模式 vs 外部映射。这些对比让人理解"为什么这样设计更好"。

**7. 别人做了不是失败的理由**

能不能做出来是自己的问题。本地扩展选错了路线、规则边界判断错误、编译报错后没有反思路线——这些才是真正的失败原因。即使同事没做，v2 和 v3 的问题依然存在。
