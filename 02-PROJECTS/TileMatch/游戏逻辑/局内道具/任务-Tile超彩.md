# Tile 超彩

> 目标：新增一种局内“Tile 超彩”机制。玩家每完成 1 次成功匹配消除即获得 1 点充能；累计 6 点后触发超彩效果。充能状态机、目标选择、逻辑 Action 与表现完成回调参考 [[分析-染色炸弹实现逻辑-v1|染色炸弹实现逻辑]]；超彩的具体效果尚未确定，本任务不预设或实现效果规则。

## 状态与边界

- 当前阶段：需求整理与现有机制对位；尚未开始代码、配置、资源或关卡改动。
- 事实来源：`分析-染色炸弹实现逻辑-v1.md` 对 `tile/tile_dyeingbomb` 分支的静态核对；该结论不可替代当前目标分支的复查。
- 本次不做：不确定超彩具体效果前，不创建 TileType、Prefab、特效资源、埋点或 AB 配置；不改普通匹配、Bar 消除与染色炸弹的既有行为。

## 已确定需求

| 项目 | 规则 | 验收口径 |
|---|---|---|
| 充能来源 | 每完成 1 次**成功匹配消除结算**，超彩增加 1 点能量。一次结算消除的多张 Tile 仅计 1 次，不按消除 Tile 数重复充能。 | 一次匹配完成后能量恰好 +1；未形成匹配、仅选牌/移动/道具展示不充能。 |
| 触发门槛 | 最大能量暂定为 6；累计达到门槛时进入一次超彩触发流程。 | 第 6 次成功匹配后只触发 1 次；前 5 次不触发。 |
| 机制骨架 | 参考染色炸弹的“能量累积 → 处理锁 → 目标/规则决策 → Logic Action → ViewAction → 完成回调解锁”链路。 | 触发期间不重入；表现完成后可恢复后续结算与下一次充能。 |
| 状态归属 | 门槛、效果参数属于配置（只读）；本局当前能量和处理锁属于运行时状态（仅超彩系统写）；跨局持久化默认不做。 | 退出/重开关卡不会沿用本局能量，除非后续需求明确要求。 |

> [!important] “匹配消除 1 次”的判定边界
> 以 TileV2 的实际“匹配成功并完成结算”的统一入口为准，而不是点击 Tile、加入 Bar、单张 Tile 移除或 View 动画开始。实施前必须在当前目标分支定位该入口，并用连续匹配、连锁匹配和道具触发分别验证计数次数。

## 暂定与待确认项

| 待决项 | 选项 / 需要确认的规则 | 未确认时的处理 |
|---|---|---|
| 超彩效果 | 效果目标、选牌规则、对 Tile / Bar / OverBar / 障碍 / Effect 的影响、是否改变 TileType、是否需要额外奖励。 | 不实现效果层；仅保留“EffectSpec 待定义”节点。 |
| 触发后能量 | A. 清零；B. 消耗 6 点并结转溢出；C. 满能停留，等待玩家主动触发。 | 不写状态重置逻辑或 UI 文案。 |
| 触发时机 | A. 当前消除结算完全结束后立即自动触发；B. 后续安全帧/流程节点触发；C. 玩家主动点击。 | 先复核匹配结算与 Flow/Action 时序。 |
| 门槛可配置性 | 固定 6，或按关卡/活动/AB 下发。 | 先用单一配置字段，不预建活动或 AB 体系。 |
| 展示与反馈 | 是否显示能量条、满能提示、目标高亮、音效/粒子、可跳过策略。 | 效果确定后与 ViewAction 一并设计。 |
| 统计 | 是否记录充能、满能、触发、效果命中、完成/中断等事件及字段。 | 等效果与运营目标确认后补埋点契约。 |

## 参考实现与设计边界

### 可复用的染色炸弹骨架

```text
成功匹配结算（待定位）
  → SuperColorSystem.AddEnergy(1)
  → 达到 MaxEnergy=6
  → 锁定本次处理，生成超彩效果目标/规则（待定义）
  → ActionType.SuperColor + SuperColorActionData（名称待代码阶段确认）
  → SuperColorViewAction
  → OnSuperColorComplete() 解锁，处理剩余能量策略（待定）
```

染色炸弹已经证明的职责分层：`DyeingBombSystem` 负责运行时能量、阈值和处理锁；`CustomTargetFilterType.DyeingBomb` 负责选目标；`TileService.ModifyTile()` 负责逻辑状态变更；`DyeingBombViewAction` 只负责表现并以完成回调解除锁。超彩仅应复用这条职责边界，不能直接复用“改为 `DyedSuit=1002`”的效果规则。

### 变化轴

| 变化轴 | 当前暂定 | 后续可扩展方向 |
|---|---|---|
| 能量阈值 | 固定 6 次成功匹配 | 关卡/活动/AB 配置，待运营需求确认 |
| 触发方式 | 达阈值后自动进入处理流程 | 主动释放或延迟释放，待交互方案确认 |
| 效果规则 | 未定义 | 染色、消除、升级、障碍交互或组合效果，必须单独评审 |

## 实现规划

### 阶段一：确认结算入口与产品规则

1. **定位成功匹配结算的唯一入口**（当前 TileMatch 目标分支的 TileV2 Logic）
   - 动作：追踪玩家点击、自动匹配、道具导致的匹配与连锁匹配，确定“每次成功匹配消除”只会经过一次的业务结算点。
   - 状态：运行时能量的写入入口；仅超彩系统可写。
   - 依赖：无。
   - 复杂度：中；风险：高——若挂在 Tile 移除或 View 回调，可能多充/漏充。
   - 最小验证：三连消除、连续两次消除、未匹配选牌各自得到 1、2、0 次充能。
   - 回滚点：只撤销该入口到超彩系统的通知，不触及原匹配结算。

2. **冻结效果规格与能量结转规则**（需求文档 / 评审结论）
   - 动作：补齐“效果目标、影响范围、触发时机、是否自动、能量清空/溢出、表现和埋点”六项决策。
   - 状态：效果参数与门槛为配置，只读；跨局持久化默认无。
   - 依赖：步骤 1。
   - 复杂度：中；风险：高——效果未定义前不能正确选择 TileService、TargetFilter 或 ViewAction。
   - 最小验证：用一张效果规则表能覆盖无目标、目标不足、触发中再次结算、关卡结束中断四类场景。
   - 回滚点：规则只在任务文档中调整，尚无代码变更。

### 阶段二：最小逻辑闭环

3. **建立配置与运行时状态**（路径以目标分支实查为准，参考 `Energy.json` 与 `DyeingBombSystem.cs`）
   - 动作：新增超彩配置（初始仅 `MaxEnergy=6`）和本局 `currentEnergy`、`isProcessing`；不写 Profile。
   - 状态：配置只读；运行时状态仅 `SuperColorSystem` 写，UI/View 只读。
   - 依赖：步骤 1、2。
   - 复杂度：中；风险：中——需兼容缺少新配置的旧关卡/旧资源版本。
   - 最小验证：配置缺失时功能安全关闭；正常配置下 0→6 的状态可观察。
   - 回滚点：删除超彩配置及独立系统注册，不影响现有匹配系统。

4. **接入充能与触发状态机**（匹配结算入口、`SuperColorSystem`）
   - 动作：只在已确认的成功结算点调用 `AddEnergy(1)`；达到门槛后防重入，按已冻结的触发时机派发效果请求。
   - 状态：运行时状态；单写者为 `SuperColorSystem`。
   - 依赖：步骤 3。
   - 复杂度：中；风险：高——必须处理表现未完成、关卡退出、连续结算与能量溢出。
   - 最小验证：第 6 次仅触发一次；触发中发生新的可结算事件不会重复启动；退出时清理幂等。
   - 回滚点：解除结算入口通知即可完全禁用超彩。

5. **实现效果的 Logic Action 与目标规则**（目标路径由步骤 2 决定）
   - 动作：将“选什么、怎样改逻辑状态”限定在 Logic 层；必要时新增专用 TargetFilter 和 ActionData，不让 View 直接改 Tile 数据。
   - 状态：效果参数为配置；Tile 状态仍由既有 `TileService` 或当前项目等价服务统一写入。
   - 依赖：步骤 2、4。
   - 复杂度：较高；风险：高——不同效果对 Bar、OverBar、不可见牌和障碍的合法性不同。
   - 最小验证：目标为空/不足、候选包含不可操作牌、普通目标三类均有确定结果且不破坏原结算。
   - 回滚点：移除专用 Action/Filter 注册；既有系统不改语义。

### 阶段三：表现、统计与回归

6. **实现 ViewAction 与完成回调**（ViewAction、Prefab/粒子/音效路径待定）
   - 动作：表现层消费 Logic Action 的确定结果，播放效果并确保一次且仅一次回调系统解锁；资源与 TileType 复用必须按效果规格审查。
   - 状态：View 不拥有逻辑状态，只报告完成/失败。
   - 依赖：步骤 5。
   - 复杂度：中；风险：高——漏回调会阻塞结算，重复回调会导致重入。
   - 最小验证：正常完成、目标为空降级、关卡退出/中断均能解除锁或安全终止。
   - 回滚点：仅移除超彩 Action 的 View 注册与资源，不影响原 TileView。

7. **补齐埋点、测试与发布检查**（BI、EditMode/PlayMode、目标资源包）
   - 动作：按确认的指标建立事件字段；覆盖逻辑自动化测试和 Unity Play Mode/设备端验证；若资源进入热更新，验证 XAsset/投递闭环。
   - 状态：统计仅观察，不反写游戏状态。
   - 依赖：步骤 4-6。
   - 复杂度：中；风险：中。
   - 最小验证：见“测试策略”。
   - 回滚点：用配置开关关闭超彩入口；保留无副作用的埋点记录按发布策略处理。

## 测试策略

- 逻辑：第 1–5 次成功匹配只累计；第 6 次触发一次；一次多 Tile 消除只记一次；自动匹配、连锁匹配、道具匹配按阶段一确认的统一口径计数。
- 状态机：触发动画未完成时不重复触发；正常完成、异常中断、关卡退出都不会永久保留处理锁；按最终规则验证清零/结转。
- 效果：无目标、目标不足、目标位于可见/不可见区域、Bar/OverBar、带 Effect/障碍等场景，以阶段二冻结的效果边界为准。
- 兼容：无超彩配置的旧资源版本安全关闭；确认是否需要资源包/热更新兼容；本期默认无 Profile 迁移。
- Unity：静态代码检查或 `git diff --check` 不能证明 Unity Play Mode、资源加载、热更新或设备端表现，以上必须单独实机/Editor 验证。
