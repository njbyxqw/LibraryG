# 风车（Shuffle）优化提需

## 一、背景

### 1.1 风车是什么

风车（Shuffle）是 InGame 道具，点击后重新排列牌堆区（Board）的牌。本质是「交换牌的位置」——从高亮层和非高亮层各取一张牌，两两配对交换。

### 1.2 现有逻辑的问题

当前版本会做一次「智能优化」：看手牌区（Bar）最右边凑不齐的那张牌是什么花色，然后优先把牌堆里同花色的牌交换到高亮层，帮它凑够 3 张消除。

**问题是只优化了 1 种花色**。如果 Bar 里同时有好几种花色的牌都差几张凑不齐，风车只照顾最右边那张的花色，其他花色的牌全靠随机运气。

举个例子：
```
Bar = [A, A, B, C, C]    （每 3 张同花消除）

当前风车：只帮 C（最右边凑不齐的），A 和 B 纯随机运气
```

### 1.3 改造动机

**花道具是期待正反馈的**。但也不应该每次都帮——偶尔的随机打乱也是 Shuffle 的魅力，保留「运气」感。

因此设计两个版本：
- **默认版**：每次都帮（但帮的范围从 1 种花色扩展到所有不匹配花色）
- **测试版**：按概率帮 + 保底机制（压力大时帮，压力小时随机）

---

## 二、改造目标

```
改造前：优化 1 种花色（Bar 最右边凑不齐的）
改造后：优化 Bar 中所有凑不齐的花色，按优先级分配配额
```

一句话：**从「只帮 1 种」变成「帮所有需要帮的」**。

---

## 三、详细逻辑

### 3.1 总流程

```
道具使用
  │
  ├── 收集 Bar 中所有凑不齐的花色
  │
  ├── 排序（缺的少的优先，同等条件下可洗的多的优先）
  │
  ├── 按排序轮流分配优先配对配额
  │    每种花色分配 N 对「高亮牌 ↔ 同花色非高亮牌」交换
  │    配额受限于可用高亮牌数和非高亮牌数
  │
  └── 剩余未配对的牌 → 随机配对
```

### 3.2 收集不匹配花色

遍历 Bar 中所有牌，按花色分组计数。

只处理可匹配的牌（Matchable），忽略 Blocker 等不可匹配的。

筛选条件：

```
花色在 Bar 中的数量 mod MatchCount != 0

即：Bar 中该花色的牌数凑不够一次消除（余数不是 0）
```

例如：MatchCount=3，某花色在 Bar 有 2 张 → 2%3=2≠0 → 需要帮。某花色有 3 张 → 3%3=0 → 正好能消，不需要帮。

### 3.3 排序优先级

先按「还差多少张」升序：差 1 张的最优先（最接近消除），差 2 张的次之。

若差的数量相同，按「非高亮层该花色的牌数」降序：可洗上来越多，洗成功的概率越高，优先帮。

若还是相同，随机排。

```
差 1 张 > 差 2 张 > ...

同分情况：非高亮层同花色多的优先 > 随机
```

### 3.4 分配配额

对每种不匹配花色，计算需要洗多少对：

```
needCount = MatchCount - Bar中剩余数   （还缺多少张）
actualNeed = needCount - 高亮层同花色数 （扣除高亮层已有的，实际需从非高亮层洗上来）
available = min(actualNeed, 非高亮层同花色数, 剩余可用高亮牌数)
```

能洗多少就洗多少，不勉强。

**配额分配顺序**：按 3.3 排序后的顺序，优先级高的花色先拿配额。配额用完（没高亮牌可配了）就停，剩余牌全部走随机。

### 3.5 交换细节（不变）

每次交换仍是「1 张高亮牌 ↔ 1 张同花色非高亮牌」配对。

配对前做「合法对」检查（`IsLegalPair`）：确保交换后序列容器内不会出现重复花色。找不到合法对的降级为同花色 fallback。

位置交换逻辑（`ExchangeTilePairsPosition`）、Effect 处理（非跟随类销毁、跟随类如金牌保留）、DDA 通知、可见性更新——全部复用现有路径，不做变更。

### 3.6 若无可配对的同花色

一种花色虽然需要帮，但非高亮层一张同花色都没有 → 跳过，不分配配额。

全部不匹配花色都没可洗的牌 → 跳过优先配对阶段 → 纯随机洗牌。

## 四、测试版：概率 + 保底

### 4.1 为什么需要概率

风车如果每次都帮，会变成纯正向道具（跟 Hint 一样了），失去「随机打乱」的刺激感。但不帮的时候，偶尔出一次好结果，玩家的惊喜感更强。

同时，在 Bar 面临压力（空间快满了）时，玩家花道具是期待正反馈的，这时候必须帮。

### 4.2 概率梯度

```
剩余槽位数 = Bar 的最大容量 - Bar 当前牌数

剩余 >= 5 槽  →  0%   帮（纯随机洗，不触发优先配对）
剩余 == 4 槽  →  30%  帮
剩余 == 3 槽  →  70%  帮
剩余 <= 2 槽  →  100% 帮（压力很大，必帮）
```

`Bar 的最大容量` 用 `bar.MaxCapacity`（可能被 +1 槽位道具扩展后的值），不是写死的常量。

### 4.3 保底机制

同关卡内，每使用一次风车，下次数帮的概率 +20%。

```
本关卡内使用次数: N（从 0 起，每次 +1）
实际概率 = 梯度概率 + N * 20%（上限 100%）
关卡结束重置 N = 0
```

举例（剩余 4 槽，梯度概率 30%）

| 使用次数 | 概率 | 说明 |
|---------|------|------|
| 第 1 次 | 30% | 大概率不帮，随机打乱 |
| 第 2 次 | 50% | |
| 第 3 次 | 70% | 大概率帮 |
| 第 4 次 | 90% | |
| 第 5 次 | 100% | 必帮 |

剩余 3 槽时，第 1 次就 70%、第 2 次就 90%——压力下更快保底。

### 4.4 默认版 vs 测试版

| 维度 | 默认版 | 测试版 |
|------|--------|--------|
| 多类型优先配对 | 每次都用 | 概率触发 |
| 概率梯度 | 无 | 有（5/4/3/2 槽分四档） |
| 保底机制 | 无 | 有（每次 +20%） |
| 随机洗牌 | 仅在无可配对时 | 经常（压力小且没触发时） |

## 五、边界情况

| # | 场景 | 处理 |
|---|------|------|
| 1 | Bar 为空 | 无需要帮的花色 → 纯随机洗 |
| 2 | Bar 所有花色都凑够了 | 同上 |
| 3 | 凑不齐的花色在非高亮层完全没有同花色牌 | 跳过，不浪费配额 |
| 4 | 高亮层可配对的牌不够（比如只有 2 张高亮牌总共有 4 种花色要帮） | 按排序分配，先到先得，配额用完就停 |
| 5 | 剩余高亮牌只有 1 张（没法配对） | 不再分配优先配额，直接走随机——随机阶段会从全体牌中配对 |
| 6 | 保底 N 很大导致下一关概率异常 | N 关卡结束重置为 0 |

## 六、影响范围

| 文件 | 改动 | 说明 |
|------|------|------|
| `ShufflePropTargetFilter.cs` | **核心修改** | `FilterTiles()` 中替换 LastUnmatchedTile 相关逻辑；新增不匹配花色收集 + 排序 + 轮转分配 |
| `ShuffleProp.cs` / `MoveToOverBarProp.cs` | 不涉及 | 触发路径不变 |
| `UI 层 Shuffle.cs` | 不涉及 | 动画和事件监听不变 |
| 其他 Filter / Exchange / Effect | 不涉及 | 选牌后的交换、合法对检查、Effect 处理全部复用 |

---

## 七、不做的事

- 不改交换算法（`ExchangeTilePairsPosition`），不改 Effect 处理，不改 DDA 通知路径
- 不改 UI 动画（风扇动画 + 牌交换动画保持不变）
- 不改 Available 条件
- 测试版的概率、保底步长、梯度阈值作为可调参数，不做死——真正的值由 AB 测试数据决定

---

## 八、测试要点

1. Bar 中只有 1 种凑不齐的花色 → 行为和改前等效（本来也只帮 1 种），只是更多类型被纳入检查
2. Bar 中多花色 → 每种都分配到优先配对，配额按排序分配
3. Bar 为空 / 全凑够 → 纯随机洗，无异常
4. 剩余槽位 = 2 → 100% 帮，走优先配对
5. 剩余槽位 = 5 → 0% 帮，走纯随机
6. 连续使用风车 → 保底概率逐步上升，第 5 次必帮
7. 关卡结束 → 保底计数器重置
8. +1 槽位道具生效后 → `bar.MaxCapacity` 变大，剩余槽位数计算正确
