# 跑关机器人（LevelBot）逻辑分析文档

> 本文档记录 Tile 游戏的跑关机器人（LevelBot）系统逻辑。
> 可作为后续补充的基础文档。

---

## 一、系统定位

跑关机器人 = Unity Editor 中以自动化方式模拟玩家跑关的关卡测试框架。关卡策划用来测试关卡难度、验证平衡性的自动化工具。

---

## 二、核心架构

```
入口层（Entry）:
  LevelBotCommandLine  → 命令行模式 (--param 参数)
  LevelBotJenkins      → Jenkins CI 集成
  LevelBotView         → Unity Editor 可视化 UI

公共层（Common）:
  LevelBotCommon       → 加载场景、读取参数、创建 Runner

核心引擎（Core）:
  BotRunner            → 关卡遍历 + 重复执行 + 动作决策 + 统计收集
  BotParam             → 参数模型
  Checkpoint           → 断点续跑支持

策略接口（Interface）:
  ILevelBotActionStrategy   → 动作策略接口
  ILevelBotGameInstance      → 游戏实例接口
  ILevelBotStatsCollector    → 统计收集接口

决策引擎（Tile/Strategy）:
  NStepOptimumSolutionWithProbabilityBlocker  → 策略入口（适配器）
  BotNStepProbabilityBlockerEngine             → 共享决策引擎（在 GameLogic 层）

游戏实例（Tile）:
  TileLevelBotGameInstance   → Tile 游戏封装（接管 Tick、动画、DDA）

统计分析（Tile/Statistic）:
  TileLevelBotStatsCollector   → 统计收集器
  TileLevelBotRecordPersister  → CSV 持久化
  TileLevelBotHeaderWriter     → CSV 格式
```

---

## 三、执行流程

### 步骤 1：启动入口
- 命令行: `Unity.exe -batchMode -executeMethod LevelBotCommandLine --param param.json`
- Jenkins: `LevelBotJenkins.RunFromJenkins()`
- Editor: LevelBotView 窗口

### 步骤 2：加载场景与参数
- 加载专用场景 `LevelBotScene.unity`
- 读取 `param.json` 配置
- 设置输出目录: `Output~/组名_索引_关卡范围_MMdd_HHmmss/`

### 步骤 3：BotRunner 三层循环

**第一层 — 关卡遍历**
```
for level in levelNames[]:
    ProcessLevel(level)
```

**第二层 — 重复执行**（每关 repeatTimesPerLevel 次，默认 10）：
```
for repeat in repeatTimesPerLevel:
    ProcessRepeat(level, repeat)
```

**第三层 — 局内游戏循环**：
```
While steps < maxStepsPerRepeat (默认 200):
    WaitForPendingCompletion()     // 等待动画/连锁反应
    GetState()                     // 检查游戏状态

    if Succeeded → 记录，跳出
    if Failed    → DealState() → Revive（复活动作）
    if Playing   → 获取下一步动作 → Invoke

    每次复活：
    RecordFailureStats()           // 记录失败进度分布
```

### 步骤 4：游戏状态流转

```
Entered → Start → Playing ──→ Succeeded (通关)
                           └─→ Failed → Revive → Playing (循环)
                                    └─→ maxDeathCount → 跳过 (OverHard)
                                    └─→ maxSteps → 跳过 (Timeout)
```

## 四、动作决策策略（核心 AI）

### 4.1 策略架构

```
ILevelBotActionStrategy          ← 接口
  │
  └─ NStepOptimumSolutionWithProbabilityBlocker  ← LevelBot 适配器
       │
       └─ BotNStepProbabilityBlockerEngine        ← 共享决策引擎
```

两个动作类型：
- **Click**：点击某个 tile（通过 DomainEventBus 发布 TileClicked 事件）
- **Revive**：游戏失败时复活

### 4.2 总体决策流程

```
GetNextDecision(decisionContext)
│
├─ 处理多步缓存
│   TryHandlePreviousMultiStepDecision()
│   ├─ 缓存无效 → 重新决策
│   └─ 缓存有效 → P2 概率判断替换/保留
│
├─ 确定动态步长
│   GetDynamicEvaluationStep(remainingCapacity)
│
├─ 阶段一：贪婪分层搜索
│   GreedyLayerByLayerSearch()
│   ├─ 找到消除序列 → 返回 + 缓存后续步骤
│   └─ 没找到 → 进入阶段二
│
├─ 阶段二：单步评估
│   CollectSingleStepEvaluations()
│   └─ 按排序规则选最优动作
│
└─ 返回最优动作
```

### 4.3 搜索深度（动态步长）

```
剩余容量   →   搜索步数
  ≥7       →   1
  5-6      →   2
  3-4      →   3（最佳规划窗口）
  2        →   2
  ≤1       →   1
```

配置上限：1 ~ 5 步（`BotNStepProbabilityBlockerConfig`）

### 4.4 评估指标（EvaluationResult）

| 指标 | 含义 |
|------|------|
| HasMatch | 是否触发消除 |
| CapacityChange | 手牌容量变化 |
| BarTypeChange | 手牌花色数变化 |
| FirstActionTypeCount | 第一步花色在棋盘上的数量 |
| StepCount | 已消耗步数 |
| ClickableCount | 模拟后可选牌数量 |
| NewHighlightCount | 新高亮 tile 数 |
| NewVisibleCount | 新可见 tile 数 |
| IsFirstActionInPile | 第一步是否在暗牌堆 |
| IsFirstActionInBoard | 第一步是否在棋盘上 |
| TotalBlockerHPDelta | 障碍总 HP 变化量（负=打掉障碍） |
| HighlightBlockerCount | 高亮障碍数量 |

### 4.5 排序规则

> 完整排序体系共有 **5 个比较方法**，适用于不同决策阶段。
> 所有排序前均先执行 Fisher-Yates Shuffle 打乱，最终从排序并列项中随机选一。

---

#### 4.5.1 CompareGreedyCandidates —— 贪婪分层搜索阶段排序

> 适用范围：`GreedyLayerByLayerSearch` 中每层候选动作排序。
> 该过程在模拟状态上进行（可恢复），不改变真实游戏状态。
> 使用的结构体是 `GreedyEvalResult`（比 `EvaluationResult` 少了部分字段）。

| 优先级 | 指标 | 比较规则 | 释义 |
|--------|------|---------|------|
| ① | `HasMatch` | true > false | 能触发消除→直接晋级最优 |
| ② | `TotalBlockerHPDelta` | 越小越好 | 对障碍总伤害更大（负值越大越好） |
| ③ | `IsFirstActionInPile` | false > true | 非暗牌堆优先（先动棋盘上可见的） |
| ④ | `IsFirstActionInBoard` | true > false | 棋盘内的动作优先于牌堆 |
| ⑤ | `ClickableCount` | 越大越好 | 操作后可选牌数量更多 |
| ⑥ | `NewRevealedCount` | 越大越好 | 揭露更多当时不可见的牌 |
| ⑦ | `BarTypeChange` | 越小越好 | 手牌花色变化更少（保持花色集中） |

> 注：NewRevealedCount 在贪婪搜索中追踪的是 `_initialNotVisibleTileIds` — 仅计算搜索开始时不可见的 tile，后续新出现在视野中的 tile 不计入。

---

#### 4.5.2 CompareEvaluationFields —— 有匹配时的排序

> 适用范围：当至少一个评估结果的 `HasMatch == true` 时。
> 既在 `CompareEvaluationsWithMatch` 中作为包装器调用，也在 `CompareTwoEvaluations` 中处理一方有消除的情况。
> 使用的结构体是 `EvaluationResult`（比 `GreedyEvalResult` 多 `CapacityChange`、`FirstActionTypeCount`、`StepCount` 等字段）。

| 优先级 | 指标 | 比较规则 | 释义 |
|--------|------|---------|------|
| ① | `CapacityChange` | 越大越好 | 模拟后手牌释放空间更多（正=释放，负=占用） |
| ② | `BarTypeChange` | 越小越好 | 模拟后手牌花色更少 |
| ③ | `FirstActionTypeCount` | 越大越好 | 第一步花色在棋盘高亮牌中数量更多（消除潜力更大） |
| ④ | `StepCount` | 越小越好 | 达成消除所需的步数更少 |
| ⑤ | `ClickableCount` | 越大越好 | 模拟后可选牌更多 |

---

#### 4.5.3 CompareEvaluationFieldsWithoutMatchLowCapacity —— 低容量无匹配排序

> 适用范围：`CompareEvaluationsWithoutMatch` 中 `_currentRemainingCapacityForNoMatch <= 3`。
> 触发条件：引擎走完贪婪搜索没有找到消除序列，当前手牌剩余容量 ≤ 3。
> 策略倾向：**求生模式** — 容量快满了，优先抢空间。

| 优先级 | 指标 | 比较规则 | 策略逻辑 |
|--------|------|---------|---------|
| ① | `IsFirstActionInPile` | **true > false** | 🔺 暗牌堆优先！容量紧时翻暗牌赌同色消除释放空间 |
| ② | `TotalBlockerHPDelta` | 越小越好 | 顺便打障碍 |
| ③ | `IsFirstActionInBoard` | true > false | 棋盘动作优先 |
| ④ | `ClickableCount` | 越大越好 | 可选牌多 = 操作空间大 |
| ⑤ | `NewVisibleCount` | 越大越好 | 揭露更多可见牌 |
| ⑥ | `BarTypeChange` | 越小越好 | 手牌花色更集中 |

---

#### 4.5.4 CompareEvaluationFieldsWithoutMatchHighCapacity —— 高容量无匹配排序

> 适用范围：`CompareEvaluationsWithoutMatch` 中 `_currentRemainingCapacityForNoMatch >= 4`。
> 策略倾向：**求胜模式** — 容量充裕，集中火力打障碍揭布局。

| 优先级 | 指标 | 比较规则 | 策略逻辑 |
|--------|------|---------|---------|
| ① | `TotalBlockerHPDelta` | 越小越好 | 🔺 优先打障碍（HP 减少最多） |
| ② | `IsFirstActionInPile` | **false > true** | 非暗牌堆优先（容量够，先不赌牌） |
| ③ | `HighlightBlockerCount` | 越大越好 | 高亮障碍多 = 有消除潜力 |
| ④ | `IsFirstActionInBoard` | true > false | 棋盘动作优先 |
| ⑤ | `ClickableCount` | 越大越好 | 可选牌更多 |
| ⑥ | `NewHighlightCount + NewVisibleCount` | 越大越好 | 揭露更多牌（可见+高亮求和） |
| ⑦ | `BarTypeChange` | 越小越好 | 手牌花色更少 |

---

#### 4.5.5 CompareTwoEvaluations —— 多步缓存替换判定

> 适用范围：`IsActionSequenceBetterThanPrevious()` 中判断新方案是否优于缓存中的前序方案。
> `CompareTwoEvaluations(evalCurrent, evalPrevious, currentRemainingCapacity)` 在内部根据场景路由到上述方法：

```
CompareTwoEvaluations:
  ├─ 双方都无消除 → 看 capacity
  │   ├─ capacity ≤ 3 → CompareEvaluationFieldsWithoutMatchLowCapacity
  │   └─ capacity ≥ 4 → CompareEvaluationFieldsWithoutMatchHighCapacity
  └─ 至少一方有消除 → CompareEvaluationFields
```

---

#### 4.5.6 排序体系汇总对比

| 特征 | 贪婪排序 | 有消除排序 | 低容量无消除 | 高容量无消除 |
|------|---------|-----------|------------|------------|
| 使用场景 | 贪婪搜索中层内排序 | 至少一个候选有消除 | 无消除+容量≤3 | 无消除+容量≥4 |
| 第1优先 | HasMatch | CapacityChange | IsFirstActionInPile(true) | TotalBlockerHPDelta |
| 第2优先 | TotalBlockerHPDelta | BarTypeChange | TotalBlockerHPDelta | IsFirstActionInPile(false) |
| 第3优先 | IsFirstActionInPile(false) | FirstActionTypeCount | IsFirstActionInBoard | HighlightBlockerCount |
| 第4优先 | IsFirstActionInBoard | StepCount | ClickableCount | IsFirstActionInBoard |
| 第5优先 | ClickableCount | ClickableCount | NewVisibleCount | ClickableCount |
| 第6优先 | NewRevealedCount | — | BarTypeChange | NewHighlight+NewVisible |
| 第7优先 | BarTypeChange | — | — | BarTypeChange |
| 数据结构 | GreedyEvalResult | EvaluationResult | EvaluationResult | EvaluationResult |

核心理念：**容量紧 → 生存模式（暗牌优先抢空间） | 容量松 → 进取模式（打障碍揭布局）**

---

#### 4.5.7 随机机制

- **Shuffle**：每次排序前先 Fisher-Yates 打乱列表
- **等分随机**：排序后从头遍历，用 `GetRandomIndexFromEqualItems` 找出所有与第一名评分相同的候选，在其中随机选一个
- `IsActionStillValid`：执行决策前检查缓存的 tile 在当前棋盘上是否仍存在且可点击

### 4.6 多步决策缓存 + P2 概率替换

当贪婪搜索找到多步消除序列时：
- 返回第 1 步，缓存剩下步骤到 `_previousRemainingActions`
- 下次决策时检查缓存是否仍合法
- 如果合法，对比当前最佳方案
- 如果新方案更好，以 `p2Probability` 概率替换，否则保留原方案

P2 概率数组（5 个值，对应不同容量区间）：
```
容量 ≥7 → [0] | 5-6 → [1] | 3-4 → [2] | 2 → [3] | ≤1 → [4]
```
默认全 0（不替换），可通过 param.json 配置。

### 4.7 特殊处理

- **MagicBox 过滤**：从合法动作池排除
- **Fisher-Yates Shuffle**：排序前打乱 + 并列随机选
- **CandybarRevealDelta**：追踪糖果条消除后的揭露效果

## 五、参数配置（param.json）

```json
{
  "runName": "",                              // 运行名
  "repeatTimesPerLevel": 10,                  // 每关重复次数
  "maxStepsPerRepeat": 200,                   // 单次最大步数
  "enableResume": false,                      // 断点续跑
  "strategy": "NStepOptimumSolutionWithProbabilityBlocker",
  "StrategyOptions": {
    "seed": "123456",                         // 随机种子
    "enableDebugLog": "false"                 // 调试日志
  },
  "enableConsoleLog": true,
  "enableThreadQoS": false,
  "groupName": "Levels",
  "groupIndex": "new",
  "levelNames": ["1"],
  "deathCountDisplayThreshold": 10,           // 过难阈值

```

## 六、统计数据体系

每关跑完后输出三套 CSV：

| 文件 | 粒度 | 关键指标 |
|------|------|---------|
| `repeat_*.csv` | 每次重复 | Total, Succeeded, Failed, FT_0~FT_GT5 |
| `level_*.csv` | 每关汇总 | 通关率, 平均步数, 平均通道数, 复活分布 |
| `error_*.csv` | 异常记录 | 超步, 超死亡, 异常错误 |

**失败进度分布**：GR_0.0_0.2 ~ GR_0.8_1.0（失败时的完成度分布）
**首次失败进度分布**：FGR_0.0_0.2 ~ FGR_0.8_1.0
**DDA 统计**：DdaRegulationTriggerCount, DdaRegulationCount
**道具统计**：HasAddOne, HasMagicWand, HasRocket

## 七、游戏实例接管（TakeOver）

`TileLevelBotGameInstance` 接管以下系统，手动推进帧时间：
- AnimationTakeOver
- AnimatorTakeOver
- SpineTakeOver（排除）
- ParticleTakeOver（排除）
- TweenTakeOver
- UniTaskTakeOver

通过 `CustomData` 设置 `GameMode.Bot`，关闭正常交互响应。

DDA 支持：通过 `CustomData.SetDDAVersion("V1"/"V2")` 传入不同难度调控版本。

## 八、与 Activity/Robot 系统的区别

| 系统 | 用途 | 运行环境 |
|------|------|---------|
| LevelBot（本文） | 关卡测试自动化 | Unity Editor / Batch Mode |
| Activity/Robot | 游戏内 AI 假人对手（如赛马） | 运行时（Runtime） |
