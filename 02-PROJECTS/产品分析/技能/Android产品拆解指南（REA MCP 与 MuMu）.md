# Android 产品与模块拆解

从这次提供的产品、样本和问题出发。先将问题写成可观察的行为，例如「某功能在哪个条件下解锁」「重启后哪份配置决定显示内容」。

## 通用证据规则与适用范围

- 每项结论绑定样本、版本、采样时刻和来源。分别标注包内存在、缓存保存、代码选中、现场生效及未知；跨构建引用先核对相关字段或方法。
- 证据深度随问题决定。定位资产可止于资源标识，解释生效条件需追消费者，判断本次行为的来源需取得能够区分其他解释的观测。证据不足时交付已确认部分与最小补证动作。
- 工具能力以本次目标的实际解析产物验收。历史成功、工具可见和进程启动仅证明各自状态。保留实际工具与版本、输入路径/哈希、方法/地址或表/键、结果路径；工具返回 Evidence ID 时一并保留。
- 设备分支仅在需要现场取证时使用，MuMu 命令按当前系统与版本核实。Unity/IL2CPP 分支仅在识别出对应引擎后使用；其他引擎沿实际代码与资源格式分析。
- 概率、排期、活动关卡、奖励及展示优先级按模块机制选择。对不涉及的机制可省略，服务端不可见的规则保留未知。九类交付主题用于检查适用项，专题任务集中回答用户的问题。

## 活动清单与选题

用户要求盘点时，每项记录玩家可见名、内部标识、入口或触发场景、已取得的配置与资源、版本和证据状态。分别标注实机可见、仅缓存中存在或仅在包内发现。仅委托盘点时交付清单；已点名模块时直接展开；已委托选题并深拆时，在本次任务中按约定范围完成选择与分析。

## 按已有材料选择路线

| 手里有什么 | 先做什么 | 这一步能交付什么 |
|---|---|---|
| APK / XAPK | 校验真实容器和分包身份，发现本会话可调用的 REA 能力，定位对应引擎及消费者 | 包内资源、默认配置、触发条件、代码分支，标出运行时缺口 |
| 已保存的运行快照或下载资源 | 先核对采集时间、包版本、实例和操作场景，再查目标字段与资源索引 | 该样本实际保存的值、状态、期限与已下载内容 |
| 用户指定的 MuMu 实例 | 核对实例与目标应用后，主动在设备内定位实际缓存路径。包名可从安装包清单或运行应用取得，无需用户提供目录 | 配置库、下载资源或状态文件的实际绝对路径、代表文件及核验依据；按问题再做状态差分、实拍或自然换期记录 |
| 同时有包与运行材料 | 将同一字段的加载、选择、覆盖、落盘和消费方法与样本值逐项对位 | 给出规则、当前样本是否命中、版本差异及剩余未知 |

## 包体拆解

1. 记录样本来源、SHA-256、包名、版本与 ABI。对 XAPK 先读归档清单，区分主 APK、架构分包和资源包。与设备版本不同时，分别记录代码、配置和资源来自哪个构建。
2. 查看本会话实际暴露的 REA MCP 工具及参数。XAPK 先打开外层归档，取得主 APK、架构分包与资源包的实际成员路径。按当前工具签名对主 APK 调用包检查（如 `inspect_android_package`），记录包身份、Manifest、DEX 和资源覆盖。以模块内部名、类名片段或包命名空间检索类（如 `search_android_classes`），用支持全文或字符串检索的工具查本地化键和配置键。定位入口后追踪请求构建、解析、持久化与调用者，保留工具结果及 Evidence ID。若 DEX 主要是 Android 外壳，继续检查承载玩法的资源和原生程序集。
3. 遇到 Unity，用资源目录或 Addressables 索引定位 Bundle，以 Bundle 和 path ID 标记对象。遇到 IL2CPP，配对同一构建的 `global-metadata.dat` 与目标 ABI 的 `libil2cpp.so`，由类型索引追到具体方法。关键分支需要时核对原始指令。

### 工具降级与验收

仅检查回答当前问题所需的能力层。REA 不可用或某层失败时，使用已有且能解析本样本的本机工具，记录失败点和实际覆盖范围。

连接正常时直接分析目标。首次接入、配置变更或能力报错时，按[包体与设备取证](#包体与设备取证)中的接入核验区分核心通信、Provider 就绪、目标解析与业务全链路验收。独立测试会话通过后，当前聊天仍需确认已载入对应配置。

| 所需能力 | 本次目标的验收产物 | 可用降级与结论边界 |
|---|---|---|
| 归档与包身份 | 可读取成员清单、Manifest、版本及分包关系 | ZIP 工具读容器，Apktool 或 JADX 解析 Android 内容。只能读归档时止于成员清单；主 APK 未命中且相关分包未检索时，仅报告主包未命中。 |
| DEX 逻辑 | 目标方法体、调用者及相关条件可读 | JADX，必要时核对 Apktool 导出的 smali。字符串或类名命中只支持定位；方法反编译失败时保留该分支未知。 |
| Unity 资源 | 索引可关联到具体对象，所需对象可解析 | UnityPy；保留 Bundle、path ID 与侧车文件。缺依赖或版本不支持时记录未解析对象，导出图片不足以证明运行时展示。 |
| 原生/IL2CPP 逻辑 | 配对输入明确，关键方法的返回值、分支及读写点可核对 | Cpp2IL 建索引，已有且可用的原生分析器核对关键指令。只有签名或未解析间接调用时止于定位；无法确认的行为保留未知。 |
| 设备与私有存储 | serial、用户、包版本、实际可读目录明确 | 私有目录不可读时继续外部目录、包体和已有快照。Root 是一种访问方式；其他已有授权身份是否可读须实测，缺权限记为采样缺口。 |

非 Unity 的最小路线可从 Manifest 入口追踪 DEX 中的请求、解析与状态读写；若经 JNI 进入 `.so`，记录库、桥接入口与已有调用证据，再按原生分析能力继续。若逻辑在脚本或 WebView 资源中，沿实际加载入口追踪。无法读取下一层时，结论止于已确认的调用边界。

## 主动定位 MuMu 实际缓存

用户指定实例和目标应用后，直接完成路径定位，无需用户先找目录。以下命令中的占位符应替换为当次核实的值。

1. 从当前 MuMu 实例管理信息取得实际 ADB 端点。Windows 上可用时，通过 `MuMuManager.exe info -v <实例编号>` 查询 `adb_port`。检查实例信息的来源；仅返回本地配置（如 `info_source=local`）时，运行状态与端口可能未取得，须通过可访问的管理服务（如 `rpc`）及 ADB 实连核实，不能直接据此断言实例关闭。将后续 ADB 调用绑定该实例的 serial。包名从 APK 清单或前台应用取得。用 `adb -s <serial> shell pm path <包名>` 核对安装分包，用包信息核对版本。读取个人状态或比较账号时，另以应用内最小标识核对测试账号，报告使用别名。实例不符时暂停设备步骤；账号不符时暂停依赖该账号的采样，继续独立的离线分析。
2. 用 `adb -s <serial> shell am get-current-user` 查 Android 用户，用 `adb -s <serial> shell dumpsys package <包名>` 查 `dataDir`，核实该用户的私有目录。同时检查 `/storage/emulated/<用户号>/Android/data/<包名>/`。访问私有目录前确认已有授权身份和实际读取能力，使用 Root 时核对 `su` 身份。
3. 在目标应用目录内列出实际存在的子目录，再定向检查 `files`、`cache`、`databases`、`shared_prefs`、`app_*` 和下载资源。用文件头、只读 SQLite 表结构或资源索引确认用途。遇到无扩展名数据库或哈希命名的资源，抽查文件头，再通过表结构或资源索引判断用途。
4. 输出路径表，列出用途、设备内绝对路径、代表文件或表、核验依据和采样时刻。区分现场实读、历史快照与当前不可读。关联同一 SQLite 库的多个字段时，优先在同一只读事务中查询，或在可用时取得一致的在线备份。逐文件复制主库与 WAL/SHM 不能自动保证一致性；跨库或库与资源的一致性需另证。未证实的跨表/文件差分仅作线索。只读取目标所需数据。
5. 按坐标导航时，每步以新截图确认页面后再决定下一步。已有可靠页面标识或控件状态时可据此确认，证明实际曝光和表现时保留对应实拍。出现意外对局或页面变化时停止沿用旧坐标。

## 动态验证与停止归因的标准

解释某次运行行为时，先列竞争解释与能区分它们的观察，再记录起始状态、动作、采样起止时刻、前后值及证据。按需使用截图、状态差分、日志、请求/响应或运行时追踪，选择已有能力中能补齐缺口的方法。

例如判断“重启后重新下发还是恢复缓存”，在任务授权范围内先记录已有副本和配置版本，再观察离线重开后的值、恢复联网后的变化，并对位加载、反序列化与落盘路径。相同正文只证明值相同；本次来源需要对应加载路径观测或响应与消费的关联证据。离线仍有该值支持离线可用，还需区分包内默认与持久化副本。若这些证据无法取得，交付可确认的值和候选来源，停止断言本次来源。

自然操作、改时、改等级、改库与清库按委托范围分别处理。人工状态实验单独标注起点和修改，避免混入自然概率、周期及成长记录。服务端选择器不可见时，只报告已确认的客户端输入、响应、消费与样本结果。

## 追踪配置如何影响产品行为

1. 从玩家可见名反查内部类型、本地化键、入口资源及配置键。沿“资格判断 → 触发操作 → 状态写入 → 关卡或系统回调 → 界面/奖励”追踪。把入口显示、逻辑参加、引导已见、实际推进分别定位。
2. 对关键数值记录字段名、原值、单位、版本、层级、读取者和生效条件。区分包内默认、公共下发、用户副本、当前阶段锁定值和展示值。比较 AB 或人群分层时，找出分支条件、选中表和实际消费者，样本不足就写明还缺哪一个对照。
3. 查隐藏策略时，先确定它修改的对象。分别检查关内参数、活动步数、展示人数/机器人、奖励池、抽取概率及失败补偿。追到实际返回值、写入与后续读取。两系统都监听胜利回调，只能先说明它们共享触发事件。恢复概率时注明条件、候选集合、权重修正及分母。
4. 查排期时分列采样时刻、期 ID、公共截止、个人截止、已知开始、下期开始、冷却和复开条件。快照用于回答「在这次采样时保存了什么」，连续期 ID 与截止差用于提出周期候选。记录时区、设备时钟校验、跨期采样区间及例外清理分支。
5. 查表现时建立“资源及对象 ID → Prefab/组件 → 加载或调用者 → 触发状态 → 实机画面/声音”的对应关系。问题涉及布局时再查相机、父变换、排序、裁切与字体。导出清单只代表已定位资产。

### 按机制选择的专项验证

- **概率分母。** 存在客户端可见的候选池和抽取机制时，先用同版本的根配置确定当前档位与可用集合，再按稳定组合键关联单项配置、资源和本地化，检查缺项及重复。至少复算一个明确状态下的候选数、总权重与首抽概率，库存参与规则时注明库存。追踪一次抽取如何改变下一次的候选和权重。分别给出单次抽取、整包结果和条件保底的口径。固定奖励可省略；服务端直接给结果且机制不可见时，客户端结果样本不足以还原真实候选池与概率。
- **展示优先级。** 从候选检查追到返回值、安排展示、实际曝光、用户操作和状态写入。检查返回成功时究竟跳过哪一组，关闭后是补排还是等下一次触发重查。分别标明代码可证的控制流和已实拍的曝光。

### 复盘与方法维护

出现漏判、反例或新的验证动作时，回看其是否会改变下一次分析决策。必要时放回原始样本试算或复走关键分支，记录输入、预期、结果及适用范围。个案参数与待证实判断留在产品报告；经验证可复用、现有指引未覆盖且本次委托包含方法维护时，再修订通用 skill，否则记录修订建议。

## 交付与持续维护

### 单活动深拆的正文格式

用户选定活动后，在指定范围内尽可能详细。每个适用主题尽量给出字段、条件、实际分支、数值和例外。缺证据时说明已检查的路径和仍需补的样本。若提示词只问一个专题，集中展开对应章节。格式可参考随包案例，目标产品的规则和数据须独立核对。

| 主题 | 应回答的问题和产物 |
|---|---|
| 玩家流程与模块职责 | 玩家目标是什么？从首页入口到结算，列明弹窗、教程、主界面、帮助页和返回路径。以流程图对齐界面事件与状态写入。 |
| 解锁、参加与分组 | 列等级、期 ID、互斥与前置教程等条件。区分自动参加与主动点击，追请求参数、成功/失败回调和恢复逻辑。 |
| 状态机与关卡关联 | 用状态转移表列出触发、条件、字段变化和下一状态。检查正常胜负、连胜、同关重试、阶段检查点、重开及异常退出。 |
| 配置、分层与 AB | 对位包内默认、公共下发、用户副本和已选档位。列字段、原值、单位、版本、选表时机与读取方法。多套目标和奖励逐档比较。 |
| 周期、下发与复开 | 分列公共窗口、个人期限、报名时刻、冷却和清理例外。对位请求触发、响应或缓存、落盘与生效，按期 ID 整理实际时间表。 |
| 数值、隐藏策略与概率 | 查阶段目标、对手或机器人数、人数曲线、展示抽样、权重与保底、失败补偿和关内调节。列条件公式、计算样例及能区分不同解释的证据。 |
| 奖励与保存恢复 | 拆奖池、分摊、取整、领取资格、防重标记与库存写入。解码进度字段或位域时列读写点，跟踪超时、重连与跨期恢复。 |
| 资源与表现 | 将图标、图集、Prefab、动效、音效与调用者、触发状态、具体页面对位。需要还原画面时补布局层级、字体、遮罩、时间轴与同状态实拍。 |
| 上报、证据与未知 | 区分业务请求和统计上报。索引样本版本、方法或地址、表/键、实拍与差分。服务端策略未知时列出已确认的输入、输出和最小验证办法。 |

用一句话先回答用户的问题，再给支撑它的最短证据链。核心结论可用表格组织。

| 问题/行为 | 配置或状态原值 | 消费方法及条件 | 实际观测与版本 | 判断与待验证项 |
|---|---|---|---|---|
| 每行回答一个判断 | 表/键、单位或资源标识 | 方法、分支，必要时附地址 | 截图、快照或前后差分 | 区分代码确认、样本观察、推测和未知 |

按问题选择交付形式。流程问题给状态图，数值问题给原始字段、选表条件与计算例，排期问题用表格列出观察时刻、时区及推算依据。已有报告就修订对应章节，首次分析则交付一份标明样本和版本的独立报告。存放位置和归档方式依当前任务约定。

调用示例：`$analyze-android-product 分析这个 XAPK 中指定功能的解锁条件。结合指定 MuMu 实例定位实际缓存，核对默认配置与当前生效值，并列出证据。`

包体与设备取证的详细步骤及历史案例附在下文，按问题选读。新产品的结论以本次样本重新核验。

# 包体与设备取证

## 首次接入、配置变更与能力报错

已有连接正常时直接处理目标。遇到接入或能力问题，再做以下定向核验；某个 Provider 缺失只影响依赖它的分支。

| 要确认的状态 | 核验方式与可报告范围 |
|---|---|
| 当前聊天已连接 REA | 实际调用 `binary_session` 或当前版本等价工具，核对服务身份、版本与所需操作的可用性。配置文件存在或工具目录可见仍需真实调用确认。 |
| 所需 Provider 就绪 | 按报错补当前工具要求的依赖与环境。ADB 可用 `inspect_adb_client`，Apktool 可用 `inspect_apktool_client`；客户端版本检查通过仅证明工具可启动。JADX 按当前服务要求核对 JAR、Java 及编译器模块。 |
| 目标解析成功 | 用授权的真实目标调用包检查、资源解码或方法分析，记录输入哈希与实际结果。APK 身份、类数和资源数仅覆盖基础解析；具体方法、资源和原生逻辑按问题继续验收。 |
| 业务全链路通过 | 针对用户问题，将包内规则、运行配置、消费者与观测逐项对位，并说明未覆盖路径。设备连接成功或基础包解析成功不能代替这一步。 |

只有在委托包含工具修复时才更改安装与注册，优先复用现有依赖，按具体报错补配置。常见环境项有 `JAVA_HOME`、`REA_JADX_MCP_JAR`、`REA_ADB_PATH`、`REA_APKTOOL_COMMAND`，使用当前机器上核实的绝对路径，实际要求以已连接服务的诊断为准。修改注册前回读并备份，写前检查并发变化，保留其他服务器和已有有效配置。

修改启动环境后，旧 MCP 进程可能仍持旧值。需要时重连服务，并在当前聊天中重新调用此前失败的工具。使用相同注册启动的独立 MCP 测试可以验证新配置，但应标明测试会话；当前聊天的复验成功后再解除其阻塞。客户端没有可用重连能力时，明确告知需要用户重连或重启。

选定证据需要跨会话复用时保存返回正文、输入标识和结果路径。若只返回摘要，标明摘要覆盖范围；临时会话的 Evidence ID 或父结果引用不保证在关闭后仍可读取。已取得结果就保留，缺少正文时按需要重新解析原样本。

## APK / XAPK 与 REA MCP

- 记录来源、字节数、SHA-256、包名、versionName/versionCode 和 ABI。先读 ZIP 中央目录及清单。归档无法打开时，先检查文件签名并确认路径指向实际包体。
- 从本会话的工具清单发现 REA，读取可用工具签名与 provider 状态。先识别容器、检查归档图和实际成员，再对主 APK 调用已暴露的 Android 包检查与类检索能力。留存工具名和有用的 Evidence ID。服务启用、能打开 ZIP、能解析 DEX、能反编译原生方法是四项独立检查。
- 把主 APK、ABI 分包和资源包分别列出。JADX 适合 Manifest、Java/Kotlin 入口及 SDK。若发现 Unity 数据，沿目录或 Addressables catalog 找 Bundle、Prefab、ScriptableObject。遇到流式音频或贴图，保留关联侧车。导出对象用 Bundle＋path ID 标识。
- 对 IL2CPP，在同一构建内配对 metadata、目标 ABI 的 libil2cpp.so 和 Unity 版本。用 Cpp2IL 等已有工具建类型/方法索引，优先查写字段、读字段及其调用方。若伪代码只有签名、存在间接调用或返回条件可疑，对关键分支核对 ISIL/原始指令，记录二进制哈希和地址。其他引擎按识别出的资源格式与运行层选工具。
- 缺 REA 时，ZIP 工具读归档，Apktool 解码 Android 资源与 smali，JADX 查 DEX 方法与调用者，UnityPy 读 Unity 资源，Cpp2IL 辅助建 IL2CPP 索引。各工具只承担其实际解析成功的部分，方法签名不能单独证明分支。原生关键分支可用已有分析器核对指令，仍不可读时保留未知。按主文的能力表验收本次目标，报告实际工具版本、输入哈希与产物。安装包与设备构建不同就保留两行来源，按字段或方法对位后再引用。

## MuMu 运行后存储

**现场定位命令示意**。替换尖括号变量后执行。若包名未知，从包清单或指定实例前台应用取得。

```text
MuMuManager.exe info -v <实例编号>
adb connect 127.0.0.1:<实际端口>
adb devices -l
adb -s <serial> shell am get-current-user
adb -s <serial> shell pm path <目标包名>
adb -s <serial> shell dumpsys package <目标包名>
adb -s <serial> shell ls -la /storage/emulated/<用户号>/Android/data/<目标包名>/files
```

从包信息取版本与 `dataDir`。已获授权的 Root 实例可进入绑定该 serial 的 Android shell，执行 `su`、`id` 核对身份后，对实际 `dataDir` 执行 `ls -la`。按文件头检查候选文件，对数据库先只读列出表名，对下载资源先查索引再找对象。私有目录不可读时，列明外部目录、包体和既有快照的实际覆盖范围。

1. 从实例管理信息核实**本次指定实例**的实际 ADB serial。核对返回的 `info_source`；`local` 可能只代表配置回退，未证明实时运行状态。若缺失端口或与现场冲突，先解决管理服务访问问题，再用 `rpc` 信息和绑定端点的 ADB 实连确认；避免据回退信息反复启动或重启。每次调用绑定 serial。用 `adb -s <serial> shell pm path <package>` 枚举实际安装分包，用 `dumpsys package` 核对版本。读取私有目录前确认授权和可用身份，使用 Root 时核对 `su -c id`。读取个人状态或比较账号时，以应用内最小标识另行核验账号，报告使用别名。实例不符时停在设备步骤，账号不符时暂停依赖该账号的采样，继续独立的离线分析。
2. 主动定位设备内的实际路径。Windows 可用 `MuMuManager.exe info -v <实例编号>` 查目标实例的 `adb_port`。包名优先从 APK 清单或该实例的前台应用取得，再与已安装包核对。用绑定 serial 的 `shell am get-current-user` 确定 Android 用户，读取 `shell dumpsys package <package>` 中的 `dataDir` 并核对所属用户。多用户设备须核实目标用户实际可见的目录。另检查该用户的外部应用目录，常见形式是 `/storage/emulated/<用户号>/Android/data/<包名>/`。
   - 在这两个应用目录内先列一级目录，再定向查看有内容的 `files`、`cache`、`databases`、`shared_prefs`、`app_*` 和下载目录。保留自定义目录、无扩展名数据库、哈希文件名这些可能性。按文件头、SQLite schema、资源索引或加载代码确认用途。
   - 汇报时列出“用途｜设备内绝对路径｜代表文件/表｜核验依据”。按当前目标应用的实读结果填写。当前现场读到、仅历史快照可见、权限受限或尚未下载，分别标注。
3. 数据库先只读列 schema，再查询目标键。需要关联同一数据库的字段时，用同一连接、同一只读事务取得它们；具备备份能力时，可用 SQLite 在线备份取得一致的单库副本，再在副本上解析。记录采样起止、采集方式和所涉文件。
   - 活跃数据库按顺序复制主库、WAL、SHM 可能跨越提交时刻，即使文件齐全也不能据此认定同一快照。无法取得一致读或证明写入静止时，保留原始文件与时间窗口，将跨表差分标作线索，暂停对发奖、防重或跨期状态的确定归因。
   - 单库一致性不自动覆盖其他库、偏好文件及资源索引。跨文件结论需应用级一致采样或其他可证明的对应关系；仅有相近时间戳不足以证明一致。
   - 采集应控制在目标数据范围内。在线备份会复制所选数据库，只在确有需要且采集范围允许时使用，避免带出令牌、支付凭据、社交记录及无关整库。停应用等操作会改变运行状态，只有任务范围允许时使用，并记录其影响。
4. 对“补发还是恢复”的问题，分别记录包内兜底、本地已有副本、配置版本、离线重开、联网后差分及反序列化/落盘消费者。恢复出相同正文只证明值恢复；要判断本次具体来自哪里，还需要对应加载路径的观测或响应证据。优先使用已有样本，自然操作、改时、改等级与清库属于不同范围。
5. 需要现场对照时先截稳定画面。按坐标导航时每步核对新图；已有可靠页面标识或控件状态时可用于确认页面，实际曝光与表现证据仍保留实拍。出现意外对局或画面变化就停止旧坐标操作。自然采样记录主机和设备时间、时区、校时状态、账号别名、应用版本、期 ID 与动作。实拍倒计时只在有截取时刻时换算近似截止。改时、改库等人工实验另存，不混入自然样本序列。

## 恢复与重新下发的最小对照

按主文的动态验证标准，先说明要区分的来源，再在任务允许的范围内安排以下观察。某一步不可执行时标明缺口，继续利用已有证据。

| 时点 | 记录内容 | 可支持的判断 |
|---|---|---|
| 操作前 | 应用构建、账号别名、已有副本、配置版本、包内默认、目标字段 | 建立可供恢复的来源候选和初始状态 |
| 离线重开后 | 网络状态、画面/目标值、实际加载路径证据（若可取得） | 该值可离线获得；具体来自默认或持久化副本仍需定位 |
| 恢复联网后 | 值及版本变化、相关响应、反序列化/落盘/消费时序 | 响应与目标值消费关联明确时，支持本次下发来源；正文相同只证明值相同 |

日志、网络观测和运行时追踪按问题与当前可用能力选择，记录观测的覆盖范围。没有捕获到响应不足以单独证明没有请求。服务端选择策略不可见时，保留已知输入输出与最小补证需求。

SQLite 一致性实现可查 [在线备份说明](https://www.sqlite.org/backup.html)；ADB 的设备选择与包操作可查 [Android 官方文档](https://developer.android.com/tools/adb)。实际命令与工具支持仍以当前环境为准。

最小复现记录包含样本或选定证据的路径/哈希、工具与版本、方法/地址或表/键、操作前后值、结论适用范围。服务端选择器不可见时，列出客户端已确认的请求输入、响应字段与消费方式，并指出仍需哪份证据才能回答原问题。

# 两种连胜活动如何得到不同结论

这是可选的取证示例。Royal Match 的 38911 构建提供机制与资源基线，39781 对部分入场、恢复和周期路径做过定向核验。下表最后一列提炼可迁移的查证问题；具体阈值、字段和活动规则仅属于这些历史样本。

| 待回答的问题 | Lava Quest | Ancient Adventure | 换产品时先查什么 |
|---|---|---|---|
| 点按钮是否等于参加？ | 玩家点 Start 发起分组请求，成功回调进入 EnteredEvent，建立个人期限，再展示寻找玩家及主界面 | 中央管理器在资格、选择和锁定条件满足时写入参加状态。教程状态另行控制普通关卡何时可推进 | 对照点击处理、请求成功回调、首次写参与位以及进度门槛，分别画出界面流与状态流 |
| 连胜和入组关卡影响什么？ | 入组起始关写入并随请求发送，活动步数从该轮重新开始。历史场景名与关卡相符，服务端如何选择场景仍未知 | 普通路线有5/7/10阶段和单7分支，失败处理要看当前阶段与已完成检查点 | 区分局内步数、同关重试、跨关连胜和活动期计数。沿输入追到修改目标及最终消费者 |
| 发现随机函数能否推回真实胜率？ | 历史分组含人数曲线与胜者数，部分人数变化属于展示抽样。曾核对疑似扣步函数，其已查返回路径恒为假 | Heist等奖励需检查教程池、洗牌、已揭牌面和停止条件。条件概率随当前状态变化 | 列出候选、权重、状态更新与退出条件；对手人数、展示随机、发奖与关内难度各自取证 |
| 两期截止约差24小时意味着什么？ | 公共报名窗、个人24小时、失败冷却分别计算。个人期限可跨公共截止，恢复或禁用路径有清理例外 | 设备-1自然采样中先见316期，后见317期，两期截止相差23:59:57.546 | 可记录“相邻期截止约隔24小时”。精确开始、零间隔、固定星期窗口与跨期实际结算各需独立证据 |

**可复用的反证问题**：如果只改界面按钮文案、只返回同一份配置、只看到同一胜利回调、只观察到一期截止，这一结论还能区分哪些可能性？选能区分它们的最小下一步，例如找写参与位的调用者、比对离线已有副本、查看疑似调控函数的实际返回值，或在自然换期前后各留一份带时间的快照。
