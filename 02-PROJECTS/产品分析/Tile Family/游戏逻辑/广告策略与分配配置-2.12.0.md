# Tile Family 广告策略与分配配置

本地阅读版：[[02-PROJECTS/产品分析/Tile Family/游戏逻辑/TileFamily_Ads_Strategy_2.12.0.html|HTML报告]]。本Markdown为持续维护主文档；HTML为2026-11-16正文的阅读快照，后续正文更新时应同步导出。

**TF 的广告变现包含两类决策：产品层决定谁能在什么场景看广告、得到多少奖励；广告请求层决定使用哪个广告池、以什么价格区间请求并选择可播广告。** 两类决策之外还有独立AB配置通道及设备/权益拦截。当前样本能确认规则分层、U2付费召回覆盖、发奖与重置链及动态价格算法，不能还原所有线上实验比例或当前账号的最终配置。

本次续接既有通关激励视频分析。分析对象为 **Android 2.12.0 / 21200**，配置来自 **2026-11-04 15:20:30 +08:00** 保存的初始配置及缓存。2026-11-16重新核对同构建ARM64消费者，未重新采集线上账号、观看广告或购买商品。下文“基线”均指这批配置代入已核代码，不表示所有线上玩家共同使用。

## 1. 产品策略结论

| 策略 | 已取得的依据 | 产品解读（推断） |
|---|---|---|
| 先保护早期体验，再引入强制广告 | 插屏同时检查当前主线进度>50、累计会话时长≥90分钟；预请求可以更早 | 将首次体验和强制广告变现分开，保证准备广告不等于立即展示 |
| 通过奖励与困难节点引导主动观看 | 结算金币、补体力、复活、重玩加格、活动能量等入口 | 覆盖胜利后的收益需求、失败后的解困需求及继续玩的需求 |
| 对不同商业化人群配置不同广告待遇 | U1结算日限100、单局复活10；U2初始关闭插屏、复活和重玩加格日限3 | U1更偏向广告变现；U2先保留IAP空间。此为配置意图解释，不是用户价值模型的官方定义 |
| 付费召回场景累计触发后，可以改用部分广告参数 | U2、有购买记录、距最近购买/该场景弹出至少10天、综合资产价值≤10000，进入有效弹出分支累计2次；再次购买清零 | 面向长期未续购且资源减少的历史付费用户提供广告兜底；不是新用户连续拒绝两次付费 |
| 主动看广告后暂缓插屏 | RV展示后至下一次插屏至少480秒；插屏彼此至少360秒 | 减少玩家刚完成主动观看又遭强制广告的叠加压力 |
| 提高每次可播机会的变现价值 | 国家价格表、动态请求区间、主池/备用池比较eCPM | 在请求价格与填充之间调整；不等于已经证明收入提升效果 |

“广告很多/很少”可能同时受组别、付费状态、场景开关、时间、次数、渠道和填充影响，不能从单个玩家体验反推统一频次。

## 2. 先区分不同层级的“分配”

| 层级 | 决定什么 | 本次证据状态 |
|---|---|---|
| 用户组 | U0_0、U0_2、U1_0、U2_0 | 默认策略及优先级已核；不是简单随机均分 |
| AB配置通道 | 随机UserSegment、功能配置、已应用组合 | 已核随机分段持久化及功能配置接收/保存能力；当前广告实验和权重未知 |
| 配置选择 | 使用哪一组客户端列、哪些字段改读服务端 | 客户端映射、广告策略覆盖白名单、配置拦截器先行路径已核；全层级优先级未穷尽 |
| 广告资格 | 时机、关卡、时长、次数、免广告、设备等是否放行 | 业务拦截器和设备/OS名单消费者已核 |
| 请求与选池 | 动态价格区间、主池与备用池的选择 | 关键消费者与分支已核 |
| 线上实验与网络流量 | 各实验真实占比、国家/渠道实时覆盖、各广告网络竞价与填充占比 | 未取得后台分流配置、完整请求响应和账号最终选组，不能推定 |

典型请求路径为：用户组及配置 → placement资格 → 免广告、时间和次数等拦截 → 可播广告池 → 展示 → 展示计数及奖励回调。各层并非可以互相替代；例如某组插屏开关被打开，仍可能被已购免广告资格挡住。

### 独立AB通道与配置优先级边界

`AbTestUtils.GetApSegment`读取偏好键`UserSegment`，缺省哨兵为100；命中哨兵时调用`System.Random.Next(0,100)`得到0～99并保存，后续读取保存值。`GetUserProperty`将它加入AB请求，`AbRequester.GetRequestParams`还组合应用、设备与自定义受众字段。设备字段含国家、语言、系统、机型和硬件信息。**这证明存在独立的分流输入，不证明U组随机分配，也不代表100个等量实验组或某实验各占1%。**

`MFABTestManager`初始化会建立请求逻辑；`AbRequester.HandleResponse`处理功能配置，`AbUserData.SaveFeaturesToDisk`保存`AbTestConfig.json`，`GetCsvDataByFeatures`把功能配置转换为CSV数据，另有`GetAbAppliedCombList`及确认应用状态。仅收到/保存不能等同当前业务已应用；本批没有取得对应广告实验的响应正文、当前已应用组合与权重。

本轮还跟进`ClientConfig.GameIntValue → 0x4c22eb4 → 0x3834094`：先遍历配置拦截器，接口`IGameConfigInterceptor.GetConfigValue`返回命中时直接取返回值，否则走后续通用取值路径。这只补齐一段优先顺序；具体广告键是否有拦截器、AB与远端CSV及缓存的完整覆盖顺序仍未全证，不能据静态客户端列推定所有玩家最终值。

## 3. 用户分组：真实规则与优先级

配置为 `config_server_user_group.csv`。`UserGroupDefaultStrategy.CalculationUserGroupNode` 按 **ID降序** 遍历，取首个同时满足campaign、LT和IAP条件的规则。

| 优先级ID | 条件 | 结果 |
|---:|---|---|
| 500 | 累计`iap_ltv ≥ 0.1`，campaign不限 | U2_0 |
| 450 | campaign标签`u0_2`，安装起游戏日序号≥8 | U1_0 |
| 400 | campaign标签`u0_2` | U0_2 |
| 350 | campaign标签`u1_0` | U1_0 |
| 300 | 安装起游戏日序号≥2，campaign不限 | U1_0 |
| 200 | campaign标签`af_initializing` | U0_0 |
| 100 | 兜底 | U0_0 |

因此，按默认规则：普通未付费玩家首日通常在U0_0，第2个游戏日可到U1_0；IAP买量标签u0_2玩家可先留在U0_2，第8个游戏日起转U1_0；累计IAP达到0.1会优先进入U2_0。实际变化还要等重算入口执行，不能声称到零点瞬间全部切换。0.1是内部收入字段的阈值，不在这里未经货币口径核验换算为人民币或单笔商品价。

**两处名称/备注容易误导：**

- 表头把LT写为“生命周期绝对活跃天数”，但本构建调用`GetLoginDaysAbsolute`，实际返回`GetDaysAfterInstall()+1`，是以首次登录日期为起点的游戏日序号，不是实际登录了多少天，也不是安装后精确满24/168小时。游戏时钟的固定时区仍未核定。
- `ModifyCampain`先Trim并保留`af_initializing`，再用`(.*)_([uU](\d+)(_\d+)?)$`提取末尾标签；未匹配走`all`。特定标签比较区分大小写，不能把规则简化成任意位置包含u0_2。

用户组枚举映射：0→U0_0，1→U1_0，2→U2_0，3→U0_2；其他回退Value。`user_group_predict_switch=F`，且初始化分支确实选择默认规则；T时存在另一套ThinkBox预测策略。预测表和模型文件存在不能证明本批正在按预测模型分组，表内阈值50也不是“50%玩家分流”。

已核重算触发包括：启动链、客户端归因成功、服务端归因合并、购买成功处理，以及特定商业化弹窗退出。归因回调带初始化状态门禁，并非每份回调都会盲覆盖；未找到据此证明第2/8游戏日零点立即切组的定时链。

### U2条件广告策略与改组不是同一件事

`ShouldUseServerGameForAdStrategy`需同时满足：服务端`u2_ad=T`、当前枚举为U2、通过IAP预测标签资格、`popup_Scene_no_payment_show_count≥u2_ad_check_times`。本批阈值2；`iap_group_predict_switch=F`时标签资格直接通过，若T则要求`GetIAPGroupTag()==R0`。

本批计数场景为`u2_ad_popup_scene=no_payment_check`。实际入口是首页的`ShowNoPaymentCheck`，选中`no_payment_bundle`并进入买一送一弹窗路径；相关Lua和配置把资格限定为：

| 前置条件 | 本批实际判断 |
|---|---|
| 当前用户 | U2，且存在历史购买记录 |
| 时间 | 当前时间距离“最近购买”和“此action/rule上次弹出”两者中更晚者至少10×24小时 |
| 库存 | `allAssetWorth≤10000`，与时间条件同时满足 |
| 展示安排 | 首页机会、场景开关及流程调度仍需通过；Priority500，不保证立刻弹出 |

`allAssetWorth`是加权库存价值，不是金币余额：本批金币×1、体力×100、撤回×300、磁铁×600、抓取/洗牌×450、加格×600，Carnival三个buff各×8000；新道具另按各自资产表取值。消费者也支持限时资产按剩余分钟折算，但本批这些资产价值为0。只看金币低于10000不足以判断资格。Lua旧注释写“7天/2000”，实际参数为`10|10000`，以消费者和当前配置为准。

有效商品分支先`SavePopupShowInfo`保存本次时间，再增加计数，最后打开弹窗。**它不是成功曝光计数，更不是明确拒绝购买计数。** 本批商品组对应`com.middle.favor.bundle`，配置价格1.99、奖励包`100_3000;502_1;506_1;300_60;515_1;503_1;708_30`；不将内部价格视为当前商店实价。

条件算例：计数初始0、仅由这条场景增长、配置不变且资格始终满足时，最早约最后购买后第10天第一次、第20天第二次，达到阈值2；资产、登录和调度可进一步延后。这不是“所有付费用户20天后开始看插屏”的固定规则。

购买成功处理`DoSuccessWithReceipt`进入时调用`ClearPopupSceneNoPaymentShowCount`清0，再执行购买动作与组别重算。清零可使U2重新读取基础广告参数，**该覆盖可回退，不是永久转为广告用户**。这里证明成功处理链的动作顺序，未实测资产到账原子性；直接调用扫描未发现每日/每次重启清零，不排除统一清库或未解开的间接路径。

| 参数 | U2客户端值 | 满足策略后服务端值 |
|---|---:|---:|
| 插屏总开关`interstitial` | 0 | 1 |
| 结算金币日限 | 20 | 100 |
| 复活广告日限 | 3 | 20 |
| 复活广告单局上限 | 1 | 10 |
| 重玩加格日限 | 3 | 20 |
| 重玩送道具日限 | 3 | 20，但入口开关仍为0 |

**覆盖不是整张表替换。** `NoChance`所核白名单只有结算金币、复活、重玩加格、重玩道具4项日限；复活单局和插屏总开关另有独立选表。生命、Order Merge日限不在这4项白名单中，全局RV展示100也不由此改成其他数值。

`TryToUpdateU2ToU1`名称并不能证明直接赋值U1；其实际触发`update_user_group`，由已注册策略重新计算。默认规则下累计IAP仍≥0.1时仍可返回U2。必须分开描述“改用广告参数”和“账号改组”。

此外，U2客户端`all_iap_remove_ad_switch=T`，有有效购买记录时仍会被独立免广告拦截器阻止插屏。因此**服务端把interstitial改为1不代表这个U2玩家下一次必看插屏**。

表中日限是资格上限而不是实际观看量。Reward、Interstitial、Banner各自计数，不是三类共用100。业务领取额度与广告展示额度也不同：广告已展示但未得到奖励回调时，可能只消耗外层展示额度。

渠道屏蔽值为`block_rv_campaign=u0_4`。已核是忽略大小写的campaign后缀匹配。虽然字段名写RV，但`MFAdTypeConfigInterceptor.AdTypeSwitch`在三类广告开关通过后均调用这一判断，不能按名字把作用域仅限定到激励视频。

设备另有独立名单：`config_device_blacklist.csv`共406条配置，其中402条禁插屏/Banner而保留RV，2条三类都禁，2条广告字段为空。这里是表行数，非去重机型数或玩家比例。消费者将品牌/型号移除空格并转小写，要求品牌相等且运行型号以配置型号开头，取首个匹配项；不能扩大为该品牌全部禁用。命中后加载和展示两处都拦截。`config_os_blacklist.csv`虽有`a-27/a-29`，三类字段均F，本批不能解读为禁用这两类系统的广告。

## 5. 插屏：位置、保护期与节奏

### 触发场景

| 场景 | 本批开关 | 行为含义 |
|---|---:|---|
| 胜利结算点击继续 | 1 | 进入插屏展示尝试；仍检查全部资格 |
| 主玩退出确认后离开 | 1 | 退出路径的插屏机会 |
| 退出确认点击重试 | 0 | 实现存在，本基线关闭 |
| 胜负结果产生、结算页之前 | 0 | 实现存在，本基线关闭 |

这是**场景触发＋时间约束**，未在这些直接路径中发现统一“每3关一次”规则。单局时长不同，会使玩家体感呈现不同的“隔几关一次”。

### 同时满足的关键门槛

| 条件 | 配置/已核代码解释 |
|---|---|
| 总开关、当前placement开启 | 结合用户组和U2条件选表 |
| 当前主线进度>50 | `current_level<=50`被拦截；完成50关后已推进51可能符合，不是进入50关就弹 |
| 生命周期累计会话时长≥90分钟 | `GetTotalSessionTime`累计在线会话；不是安装后放置90分钟 |
| 当天完成关数达到0、当天会话时长达到0分钟 | 本批无额外日内保护；有配置能力 |
| 距上次插屏至少360秒 | INT时间在`OnAdWillShow`记录 |
| 距上次激励广告至少480秒 | RV时间在展示回调记录，不等待奖励到账 |
| 当日插屏展示<30 | 与RV额度独立 |
| 没有命中免广告、渠道或其他拦截 | 开关为1也可能不展示 |
| 广告系统可用、广告已准备好 | 无填充时不保证出现 |

上次INT/RV时间写入偏好存储，不能假设重启立即绕过间隔。480秒是**RV后限制下一次插屏**，不是两次RV之间必须等8分钟。

### 预请求早于展示

插屏提前请求量为45关和80分钟。已核首次请求检查要求等级、时间两个标记都成立，代入基线为 **当前关卡≥5且累计会话时长≥10分钟**，再经过初始化、总开关等条件。预请求使后续有机会可播，不产生玩家展示事件。

激励预请求取已开启时机中最早门槛，再减`reward_request_advance_level=12`；本批纳入的最早门槛是结算12。此等级条件可以很早成立，但不能因此声称第0关已发出网络请求，或断言预加载的目的就是用户eCPM分组。

## 6. 激励视频：奖励与经济入口

| 入口 | 资格门槛/状态 | 玩家获得什么 | 其他约束与证据边界 |
|---|---|---|---|
| 通关金币 | 资格12；30关起奖励金额非0 | **额外300金币** | 普通金币另算；单个结算页成功后隐藏按钮 |
| 补生命 | 20关起 | 正常未满时补满5点体力 | 成功动作传入8，资产层按上限5截断；不是一天8次或实得8点 |
| 广告复活弹簧 | 20关起，另检查资产解锁 | 手牌区末尾最多2张搬到暂存区，释放槽位继续本局 | 509→PropBagSpring→继承PropSpring.DoHandle，TargetCount=2；不是永久消除或随机放回棋盘；暂存区表现未实拍 |
| 重玩加一格 | 20关起，真实重玩及其他资格 | 本局背包额外1格，回调`508_1` | 需要扩容开关、资产资格、无有效对应无限道具及可播状态 |
| 重玩送道具 | 开关0，本基线关闭 | 若开启，配置为洗牌515×1 | 与重玩加格方案替换；use_type=1，不累计，清关销毁全链未核 |
| Order Merge活动能量 | 广告资格1，活动另有开启要求 | 配置单次10点活动能量 | 当前活动资格、能量到账/截断及额度每日恢复未核；不能说主线第1关已有入口 |

上述是所核中央RV时机分发器识别的6类，不排除其他模块有独立路径。日限对照上一节；U2覆盖的范围见第3节。

**奖励强度的产品意义：** 普通通关金币从30关起按`50,10,10,10,10,10,30,10,10,10`循环；广告始终额外300，是当次普通奖励的6～30倍。它为主动观看提供明显的收益差，而非通常意义的“双倍领取”。能否支撑复活或道具消耗，仍要结合物价、领取率和消耗行为，不能仅用最高次数估计每日实际产币。

入口显示并不统一：结算和重玩加格读取`CanShowRewardAndReady`；体力和复活初始化读取`CanShowReward`，没有这一步额外Ready检查。所以“按钮显示/不显示”与广告当前可播状态的关系需逐入口核对。

重玩奖励选择优先判断`reward_retry_props==1`，否则读`retry_extra_space_type`（本批ad，可配coin），不是同一弹窗并列提供两个广告奖励。

业务成功领取计数键分别为金币100、生命200、复活509、加格508、Order Merge能量15014；外层全部RV展示共用100次。比如结算成功10次、复活成功5次且各展示一次：金币入口用10，复活入口用5，总RV展示用15。

### 发奖信号与防重边界

`ShowRewarded`实际注册普通广告、激励奖励、收益三种监听；`OnUserRewarded`与`onAdRevenuePaid`都可单独进入`TryReceiveReward`，继而执行业务成功委托。**成功领取并不严格等于SDK已经确认完整看完激励视频。** 收益事件也能启动这条链；不能因此反向保证玩家提前退出必然领奖，SDK何时发送事件与实际播放行为未观测。

wrapper用实例布尔`hasReceivedReward`防止顺次重复处理，标记在业务回调返回后设置并注销监听。它不是持久交易ID或崩溃原子性保证，重入、异常及重复事件的运行表现未实测。未准备好/显示失败走失败清理；已经扣掉的展示次数并不因此自动回退。

还有事件归属边界：dispatcher把Banner、Interstitial和Rewarded的收益事件交给同一收益监听列表；其共享遍历和wrapper中未按本次RV的AdUnitId、placement或广告类型过滤，两个成功入口甚至不读取事件参数。已用原始泛型映射补核这段派发，不只依赖方法名。由此不能把一次业务成功严格归因为“本次RV的完整观看”；是否发生其他广告迟到事件导致误领奖仍无实测，不能直接定性为已发生的线上漏洞。

等待逻辑为两轮2秒调度，底层是Unity `WaitForSeconds`：成功信号取消等待，否则第二轮触发`OnRewardCloseBeforeRewarded`并清理。wrapper继承的`OnAdHidden`为空，不能写成广告关闭事件本身立即判领奖失败；Unity执行、暂停及时间缩放未实测，也不能把调度参数直接称为墙钟4秒超时。

## 7. 去广告商品与Banner

### 去广告保护的范围

`MFAdIAPInterceptor`只处理Banner/Interstitial，Reward直接通过，因此购买去广告不等于关闭所有自愿激励入口。该对象同时注册到加载和展示列表：满足权益后，后续加载也经过免广告检查；不能据此推定关闭整个SDK、即时清除缓存或销毁已加载广告。

| 当前客户端开关 | 判断依据 | 本批组别 |
|---|---|---|
| `all_iap_remove_ad_switch=T` | `iap.products_buy_times`集合存在购买记录 | Value/U0_0/U0_2/U2_0 |
| `all_iap_remove_ad_switch=F` | 专门的`iap.remove_ad_purchased`状态 | U1_0 |

所以不能概括为“所有玩家任何付费都免广告”，也不能概括为“只有购买专门去广告才免广告”。服务端同名配置标记Abandoned=T，已核消费者读客户端表；不要用该废弃项覆盖组别差异。最终权益仍与组别变化和购买历史恢复相联系。

`config_server_iap.csv`存在`com.no.ads.bundle`、no_ads组、BuyPrice=1.99；同组3.99/5.99条目备注“未启用”。这些是样本配置，不能当成当前地区结账价格或已实施的价格AB。

## 8. 广告请求价格与主备池：另一套“分层”

### 8.1 新MAX动态区间是本批选择的主策略

`MFAdTypeStrategyController.CreateMainAdUnitIdStrategy`先创建原有分层策略，若对应`*_max_switch=T`则改用`MFAdTypeDynamicStrategy`。本批插屏、激励均T，Banner为F。因此不能直接把旧三档Ad Unit、每2次升级等参数当成本批主策略的全部行为。

`GetMatchCountryRequestConfig`从`GetOriginalCountryCodeBySimThenSettings`取得国家，匹配`config_client_request_ecpm.csv`，缺失回退other。已核不是在此处按IP实时判国，也不是按U1/U2列选择这张表。选中对象在模块内缓存。

下表列新请求策略的国家基线。数值是eCPM价格口径参数，不是给玩家的货币，也不是保证成交收入。

| 国家组举例 | INT中价 / floor长度 / ceiling长度 | INT初始请求区间 | RV中价 / floor长度 / ceiling长度 | RV初始请求区间 |
|---|---|---|---|---|
| 美国 | 20 / 3 / 12 | [17,32] | 30 / 15 / 15 | [15,45] |
| 日本、澳大利亚、加拿大、韩国 | 15 / 2.25 / 10 | [12.75,25] | 20 / 10 / 10 | [10,30] |
| 英国、德国、法国、台湾等 | 7.5 / 1.12 / 5 | [6.38,12.5] | 10 / 5 / 10 | [5,20] |
| 意大利、西班牙、巴西、印尼等 | 5 / 0.75 / 3.5 | [4.25,8.5] | 7 / 3 / 6 | [4,13] |
| other | 2 / 0.3 / 1.2 | [1.7,3.2] | 4 / 1 / 2 | [3,6] |

初始区间按`middle-floorLength`到`middle+ceilingLength`计算，再受min等边界处理。每次变价保存中价，偏好键为`unit_id_middle_price_key_`＋广告类型，键内没有国家、U组或具体AdUnitId；初始化已有保存值时直接恢复，不能保证每次启动回国家表初值。所核初始化/回调内没有日切或组变更清零，但未穷尽全应用删键路径，不宣布永久不重置。

关键行为已核：

- `OnAdLoaded`读取加载结果eCPM更新区间，不应照配置备注一概称“展示两次后才更新”。facebook网络分支在此函数跳过更新。
- `*_request_up_type=T`时，将这次eCPM作为下一次floor；例如美国RV加载结果eCPM=30，候选新区间为[30,60]。这是代码代入示例，不是现场广告报价。
- `*_request_ceiling_type=F`，此分支允许向表中max之上继续请求；所以美国RV的request_max=200不能当成所有情况下硬上限。
- `*_request_down_type=1`：合规加载失败时向下调整，当前floor成为新的ceiling，再保留区间长度；最终仍受min保护。错误码-1000/-1001/-1009排除在降级依据之外。
- floor/ceiling通过`MaxSdkAndroid.SetInterstitialExtraParameter`、`SetRewardedAdExtraParameter`传入请求，同时记录`request_floor`/`request_ceiling`数据。
- `MFAdExtened.Ecpm`从非负收入字段乘1000，已核原生常量1000；不应把每次展示收入与eCPM混用。

### 8.2 主池与备用池

`interstitial_winner_switch=T`、`reward_winner_switch=T`，有独立备用Ad Unit配置。控制器创建主、备用策略；一边Ready时可走该边，两边Ready且信息有效时比较eCPM，选更高者，相等保留主池。

这是**可播结果比较机制**，不是已发现“主池70%、备用池30%”的分配比例。广告网络内部的竞价、底价生效、收益估计精度和最终网络占比仍由SDK/平台及实际流量决定，现有材料不能恢复完整后台瀑布流。

主备ID都被加入首次加载列表，由加载服务依次提交；只能确认同轮准备，不能保证底层网络严格同时发出。备用池也影响主池定价：备用加载eCPM高于主策略当前**中价**时，`OnAlternateSuccess`触发向上更新。本批up_type=T，例如美国RV初始中价30/区间[15,45]，备用eCPM35可使主池候选区间变成[35,65]。这是代码算例，说明备用池兼具填充补充与提价参照作用，不是现场报价。

### 8.3 旧三档与备用能力

旧策略保留3个正式Ad Unit；初始tier=3；初始评估、升级和降级各配置2次；session最大升级3次；升级计数类型F表示连续；冷启动base重置间隔=-1表示关闭。美国旧档升级阈值为INT `5|14`、RV `5|23`，来自另一张`config_adunit_ecpm.csv`，不能与新请求区间[17,32]/[15,45]混用。

这些参数在旧分支仍有意义，但本批新MAX开关T优先选择动态价格主策略。新用户专用广告ID开关INT/RV均F，不能因为存在“前2次展示/2次无填充”参数就认定本批启用新客专池。

### 8.4 失败重试与空池补充

| 状态 | 已核行为 | 易误判之处 |
|---|---|---|
| 动态价格尚未降到最低floor | 普通失败先按规则降价，再快速请求；`-1009`在此分支另延3秒 | 某错误不参加降价，不代表不重试 |
| 已到最低floor | 判断`abs(floor-min)<0.001`，走2、4、8、16、32、64、64…秒退避 | 配置6是指数上限，不是最多尝试6次 |
| 成功加载 | 对应策略重试计数归零 | 主备各有自己的RetryPolicy，不共用失败次数 |
| 广告池持续未准备好 | 每30秒检查，距上次请求开始>63999毫秒时尝试`empty_pool`补请求 | 字段虽叫lastLoadFailTimestamp，实际在请求开始写入；不是玩家必须等64秒 |
| 广告关闭／显示失败 | 重新加载对应策略，仍经过加载拦截器 | 加载次数不等于展示次数，也不绕过免广告/设备屏蔽 |

本批INT/RV/Banner首次请求额外延迟配置均0，但业务预请求门槛仍在。空池检查的轮询相位、前后台暂停与SDK内部队列会改变实际网络时间；网络并发、超时、最终价格接受和实际填充效果尚未观测。
