# Tile Kingdom 1.58 资源与逻辑分析总览

> [!info] 分析口径
> 竞品包分析以“资源怎么被使用”为核心，而不止于文件导出。固定覆盖图片、动效、音效和逻辑，并尽量形成 `资源 → Prefab/组件 → 控制逻辑 → 触发条件 → 屏幕结果` 的最短证据链。静态可见、静态推断、运行时已验证和远端缺失必须分开记录。

### 已见类型与例子

- Animator/AnimationClip：按钮 Normal/Pressed/Selected/Disabled、开锁、章节烟花、法杖执行、活动入口、关卡进度条、角色待机与结算；
- ParticleSystem：Poof、BuildSparkles、BombMechanicsExplode、IceBreakEffect、GrassParticleEffect、GemSparkle、Firework、MagicNova、TileStarTrail 等；
- Spine：Addressables 目录暴露 `70` 个 `.atlas.txt` 引用和 `28` 个 `SkeletonData.asset` 引用，覆盖 Grollo 皮肤、角色头像、Chef、Dragon、Gryphon、活动场景与障碍演出。

### Tile Temple 动效对位

| 资源/组件 | 控制入口 | 触发与结果 |
|---|---|---|
| `SpineAnimationTileTempleController` | `BreakPlatform()`、`PlayBreakAnimation()`、`PlayBounceAnimation()` | 控制台阶 Spine 的破裂与弹跳，并发出 `PlatformBroke` 事件 |
| 当前/晋级台阶 Spine | `TileTempleScreenComponent.ReplaceCurrentStepWithSpine`、`ReplaceAdvancedStepWithSpine` | 用 Spine 表现替换对应阶段节点 |
| `starExplosionEffect` | `TileTempleLoadScreenComponent.PlaySimulation` | 结算模拟中的星星爆发粒子 |
| 头像与台阶序列 | `TileTempleScreenComponent.PlaySimulation` | 根据淘汰结果移动/淘汰头像并推进阶段 |
| 奖励元素弹跳与飞行 | `TileTempleRewardScreenComponent` | 数字滚动、元素依次弹跳和奖励飞行 |

当前能确认控制组件和触发链，但 Tile Temple 专属 Prefab/bundle 未完整落盘，因此不能宣称已还原最终屏幕效果。

## 逻辑分析

逻辑分析不只列类名，至少覆盖入口、状态流、核心数据、判定、奖励、表现调用、埋点和远端配置边界。本轮以 Tile Temple 验证：

1. 活动由 `TileTempleAddon` 统一组合关卡计分、玩家淘汰和奖励三个 Addon。
2. 参与时订阅分数变化；结束时解除订阅。
3. 只有关卡带 `IsTileTempleActive` 特性时，分数变化才推进淘汰模拟。
4. 未领奖且淘汰赛获胜才可领奖，奖励读取首个奖励项。
5. 单实例累计胜利次数小于 `2` 才可再次参与；胜利后实例胜场加一。
6. UI 状态覆盖 EventStarted、Info、Load、主界面和 Reward；表现层再调用头像、台阶 Spine、粒子和音效。

详细证据见 [[02-PROJECTS/产品分析/Tile Kingdom/活动拆解-Tile Temple-1.58|Tile Temple 活动静态拆解]]。

界面系统方面，弹窗复用统一的 `ScreenStateStackComponent / ScreenStateStack`：业务创建 State 并 `Push`，`ScreenState<T>` 管理创建、激活、订阅和进退场，`PopupComponent` 合并关闭按钮与遮罩点击，默认动效由 DOTween 组合面板缩放、面板淡入淡出和遮罩淡入淡出。详见 [[02-PROJECTS/产品分析/Tile Kingdom/系统拆解-弹窗框架-1.58|弹窗框架静态拆解]]。

## 固定交付结构

以后同类竞品分析默认按下表输出：

| 章节 | 必答问题 |
|---|---|
| 包与版本 | 哪个版本、平台、架构、Unity/引擎版本，哪些内容在本地、哪些是远端 |
| 图片 | 有什么资源、在哪里、被哪个 Prefab/UI 使用、何时出现、依赖什么 Atlas/材质 |
| 动效 | 使用 Animator、粒子、Spine 还是 Tween；控制组件、动画名、触发条件、材质/Shader/骨骼依赖是什么 |
| 音效 | AudioClip、SoundKey、调用代码、触发事件、循环/一次性、Mixer 分组与实际绑定是什么 |
| 逻辑 | 入口、状态机、数据、判定、奖励、失败、埋点、远端配置如何串起来 |
| 证据链 | `资源 → Prefab/组件 → 控制逻辑 → 触发条件 → 屏幕/声音结果` |
| 验证边界 | 哪些是静态确认、静态推断、运行时确认、远端缺失或工具无法恢复 |

## 后续优先级

1. 选定具体活动或局内机制，而不是继续无边界批量导出；
2. 为目标建立图片、动效、音效、逻辑四张资源使用表；
3. 优先补齐 Prefab/配置，使资源与消费者形成引用链；
4. 仅在静态证据不足时做授权范围内的运行时验证；
5. 对远端 bundle 和单次服务端配置保持“待验证”，不写成固定规则。
