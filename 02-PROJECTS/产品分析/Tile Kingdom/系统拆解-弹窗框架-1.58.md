# Tile Kingdom 1.58 弹窗框架静态拆解

> [!info] 结论边界
> 本文基于 Tile Kingdom 1.58 ARM64 IL2CPP 的 Cpp2IL C# 结构与 ISIL 指令证据整理。类关系、方法调用和字段可以静态确认；Prefab 的实际序列化参数、最终动效观感、Android 返回键行为、远端活动界面与运行时竞态尚未验证。

## 一句话结论

Tile Kingdom 没有另建一套独立的弹窗管理器；弹窗复用统一的 `ScreenStateStackComponent / ScreenStateStack` 屏幕状态栈，由业务创建 `PopupState` 或普通 `ScreenState` 并执行 `Push`，再通过 `ScreenState` 生命周期完成资源创建、激活、订阅、进场、退场与销毁。`PopupComponent` 只补充遮罩点击关闭，`PopupAnimationComponent` 提供默认缩放与淡入淡出。

## 分层结构

| 层级 | 核心类型 | 已确认职责 |
|---|---|---|
| 资源映射 | `ScreensScriptableObject` | 以 `IdAddressablePair[]` 保存界面类型/ID到 Addressable `AssetReference` 的映射 |
| 实例与画布 | `ScreenManagerComponent` | 获取或创建 Screen、创建适配画布、设置层级、打开和销毁；相邻画布排序间隔为 `4` |
| 实例缓存 | `ScreenCacheComponent` | 按类型缓存并取回 `ScreenComponent` 实例 |
| 状态容器 | `ScreenStateStackComponent` | 暴露 `Push`、`Pop`、`Build`、`Switch`、`Redirect`、`Remove`、`PopAll`、`Clear`，并可读取 `Top`、`BelowTop`、`StackContent` |
| 状态执行 | `ScreenStateStack` | 实际执行异步栈变更，结合 Loading Provider 和 `IsWorking` 状态管理进行中的切换 |
| 生命周期 | `ScreenState<T>` | 持有 Screen，执行 `Create → Activate → AnimateIn` 与 `AnimateOut → Deactivate/Destroy`；管理创建期和激活期订阅 |
| 通用界面 | `ScreenComponent` / `GameScreenComponent` | 提供关闭按钮、画布类型、参考分辨率、是否隐藏下层、Open/Close 和基础动效入口 |
| 弹窗特化 | `PopupComponent` / `PopupState<T>` | `PopupComponent` 合并关闭按钮与遮罩点击；`PopupState<T>` 本身没有额外逻辑，只是类型语义层 |
| 默认弹窗动效 | `PopupAnimationComponent` | 使用 DOTween Sequence，组合面板 `DOScale`、面板 CanvasGroup `DOFade` 和遮罩 CanvasGroup `DOFade` |
| 业务状态 | `OkayPopupState`、`YesNoPopupState`、`QuitLevelPopupState` 等 | 注入文案和业务数据，订阅按钮，决定关闭后的业务动作 |

## 打开链路

```text
业务条件成立
  ↓
StateFactory 创建通用弹窗，或业务直接 new 对应 State
  ↓
ScreenStateStackComponent.Push(state, PushSettings)
  ↓
ScreenState.LoadResources / Create
  ↓
ScreenManagerComponent 从缓存或 Addressable 映射取得 Screen
  ↓
OnCreate：写入标题、正文、按钮和业务数据
  ↓
Activate：激活 GameObject、订阅 CloseClicked、执行 OnActivate
  ↓
AnimateIn：调用 Screen / PopupAnimationComponent 进场表现
```

这里的核心对象是“状态”，不是直接对 Prefab 调用 `SetActive`。业务状态负责数据与回调，Screen Component 负责视图和交互，状态栈负责界面的上下层关系与生命周期。

## 关闭链路

### 默认关闭

1. `ScreenState<T>.Activate()` 订阅当前 Screen 的 `CloseClicked`。
2. 普通 `ScreenState<T>.OnCloseClicked()` 默认调用 `ScreenStateStackComponent.Pop()`。
3. `PopSettings` 决定是否播放当前界面退场、是否重新激活下层、是否让下层播放进场。
4. 弹窗退场后释放激活期订阅，并恢复或显示下层状态。

### 弹窗的关闭输入

`PopupComponent.CloseClicked` 将两类输入合并为同一条 Observable：

- `ScreenComponent` 原有关闭按钮；
- `cover` 遮罩按钮的点击。

因此，对继承 `PopupComponent` 且没有另行拦截的弹窗，点关闭按钮和点遮罩走同一条关闭链。若 Prefab 未配置 `cover`，代码以空 Observable 代替，不会因缺失遮罩按钮而产生该路点击。

业务按钮也可以并入关闭流。例如 `OkayPopupComponent.CloseClicked` 会把 `okayButton` 点击和 `PopupComponent.CloseClicked` 再次合并，因此确定按钮、右上角关闭和遮罩最终都进入 `OkayPopupState.OnCloseClicked()`。

## 栈切换参数

| 操作 | 可控参数 | 含义 |
|---|---|---|
| `Push` | `ActivatePush` | 是否激活新压入的状态 |
| `Push` | `AnimateOutBelow` | 压入新状态时是否让下层播放退场 |
| `Push` | `WaitAnimateOutBelow` | 是否等待下层退场完成 |
| `Push` | `HideBelow` | 是否隐藏下层界面 |
| `Pop` | `ActivateBelow` | 弹出当前状态后是否激活下层 |
| `Pop` | `AnimateInBelow` | 下层恢复时是否播放进场 |
| `Pop` | `AnimateOut` | 当前状态是否播放退场 |
| `Build` | `LoadingScreenId`、下层退场参数 | 批量构建状态链并可插入 Loading |
| `Switch` | `AnimateOut`、`LoadingScreenId` | 替换当前状态时控制退场和 Loading |
| `Redirect` | `AnimateIn`、`Activate` | 重定向到目标状态时控制激活和进场 |

这说明“弹窗打开后底层是否保留、隐藏或播放退场”不是写死在 `PopupComponent` 中，而是由状态自身的 Screen 配置和具体栈操作参数共同决定。

## 默认动效

`PopupAnimationComponent.DefaultPopupAnimation(bool isInAnimation)` 静态确认会创建 DOTween Sequence，并在同一序列中组合：

- `panel` Transform 的 `DOScale`；
- `panel` 上 CanvasGroup 的 `DOFade`；
- `cover` 上 CanvasGroup 的 `DOFade`；
- 最后 `WaitForCompletion`，使状态生命周期可以等待动效完成。

组件暴露 `animationTime`、`fadeTime`、`coverFadeTime` 和 `panelScale`。这能确认“面板缩放 + 面板淡入淡出 + 遮罩淡入淡出”的默认结构，但当前还未从 Prefab 恢复各弹窗实际数值、曲线和是否覆盖默认组件，因此不能写成最终运行时视觉参数。

## 两类通用弹窗

### Okay：单按钮信息弹窗

入口为 `StateFactory.GetOkayPopup()` 或 `StateFactory.PushOkayPopup()`：

1. 工厂对传入的标题、正文和按钮文案执行本地化读取；
2. 创建 `OkayPopupState`；
3. `OnCreate` 调用 `OkayPopupComponent.Setup()` 写入标题、正文、按钮、补充文本与关闭按钮显隐；
4. 用户点击确定、关闭或遮罩后进入 `OnCloseClicked()`；
5. 若传入 `okClicked`，`OnCloseClicked()` 调用该回调而不再自动调用基类 `Pop`，关闭责任交给回调；未传回调时才走基类默认 `Pop`。

本版本静态见到的直接工厂调用包括：启动流程 `SplashState.StartSplashSequence`，以及队伍创建流程 `TeamCreatorComponent.OnCreateClicked`。

### Yes/No：结果型确认弹窗

入口为 `StateFactory.PushYesNoPopup()`：

1. 工厂本地化标题和正文，创建 `YesNoPopupState` 后压栈；
2. `OnCreate` 调用 `YesNoPopupComponent.Setup()`；
3. `OnActivate` 分别订阅 `YesClicked` 与 Screen 的 `CloseClicked`；
4. Yes 映射为 `YesNoResult.Yes = 0`；关闭按钮/遮罩映射为 `YesNoResult.No = 1`；枚举还定义 `Canceled = 2`，但本轮未在该状态的按钮订阅中看到它被使用；
5. `DoActionCoroutine` 先执行 `StateStack.Pop()`，等待弹窗离栈后再调用 `Action<YesNoResult>`，避免业务回调与当前弹窗同时占用栈顶。

本版本静态见到的直接工厂调用包括：玩家信息中的踢人确认 `PlayerInfoState.OnKickClicked`，以及队伍信息中的离队确认 `TeamInfoState.OnLeaveClicked`。`PushQuitPopup()` 是基于同一 Yes/No 工厂的退出确认便捷入口。

| 场景 | State / Component | 静态可见职责 |
|---|---|---|
| 关卡退出 | `QuitLevelPopupState` / `QuitLevelPopupComponent` | Yes 按钮、失去生命提示、挽留面板、困难/超难关标识、无限生命状态 |
| 内购失败 | `PurchaseFailedPopupState` / `PurchaseFailedPopupComponent` | 按 `NoConnection / Failed / Cancelled` 选择失败、取消或无网络面板；由 `GameIapManagerComponent` 创建 |
| 宝石不足 | `OutOfGemsState` / `OutOfGemsScreen` | 建造等流程在货币不足时创建；后续跳转仍需结合运行时验证 |

## 类型盘点与命名边界

本轮在恢复出的游戏程序集内静态检出：

- `19` 个直接继承 `PopupComponent` 的组件；
- `7` 个直接继承 `PopupState<T>` 的状态，其中含 `1` 个抽象基类；
- 若干名称包含 `Popup`、但状态仍直接继承 `ScreenState<T>` 的业务界面；
- `KeyChestPopupState` 对应的 Component 继承 `GameScreenComponent`，并非 `PopupComponent`。

因此不能只按类名含不含 `Popup` 判断实际关闭方式或遮罩行为。应沿 `State → Component 基类 → CloseClicked → Push/Pop 调用` 逐项确认。

直接 `PopupComponent` 子类包括：

`BuyBoosterOrWatchAdScreenComponent`、`ChangeNamePopupComponent`、`GrolloMoodInfoScreenComponent`、`LevelLoseScreenComponent`、`OutOfLivesScreenComponent`、`PurchaseFailedPopupComponent`、`BoosterFreeClaimScreenComponent`、`BuyBoosterScreenComponent`、`BlockGameFailedScreenComponent`、`BlockGameMoreTicketsScreenComponent`、`LevelFailedScreenComponent`、`AdOfferMrecScreenComponent`、`DungeonEscapeRestartEventPopupComponent`、`EditProfilePopupComponent`、`OkayPopupComponent`、`OutOfGemsScreen`、`PerilStartPopupComponent`、`QuitLevelPopupComponent`、`YesNoPopupComponent`。

## 自动弹出与弹窗栈的关系

活动和商业化内容另有触发层，例如：

- `AutoShowEventsCommand` 查找可自动展示的 Home Addon，并调用 `HomeState.ShowAddonState()`；
- 社交活动通过 `IAutoShow.AutoShow` 暴露是否允许自动展示；
- `ShowHomeOffersCommand`、`AutoShowChapterOfferCommand`、`ShowEventStartedCommand` 等分别负责特定内容的触发判断。

这些命令解决的是“什么条件下要展示哪个业务状态”，而 `ScreenStateStackComponent` 解决“界面如何进栈、退栈和恢复下层”。当前证据没有显示一个统一的 `PopupQueue` 会把所有弹窗按优先级排成单队列；若要进一步还原首页连弹顺序，应单独追踪 Home Command 的组合、blocker、`CanExecute` 和执行顺序。

Tile Temple 的具体例子见 [[02-PROJECTS/产品分析/Tile Kingdom/活动拆解-Tile Temple-1.58#活动弹窗时机|Tile Temple 活动弹窗时机]]：它以 `PlayerEliminationAddon.NeedCheck` 驱动关后自动展示，以 `IForceShowOnLevelLose` 驱动失败后的强制展示，并在主界面模拟完成且 `CanReward()` 为真时再压入奖励页。
