## 采集范围建议

### Royal Match 样本接收补充

2026-10-26 用户提供 `D:\Downloads\Royal+Match_38911_APKPure.xapk`。已只读打开 ZIP 中央目录与 `manifest.json`：文件大小 244,604,926 字节，清单声明包名 `com.dreamgames.royalmatch`，versionName/versionCode 均为 `38911`；实际条目包括主 APK、`UnityDataAssetPack.apk` 和 `config.arm64_v8a.apk`。仅完成容器与清单检查，未验证 APK 签名、内容完整性或与 Mac 历史样本的哈希一致性。原包保持原位。

再次在沙盒外执行 `adb devices -l`，设备列表仍为空，未发现 MuMu 进程；尚不能确定模拟器安装版本或读取沙盒。后续以模拟器实际安装版本及其 base/split APK 为主基线，此 38911 包用于辅助对照；不可直接复用旧版本函数地址或将旧配置标为当前生效值。

路径是候选，不是本机已发现事实。先通过包信息确定 Android 用户、包名、dataDir、版本和 ABI。

| 候选来源 | 主要内容与注意点 |
|---|---|
| `pm path <package>` 返回的 base/split APK | 保留当前安装版本的静态基线；不要直接套用旧版类地址和资源映射 |
| `/data/user/<userId>/<package>/` | files、cache、shared_prefs、databases、no_backup；可能包含活动配置、进度、SDK 缓存 |
| `/data/data/<package>/` | 常见 user 0 入口，先核实是否与上一路径指向同一位置，避免重复统计 |
| `/data/user_de/<userId>/<package>/` | 若存在，检查设备保护存储 |
| `/storage/emulated/<userId>/Android/data/<package>/` | Unity persistentDataPath 常见候选、外部 files/cache、下载资源 |
| `/storage/emulated/<userId>/Android/obb/<package>/` | 若存在，保留扩展资源 |

Unity catalog 与 AssetBundle 缓存不一定在同一目录；缓存文件可能没有 `.bundle` 后缀，要用文件头、清单和加载代码对位。Root 解决访问权限，不自动解决压缩、序列化、应用层加密或内存独有内容。

## 最小实现流程（建议，未执行）

1. 启动指定 MuMu 实例，枚举设备，验证 `shell id` 与 `shell su -c id`，定位目标包与安装版本；先只列目录和大小。
2. 保存初始快照，再由正常游戏流程打开目标活动、等待下载，保存第二份快照；不要先清缓存或重装。
3. 导出时保留路径、大小、时间、SHA-256、设备实例、包版本、采集场景；SQLite 连同 WAL/SHM 处理，在副本上检查一致性。活跃进程的跨文件复制不是原子快照，必要时单独安排一致性采集窗口。
4. 在主机副本中识别 JSON/XML/SQLite/压缩文件/UnityFS 等格式；解码与静态 APK、IL2CPP 配置消费者对照。敏感账号凭据不写入知识文档。
5. 交付“字段—来源文件—消费者—场景—是否生效—缺口”表，而非只有导出文件夹。缓存存在只能证明已落盘，不能直接证明正在生效。
6. 输出覆盖矩阵：包内内容、下载目录条目、磁盘实有、可解码、已对位、运行时验证、仍缺失。对未下载、其他分组、仅内存和服务端内容分别标注。

原始采集建议落在 `D:\LibraryG\06-PRODUCT-ASSETS\<Product>\<ActualVersion>\05-Runtime\<Timestamp>\`，稳定结论回到产品文档。优先复用经源码复核的 common_tools 沙盒导出/差异能力；REA 负责可用的代码分析，Unity 专用工具负责资源解析。无需把采集全部塞进 REA MCP，也不以 Frida 为第一阶段前置条件。

首选验证案例是 Tile Kingdom 的 Tile Temple：已有明确缺失 Bundle 和待确认数值。若该活动在当前账号不可用，则选实际已开启的 Royal Match 或 Match Villains 活动。待用户指定目标应用/实例后再开展采集。
