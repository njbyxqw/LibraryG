# 活动配置与资源加载

**已取得实时响应：本机成功刷新后，服务器明确关闭Joy、开启Wonders；单改等级没有将它改为Joy。** 随后按用户授权从80跳到106，Wonders资源自动下载，第二次冷启动建立个人场次并实机进入棋盘。另确认一项本地排期差异：个人轮次105与包内排期一致，服务器窗口缓存却为77；客户端存在“排期表先于窗口缓存”的分支。不能把这几层合称为“全是旧包默认”，也不能用补下载素材替代活动选择。

## 加载链路与条件

以下原生地址来自原始2.7.3 **ARMv7** `libil2cpp.so`，不是当前ARM64运行地址。原主APK／数据分包与当前安装对应分包SHA256已对齐，但未新核对运行热更DLL。REA当前Ghidra未配置且Windows该入口不支持本ELF路线，使用现有Cpp2IL方法索引、Capstone 5.0.7及pyelftools检查原始指令；未解析的虚调用保留未知。

| 环节 | 方法／地址 | 已核对的事实与边界 |
|---|---|---|
| AutoP刷新入口及消费 | `M3NetMgr.LoginComplete` `0x33F971C`调用`NetGameMgr.ReceiveAutop`与`RequestSystemOpenState`；`M3NetAutopData.NetworkResultJsonData` `0x33E9804`在`0x33E9918`调用`M3AutopMgr.SetAutoP_Step` | 登录成功有正常刷新入口，本入口无关卡判断；现已取得80关刷新正文与成功末段。不是只有方法存在的证据。 |
| AutoP缓存 | `SetAutoP_Step` `0x33E9A0C`、`get_AutopJson` `0x33F6A20` | 更新路径解析JSON、访问既有AutoP与保存对象；80关响应开关与其后文件回读一致。106关只取得刷新后缓存值，来源证据等级分别保留。 |
| 表名回退 | `FileHashMgr.GetAutoPConfig` `0x343763C` | 调用`M3AutopMgr.GetAutoPJsonValue`，空值／`"null"`回到`GetDefaultConfig`。选默认名称与最终读包内文件不是同一个判断。 |
| 文件来源 | `ConfigLoader.ReadConfigTxtForName` `0x2D0BD78` | 允许远端配置、`FileHashMgr.IsUseRemoteConfig`通过且持久化文件可读时读持久化字节；否则走`ReadConfigTxtForName_PackageRes`。尚未截获当前Joy表的读取调用。 |
| 缓存适用性 | `FileHashMgr.IsUseRemoteConfig` `0x3436708` | 此路径比较持久化／包内配置版本及最小应用版本。不据此泛化所有DLC都不看玩家等级。 |
| Wonders门槛 | `MergeDM.GetUnlockLevel` `0x3412F80`、`GetUnlockActivityDay` `0x3412FD0` | 均取`AutoPMerge.get_merge_start`，分别返回Start对象偏移`0x10`／`0x14`的level／day，与缓存106／1对位。 |
| 活动资格 | `ActivityDM.UnlockBaseCheck` `0x305F860` | 开关、等级、活跃天数和Bundle是分别检查的项目；按调用传入的条件标志执行，Bundle路径调用`BundleDM.HasBundle`。改单个等级不能自动越过关闭的总开关。 |
| 下载编排 | `BundleDownloadOrchestrator.<CheckDownloadGameBundles>d__7.MoveNext` `0x31EA734` | 读取Bundle配置／模型，跳过`BdDms.invalid!=0`，再分本体／热更模型路径。具体虚调用条件尚未完整恢复，不能给出已验证的Joy DLC触发关卡。 |

当前应分别验收：**表是否下载 → 活动开关／场次是否选中 → 资源满足且实际进入玩法**。本样本有Joy新表，但Joy未选中；Wonders则已完成资源下载和进入棋盘。不能用某一层替代其他层。

## 排期表与服务器窗口的优先关系

`ActivityHelper.GetSystemOpenItem(acType,cannotNull=true,checkScheduleConfig=true,targetTime=null)`，ARMv7 RVA`0x3146534`：

1. `checkScheduleConfig=true`时先取排期Provider，调用`ActivityPlanConfigProvider.ToOpenItem`；返回非空便在`0x31466C8`分支直接返回。
2. 仅当不查排期或排期返回空时，才在`0x31466EC`以后读取`M3NetGameData.openInfo`。
3. `BaseActivity.GetActivityRound` `0x3149494`传入`checkScheduleConfig=true`；`GetCurRoundOpenItem` `0x3149044`也存在该调用路径。

本包Wonders排期锚点为2024-11-25 16:00至12-02 15:29:59（UTC+8），`interval=1801`，开场间隔7天；2026-11-24计算得到第105轮，窗口11/23 16:00至11/30 15:29:59。106关第二次启动后的个人场次与此完全一致；同批SystemOpen缓存仍是第77轮、11/16开始。因此**缓存有服务端窗口不等于玩法当前采用该轮次**。

这是同版本ARMv7消费者分支与ARM64现场结果的对位；未现场挂接该Helper，不能声称捕获了它的实际入参。模板`netTimeOpen=true`也不能单独推翻上述取值顺序。用户对“本地默认”的观察在轮次层面有依据，但不能据此把已证实的服务器AutoP开关也归为包内默认。

## 原因仍待区分

### 正常取得Joy下发的路径

当前可验证的客户端入口是正常登录／重连后调用`ReceiveAutop`。`M3NetAutopData.Body`仅声明`autop_replace_ilot_batch`与`no_ser`，继承基础请求的`user_id`；发送器会在未指定用户时补当前UID。构建时固定写50和2，未取得任何可以在此请求指定Joy、期号或重选活动组的字段。对`Game.Scripts/M3`中相关命名的局部检索也未定位活动重选入口；这个阴性结论不覆盖隐藏后台或未分析代码。

因此，主动请求与服务器选择必须分别解决：刷新已能成功执行；要让响应变为Joy开启，仍需满足服务器选择器，或由开发方在服务端调整该测试账号的资格。不能把修改`autop_replace_ilot_batch`／`no_ser`当作已验证的强开或重新分组办法，服务端对这些参数的完整语义并未取得。

现有条件下，最有价值的正常对照是在**单独实例、与真机相同版本**中登录已正常开放Joy的账号，再记录真实响应。若Joy选择随账号迁移，可继续跟进该样本下载和消费；若仍关闭，再对位两端设备／地区／渠道等请求输入。账号、版本或设备哪个决定选择，当前均未确认；不能把该方案承诺为必定成功，也不能只复制本地UID就当作正常登录。

下发验收至少包含：本次响应`mergemini_on=true`；资格通过且Joy在组11实际被选中；配置表与Bundle确实被消费者采用；实机主题／场次与对照一致。直接修改本地开关属于另一种受控客户端实验，不能替代上述验收。本次只核查入口与请求结构，没有登录其他账号、改身份参数、改活动开关或发起构造请求。

| 候选原因 | 证据边界 | 最小补证 |
|---|---|---|
| 新号／设备／账号分组不同 | 与不同开关选择相容；没有服务端选择器或另一设备快照，未确认AB实验。 | 两端包版本、是否同账号、同时间AutoP和SystemOpen记录。 |
| 跳关后完全没有刷新 | 80关实时成功响应及末段已取得，此解释不成立。 | 正常成长可能另外影响服务端画像／分组，但本轮没有自然通关对照，不能扩大为已排除全部成长条件。 |
| DLC素材未满足 | Wonders已自动下载并进入棋盘，不能以普遍下载失败解释；Joy仍先被服务器开关关闭。 | 在Joy已开启且存在场次的样本上，才继续对位Joy所需Bundle与下载结果。 |

用户后续明确允许跳到所需关卡，本轮因此备份后只改80→106；没有强开Joy、换账号、清库、改时间或替换配置。为触发正常重连，短时中断本应用的正式服务器连接并返回桌面／恢复；早期一次选中另一条同应用后端连接，未触发目标刷新，后以运行时WebSocket对象验证目标。短时诊断日志标志已恢复0，Frida脚本已卸载、任务自有服务与27047转发已移除。**不能承诺再改若干存档字段就能取得真机同期Joy**；服务端分组原因仍无同账号／同版本真机对照。用户仅确认对照端为正常游玩的真机账号，未提供版本。
