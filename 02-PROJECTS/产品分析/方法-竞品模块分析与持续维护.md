# 竞品模块分析与持续维护

## 适用范围

用于竞品产品、模块、功能和活动的持续研究。范例为 [[02-PROJECTS/产品分析/Royal Match/活动/Lava Quest/README|Lava Quest]]；复用的是证据方法、分析维度和维护方式，不是它的七胜规则、路径、包名或数值。长期目标与队列见 [[02-PROJECTS/产品分析/任务-竞品调研体系建设与持续维护|长期任务]]。

## 从包体到运行内容的来源矩阵

| 来源 | 能回答什么 | 不能单独证明什么 |
|---|---|---|
| APK/XAPK、安装分包、原生程序集与元数据 | 包内兜底、类型、协议、消费者和调用链 | 当前账号采用的远端覆盖、代码分支已启用 |
| 应用运行后的私有存储/SQLite/偏好 | 已落盘的配置、活动实例、状态、实验相关值 | 值仍有效、读取时已生效、全体账号都使用它 |
| 下载目录与缓存 Bundle | 包外图片、音频、Prefab、动效及局部引用 | 完整服务端资源、该资源一定在当前界面触发 |
| 自然操作前后的状态/日志/画面 | 触发、时间、数据差分和体验对应 | 单样本足以代表全量分布或证明因果 |
| 官方说明 | 对外玩法与体验口径 | 内部权重、服务端策略、AB 实现 |

当前已验证 Android Root MuMu＋Unity/IL2CPP 路线；其他平台或格式先评估可读性与工具能力，不宣称自动通用。REA 是可用工具之一，方法不依赖某个会话必须提供 REA MCP；本次 Windows 实际采用 ADB、SQLite、UnityPy 与 Cpp2IL。既有静态工具指南继续作为专项入口。

## 分析流程

1. **问题与清单定位**：从产品 MOC 和功能清单选定模块，读取已有正文，列明此次要解释的行为、配置、资源或策略。
2. **识别样本**：记录包来源、版本、哈希、安装版本/分包、设备、采集时间与游戏状态。包体和运行版本不一致时分开保留，逐字段/方法建立对应关系，不混写成一个已验证版本。
3. **定向采集**：先列目录和数据库结构，再取必要配置、状态和资源；保持字段白名单与最小数据范围。记录非原子快照、过期实例和解码失败，不以 Root 权限替代证据。
4. **内容解析**：解析 Bundle、SQLite、位域与配置对象，保存原件、输出清单、对象 ID、哈希和错误。重名资源用 Bundle＋对象 ID 区分，不能只按名称覆盖导出。
5. **代码对位**：从字段消费者、触发入口、持久化及协议反查实现；类型/方法名是线索，实际控制流与返回值才是行为证据。反编译不完整时核对原始指令，保留无法解析的间接调用边界。
6. **解释与核验**：按下表分析；需要确认生效、因果或到账时再补运行差分。无法取得的服务器逻辑明确保留未知。
7. **归位与导航**：先修订现有主题章节，再更新摘要、待验证项、MOC 状态、证据索引和 Daily；检查新增链接与历史状态。

## 模块正文的主题维度

按模块特点选用，未知项标缺口；不强行套用无关章节。

| 主题 | 要解释的内容 |
|---|---|
| 定位与体验 | 玩家目标、入口、完整体验链、与主循环的关系 |
| 资格与触发 | 解锁、档期、入组参数、互斥、重试、提醒与优先级 |
| 状态和异常 | 胜负/进度、保存恢复、退出、超时、重复结算 |
| 配置与覆盖 | 包内兜底、远端缓存、版本、解析模型、实际消费者 |
| 数值与策略 | 奖励、人数/机器人、概率、保底、AB、人群、计时与商业化；不局限于局内 DDA |
| 关联机制 | 连胜/失败引起的其他系统变化；区分共同响应与直接因果 |
| 图片/动效/音效 | 资源 → Prefab/组件 → 控制逻辑 → 触发条件 → 表现；库存与已对位资源分开 |
| 来源与验证 | 样本身份、精确方法/路径、推导、运行观测、未知和反证 |

## 调控判断的检查规则

- 区分模拟人数、展示抽样与真实胜率；Random 调用不自动等于胜负控制。
- 区分单局阶段、跨局连胜、同关重试、账号历史与活动轮次，明确每个计数何时增加/清零。
- 顺着“输入 → 条件 → 修改目标 → 消费者”检查是否确实有作用；Lava 中 ShouldRemoveOneMove 最终恒 false，说明仅凭方法名或 AB 调用会误判。
- 负面结论限定为已检查路径中未发现，不写成全游戏不存在；客户端不能恢复从未下发的全部服务端配置或策略。
- 数值公式、保存标记、库存实际到账是不同证据层；观察到相关变化不自动得出服务端针对玩家调控的结论。

## 档案与持续修订

### 从研究到本地复刻的注意事项

2026-10-29 Royal Match实践补充；下列是方法约束，具体机制仍以各模块证据为准。

| 易混淆项 | 维护方式 |
|---|---|
| 资源库存与当前入口 | 缓存存在不代表当前显示/可参加；首页以实拍入口为基准，缓存项另进配置/排期目录 |
| 排期记录与推测 | 正常现实时间下连续记录采样时间、期ID、明确截止；相邻期截止可支持周期候选，不能单独证明精确开始或零间隔复开；公共/个人/预告字段分开 |
| 原图导出与视觉还原 | 核对Prefab和运行时相机、父变换、嵌套排序、遮罩、字体参数；同状态截图对照，不以资源数量或浏览器无报错作为视觉完成标准 |
| 占位与内容闭环 | 允许先占位名称/期限/入口，再补内容；分别记录资源取得、代码核对、页面接入、本地检查、实机对照，不能合并为一个“完成” |
| 实机接管与画面变化 | 每次点击后读新截图，用户也可能在操作；遇意外画面暂停旧坐标导航；截图名称应如实反映内容，不把过渡/关卡画面当目标页 |
| 分阶段维护 | 长期总任务负责目标与队列，子任务负责阶段目标/依赖/退出标准，模块正文负责机制；下一批工作保持具体、可验收，不让多份计划各自成为当前源 |

模块可以用一份主文档起步；内容足够多时，采用 Lava 的结构：README 简介/路由、逻辑与配置主文档、资源与表现专题、证据与验证。功能可使用更贴切的标题，不强制全部建四份文件。版本不同但逻辑一致时保留映射；有实质差异时保留各版本基线。

**每次深化先判断对已有章节的影响。** 新证据可能补全章节，也可能推翻旧结论、合并重复主题或要求重排全文。当前文档应可独立阅读，无需按调查顺序拼接理解；不新增“第二轮/第三轮深挖”等尾章。只有独立、稳定且有复用价值的专题才拆文档。

历史调查快照仅供追溯，不作为并列当前版本。MOC 采用完整 vault 路径与明确显示名；下级回链产品入口，证据回链结论，长期任务回链总 MOC。方法扩展回写本文，产品事实回写模块，过程写 Daily，不跨层复制同一段正文。
