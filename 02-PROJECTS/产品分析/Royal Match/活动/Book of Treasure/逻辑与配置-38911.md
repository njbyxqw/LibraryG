# Book of Treasure：数值与分层配置

本次为初步分析，依据设备-1的38911运行配置与同版原生代码；不代表39781已复核，不代表全部服务器人群。返回 [[02-PROJECTS/产品分析/Royal Match/活动/_MOC|活动 MOC]]。

## 定位与当前样本

Book of Treasure属于Madness通用收集活动，协议`MadnessEventType.Book=3`，本机App.Madness记录类型3、事件717。`GetCollectMatchType`在Book分支返回3，对应Red；目标表中的t是阶段收集目标，不是关卡数或金币消耗。MadnessManager声明解锁常量28，完整解锁/互斥条件本轮未逐项实测。

10-28设备-1当前为81关（此前用户要求改为79关，之后再次采样已81；变化来源未作推断，本轮保留81）。两套配置均为2203版，各25阶段。校准时钟下当前截止约北京时间10-30 16点；这是剩余时间换算结果，不含开始时间，也不能证明本期总长。

## 分层与切换条件

### 两套目标表：超级光球解锁条件

`MadnessManager.GetShouldUseConfig2`的原始ARM64控制流为：用户等级达到`SuperBoosterManager.GetSuperBoosterUnlockLevel(HasShowedTutorial)`，且Config2已创建，才返回true。判断的是解锁门槛与配置存在，不是“当前已激活超级光球”，也没有在该选择器中直接按付费金额、失败次数或随机数选表。

解锁等级并非全体固定值：已看过主体教程走92；未看过则受SLB实验组和标签教程状态影响，默认292。使用Capstone校正Cpp2IL的ADRP显示后，直接从ELF读取两张整数表：

| 内部SLB组值 | 标签教程已看、主体未看 | 标签教程未看、主体未看 |
|---|---:|---:|
| 1 | 101 | 292（默认） |
| 2 | 101 | 301 |
| 3 | 101 | 201 |
| 4 | 101 | 101 |
| 5 | 292 | 292 |
| 6 | 101 | 101 |
| 7 | 101 | 101 |
| 8 | 101 | 201 |
| 其他 | 292（默认） | 292（默认） |

组值来自`SetAbValues`，涉及SLB历史组保存、当前AB项；`GetSlbLevelChangeAbGroup`可读取226/227、203/204并映射部分组值。这里列的是客户端选择规则，不是服务器分组人口比例或分群算法。后续运营配置归集已读到测试号AB226原值4，按本版helper映射入口为内部8；SetAbValues最终采用的历史组/教程状态仍需核对，81低于上述最小门槛。详见[[02-PROJECTS/产品分析/Royal Match/运营配置/分层与AB实验|AB对照]]。

### 当前阶段保留原档位

`GetSelectedConfigForStep`优先使用阶段运行缓存；当前阶段首次初始化时保存是否用Config2，以后读取保存标记；其他阶段可按当前资格选表。`LiveOpsCommonUse1`第40位表示当前阶段配置已初始化，第41位表示使用Config2。本轮补取后的实读为第40位1、第41位0，支持当前阶段用Config1。

因此，改等级跨过门槛不能只看当前奖励条是否立刻变长；应分别检查当前阶段保存位、后续阶段选择与阶段切换。切换高目标表并不要求服务器只发一套：两套可以同时在本地。

### 奖励覆盖层

- `SelectedSteps`另有Butler倍率AB分支，仅AB满足且`butlerMultiplierAbSteps`非空时使用；当前两套该数组均为空，未发现此样本的第三套目标表。
- `multiplierTokenOverride`两套相同：阶段4为`2xT×5`；8、12、17、20为`2xT×10`。它们的t=0是覆盖记录，不能作为阶段目标0。
- `TryReplaceWithMultiplierToken`受`MultiplierTokenManager.ShouldGiveTokenReward`控制，按阶段寻找覆盖并保留原阶段目标，另有fallback；不是无条件把所有奖励替换成代币。本轮未验证具体时长单位和最终到账。
- `GetStepInfo`还经过`GetOverridenRewardStep`/EventRewardOverrider，故基础JSON不等于所有账号最终奖励。该覆盖链的全部分群与卡包条件待后续专项核对。

本轮没有证据说明Book存在额外的机器人胜率或随机概率分层；已确认的是目标表选择、AB入口和奖励覆盖。未读取服务器内部概率，不能据此宣称不存在其他调控。

## 配置下发与前端修改实验

协议`MadnessEventInfo`包含Id、Type、RemainingTime、ConfigVersion、Config1、Config2；PingRequest包含MadnessEventVersion。客户端`UpdateConfig/UpdateConfig2`把正文解析后存入用户KeyValue的MadnessConfig/MadnessConfig2。

修改79关之前保留的2关数据库里，两套2203配置已经存在，且与本次81关正文完全一致。因此本例获取两套目标表不需要先提升关卡，提升关卡主要改变客户端资格/选择，不能把“后来读到”当成“后来首次下发”。

本轮另做版本失效对照：停游戏、备份指定键，只把两份JSON中的version改0，保留目标、奖励与同步标志。恢复正常启动后10/20/30秒均回到2203版；测试标记已由游戏替换，无需回滚。结合协议支持正常版本检查补取路径，但本轮没有Book离线对照/解密响应，不能把恢复单独视为已证明服务器重发正文。此前Ancient的40秒离线/在线实验有更强网络依赖证据。

**可行边界**：可以利用正常客户端的资格与版本检查观察它收到的配置；不能由改关卡/版本/时钟推导出任意未来活动、所有分群或完整服务器配置。制造本地JSON只会产生人工样本，必须与实际补回内容区分。

同日22:33扩展到模拟11-02 16:10再次将两表版本置0：12秒后首个在线采样已恢复2203/2203，后续两次相同，事件仍717，两套正文与正常时间原配置一致。补取后恢复真实时间，无遗留0版本。此结果没有显示“客户端进入下周就能补到下周Book配置”；仍保留缺少直接响应的边界。

## 时间与排期：设备时间对照

10-28设备-1临时关闭自动校时、将本机时钟前移48小时至10-30，正常启动观测30秒后恢复真实时间与自动校时1。没有更改事件ID、领奖或活动进度，关卡保持81，原设备保持关闭。

| 观察对象 | 前移48小时后的结果 | 可支持的判断 |
|---|---|---|
| Ancient | 仍316期；推算截止由10-29约16点移至10-31约16点；剩余约19.1小时持续递减 | 截止由本地时间与剩余量换算，不能据日期变化认定换期 |
| Book | 仍717期；推算截止同样后移48小时 | 没有因模拟周五取得新Book事件 |
| Lava | 活动ID/配置/期限仍缺失 | 本地日期为周五不足以使服务器下发有效Lava期 |
| UpcomingEvents | 仍只含TeamTournamentStartDate=1793347260000 | 这是团队锦标赛日期，不可套给Lava/Ancient |

恢复后的Ancient截止1793260800150（北京时间10-29 16:00:00.150），Book截止1793347200149（10-30 16:00:00.149）；时钟与自动校时核验通过。Ancient剩余量从约19.1069小时自然减至19.0939小时，没有增加两天。

原生`AncientAdventureManager.UpdateInfo`、`MadnessManager.UpdateInfo`都使用`TimeUtil.CurrentLocalTimeInMs()+RemainingTime`形成截止。通用TimeHelper虽存在服务器校时机制，不能把它笼统套为所有活动直接使用服务器绝对时间。当前实验未解密响应，也未在真实跨期瞬间抓样本。

扩展的四日期离线/联网矩阵中，Book一直717期；离线保留已有截止，联网后随假时间换算，恢复后回到10-30约16点。其他活动出现用户配置版本清零及集卡公共缓存清空，说明改时间并非无副作用；公共集卡缓存已用备份定向恢复，未伪造用户参与进度。本轮开始/结束均82关，未主动改关卡。详细矩阵、恢复边界及新增零值键判读见 [[02-PROJECTS/产品分析/Royal Match/运营配置/排期与配置总览#改设备时间能否补出其他排期|排期总览]]；本机证据为设备-1`schedule-probe-local/`、`schedule-refetch/`。

Lava/Ancient排期结论回写各自原周期章节：周一至周四/周五至周日仍为用户观察；每天16点附近截止有样本支持，完整周历、下一期开始和复开间隔尚未取得。
