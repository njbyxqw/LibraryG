# 任务产出入库与维护规范

> 本规范定义以后任务记录、项目文档、规范、报告和复盘如何进入 LibraryG。目标是让知识可追溯、可检索、可维护，而不是只在对话里短暂存在。

---

## 核心原则

| 原则 | 规则 |
|---|---|
| LG 唯一源 | LG 是唯一知识库与规范源；TS / MT 是项目执行空间和事实来源，必须同步并遵守 LG 最新规范。 |
| 项目 Docs 默认只读 | TS / MT 的 `Docs/`、`Docs/Knowledge/` 和源码旁 Markdown 必须可读、可检索以取得项目事实；除用户明确要求团队交付/评审外，不写入个人任务档案、Daily、MOC、规范或执行记录。 |
| 入口稳定 | 查知识库先从 `HOME.md`、`工作空间总纲.md`、`Memory.md`、项目 `_MOC.md` 逐级进入，不默认全盘搜索。 |
| 先定归属 | 任何产出入库前，先判断它属于 Daily、项目目录、通用知识、工作流规范、模板还是归档。 |
| 过程和结论分离 | 持续任务档案记录背景、设计、进度、决策与最终方案；DAILY 只做当日备份索引；稳定文档存放可复用内容。 |
| 来源可追溯 | 文档必须说明来源：代码、规范、用户确认、历史记录、对话整理、外部资料或待验证推断。 |
| 状态要诚实 | 未确认内容标为建议或待确认，不写成正式规则。旧内容优先标状态，不直接删除。 |
| 导航必须更新 | 稳定文档入库后，必须挂到对应 MOC、索引或入口文档。 |
| 小步维护 | 批量重排、删除、移动、覆盖、git commit/push 都需要用户明确确认。 |

## 入库路径判断

| 产出类型 | 首选位置 | 何时使用 |
|---|---|---|
| 持续项目任务 | `02-PROJECTS/<项目>/<领域>/任务-<主题>.md` | 预计跨天推进、需要持续追踪背景/设计/进度/实现/验证的任务；该文档是唯一主线。 |
| 活索引 / 快速查找 | `02-PROJECTS/<项目>/参考/`、`工具/` 或已有专题索引 | 需要边查边补、长期作为入口使用的路径表、资源表、快速定位索引。 |
| 每日工作记录 | `01-DAILY/YYYY-MM-DD.md` | 记录今天做了什么、结论、路径、踩坑、后续入口。 |
| 临时对话产物 | `00-INBOX/YYYY-MM-DD-主题/` | 仅用于需要跨回合保留、尚未分类的草稿、原始对比或附件；不是每次对话的必经路径。 |
| 项目文档 | `02-PROJECTS/<项目>/` | 属于 TileMatch、TileScape 或具体项目的分析、报告、规范、参考。 |
| Agent / 工作流规范 | `02-PROJECTS/Agent/工作流/` | 跨项目方法、入库规则、MOC 规则、日志规则、复现流程。 |
| 通用知识 | `03-KNOWLEDGE/<领域>/` | 跨项目已验证的共同机制、方法论，或源自单一项目但明显可迁移的 Unity / 编辑器 / 设计方法；必须标来源项目、适用范围、验证状态。 |
| 模板 | `04-TEMPLATES/` | 会反复使用的文档骨架或记录格式。 |
| 历史归档 | `05-ARCHIVE/` 或项目内归档区 | 已过期但有追溯价值的材料。 |

> [!note] 通用知识边界
> `03-KNOWLEDGE` 是可迁移知识层，不是项目文档的副本。源自单一项目但明显可迁移的 Unity / 编辑器 / 设计方法允许入库，但必须标来源项目、适用范围、验证状态，并回链项目事实；单项目专属的类、路径、配置值、功能实现与任务进度不入 Knowledge。详见 [[03-KNOWLEDGE/_MOC|通用知识 MOC]]。

## 三类任务对话的产出规则

| 类型 | 判断 | 主载体 | DAILY 与其他材料 |
|---|---|---|---|
| 持续项目任务 | 如 DLC、功能重构、跨日设计/实现，后续会反复进入且需要跟踪状态。 | 在对应项目领域直接创建 `任务-<主题>.md`，持续迭代背景、范围、进度、方案、讨论结论、实现、验证和后续。文档变长后可拆设计/实施/审计子文档，但任务文档始终做入口。 | DAILY 只追加当天摘要、变更与任务文档链接；零碎讨论、相关结论优先回写任务档案或其子文档。 |
| 活索引 / 快速查找 | 如路径速查、资源替换、配置入口；既是沉淀又是工作时直接使用的入口。 | 直接维护已有索引或对应专题索引，按条目追加来源、定位、适用范围和易混淆点。 | 只有本次查找形成可复用条目或重要判断时才记 Daily；不为每条查找创建独立任务档案。 |
| 零碎临时任务 | 一次性问答、小修改、临时排查，暂不确定是否值得长期保存。 | 默认留在对话；需要跨回合保留时才进 INBOX。 | 用户要求整理、后续发现可复用，或与前两类任务关联时，再升级为任务档案内容或索引条目；否则不强行入库。 |

> [!important]
> 代码、配置、资源和运行产物仍留在 TS / MT 仓库。持续任务一旦形成可复用结论，应当日直接写入 LG 对应项目路径，而不是等“以后统一整理”；LG 记录入口、设计和结论，不复制项目源码或与仓库绑定的活文档正文。TS / MT 内的规则、AI 记忆和源码旁文档只作执行上下文，不能作为独立规范源。

> [!note] 本机项目桥接
> 当前用户的个人 AI 流程以 LG 为唯一规范源，但不修改 TS / MT 团队规则或 Docs 来复制该流程。项目 Docs 默认只读、可检索；本机读取与写入边界见 [[规范-本机项目执行与LG知识库桥接|本机项目执行与 LG 知识库桥接规范]]。

## 对话整理触发与去重

当用户提出“整理近期对话”“整理对话”“归档本次查找”“沉淀定位结论”或同等意思时，按以下规则处理：

1. 先对照已有任务档案、活索引和当日 Daily；已存在且没有新增结论的内容不重复记录。
2. 提取的对象必须是已验证的路径、实际引用、配置/字段含义、资源替换入口、兼容性影响、用户确认的工作流规则，或明确标记为 `待验证` 的未决项。
3. 持续任务的新增结论回写对应 `任务-<主题>.md`；路径、多语言、配置和资源查找回写项目活索引；一次性内容仅在具备复用价值或用户明确要求时入库。
4. 只在本次形成可复用条目、重要决策或稳定文档更新时，补当日 Daily 摘要和入口；不为每条普通查询单独建文档。
5. 对话中的技术判断必须保留“静态检索 / 用户确认 / 待运行时验证”等依据边界，不把未验证推断写成代码事实。

`archive-lookup-findings` 个人全局 skill 可协助执行此流程，但本规范和 LG 中的项目索引才是长期的单一知识来源。

## 入库流程

1. **定位入口**：从 `HOME.md`、`Memory.md` 或项目 `_MOC.md` 找到目标项目和目录。
2. **先判任务形态**：持续任务、活索引还是零碎临时任务；不要把跨日任务拆散到 Daily 或 INBOX。
3. **判断产出类型**：确定产物是日志、规范、分析、报告、参考、模板、复盘还是临时草稿。
4. **选择路径**：按“入库路径判断”表放到最小合适目录。
5. **补齐元信息**：写 frontmatter，至少包含标题、日期、类型、状态、标签；项目内文档按项目规范补 `cat_order`。
6. **标注来源状态**：明确“已确认规则 / 建议 / 待确认 / 来源与版本”，避免把聊天推断写成事实。
7. **更新导航**：新增稳定文档后更新对应 `_MOC.md`、专题 MOC、顺序索引或 HOME 高价值入口。
8. **记录 DAILY**：当日 Daily 追加产出摘要、保存路径、关键结论和后续入口；持续任务的完整进展写回任务档案。
9. **轻量核查**：检查链接是否能从 MOC 走到文档，文档末尾是否有 `## 关联`。

## AI 读取 LG 稳定协议

| 步骤 | 规则 |
|---|---|
| 1. 固定入口 | 先读 `AGENTS.md`、`HOME.md`、`工作空间总纲.md`、`02-PROJECTS/Agent/Memory.md`。 |
| 2. 判断任务域 | 明确任务属于 LG 工作流、TileMatch、TileScape、跨项目、Daily/INBOX、通用知识还是代码任务。 |
| 3. 进入 MOC | 按任务域进入对应项目 `_MOC.md` 或 Agent 工作流规范。 |
| 4. 读取稳定规范 | 涉及入库、MOC、Daily、INBOX、多项目复现时，必须读对应规范。 |
| 5. 局部检索 | 只在已定位目录内检索；找不到再沿 MOC 上一级扩大范围。 |
| 6. 避免盲搜 | 不默认全盘搜索；只有用户要求或入口失效时才扩大到全库。 |
| 7. 标注依据 | 回答、改文档、归档时说明依据文件和状态。 |
| 8. 入库收尾 | 任务结束时更新 Daily、MOC 和必要索引。 |
| 9. 同步项目 | 涉及 TS / MT 的任务，项目内执行规则只作为局部约束；稳定结论和规范更新必须同步回 LG。 |

## 文档状态

| 状态 | 含义 | 使用规则 |
|---|---|---|
| `finalized` / `current` | 当前可作为执行依据 | 只用于已确认、结构完整、来源清楚的规则或文档。 |
| `draft` | 草稿 | 内容还在形成中，不作为最终规则。 |
| `needs-review` | 待确认 | 可能有用，但来源、时效或准确性未确认。 |
| `historical` | 历史记录 | 保留追溯价值，不一定适用于当前环境。 |
| `deprecated` | 已废弃 | 明确不再作为执行依据。 |

> TileMatch 目录内的 `status` 仍按其分类标准使用；跨 Agent 工作流文档可增加 `lifecycle` 表达当前可用性。

## 来源标注标准

| 来源类型 | 写法 |
|---|---|
| 已有规范 | 写明文件名、状态、日期或版本。 |
| 代码事实 | 写明项目路径、关键文件、必要时写 commit 或分支。 |
| 用户确认 | 写明确认日期和确认内容摘要。 |
| 对话整理 | 标为“对话整理”，只作为记录；未经确认不得升为正式规则。 |
| 历史资料 | 标为 `historical` 或在正文顶部写当前适用性。 |
| 推断 / 建议 | 明确写“建议”“待验证”或“待确认”。 |

## MOC 与索引维护

- `HOME.md` 只登记全库主入口、高价值入口和跨项目工作流，不承载大量正文。
- 项目 `_MOC.md` 负责项目内模块导航；新增项目文档后应在对应模块补入口。
- 专题 MOC 负责专题入口，文件名或 alias 必须唯一可路由。
- 顺序索引用于排序和静态备份，不替代 MOC。
- 跨项目链接优先写 vault-root 完整路径，避免同名 `_MOC.md` 误入。

## DAILY 记录要求

每次任务结束或形成稳定产物时，当日 Daily 至少记录：

| 项目 | 内容 |
|---|---|
| 做了什么 | 一句话说明任务内容。 |
| 关键结论 | 明确结论、决策或状态。 |
| 产出文档 | 写入库路径和文档名。 |
| 来源依据 | 说明依据来自代码、规范、用户确认还是对话整理。 |
| 后续入口 | 给出下次继续时应打开的文档或 MOC。 |

## 任务结束硬门槛

有代码阅读、逻辑分析、实现、调研、方案或新资料整理的任务，在回复完成前必须逐项检查：

| 检查项 | 规则 |
|---|---|
| 任务入口 | 已按任务域读取对应 MOC、项目规则和必要的稳定索引；不能只根据对话摘要判断。 |
| DAILY | 已更新当日 Daily 的对应项目节；无稳定结论也要记录定位范围与未确认项。 |
| 游戏逻辑 | 新确认的机制、规则、ECA、DDA、状态机、行为链路进入对应项目 `游戏逻辑/`，并挂到专题 MOC。 |
| 代码定位 | 新确认的程序集、文件路径、调用链、加载链路、配置入口进入 LG 项目 `代码框架/`、`参考/`；TS `Docs/Knowledge/CodeMap.md` 可同步作执行索引，但不能作为唯一长期来源。 |
| 导航 | 新建稳定文档必须从项目 `_MOC.md`、专题索引或 CodeMap 到达；跨项目文档使用完整 vault 路径。 |
| 证据边界 | 标明代码事实、用户确认、对话整理、静态审计或未验证推断；不得将团队提交自动记为个人工作。 |

> [!warning] 不可跳过
> “没有写新代码”不是跳过入库的理由。只要形成了可复用的代码位置、行为结论、排查路径或资料索引，就应按上表判断是否需要沉淀。

---

## 禁止事项

- 不默认全盘搜索知识库；只有逐级入口找不到且有必要时，才在已定位范围内扩大检索。
- 不把未确认聊天内容写成正式规则。
- 不让稳定产物长期留在 INBOX。
- 不新增文档后忘记更新 MOC 或 Daily。
- 不批量删除历史材料；先标状态，再逐步归档。
- 不自动 commit / push。

---

## 维护节奏

| 节奏 | 内容 |
|---|---|
| 每次任务结束 | 更新 DAILY，确认稳定产物是否已入库并挂入口。 |
| 每次新增稳定文档 | 更新 MOC / 索引 / 关联章节。 |
| 每周或阶段结束 | 检查 INBOX 是否有残留、MOC 是否漏挂、待确认项是否可推进。 |
| 大规模整理前 | 先列清单和风险，等待用户确认后再移动、覆盖或删除。 |
