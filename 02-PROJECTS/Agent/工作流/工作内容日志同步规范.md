# 工作内容日志同步规范

> 当前定位：共用 Daily 的命名、内容与合并规则。LG 内容和维护方案共用，设备标签只区分日志来源，不拆分知识库或维护体系。日常入库边界以 [[02-PROJECTS/Agent/工作流/规范-任务产出入库与维护|任务产出入库与维护规范]] 为准。

## 核心原则与命名

- 业务日期统一按 `Asia/Shanghai`（UTC+08）确定，不使用执行环境的默认时区推定日期。
- 新工作记录写入 `01-DAILY/YYYY-MM-DD-mac.md` 或 `01-DAILY/YYYY-MM-DD-win.md`；各端只追加自己的源日志，同日多次任务写入同一文件。
- `01-DAILY/YYYY-MM-DD.md` 保留为共用当日总览，由既有维护自动化汇集；原始设备日志永久保留，不因合并删除、清空或替换。
- 历史无设备后缀日志保留原文，不批量迁移。不能可靠判定设备的既有条目保留为历史来源未区分，不根据路径、mtime 或猜测强拆。
- Daily 保留简明完整的工作条目与产物入口；完整研究、SQL、源码、资源仍留在对应产物文档或资源目录，不搬进日志。

## 记录时机与内容

任务形成稳定产物、重要决策或可复用定位时立即更新本机源日志；没有新增事实的普通问答不强行造记录。纯定位也应如实说明范围和未确认项。

统一条目使用五项，按需简写，但不能省去关键状态或验证限制：

```markdown
### 任务名称

- 工作：做了什么。
- 结论或状态：已完成部分、待确认部分；归档状态与业务状态分开。
- 产物链接：任务主档、稳定文档或关键路径。
- 验证边界：来源依据、版本和设备适用范围，已验证与未验证分别说明。
- 下一步：具体未决项及继续入口；无后续则明确写无。
```

两端严格共用同一模板与五项条目，仅文件名 mac/win 后缀区分来源。轻量元信息使用 `date`、`timezone: Asia/Shanghai`、`tags: [daily]`，不另加设备字段；日期由已确认的业务日期和文件名确定，不靠系统时区推定。模板见 [[04-TEMPLATES/tp-daily]]。

源日志设 `## 今日索引`，列任务状态与产物入口；随后按实际涉及项目设 `## 项目名`，任务使用三级标题。项目可为 TileMatch、TileScape、LibraryG、产品分析、Chuzzle 等，不硬性补齐三个空项目节。索引不重复展开正文。

## 当日总览：设备内容分别保留

总览保留今日索引，按 `## Mac`、`## Windows` 分区，各区内以 `### 项目名`、`#### 任务名称` 保留对应源日志的完整工作条目、验证边界及下一步，并回链到源日志。可去除重复排版和模板说明，不将多项工作压成一句话，不合并两端事实归属；同一任务在两端推进时分别保留增量并指向同一任务主档。

```markdown
## Mac

来源：[[01-DAILY/YYYY-MM-DD-mac]]
### 产品分析
#### 任务名称
- 工作：……
- 结论或状态：……
- 产物链接：……
- 验证边界：……
- 下一步：……

## Windows

来源：[[01-DAILY/YYYY-MM-DD-win]]
### TileScape
……
```

仅对实际取得的源文件建立有效回链。缺源时写“尚未取得该端源日志，不能判断是否有工作”，不造空源文件、不写“无工作”。只有源端明确记录无工作时才可转述。存在历史正文时原样保留于受管区块之外，说明历史设备来源未区分；避免复制历史条目到两端。

## 既有自动化合并约定

只扩展既有 `libraryg` 维护任务，不创建新调度、不启用休眠 WorkBuddy 方案，不改变原有频率、启用状态、通知偏好或 LG-only 边界。此规则落盘不代表实际自动化 prompt 已修改；修改配置前须回读现行定义并保留原有职责。

1. **一个总览写入端**：核实实际执行端及是否有任务副本，指定既有任务的一个执行端写总览；另一端只写自己的源日志。身份未核实或两个副本都可能写时，只报告冲突，不生成总览。本机文件锁不能充当跨设备锁。
2. **检查可取得的源**：读取当日及最近 7 个业务日的设备源日志和总览；另复查仍标缺源的日期，以及上次检查后新增或变化的更早源文件。按文件日期、来源内容和变更证据判断，不以文件存在或 mtime 单独判定完整同步。
3. **幂等更新**：每个设备使用唯一受管标记，例如 `<!-- daily-merge:2026-10-26:win:start -->` / `<!-- daily-merge:2026-10-26:win:end -->`；块内记录源相对路径、源字节 SHA-256 和最近生成内容的 SHA-256（后者计算时排除记录该哈希的元信息行）。输入未变且受管内容完整时不写；输入变化时只更新该设备受管区块，不整篇覆盖或重复追加。
4. **写前复核**：读取时保存源和目标字节摘要，落盘前再次核对；源/目标变化、标记不唯一或不完整、受管内容被人工改动、Git 冲突标记出现时停止该文件写入并报告。自动化每次只由单一执行实例写入；其他设备内容及受管区外正文原样保留。首次接管已有手写设备区块必须先核对，不用相似标题直接覆盖。
5. **迟到与缺源**：缺源或本地同步状态不明时不能标记完整合并。后续取得或修订源日志时重新核对相应日期；已合并不代表该日永远关闭。再次运行应得到相同内容，除真实新增证据外不产生重复条目。
6. **同步边界**：本地合并不负责跨设备传输；不自动 pull、commit、push。无法取得另一端最新版本时保留不完整状态，不猜测远端无新增。
7. **写后核对**：源日志未改变；设备区块和标记唯一；每项工作、结论或状态、产物链接、验证边界、下一步均有对应来源；报告已合并、待同步/待确认、冲突，沿用既有通知设置。

合并状态仅表示当前可读源版本已被汇集，不是全天工作完整性证明。元信息只服务重复检测与冲突保护，不要求每条日志增加任务 ID 等繁重字段。

## 产物与验证边界

- 持续任务与稳定结论直接维护既有任务主档或专题，Daily 记录当日增量和入口；INBOX 仅用于尚未分类、需要跨回合保留的材料，不强制经过 INBOX，也不自动清理或删除。
- 归档完成、导航可达不等于业务实现完成或运行验证通过；例如 SQL 未执行、静态结论未做运行差分，必须保留原状态。
- 原始安装包、采集数据、批量解包/导出和反编译材料保留在不入库的 `06-PRODUCT-ASSETS/`。报告选用的配图、图表、必要音频/动效示例等随附资源属于报告产物，应进入 `02-PROJECTS/<项目>/<专题>/` 下的配套资源子目录，由报告或资源索引记录来源、版本和相对路径，并纳入链接、存在性及 Git 跟踪/忽略状态维护。只有引用明确属于不共享原始材料且本机确实缺失时才标“本机不可核验”；报告附件缺失或仍在原始目录应登记归位/共享缺口，不得一概豁免。未核验跟踪状态不能声称已共享；不自动删链接、搬大量资源或复制资源进 Daily。详见 [[02-PROJECTS/产品分析/资源目录规范]]。
- 知识库内链接使用 vault 相对路径；本机外部路径应标设备，避免套用另一端绝对路径。跨项目结论保留必要的对位入口。

## 历史同步流程的适用性

旧项目 `.workbuddy/memory/` 日志、`inbox-organizer`、旧 WorkBuddy 同步脚本与自动化备份仅作历史来源，不作为当前执行器或默认日志源。休眠的 WorkBuddy 交接方案保持休眠；其单设备路径、旧日志命名和三项目要求不覆盖本规范。日常源日志直接写共用 LG 的对应设备文件。
