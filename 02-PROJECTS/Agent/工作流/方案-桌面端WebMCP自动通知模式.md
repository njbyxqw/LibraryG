# 桌面端 WebMCP 自动通知模式

> [!important] 当前调整（2026-09-17）
> WebMCP 不是 Chat → 本地 INBOX 的唯一通道。当前固定为“网站工具快捷通道 + 本机粘贴交接包保底通道”。这样即使普通 Chat 没有发现网站工具，也不会把临时预览文件误当作 LibraryG 任务卡。

## 当前规则

### 需求回归与验收（2026-09-17）

核心目标：普通 Chat 形成方案，用户明确要求后存入本机 `00-INBOX`，由可访问本机的执行端读取。理想操作为一句话自动交接；复制导入属于后备流程，不能作为自动化目标已达成的证明。

| 验收项 | 当前证据与状态 |
|---|---|
| 方案导入本地 | 已实测：从剪贴板读取带 JSON 代码块的测试方案，生成真实任务卡 |
| 执行端可读 | 当前本机 Codex 已读取生成文件，核对目标、换行、状态、下一步 |
| 固定交接格式 | 页面提供可复制的 Chat 说明，缺少工具时要求输出“待导入本地”，不得声称已写入 |
| 成功回执 | 页面显示完整绝对路径及执行端读取指令；只在服务返回成功后出现 |
| 普通 Chat 一句话自动写入 | 尚未通过；本机 Codex 代调 WebMCP 不等于普通 Chat 验收 |
| Work 读取 | 仅对能访问该本机目录的环境适用；远程执行环境未验证 |
| 重启后使用 | 当前服务需启动；未安装开机自启 |

本轮修复：代码块解析改为可直接测试的函数，验证实际输出的浏览器脚本；后端拒绝额外字段；同一页面请求进行中拒绝并发提交（不增加时间去重或频率上限）；修正 HTTP 测试日期写死。12 项测试通过；剪贴板按钮实测创建 [[00-INBOX/2026-09-17 - INBOX 完整交接验收]]。该测试包由 Codex 构造，不能算普通 Chat 已通过。

用户验收步骤：

1. 在 `http://127.0.0.1:38741/` 复制“给普通 Chat 的交接说明”到实际讨论方案的 Chat。
2. 说“整理进 INBOX”。若调用工具并收到完整本地路径，核查文件；若仅输出 JSON，则自动路径本次未通过，使用复制导入继续。
3. 导入后将页面“执行端读取指令”交给本机执行对话，核对方案内容；建卡本身不授权执行修改。

页面是否注册工具只证明当前页面能力。此前普通 Chat 的失败原因尚未定位，不能仅凭端口差异断言是打开测试页造成的。

用户明确说“整理进 INBOX”后，优先由助手调用唯一的 `create_inbox_task`；若当前 Chat 没有调用网站工具，则 Chat 输出同一字段的 JSON 任务交接包，用户在 Chat 点复制、回到本机收件页点一次“从剪贴板创建”。浏览器拒绝剪贴板访问时，才改为手动粘贴并点击创建。三条路径都调用同一个受限接口，直接原子新建 `00-INBOX/` 任务卡，页面显示非阻塞的“已创建：相对路径”通知。

```text
明确触发 → 结构化任务字段 → 网站工具或复制交接包 → 自动新建 INBOX 卡 → 页面通知结果
```

不再要求每张卡手动确认。

## 固定入口与保底通道

生产入口唯一固定为 `http://127.0.0.1:38741/`。历史 D1 探针改用 `38743`，只写系统临时目录；日常不应打开它。打开生产地址时页面标题必须是“LibraryG INBOX 收件器”，且说明必须是写入 `00-INBOX`，否则停止建卡并排查。

保底通道的 Chat 输出只应包含下列 JSON 字段。页面仅在用户点“从剪贴板创建”时读取一次剪贴板，不会后台监听、留存或上传其他剪贴板内容：

```json
{
  "title": "任务标题",
  "state": "方案",
  "target": "LG",
  "next_owner": "用户",
  "next_action": "下一步动作",
  "conclusion": "当前方案或结论"
}
```

可选字段仍为 `facts_to_verify`、`related_links`。本机页面允许粘贴裸 JSON 或 `json` 代码块；解析失败或字段不合规则零写入。粘贴入口不扩展任何文件读取、编辑、删除或路径选择能力。

## 用户可见总开关

生产页面始终显示：

- `自动建卡：已开启` / `已暂停`
- `暂停自动建卡` / `恢复自动建卡` 按钮

开关保存在 Git 忽略的 `.inbox-receiver/settings.json`，重启后保留。暂停时，工具调用失败且不写卡；恢复只能通过本机页面按钮完成。停止生产进程同样会停止后续建卡。

> [!warning] 边界
> “暂停”只能阻止后续写入，不能撤回已创建的卡。自动通知不是确认，也不应被表述为安全闸门。

## 保留与移除的规则

| 项目 | 当前决定 |
|---|---|
| 本机页面确认框 | 移除；改为写后通知。 |
| 跨重启 30 分钟去重 | 移除。统一对话中的更新方案可直接新建新卡。 |
| 新增频率上限 | 不做。用户明确触发是前提。 |
| 原子新建、永不覆盖 | 保留。 |
| 固定根目录 | 保留：仅 `00-INBOX/`。 |
| 唯一 WebMCP 工具 | 保留：仅 `create_inbox_task`。 |
| WebMCP 未被普通 Chat 发现 | 不阻塞：在 Chat 复制 JSON 交接包后，页面一键从剪贴板创建；权限受限时才手动粘贴。 |
| 测试与生产端口 | 不再并存：生产固定 `38741`；D1 探针为历史组件。 |
| 路径、读取、更新、删除、终端能力 | 不增加。 |

## 已实现与首次实测

生产组件已改为自动通知模式：设置模块、暂停/恢复页面按钮与服务端暂停检查均已完成。调整后 `npm test` 10/10 通过，其中包含“与粘贴交接包相同的受限字段可通过生产接口新建临时 INBOX”验证。生产入口已统一重启至 `38741`：新页面实测由粘贴交接包创建 [[00-INBOX/2026-09-17 - INBOX 粘贴交接通道试用|粘贴交接通道试用卡]]；暂停后再次粘贴创建被拒绝，随后恢复为开启。后续新增的一键剪贴板入口已在页面加载和静态边界测试中验证，待用户从普通 Chat 复制真实交接包后完成体验验收。

首张真实试用卡 [[00-INBOX/2026-09-17 - WebMCP 生产 INBOX 首次试用]] 保留，作为每卡确认版的历史试用记录。

## 日常试用观察点

连续使用 3–5 次后只评估：

1. 普通 Chat 是否能稳定发现并调用网站工具；不能时，交接包复制粘贴是否足够顺畅。
2. 明确触发词是否足以避免普通讨论误建卡。
3. 写后通知是否足够让用户发现问题并及时暂停。
4. 同一主题多张卡是否仍便于阅读与后续执行。

发现误建卡时，先点击暂停，再记录触发语境；不要直接扩展权限或增加自动删除。
