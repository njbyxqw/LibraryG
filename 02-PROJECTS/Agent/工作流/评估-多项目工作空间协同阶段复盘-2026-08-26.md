# 多项目工作空间协同阶段复盘

## 总体判断

过去一个月的工作空间协同设计已经从“文档整理”进入“可执行工作系统”阶段。当前结构能支持 AI 冷启动、项目路由、Daily 追踪、稳定结论入库和后续复盘。

主要有效点：

- `AGENTS.md`、`AI总MOC.md`、`Agent Memory` 形成了清晰冷启动链路。
- `LibraryG`、`TileScape`、`TileMatch` 的职责边界已经明确。
- TS 已经形成项目 MOC、快速定位索引、代码框架、游戏逻辑文档和 CodeMap 联动。
- Daily 从单纯日志升级为“过程、结论、来源、验证边界、后续入口”的追踪账。
- 自动巡检规则开始发挥作用，能明确区分“已补”“待确认”“无证据”。

主要不足：

- TS 实质进展多为需求辅助、静态审计、代码定位、局部实现和设计归档；其中只有进入交付、发布或高风险判断链路的事项才需要提升为运行时验证债。
- MT 近一个月更多作为历史基线，真实跨 MT / TS 对位文件表积累还少。
- WorkBuddy 交接仍停留在方案阶段，尚未完成小样本幂等试运行。
- 规范层已较完整，但执行成本偏高，长期需要防止每次任务收尾过重。

## 工作重心变化

| 空间 | 阶段表现 | 判断 |
|---|---|---|
| LG | 完成总入口、Memory、AI 总 MOC、入库规范、自动巡检、阶段看板 | 基础工作空间搭建基本完成，后续重点应转为维护质量和降低执行成本 |
| TS | 成为主要实质工作区，覆盖 DLC、Home、道具、活动、GM、资源定位等 | 知识沉淀速度明显提升；验证应按任务性质触发，不应默认变成高优先级管理负担 |
| MT | 主要提供历史行为、旧知识库、ML/Magnet 待验证任务 | 不应强行制造 MT 工作；有真实对照需求时再进入 |

## 设计效果

### 有效的设计

| 设计 | 实际效果 |
|---|---|
| LG 作为上层路由 | 避免 TS / MT 各自重复建一套长期记忆，AI 能先判断任务域再进入项目 |
| 项目不固定主次 | 避免因近期 TS 多而忽略 MT 历史基线；符合实际项目关系 |
| Daily 三项目分节 | 能记录“无新增结论”，防止 AI 用文件时间或团队提交虚构个人工作 |
| 产出入库规范 | TS 的快速定位、Home、道具、GM 等结论能从 MOC 到达 |
| 状态/来源/验证边界 | 有效区分静态审计、用户确认、已实施、未验证和设计讨论稿 |
| Agent Memory + AI 总 MOC | 冷启动更稳定，减少重复问路径和重复全库搜索 |

### 暴露的问题

| 问题 | 影响 | 处理建议 |
|---|---|---|
| 静态结论增长快，运行时验证慢 | 对交付类任务会影响功能可信度；对需求辅助类任务则只需要保留“未运行验证”边界 | 不建立默认高优先级验证队列；只对交付、发布、高风险或用户明确要求的事项收敛验收点 |
| 跨项目对位表不足 | MT/TS 同源复现能力还没有被充分验证 | 只在真实任务中积累，不做空表工程 |
| WorkBuddy 未进入试运行 | 自动巡检仍依赖 Codex/人工，闭环自动化收益未兑现 | 先做 `report_only`，再做单条 `daily_append + moc_append` |
| 入口较多 | 新 Agent 可能读完入口但仍不确定本次最小必读集 | 保持 `AI总MOC.md` 为唯一最短入口，不再继续增加同级入口 |
| 收尾规范偏重 | 小任务也可能被 Daily/MOC/入库拖慢 | 采用分级闭环：小任务只写 Daily，稳定结论才补专题/MOC |

## 近期工作事实摘要

### TileScape

TS 是 8 月的实质主线。已沉淀的主要领域：

- DLC 全影响审计、下载/章节门禁、Home DLC 与 Endless 最大关卡链路。
- 公共接口、通知、Reward/Item、音效与三子仓依赖审计。
- 风车 Shuffle 单组保底、四道具实际逻辑。
- Home 章节解锁镜头、Forest 云层推进、解锁动画时机。
- 活动 DLC 扩展框架讨论稿。
- GM 工具注册、面板执行、业务入口与动态关卡屏蔽开关。

当前边界：多数结论明确标注为静态代码审计或设计讨论。只有当这些结论要进入正式交付、发布判断、问题复盘或后续依赖决策时，才需要补 Unity、真机、CDN、Jenkins、资源 Manifest 等验证。

### TileMatch

MT 近一个月不是实质主线，主要作为：

- 旧逻辑与行为基线。
- 关卡难度 ML 与 Magnet 的待验证任务来源。
- TileMatch 既有知识库、工具、障碍、Rocket、打点和编辑器资料库。

当前风险：如果后续 TS 任务需要“行为等价”，必须回 MT 做对位核验；不能只按 TS 当前结构推断旧行为。

### LibraryG

LG 的阶段性成果最明确：

- 根入口：`AGENTS.md`、`AI总MOC.md`、`HOME.md`、`工作空间总纲.md`。
- 记忆：`02-PROJECTS/Agent/Memory.md`。
- 工作流规范：入库、MOC、Daily、INBOX、多项目复现、AI 注意事项、自动巡检。
- 近期看板：`01-DAILY/summaries/近期工作进度与待办-2026-08-20.md`。

当前风险：规范已经够用，继续增加规范文档的边际收益下降；更需要按真实任务降低摩擦，避免把辅助型工作升级成全链路交付流程。

## 阶段建议

### 1. 下阶段主目标从“搭建体系”切到“代码逻辑读取与知识沉淀”

LG 框架已经可用。后续不应继续扩充工作流规范，也不应默认建立高优先级验证队列。更合理的方式是：日常需求辅助以读取当前代码逻辑、定位入口、解释影响面、局部实现和知识沉淀为主；进入交付、发布、高风险功能或用户明确要求时，再补最小验收闭环。

优先沉淀的内容：

1. 当前代码入口、主调用链和 owner 模块。
2. 配置读取路径、运行时数据与可读备份的差异。
3. Prefab、图片、音效、Spine、locale key 等资源替换入口。
4. 业务规则、边界条件、异常分支和易误读点。
5. 与 MT 旧逻辑的同源、重构、缺失或产品差异。

需要主动验收的触发条件：

1. 用户明确说要验收、发布、上线、确认最终效果。
2. 功能涉及资源下载、配置生成、支付、存档、关卡加载、GM 开关等高影响面。
3. 当前结论会作为后续方案或代码修改的前置事实。
4. 用户反馈运行异常或效果不符合预期。

### 2. 保持 MT 为按需基线，不做主动大整理

MT 资料已经足够厚。除非 TS 任务需要旧行为对照，不建议再主动大规模整理 MT。

触发 MT 的合理条件：

- TS 行为与历史预期不一致。
- 需要迁移旧功能或复刻表现。
- 需要确认 ML、Magnet、道具、障碍等旧逻辑。
- 用户明确要求查旧项目。

### 3. 跨项目对位表只在真实任务中积累

对位表的价值在“真实用过”。不要预先为 MT/TS 做大而全映射。

每次跨项目任务只记录：

- 本次实际读到的 MT 文件；
- 本次实际读到的 TS 文件；
- 二者关系：同源、已重构、缺失、产品差异；
- 本次结论和验证边界。

### 4. 知识闭环分级执行

避免每个小任务都走完整入库链路。

| 任务级别 | 最小闭环 |
|---|---|
| 小定位 / 小问答 | Daily 一条即可，若无新增事实可不建专题 |
| 形成可复用路径或调用链 | Daily + 参考/代码框架/CodeMap |
| 形成游戏机制或行为结论 | Daily + 游戏逻辑专题 + MOC |
| 跨 MT/TS 复现 | Daily + 对位文件表 + 对应项目入口 |
| 工作流规则变化 | Agent 工作流文档 + AI 总 MOC |

### 5. WorkBuddy 交接只做低风险试运行

当前不建议直接启用完整自动化。先做三步：

1. `report_only`：只生成巡检报告，不写 Daily/MOC。
2. 单条 `daily_append`：验证重复执行时为 `already-applied`。
3. 单条 `moc_append`：只追加已确认入口，观察 7 天。

通过后再决定是否扩大范围。

## 下阶段优先级建议

| 优先级 | 工作类型 | 执行口径 |
|---|---|---|
| P0 | TS 当前代码逻辑读取与知识沉淀 | 围绕实际需求读代码，沉淀入口、调用链、配置、资源、边界和后续修改点 |
| P0 | 需求辅助与影响面判断 | 用户提出需求时，先给当前逻辑、可改位置、影响面和最小方案 |
| P1 | 局部实现与记录 | 按需求改代码；记录“已实现 / 待反馈 / 已反馈异常”，不强制验收表 |
| P1 | 高风险或交付型功能验收 | 仅在发布、上线、配置生成、下载、存档、GM 等场景给最小验收点 |
| P1 | 活动 DLC 设计收敛 | 活动名单、Loading 必要资源开关、版本切换、弹窗策略确定 |
| P2 | WorkBuddy 小样本 | 有自动化需求时再做 report_only 与幂等追加 |
| P2 | MT Magnet / ML | 只在有环境、数据或明确需求时推进，不挤占 TS 日常需求辅助 |

## 结论

多项目协同设计是有效的，尤其解决了三个核心问题：

1. AI 进入任务时知道先读哪里。
2. TS/MT 同源但不重复劳动。
3. 结论不会只留在聊天里。

当前最大的框架风险不在知识库结构，而在“把辅助型工作过度流程化”。下一阶段应减少新增规范，保持需求辅助的低摩擦；优先读取当前代码逻辑并沉淀可复用知识，只在交付、发布、高风险或用户明确要求时补运行时验收闭环，同时用真实任务积累 MT/TS 对位记录。
