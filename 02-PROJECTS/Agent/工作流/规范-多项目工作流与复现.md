# 多项目工作流与复现规范

> 当前有三个核心空间：MT、TS、LG。项目之间不固定主次，阶段性工作重心会随任务变化；近期 TS 工作会更多，但不意味着检索或判断时天然优先 TS。两边存在大量相同或同源代码，因此不要求所有内容在两边重复做；推荐在一边形成稳定方案和工作记录后，再用 LG 中的记录在另一边快速复现。

---

## 核心原则

- **按任务进入**：根据问题领域、索引和已有记录决定先读 MT、TS 或 LG，不预设项目主次。
- **一边做深，一边复现**：先在一个项目中形成方案、验证和记录，再在另一边按记录最小复现。
- **LG 沉淀**：基础、全面、纲领、规范、记忆、成功记录、备份追踪和复现步骤写入 LibraryG。
- **项目目录执行化**：项目内文档偏快速入口、模块梗概、任务索引和执行上下文；必要长文档可以留在项目内，再由 LG 建索引或沉淀总纲。
- **可复现**：每个中等以上任务尽量留下“背景、改动点、关键路径、验证方式、可复现步骤”。
- **保守整理**：旧路径、旧结论、失败记录和长文档可能有追溯价值；整理时先标注、索引、迁移，避免直接删减。

## 一次任务的标准闭环

| 阶段 | 要做什么 | 输出位置 |
|---|---|---|
| 1. 定位 | 明确任务属于哪个项目、是否需要跨项目对照、是否需要 LG 沉淀 | 对话中说明 |
| 2. 读上下文 | 读项目入口、模块文档、必要代码 | 不产生长期文档 |
| 3. 方案 | 写清假设、改动范围、验证标准 | 对话或 `00-INBOX/` |
| 4. 实施 | 按项目规则最小范围修改 | 对应代码仓库 |
| 5. 验证 | 编译、静态审查、测试、运行验收，按任务可行性选择 | 对话 + 工作记录 |
| 6. 沉淀 | 记录成功路径、踩坑、可复现步骤 | LG 项目文档或 DAILY |
| 7. 复现 | 如另一边需要同步，按沉淀记录做最小复现 | 对应代码仓库 + LG 记录 |

## 工作记录模板

中等以上任务完成后，推荐在 LG 中保留如下结构：

```markdown
## 背景

为什么做，关联 TS/MT 哪一侧。

## 结论

最终采用什么方案，一句话说明原因。

## 关键路径

- TS 文件：
- MT 对位文件：
- LG 参考文档：

## 实施记录

- 改了什么：
- 没改什么：
- 和另一侧的差异：

## 验证

- 已验证：
- 未验证：
- 后续复现注意：
```

## 对位文件表

跨 MT / TS 的任务必须尽量留下对位文件表。它不要求一次覆盖全模块，只记录本次真实用到的文件，后续逐步积累。

```markdown
| 领域 | MT 文件 | TS 文件 | 关系 | 本次结论 |
|---|---|---|---|---|
| 入口 | `...` | `...` | 同源 / 已重构 / 缺失 / 产品差异 |  |
| 配置 | `...` | `...` | 同源 / 已重构 / 缺失 / 产品差异 |  |
| UI | `...` | `...` | 同源 / 已重构 / 缺失 / 产品差异 |  |
```

关系字段建议：

- `同源`：文件结构或职责基本一致，可按一侧经验快速定位另一侧。
- `已重构`：行为目标相近，但生命周期、接口或层级不同。
- `缺失`：一侧没有等价实现，需要判断是迁移缺口还是产品范围差异。
- `产品差异`：确认不是 bug，而是项目范围或产品设计不同。

## 文档归属规则

| 内容 | 放哪里 |
|---|---|
| 项目当前代码入口、模块结构、任务索引 | 对应项目内文档，如 `/Users/dean/TileScape/Docs/Knowledge/` |
| 稳定方案、跨会话经验、完整总结 | `LibraryG/02-PROJECTS/<项目>/` 或 `03-KNOWLEDGE/` |
| MT 旧逻辑分析、旧行为基线 | `LibraryG/02-PROJECTS/TileMatch/` |
| TS ↔ MT 差异、复现方案 | 优先 `LibraryG/02-PROJECTS/Agent/工作流/` 或对应项目专题 |
| 跨项目规范、AI 使用习惯、知识库维护 | `LibraryG/02-PROJECTS/Agent/工作流/` |
| 当天详细工作日志、备份追踪、成功记录和决策索引 | `LibraryG/01-DAILY/YYYY-MM-DD.md` |
| 临时草稿、中间比对表 | `LibraryG/00-INBOX/`，结束后清理 |

## DAILY 的定位

DAILY 可以写得很详细。它的价值不只是快速检索，也包括每日工作日志、备份追踪和历史存档。推荐重点记录：

- 今天完成了哪个可复现的成功路径；
- 哪个方案被确认有效或被否定；
- 哪些 TS/MT 文件形成了稳定对照；
- 关键过程、尝试、失败原因、验证命令、路径和参数；
- 后续再做同类任务应该先看哪篇文档。

如果当天内容很碎，也可以只记录可追踪摘要；但不应因为“不是最终结论”就否定 DAILY 的存档价值。

当前 `02-PROJECTS/Agent/工作流/工作内容日志同步规范.md` 和 `04-TEMPLATES/tp-daily.md` 已经支持“项目分节 + 开头总结 + 详细过程”的格式，后续沿用即可；必要时只在具体日志中补充对位文件表或产出链接。

推荐在每篇 DAILY 顶部保留 `今日索引`，先给可扫描摘要，再写详细过程：

```markdown
## 今日索引

- 涉及项目：
- 完成事项：
- 关键结论：
- 产出文档：
- 关键路径：
- 后续入口：
```

## MOC 导航约定

- `HOME.md` 只做主路由，不把所有项目细节塞进主入口。
- 项目 `_MOC.md` 可以同名，但从跨项目文档链接时必须写完整路径，例如 `[[02-PROJECTS/TileScape/_MOC|TileScape MOC]]`。
- 子 MOC 要有明确领域名或唯一 alias，避免 AI 只按 `_MOC` 搜索时误入。
- 详细规则见 [[规范-MOC命名与导航层级|MOC 命名与导航层级规范]]。
