# 知识库维护降噪与 Obsidian 深化计划

## 目标

当前 LG 框架已经可用，但维护规则开始重复，项目内 Obsidian 能力使用还偏浅。本计划用于逐步降低规则读取成本，并提升项目知识库的链接、分类、属性、索引和复用能力。

目标不是重建目录，也不是批量删文档，而是：

- 减少 AI 每次任务需要读取的规则数量；
- 保留历史文档的追溯价值；
- 让项目内知识从“文件堆叠”升级为“可导航、可筛选、可回溯”的 Obsidian 知识网络；
- 让日常需求辅助保持低摩擦。

---

## 总原则

| 原则 | 执行方式 |
|---|---|
| 不大改目录 | 优先改入口、状态和索引，不批量移动文件 |
| 不删历史 | 历史文档标记 `historical` / `dormant`，不直接删除 |
| 低摩擦优先 | 小任务不强制完整闭环，稳定结论才补 MOC / 专题 |
| 先 TS 后 MT | TS 是当前活跃项目，优先提升 TS；MT 按真实对照需求补 |
| Obsidian 能力按需开发 | 先用属性、链接、MOC、Dataview/Bases，再考虑复杂自动化 |

## 阶段 1：规则降噪和分层

**目标**：把当前 14 个 Agent 工作流文件从“平级规则”改成“核心 / 参考 / 休眠 / 历史”。

| 动作 | 文件 | 处理方式 |
|---|---|---|
| 明确唯一最短入口 | `AI总MOC.md` | 增加规则分层表，减少平级路由压力 |
| 保留根入口 | `AGENTS.md` | 只放冷启动、用户偏好、项目桥接，不扩写细节 |
| 保留长期记忆 | `02-PROJECTS/Agent/Memory.md` | 只保留当前有效偏好和优先级，不复制所有规范 |
| 合并执行规则 | `规范-任务产出入库与维护.md` | 作为唯一“入库与维护”执行规则 |
| 降级重复规则 | `工作内容日志同步规范.md`、`规范-任务知识沉淀闭环与自动巡检.md` | 标为参考；核心内容以后以入库规范为准 |
| 标记休眠方案 | `方案-WorkBuddy日志知识闭环自动化实施.md` | 标为 dormant，只有启用 WorkBuddy 时读取 |
| 标记历史资料 | `DailyLogs同步流程.md`、`知识库同步比对报告-2026-07-01.md` | 标为 historical，仅追溯使用 |

验收标准：

- AI 总 MOC 能一眼区分当前必读、按需读、历史读。
- Agent Memory 不再推动“过度闭环”。
- 不删除任何历史材料。

## 阶段 2：项目内 Obsidian 结构补强

**目标**：提升项目内文档的分类、关联和检索质量，优先从 TS 开始。

### 2.1 TS 项目

| 动作 | 说明 |
|---|---|
| 补文档类型字段 | 统一常用 `type`：`logic`、`reference`、`codemap`、`design`、`report`、`plan` |
| 补状态字段 | 使用 `status` / `lifecycle` 区分 `current`、`draft`、`implemented`、`runtime-feedback-pending`、`verified` |
| 强化双链 | 每篇稳定文档至少关联项目 MOC、相关逻辑文档、关键参考索引 |
| 建专题入口 | Home、DLC、GM、道具、活动等内容增长后，再建专题 MOC |
| 强化快速定位索引 | 继续记录多语言、配置、资源、Prefab、入口脚本和易混淆点 |
| 同步 CodeMap | 新确认的代码入口同步到 TS `Docs/Knowledge/CodeMap.md` |

优先顺序：

1. `02-PROJECTS/TileScape/_MOC.md`
2. `02-PROJECTS/TileScape/参考/快速定位与资源替换索引.md`
3. `02-PROJECTS/TileScape/代码框架/代码框架总览.md`
4. 近期新增的 Home / GM / DLC / 道具文档

### 2.2 MT 项目

| 动作 | 说明 |
|---|---|
| 保持历史基线定位 | 不主动全量重构 MT 文档 |
| 补关键入口 | 只在 TS 对照用到时，补 MT 对位入口 |
| 标历史状态 | 对旧路径、旧方案、旧工具说明加历史说明 |
| 保留长文档 | 不为“整齐”删减旧知识库内容 |

## 阶段 3：Obsidian 工具能力深化

**目标**：让 Obsidian 不只是 Markdown 文件夹，而能辅助筛选、回顾和导航。

| 能力 | 优先级 | 用法 |
|---|---|---|
| Properties / frontmatter | P0 | 支撑状态、来源、类型、项目、生命周期筛选 |
| Dataview | P1 | 做项目文档列表、待确认项、最近更新、draft/current 视图 |
| Bases | P1 | 后续可做项目知识表、待验证/待反馈列表、文档维护视图 |
| Backlinks / Outlinks | P1 | 检查核心文档是否孤立、专题是否可达 |
| Templates | P1 | 为“代码逻辑沉淀”“快速定位条目”“阶段复盘”补轻模板 |
| Canvas | P2 | 用于复杂系统链路图，如 DLC、Home、GM，不作为日常必需 |
| Tags | P2 | 控制数量，优先用属性分类，标签只做跨切面 |

建议先开发的视图：

1. TS 当前文档总览：按 `type`、`status`、`date`。
2. 待确认 / 待反馈列表：筛出 `runtime-feedback-pending`、`needs-review`。
3. 最近新增知识：按最近 14 天文档。
4. 代码逻辑沉淀视图：筛 `type: codemap` / `logic` / `reference`。

---

## 阶段 4：维护节奏落地

**目标**：避免维护本身变成负担。

| 节奏 | 做什么 | 不做什么 |
|---|---|---|
| 每次需求结束 | 只记录有复用价值的入口、结论、路径 | 不强行写长文档 |
| 每周一次 | 检查 TS MOC、快速定位索引、最近新增文档状态 | 不批量重排历史 |
| 每阶段一次 | 做阶段复盘和待办收敛 | 不新增重复规范 |
| 出现明显混乱时 | 针对一个目录做小范围整理 | 不全库治理 |

## 暂不做

- 不批量删除或移动旧 WorkBuddy 文档。
- 不全量重写 TileMatch 知识库。
- 不把运行时验收队列设为默认高优先级。
- 不继续新增大规范，除非重复问题无法通过现有文档解决。
- 不在没有真实任务触发时建立 MT/TS 全量对位表。
