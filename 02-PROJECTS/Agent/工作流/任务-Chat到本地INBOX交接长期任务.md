# Chat 到本地 INBOX 交接长期任务

## 目标与完成标准

普通 Chat 先完成需求讨论和方案收敛；用户明确说“整理进 INBOX”后，把结构化方案存入本机 LibraryG `00-INBOX/`；随后由能访问本机文件的 Codex / Work 读取任务卡并继续执行。

| 层级 | 完成标准 | 当前状态 |
|---|---|---|
| 本地收件 | JSON 任务包经唯一受限入口新建 `00-INBOX` 卡，显示成功路径，暂停时零写入 | 已通过 |
| Chat 自动交接 | 普通 Chat 实际调用 `create_inbox_task` 并返回本地成功回执 | 待验证 |
| 执行交接 | Work / Codex 读取本机任务卡、复述范围与下一步，再由用户授权实施 | 本机 Codex 已验证；Work 独立环境待验证 |

> [!warning] 当前结论
> 当前实现是可用的本地收件器和手动后备流程，不是已经验收的“普通 Chat 自动写入本地”。没有成功回执的 Chat 只能称为“已产出待导入任务包”。

## 当前可用流程

```text
普通 Chat 形成方案
        │
        ├─ 当前窗口发现并调用 WebMCP 工具 → 本机 00-INBOX
        │
        └─ 未调用工具 → Chat 输出 JSON → 用户复制 → 本机页面读取剪贴板 → 本机 00-INBOX
                                                               │
                                                   成功路径 / 执行端读取指令
                                                               │
                                                   本机 Codex 或 Work 读取
```

生产入口是 `http://127.0.0.1:38741/`。当前没有开机自启，使用时需在工具目录运行 `npm run serve:webmcp-inbox`。

页面只暴露 `create_inbox_task`：固定写入 `/Users/dean/LibraryG/00-INBOX`，不支持读取、更新、删除、路径选择、终端或项目文件访问。自动开关保存在被 Git 忽略的 `.inbox-receiver/settings.json`。

## 已实现与实证

| 内容 | 证据 | 边界 |
|---|---|---|
| 严格任务格式 | 固定枚举，标题禁止路径片段，额外字段拒绝 | 不判断任务方案是否正确 |
| 原子新建 | 同标题追加序号，永不覆盖 | 不做跨时间去重，允许同主题方案更新 |
| WebMCP 页面 | 当前页面可注册唯一工具 | 只证明当前内置浏览器页面能力 |
| 剪贴板后备 | 接受裸 JSON 或完整 `json` 代码块；用户点击时读取一次 | 仍需复制和一次点击 |
| 成功回执 | 服务成功后显示绝对路径与执行端读取指令 | 不自动启动 Work / Codex |
| 暂停开关 | 服务端也检查；暂停时拒绝请求 | 有历史实测，当前服务未常驻 |
| 代码验证 | 2026-09-24 生产测试 9/9 通过 | 回环接口测试须在允许监听 `127.0.0.1` 的环境运行 |

## 遇到的问题与判断

| 现象 | 已确认原因或证据 | 当前处理 |
|---|---|---|
| Chat 生成 `/private/var/folders/.../codex-file-preview-...` | Chat 临时工作区，不是本机 LibraryG | 没有工具成功回执时，不认定为已入库 |
| 本机工具调用成功 | 由当前 Codex 内置浏览器适配层发起 | 不能外推为普通 Chat 自然语言会选工具 |
| 普通 Chat 自动路径停滞 | 没有普通 Chat 成功工具调用记录；账号、模型、页面和会话都可能影响 | 保留待验收，不臆测单一原因 |
| 曾看到“能力探针”页面 | 早期 D1 探针与生产页容易混淆，标签页会保留旧内容 | 历史探针已归档；使用前确认标题为“LibraryG INBOX 收件器”和端口 `38741` |
| 回环接口测试报 `listen EPERM` | 当前受限执行环境禁止监听，不代表接口失败 | 允许本机回环后，2026-09-24 测试 9/9 通过 |
| 服务后来不可用 | 没有开机自启；2026-09-24 检查时无监听进程 | 仅在验收或使用时手动启动，暂不加常驻服务 |
| Work 读取不明确 | Work 可能是同机本地或无本地权限的远程环境 | 以实际环境读取该绝对路径为准 |
| 自动写入与逐卡确认取舍 | 用户确认“写后通知 + 暂停开关”，移除逐卡确认、30 分钟去重和频率上限 | 仍只允许用户明确触发时建卡 |

## 已尝试路线

| 路线 | 结果 | 结论 |
|---|---|---|
| Custom MCP + tunnel | 未实施 | 个人 Plus 不具备所需写入前提，不绕行扩大权限 |
| Chat-on-St​eroids | 未采用 | 本机 Core / tunnel / 浏览器自动化能力超出仅建卡需求 |
| WebMCP D1/D2 临时探针 | 历史验证完成 | 证明页面 API、工具注册、临时建卡、确认与同进程去重；原件见 [[05-ARCHIVE/Agent/INBOX收件工具-历史验证-2026-09-18]] |
| WebMCP 生产页 | 已实现 | 自动候选和后备流程共享受限写入端 |
| JSON + 剪贴板导入 | 已实现并验证 | 当前稳定后备，不等同自动化 |
| 网页扩展 + localhost helper | 仅设计 | 只在必须零点击自动交接时再评估；适用 Chrome / Edge 网页版，需单独审查扩展权限与 DOM 适配 |

## 当前阻塞与下一步

当前阻塞不是代码缺失，而是缺少一次真实普通 Chat 验收，以及对“是否值得追求零点击自动化”的选择。

1. 在同一个 ChatGPT 桌面窗口内置侧边栏打开 `http://127.0.0.1:38741/`，确认标题和工具箭头。
2. 在普通 Chat 完成一个小方案后，说“整理进 INBOX”。
3. 记录结果：是否调用工具、是否显示平台确认、是否返回真实绝对路径、卡片是否在 `00-INBOX/`。
4. 如果自动调用失败但 JSON 导入顺畅，先把“复制 + 一键导入”定为日常流程；不为消灭一次点击提前扩大权限。
5. 只有用户仍坚持零点击自动交接，才回到网页扩展路线，先做只读 DOM 提取和可见保存按钮试用。
6. 本地任务卡稳定后，再在实际 Work 环境验证读取；该验证不授权项目修改。
