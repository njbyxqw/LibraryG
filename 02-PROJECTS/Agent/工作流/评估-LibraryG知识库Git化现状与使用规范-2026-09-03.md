> 本文用于把初步 Git 化从“已能同步”推进到“长期稳定、低冲突、边界清楚”。其中建议须经用户确认后才改动追踪范围、插件配置、SQLite 或 Git 配置。

## 建议的共享边界

| 类别 | Git 中保留 | 本机保留 |
|---|---|---|
| 知识内容 | Markdown、Canvas（非临时）、模板、MOC、Daily、可复用脚本与明确来源数据。 | 临时草稿、缓存、回收站。 |
| Obsidian | `app.json`、主题/快捷键/图谱、插件清单及经确认的无敏感语义配置。 | `workspace*.json`、cache、插件安装包、插件 `data.json`、含 Token/端口/设备状态的配置。 |
| 数据库与大文件 | 可读导出、输入数据、建库脚本、必要的最终证据。 | 活跃 SQLite 数据库及 WAL/SHM；可再生报告、临时图片。 |
| 历史 | 小体量、可追溯的归档说明与关键证据。 | 大附件原件可迁移到专用存储，Git 保留索引与来源说明。 |

## 双设备低冲突流程

```text
切换到设备 → 拉取并只允许快进 → 确认工作区干净 → 编辑
→ 按一类目的检查差异并提交 → 推送 → 再切换另一台设备
```

1. 开始前执行 `git pull --ff-only`；若失败，停下并先查看差异，不用自动 merge 覆盖。
2. 一次只处理一个主题：例如“今日 Daily + 相关文档”或“Obsidian 共享设置”，不要与附件整理、插件升级混合。
3. 提交前查看 `git status` 和差异；出现插件包、数据库、`workspace` 或意外附件时先移出本次提交。
4. `01-DAILY/YYYY-MM-DD.md` 是高冲突文件：同一天尽量由一台设备写；必须切换时，先推送再开始另一台的编辑。
5. 推送成功后再换设备；不在两端同时离线编辑同一批文件。
6. 真正需要整理历史、停止跟踪文件、迁移大附件或改写历史时，先列清单并单独确认，不与普通知识更新混做。

## 近期实施顺序

1. **P0 已隔离，待轮换**：当前插件数据已不再追踪；在两台设备确认并轮换有效凭据后，才考虑历史清理。
2. **P1 已转换**：共享最小 Obsidian 清单和 manifest；插件安装包/数据与活跃 SQLite 保持本机化，SQL 快照用于恢复。
3. **P2 已设门槛**：提交前运行 `scripts/check-staged-large-files.sh`；现有历史不做重写。
4. **同步流程按默认执行**：用户确认当前以本人单人操作为主，保持“交接前推送、下一设备更新后编辑”的默认路径；不写入 `pull.ff only` 等额外本机配置，出现真实冲突再反馈处理。

## 双设备同步流程设计（待双端实测）

目标不是让 Git 自动替用户合并，而是让绝大多数切换走一条无冲突、低认知成本的路径；仅在离线并行时才升级处理方式。当前作为默认约定保留，不强制执行或自动化。

| 状态 | 使用场景 | 操作 | 预期结果 |
|---|---|---|---|
| 基线 | 开始编辑前 | 获取远端状态；本机无改动时再更新到 `origin/main`。 | 两端从同一版本开始。 |
| 日常交接（默认） | 换设备、午休或当天收尾 | 将一个主题的变更提交并推送；另一台设备更新后再编辑。 | 直接在 `main` 工作，不创建分支。 |
| 短时本地工作 | 不切换设备的普通编辑 | 保持未提交变更即可；不要在此状态换设备继续编辑相同主题。 | 保留 Obsidian 的低摩擦体验。 |
| 离线例外 | 两端均有新提交，或必须离线编辑 | 保留本机提交，先获取远端；以 rebase/人工合并处理，不能用自动 pull 覆盖。 | 冲突只在确有并行工作时出现。 |
| 长时并行例外 | 两端数小时以上独立工作且会改同一专题 | 临时创建按设备/主题命名的分支，完成后人工审阅合并。 | 不把日常笔记强行分支化。 |

### 默认交接卡片

每次只需确认四件事：**当前设备已推送、下一设备已更新、`main` 仍干净、没有两端同时编辑同一 Daily 或同一数据库。**

- 无本地改动：更新后即可继续工作。
- 有本地改动且准备换设备：先按主题提交并推送；不把插件、数据库、缓存或意外附件混入。
- 有本地改动但不能提交：留在当前设备；不要在另一台继续编辑重叠文件。
- 发现远端也有新提交：先比较改动范围；仅 Markdown 文字冲突时手动保留双方内容，数据库与插件本机文件不参与合并。

### 为什么暂不直接启用 `pull.ff only`

它适合防止隐式 merge，但在离线双端都有提交时会直接中断，仍需用户选择 rebase 或合并。故先把“交接前推送、重叠文件不并行编辑”作为主流程；待在 Windows 与 macOS 各完成一次真实交接后，再决定是否把该保护设为两端默认值。
