# LG 规范与入口降噪审查

> 结论：LG 的知识分层、项目边界、MOC 和历史保留原则是合理的；当前不合理的是 Agent 的**入口与执行规则重复**。问题不是缺规则，而是当前规则散布在多个“看似必读”的位置，并混入已停用的 WorkBuddy / WebMCP 设计。

## 审查范围与边界

| 范围 | 已检查 | 边界 |
|---|---|---|
| 全库结构 | 333 篇 Markdown 的目录、状态与入口分布 | 未逐篇重审项目业务事实的准确性。 |
| 当前 Agent 入口 | `AGENTS.md`、`AI总MOC.md`、`HOME.md`、`工作空间总纲.md`、`Agent/Memory.md` | 已读取全文或当前执行相关章节。 |
| 规则层 | Agent 工作流 MOC、入库、闭环、INBOX、Daily、MOC、多项目、桥接与多 Agent 规范 | 以 frontmatter 和正文的 `current` / `finalized` 声明交叉判断。 |
| 工具现状 | Obsidian Local REST API with MCP | 当前 Codex 仅加载 `search_simple`、`vault_read`；未验证全库链接可达性，因为本机没有 `obsidian` CLI。 |

## 已确认的有效基础

1. **职责边界正确**：LG 是长期知识、规范、决策与索引；TS / MT 是当前代码事实和执行空间；当前代码优先于 LG 历史记录。
2. **目录分层可保留**：`00-INBOX`、`01-DAILY`、`02-PROJECTS`、`03-KNOWLEDGE`、`04-TEMPLATES`、`05-ARCHIVE` 的职责没有必要重建。
3. **项目导航可保留**：TS / MT 项目 MOC、TileMatch 障碍 MOC、TS GM MOC 的职责清楚；不应为整齐而批量拆分或改名。
4. **新 P0 方向正确**：Task → 最小 Context → Worktree → Artifact → Proposal / Promote，且项目 `AGENTS.md` 只读、个人入口只放本机忽略的 `.agent/`。
5. **历史保留正确**：旧方案应有 `historical` / `dormant` 标识和归档索引，不应直接删除。

## 核心问题

| 优先级 | 问题 | 已见证据 | 风险 |
|---|---|---|---|
| P0 | 冷启动重复 | `AGENTS.md`、`AI总MOC.md`、`HOME.md`、`工作空间总纲.md`、`Memory.md` 都描述“先读什么”；其中有 4–5 篇默认必读链。 | 初始 Context 过大，且不同入口给出不同顺序。 |
| P0 | 日常闭环重复且强度不一 | 入库规范、根 `AGENTS.md`、Memory、闭环规范、Daily 规范均要求 Daily / MOC / 稳定文档；部分段落又允许小任务不入库。 | Agent 倾向把小任务流程化，或无从判断该写什么。 |
| P0 | 当前与休眠自动化混读 | Agent 工作流 MOC 已将 WorkBuddy 标为 dormant，但 Memory 与闭环规范仍把 `queue/ready/`、任务包和 WorkBuddy 执行写成常规链路。 | 未启用的自动化被误当成可执行能力。 |
| P0 | `HOME.md` 同时承担人类导航、Agent 操作手册、旧 CLI 速查和历史 WorkBuddy 说明（274 行）。 | 仍列出旧 Obsidian CLI 的创建、移动、删除命令；当前有效的是受限的只读 MCP。 | 人或 Agent 都可能沿旧路径做出错误权限判断。 |
| P1 | 状态字段语义混用 | `status` 同时出现 `current`、`finalized`、`published`、`active-trial`、`ready-for-workbuddy`、`superseded` 等。 | Dataview / 搜索不能稳定识别“当前执行依据”。 |
| P1 | 现行入口仍携带大量方案、报告、计划 | Agent 工作流目录约 5,000 行；MOC 虽分层，但历史 WebMCP / Plus / WorkBuddy 方案仍紧邻当前路由。 | 对任务无关的信息仍进入搜索和阅读候选。 |
| P2 | 人类导航和 Agent 路由没有明确分工 | `HOME`、`AI总MOC`、`工作空间总纲` 大量交叉链接与重复职责。 | 后续每加一条规则都容易写三份。 |

## 发现的明确不一致

| 主题 | 现有口径 | 建议统一口径 |
|---|---|---|
| 默认读取 | P0 要求任务最小 Context；旧入口仍要求 HOME、总纲、Memory 全读。 | **LG 维护任务**：根 `AGENTS.md` → `AI总MOC.md` → 任务路由文档。**代码任务**：项目 `AGENTS.md`（只读团队约束）→ 本机 `.agent/PROJECT.md` → Task 链接。HOME / 总纲 / Memory 仅按任务需要读取。 |
| Daily 与稳定文档 | 有“每次任务必写 Daily / MOC”的硬门槛，也有“小问答不造文档”。 | 只有形成可复用事实、决策、Artifact、持续任务进展或用户明确要求整理时，才写 Daily；只有稳定结论才新增或更新正式文档和 MOC。 |
| WorkBuddy | MOC 标 dormant；其他现行规则仍描述 ready 队列和自动执行。 | 未经再次启用，一律 **dormant**；日常工作不读取、不生成 WorkBuddy 任务包。 |
| Obsidian 接入 | HOME 仍保留旧 CLI 写、移动、删除命令；当前 MCP 只读。 | 当前默认是 Obsidian GUI + 只读 MCP 搜索/读取。写入只走用户明确授权后的 LG 文件编辑；不把 MCP 当写入通道。 |
| 项目 `AGENTS.md` | 旧桥接文字曾允许项目入口被个人流程扩展。 | 项目 `AGENTS.md` 是团队公共文件，只读；个人 Context 仅放本机忽略的 `.agent/PROJECT.md` 与 `.worktreeinclude`。 |

## 推荐目标层级

```text
L0  AGENTS.md                 最短权限边界与 LG 总入口（Agent）
L0  AI总MOC.md                任务分类与二级路由（Agent）
L0  HOME.md                   人类浏览入口，不承载执行规则
L1  工作空间总纲.md            LG / TS / MT 事实与知识边界
L1  规范-任务产出入库与维护    唯一日常入库与写回判定
L1  规范-多Agent任务上下文与交接  Task、Context、Worktree、Artifact
L2  项目 / Agent 工作流 MOC     主题路由
L3  参考规范、报告、计划、历史  仅按需进入
```

**只保留两份日常执行规范：**

- `规范-任务产出入库与维护`：回答“本次是否需要写回、写到哪里”。
- `规范-多Agent任务上下文与交接`：回答“本次怎么读最小 Context、怎么隔离执行、如何交接”。

其他文档都是按需参考，不能再复制这两份的执行条款。

| `Agent/Memory.md` | 只保留稳定偏好、路径别名、事实优先级和极少数高价值提醒；删除或改链接到重复的流程条款。 | 不再作为全规则副本。 |

### 当前使用与维护判断

LG 当前不是“不可用或失控的知识库”，而是处于 **P0 已配置、P0 尚未运营化** 的阶段：

- **知识使用**：MOC 路由、项目事实边界和近期 Daily 三项目结构实际在工作；只读 MCP 已降低检索接入成本。
- **知识维护**：新规范、模板、INBOX MOC 与收件通道没有单一权威入口，新增任务仍可能绕开 P0 字段和索引。
- **多 Agent**：目前完成了安全边界与本机准备，但没有真实 Worktree / Artifact / 接手任务样本，不能宣称多 Agent 协作已经稳定运行。

因此后续优先级应调整为：**先让一条真实任务完整跑通，再继续精简规则**，而不是继续增加 MCP、自动化、状态字段或新模板。

## 验证边界与下一步

- **已审计**：入口重复、规范关系、元数据分布、旧自动化可见性、实际可用的 MCP 只读工具。
- **未审计**：333 篇文档的业务事实时效、所有内部链接、第三方插件运行质量。
- **未执行**：未移动 / 删除历史文件，未重写 L0 入口，未更改项目公共 `AGENTS.md`，未 commit / push。

建议下一步只执行 P0-a 至 P0-c：先备份当前入口，再重写入口与路由，不动项目知识和历史正文。执行前应由用户确认最终的“L0 最短入口”文案与 WorkBuddy / WebMCP 的保留级别。
