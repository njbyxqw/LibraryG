# 任务知识沉淀闭环与自动巡检

> 目的：解决“对话未读 MOC、结论只留在聊天、Daily 断档、代码定位没有沉淀”的问题。本文把每次任务的最小闭环与周期性补漏分开定义。
> 当前定位：周期巡检、自动化补漏和明显遗漏时读取；不作为所有小任务的强制收尾清单。日常入库执行以 [[02-PROJECTS/Agent/工作流/规范-任务产出入库与维护|任务产出入库与维护规范]] 为准。
> 源头规则：LG 是唯一知识库与规范源。TS / MT 只作为项目执行空间、事实来源和代码旁上下文；自动巡检必须从 LG 当前规范出发，再进入项目目录核对证据。

## 一、四道门

| 阶段 | 强制动作 | 通过标准 |
|---|---|---|
| 任务开始 | 任务路由 | 已确定 MT / TS / LG / 跨项目归属，并读取对应 MOC 与项目规则。 |
| 任务进行 | 证据记录 | 记录已读代码、文档、结论和未验证项；中间材料可留 INBOX。 |
| 任务收尾 | 入库闭环 | Daily 已更新；稳定结论已归位；MOC / CodeMap / 专题索引已补入口。 |
| 周期巡检 | 漏项审计 | 扫描近期 Daily、INBOX、MOC 入口和项目文档，生成可执行补漏清单。 |

任务不得因“答案已给出”而跳过第三道门。没有形成稳定结论时，Daily 也必须留下范围、依据和下一步，而不是空白。

## 二、分类与落点

| 新知识类型 | 首选落点 | 必须补的导航 |
|---|---|---|
| Tile / Effect / 障碍 / ECA / DDA / 死局 / 生成 / 状态机逻辑 | `02-PROJECTS/<项目>/游戏逻辑/<专题>/` | 专题 MOC 或项目 `_MOC.md` |
| 编辑器功能、配置、工作流、工具使用 | `编辑器/`、`工具/`、`参考/` | 项目 `_MOC.md` |
| 代码位置、程序集职责、启动/加载链路、配置入口 | LG 项目 `代码框架/` 或 `参考/`；TS `Docs/Knowledge/CodeMap.md` 只作执行索引同步 | CodeMap / 项目 `_MOC.md` |
| MT / TS 行为差异与复现 | 项目专题文档或 Agent 工作流 | 对位文件表 + 两边入口 |
| 工作过程、验证、失败、待确认 | `01-DAILY/YYYY-MM-DD.md` | 今日索引与对应项目节 |
| 跨项目规则、检索与归档方法 | `02-PROJECTS/Agent/工作流/` | `AI总MOC.md` / `HOME.md` 高价值入口 |

## 三、收尾清单

在给用户最终答复前，逐项回答：

1. 这次任务属于哪一个项目？对应 MOC 是否已读？
2. 今天的 Daily 是否写了“做了什么、结论、产出/路径、后续入口”？
3. 是否发现新的游戏逻辑？若是，是否已有专题文档与 MOC 链接？
4. 是否发现新的代码位置或调用链？若是，是否已补到 CodeMap / 代码框架 / 参考？
5. 是否有跨 MT / TS 对照？若是，是否保留了本次实际用到的对位文件表？
6. 新文档的来源、验证状态、未确认项是否如实标记？

任何一项为“否”时，不应宣布知识库收尾完成；可以明确说明未入库的原因与下一步。

## 四、自动巡检职责

自动化只做证据驱动的补漏，不做猜测式写作：

### Codex 预处理与 WorkBuddy 执行

- Codex 负责路由、取证、归类和生成精确任务包；WorkBuddy 只执行 `risk: low`、来源明确、目标与正文均已指定的动作。
- 任务包必须带唯一 ID、来源、前置条件、幂等标记和验证项；冲突、推断、团队提交或仅有 mtime 的线索一律转 `needs-review`，不得写入正式记录。
- WorkBuddy 只可追加 / 新建白名单内知识库文件，不移动、删除、覆盖历史内容，也不改项目业务代码或执行 git 写操作。
- 完整的目录、任务包格式、状态流转、定时任务与验收标准见 [[02-PROJECTS/Agent/工作流/方案-WorkBuddy日志知识闭环自动化实施|WorkBuddy 日志知识闭环自动化实施方案]]。

### 每日收尾巡检

1. 读取当天 Daily、近期项目文档与当前任务明确提及的文件。
2. 先确认自动化已读取 LG 当前入口：`AGENTS.md`、`AI总MOC.md`、`工作空间总纲.md`、`02-PROJECTS/Agent/Memory.md` 和本规范；TS / MT 项目文件只作后续证据来源。
3. 检查 Daily 是否有相关项目节和今日索引；缺失时补充**可证实**的摘要，并写明来源。
4. 检查新结论是否只存在 Daily / 对话材料：
   - 逻辑类提示归入 `游戏逻辑/`；
   - 文件路径与调用链提示归入 CodeMap / 代码框架 / 参考；
   - 需要用户判断的归类保留为待确认，不擅自移档。
5. 检查新增稳定文档是否已由 MOC、专题索引或 CodeMap 链接。
6. 检查规则是否统一：对照 `AGENTS.md`、`AI总MOC.md`、`工作空间总纲.md`、`02-PROJECTS/Agent/Memory.md`、任务产出入库规范、本规范和自动化方案，确认 LG 唯一源、MOC/MEMORY 逐级检索、Daily 三项目节、TS/MT 只作执行空间等核心规则没有互相冲突。
7. 向用户汇报“已补、待确认、无证据”三类结果。

### 规则统一性检查

自动化整理规范内容时必须同时做规则统一性检查，避免新增规范扩大旧冲突。

| 检查项 | 统一口径 | 自动化动作 |
|---|---|---|
| 规范源 | LG 是唯一知识库与规范源；TS / MT 是执行空间和事实来源。 | 发现 TS / MT 或旧文档表述为独立规范源时，登记待确认或补 LG 侧说明；不直接写项目目录。 |
| 检索路径 | 先从 `AGENTS.md`、`AI总MOC.md`、`HOME.md`、`工作空间总纲.md`、Agent Memory、项目 MOC 逐级进入。 | 发现“默认全盘搜索”“只读项目本地记忆”的旧表述时，按当前规范修正 LG 文档或列入待确认。 |
| 入库位置 | 稳定结论进入 LG 对应项目区；项目内文档只作执行上下文。 | 发现稳定结论只留项目路径、Daily 或 INBOX 时，补 LG 入口摘要或生成待确认清单。 |
| Daily 结构 | 当日 Daily 使用 `今日索引`、`TileMatch`、`TileScape`、`LibraryG`。 | 缺节时只补可证实内容；无证据不补工作事实。 |
| 自动化权限 | 自动化只写 LG 白名单路径，不写 TS / MT，不 commit/push。 | 发现自动化提示或任务包放宽权限时，先修 LG 自动化规范；实际任务转待确认。 |
| 历史状态 | historical / deprecated / needs-review 不得升级为 current。 | 只补状态说明和导航，不重写历史结论。 |

冲突处理顺序：先以 `AGENTS.md` 和 `02-PROJECTS/Agent/工作流/规范-任务产出入库与维护.md` 为当前执行口径；若旧规范、旧任务包或项目内入口不一致，保留来源并登记差异，不静默覆盖。

### 每周健康巡检

1. 扫描最近 7 天 Daily 是否断档、项目分节是否缺失、今日索引是否为空。
2. 扫描 `00-INBOX/` 是否有超过 7 天的未整理材料。
3. 检查最近新增/修改的稳定文档是否有来源、状态、关联和 MOC 入口。
4. 检查最近新增/修改的规范、任务包和自动化说明是否符合“规则统一性检查”表。
5. 输出按优先级排序的补漏清单；自动补充无歧义的链接和索引，不移动、删除或覆盖历史文档。
6. 对发现的“仓库提交但无个人工作记录”只报告，不写进 Daily；需要用户提供对话或确认后再补录。

## 五、例外与边界
### 近期任务归档核对（2026-09-07 补充）

依据用户 2026-09-07 的巡检要求，每次近期任务整理须维护逐任务核对表：任务原名与 ID、是否需要整理及理由、是否已整理、已有文档路径、完整性与具体缺项、证据与验证边界、下一动作及执行结果。任务列表摘要只用于发现；完成判定必须核对任务原文和实际文档。

整理状态与业务状态分开：`未核对 / 无需整理 / 未整理 / 部分整理 / 已整理` 不代表实现或运行时验证已通过。无需整理必须有理由；来源不可读须记为证据不足，不写成没有工作。持续任务分支或多个对话关联同一主档，保留各任务入口，避免重复建档。

用户明确要求全量扫描时，先按 MOC 确认范围，再枚举 LG 内容目录做结构检查；近期任务内容逐篇核对。输出扫描分母、已核对数量、排除项、访问失败及未完成清单，不能用抽样报告宣称全量通过。正文已有来源、代码示例链接、模板占位与历史归档应分别判断。

本次专项清单及验收标准：[[02-PROJECTS/Agent/工作流/计划-近期任务归档全量巡检-2026-09-07]]。专项完成后恢复日常增量，使用执行 ID 防止重复全量修订。

### 通用边界

- 一次纯问答、没有新增事实或文件定位时，不强行造文档；Daily 可不新增，但如任务形成明确决策则仍应记录。
- 大规模重排、移动、删除或归档先列清单并等待用户确认。
- 自动化不 commit、不 push、不改项目业务代码。
- 自动化不写 TS / MT 项目目录；若需要同步项目内 `AGENTS.md`、`Docs/Knowledge` 或本地记忆，只生成待确认项或交给 Codex 在用户授权后处理。
- 团队 git 提交、文件 mtime、构建产物只能作为线索；除非能证明是本次任务或用户确认，不得写成个人工作事实。
