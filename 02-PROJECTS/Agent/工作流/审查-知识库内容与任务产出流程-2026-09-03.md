# 知识库内容与任务产出流程审查

> 目标是减少“每次任务要读很多规则、每次对话都要建文件、结论位置不确定”的摩擦；不以补齐格式、重排目录或改写历史为目标。

## 已确认现状

| 范围 | 观察 | 判断 |
|---|---|---|
| Daily | 2026-08-17 至 2026-09-03 的 Daily 均有 `今日索引`、TileMatch、TileScape、LibraryG 四个固定节。 | 当前格式已稳定；5–8 月旧日志不按新模板，不应批量回填。 |
| 内容分布 | 当前约有 73 个 Daily、191 个项目文件、6 个通用知识文件、5 个模板、97 个归档文件；`00-INBOX` 为空。 | 项目与归档是主体，通用知识层与其导航较薄。 |
| 核心规则 | `规范-任务产出入库与维护` 已是当前入库执行规则；Daily/闭环/INBOX 文档已被标成参考或按需读取。 | 分层方向正确，但旧正文仍残留局部重复和过时操作表述。 |
| 任务闭环 | 近期规范已把 Daily、稳定结论、MOC/CodeMap 与来源边界连起来。 | 可用；应进一步明确“小问答不入库、稳定结论才建文档”的分流。 |

## 推荐的最小产出分流

| 任务结果 | 是否写 Daily | 是否新建稳定文档 | 存放位置 |
|---|---|---|---|
| 纯问答、没有新事实/路径/决策 | 否 | 否 | 对话即可。 |
| 一次定位、排查或小决策，可被后续追溯 | 是，写摘要与入口 | 仅在预期复用时新建 | 当日 Daily；必要时对应项目 `参考/` 或 `代码框架/`。 |
| 已确认的逻辑、流程、方案、代码链路、复现结论 | 是 | 是 | `02-PROJECTS/<项目>/`；跨项目规则放 `02-PROJECTS/Agent/工作流/`；通用主题放 `03-KNOWLEDGE/`。 |
| 未确认草稿、原始对比、跨回合材料、附件 | 仅记录状态和下一步 | 否 | `00-INBOX/`；确认后移动到目标或归档。 |
| 生成报告、数据库、可再生预览 | 是，记录来源与恢复入口 | 视是否长期复用 | 版本化源数据/脚本/最终必要结果；缓存和可再生副本不进入共享主路径。 |

## 统一后的责任边界

- `AI总MOC`：只负责路由，不增加执行细节。
- `规范-任务产出入库与维护`：唯一的日常“是否入库、放哪里、收尾看什么”执行规则。
- `工作内容日志同步规范`：只保留 Daily 模板和详细记录口径。
- `任务知识沉淀闭环与自动巡检`：只用于明显遗漏、周期巡检和自动化边界。
- `INBOX 对话工作区工作流`：只定义临时材料何时进入、何时离开 INBOX；不再假设每个对话或某个特定 Skill 必经它。
- 项目 `_MOC` / CodeMap：负责让稳定结论可从项目入口到达；Daily 不能替代它们。

## MOC 统一规划（设计，未改结构）

现有真正承担导航职责的 MOC 是：`AI总MOC.md`、TileMatch/TileScape 两个项目 `_MOC.md`，以及 TileMatch 障碍、TileScape GM 两个专题 MOC。项目概览、路径索引、Docs 索引、快速定位索引和顺序索引应保留为**辅助索引**，不再泛化为 MOC。

| 层级 | 载体 | 职责 | 不承担 |
|---|---|---|---|
| L0 | `AI总MOC.md` | AI 最短任务路由、规则分层、项目入口。 | 全库文档目录、项目正文。 |
| L0 | `HOME.md` | 人类浏览入口、空间说明、常用入口。 | AI 执行规则的第二份副本。 |
| L1 | `工作空间总纲.md` | LG、TS、MT 与代码仓库的边界和信息流。 | 每个专题的具体导航。 |
| L2 | `02-PROJECTS/TileMatch/_MOC.md`、`02-PROJECTS/TileScape/_MOC.md`、未来 `03-KNOWLEDGE/_MOC.md` | 各知识域的主入口与专题分流。 | 完整正文、Daily 流水。 |
| L3 | 障碍 MOC、GM MOC 等专题入口 | 当某领域有多篇文档且需要重复进入时，提供专题路由。 | 只有一两篇文档的轻量主题。 |
| 辅助索引 | `_项目概览`、代码路径、Docs、快速定位、顺序索引 | 按用途、代码路径、排序或外部文档检索。 | 取代项目 MOC。 |

新增专题 MOC 的门槛：至少有 6 篇稳定文档，或存在独立的复杂工作流/代码入口，且后续会重复从该主题进入。否则直接挂在项目 MOC，避免“每多一篇文档就多一个 MOC”。

LG 的定位保持不变：它是跨工作空间的**长期知识、导航与可追溯总结层**。MOC 只把读者送到正确的位置，不复制 TileScape/TileMatch 项目中的执行细节，也不把代码仓库改造成 LG 的镜像。

## 项目空间产出的直接落点

默认不是“先都放项目里，之后再整理”，而是任务一旦形成可复用结论就直接落到 LG 的对应路径；这样不会因为后续整理被推迟而丢失。

| 产出类型 | 主存放位置 | LG 的动作 |
|---|---|---|
| 代码、配置、资源、测试、运行产物 | TS / MT 代码仓库。 | Daily 记录精确路径、结论和验证边界；需要长期复用时在 LG 项目文档总结，不复制源码。 |
| 可复用的项目结论、代码链路、设计决策、MT/TS 对位 | `LibraryG/02-PROJECTS/<项目>/`。 | 任务当日直接创建/更新并从项目 MOC、CodeMap 或专题索引可达。 |
| 与代码仓库绑定的活文档（TS CodeMap、模块任务索引、正在评审的设计） | TS `Docs/Knowledge/` 或 `Docs/`。 | LG 保留入口、摘要与最终稳定结论；不维护两份同正文。 |
| 跨项目方法、知识库规则、通用知识 | `02-PROJECTS/Agent/工作流/` 或 `03-KNOWLEDGE/`。 | 由 AI 总 MOC 或通用知识 MOC 路由。 |
| 未确认草稿、原始对比和跨回合材料 | `00-INBOX/`；TS 局部试验可放 `Docs/Knowledge/Local/`。 | 确认后直接归位；不把草稿当成唯一长期来源。 |

因此，LG 不承担代码仓库内容的“后续搬运站”，而是从任务产出时就承担**稳定知识的主存放处**；代码仓库保留运行所需和代码旁执行文档，两侧通过精确路径、链接和验证边界关联。

## 任务主档案、活索引与零碎任务（已确认）

用户确认需要按三种对话形态分流：

1. **持续项目任务**：如 DLC。对应项目领域下的 `任务-<主题>.md` 是背景、进度、设计、讨论、方案、实现和验证的唯一主线；Daily 只做备份索引。任务变大时可拆子文档，但主档案始终回链。
2. **活索引 / 快速查找**：直接持续维护路径、资源、配置等索引，既是查找入口也是边做边补的长期文档；不为每条定位另建任务档案。
3. **零碎任务**：默认只留对话；只有用户要求整理、形成复用价值，或明确关联前两类时才升级归位。

该规则已写入 [[02-PROJECTS/Agent/工作流/规范-任务产出入库与维护|任务产出入库与维护规范]]，并新增 [[04-TEMPLATES/tp-task|持续任务模板]]。
