# LG 本地 Git 冲突快速处理

> 来源：2026-11-23 Windows `D:\LibraryG` 实际修复及用户要求“记录方案，后续本地冲突快速解决”。已验证的是保留本机改动、部分暂存状态及已合并文本后完成快进；其他类型按下表分流，不把本次步骤当成万能脚本。

## 下次如何启动

对 Agent 说：“按 LG 本地 Git 冲突快速处理手册，保留本机内容和暂存状态，解决同步冲突，不 commit/push。”

Agent 先读取本手册和当前仓库状态，简要展示涉及文件及处理方式，再执行已授权的修复。当前会话已明确授权的相同步骤不重复索要许可；手册本身不授予未来会话自动 Git 写入权限。commit、push 仍遵守原有约束。

## 先用实际状态分流

在当前设备的 LG 根目录执行；下列命令只读取本地状态：

```powershell
git status --short --branch
git ls-files -u
git diff --name-only
git diff --cached --name-only
git ls-files --others --exclude-standard
git rev-list --left-right --count HEAD...origin/main
```

`origin/main` 只是本地记录。涉及远端同步时，在授权范围内执行 `git fetch origin` 并重新比较；fetch 失败时明确远端新鲜度未知。分支或 upstream 不同则使用实际名称。通过 `git rev-parse --git-path` 定位 Git 元数据，兼容 `.git` 为文件的 worktree。

| 现场表现 | 判断与处理 |
|---|---|
| `Your local changes ... would be overwritten by merge`，`git ls-files -u` 为空 | 本机修改触发覆盖保护，尚未形成未合并索引。确认无进行中的 merge/rebase 后，按下节保留本机内容并同步。2026-11-23 属于此类。 |
| 存在未合并索引项，或有进行中的 merge/rebase | 读取当前操作状态，逐文件比较共同基线、双方版本和工作区结果；解决后核验并暂存指定文件。继续或结束当前操作按原有授权处理，不擅自创建提交。 |
| HEAD 与远端双方都有独有提交，快进不可用 | 保留现有提交，先列分叉与共改文件；依据当前任务选择 merge/rebase，未授权时不自行改写历史。 |
| `.git/index.lock` 创建返回 `Permission denied` | 核对当前会话工具权限、实际 Git 目录和文件系统权限；只读成功不代表可以写 Git 元数据。权限恢复后复核现场再执行，不循环重复同一失败。 |
| 锁文件已存在，或暂存区持续变化 | 检查其他 Git 客户端、任务或进程。正在使用的锁不能删除；确认无人占用后才处理遗留锁。禁止把并发变化当成自己的修改覆盖。 |

## 本次验证的快进修复方法

适用条件：无进行中的 merge/rebase、无未合并索引项，HEAD 是目标提交的祖先；已识别所有本机与远端共改路径。用 `git merge-base --is-ancestor <旧HEAD> <目标提交>` 验证快进关系，不能只凭“落后一个提交”判断。

1. **固定目标并备份现场**：记录完整旧 HEAD、fetch 后目标 SHA、所有暂存／未暂存／未跟踪路径；在仓库外备份原始索引、逐路径工作区字节、索引条目、二进制补丁与 SHA-256。删除状态也要记录。备份须能恢复暂存和未暂存两层，仅保存普通 diff 不够。保留至本次变更已另有可靠备份。
2. **三方比较共改文件**：共同基线＝旧 HEAD，本机＝当前索引与工作区各自版本，远端＝固定目标 SHA。分别计算期望的最终索引与最终工作区，先展示合并差异。已人工合并的正文需核实包含双方改动，不能再次用某一侧整篇覆盖。
3. **保留暂存边界**：本来未暂存的本机改动继续留在工作区；索引原本等于旧 HEAD 的路径，在快进后应采用目标提交版本。部分暂存文件的两层分别合并。不能把旧索引一字不改地覆盖回新 HEAD，也不能统一 `git add` 共改文件，否则会制造反向暂存或扩大提交范围。
4. **短时间保护并发**：写前重新核对 HEAD、索引条目和相关文件摘要。检测到变化则重新备份、重算结果。2026-11-23 使用排他创建的真实 Git 索引锁阻止普通索引写入，复制原索引作为临时索引，并通过 `GIT_INDEX_FILE` 让修复命令操作该副本。索引锁不阻止其他程序直接编辑正文，写前、写后摘要检查仍必需。
5. **在临时索引完成快进**：仅把已完整备份的共改路径在临时索引和工作区临时恢复至旧 HEAD，再对固定目标执行 `git merge --ff-only <目标SHA>`；其他本机路径保持。随后恢复共改文件的期望索引条目和工作区字节。索引可通过 `git hash-object -w --stdin`、`git update-index --index-info` 精确保留两层差异。操作中的 Git 命令必须指向临时索引，否则会碰到自身持有的锁。
6. **核验后安装索引**：确认最终内容、暂存边界、HEAD 和远端增量符合预期，再将临时索引字节写入自己持有的锁文件，以原子替换安装为真实索引，清理自己创建的锁。发生异常时先检查 HEAD 和现场，依备份恢复；只有确认没有他人修改时才回退本次操作，不盲目回写分支或文件。

以上是 Agent 执行说明，不是可直接粘贴的通用命令串。路径集合、部分暂存、删除／重命名和异常恢复需按现场生成。2026-11-23 仅验证普通文件、本机修改／新增、远端修改／新增；复杂重命名、删除冲突、二进制共改、submodule 和跨设备同时写入未在本次验证。简单且无并发的现场可以采用更短实现，保留备份与核验要求即可。

## 文档合并取舍

| 内容 | 合并方式 |
|---|---|
| MOC、Docs 索引在同一位置各加条目 | 保留两侧有效入口，合并重复项，检查引用存在。不能因为插入点相同就丢弃其中一侧。 |
| 同一任务主档的新进展和附件迁移 | 保留较新的任务正文，同时叠加已确认的附件新路径；历史状态与来源保留，不自行裁决业务规则。 |
| Daily | 保留真实来源和设备分区，源日志不删除；按日志同步规范处理受管块，不能用整篇“取本机／取远端”覆盖。 |
| 配置、二进制或实质规则相互矛盾 | 比较来源与版本，不能按时间戳、设备或“保留双方”自动判定正确版本；需要时提出具体待决项。 |

不把 `reset --hard`、`clean -fd`、强推、整库 `ours/theirs` 或删除有效锁作为快速处理默认方案。部分暂存或并发现场不直接套用 `stash/pop`。未确认的业务冲突保持待决，不为了清空冲突标记擅改含义。

## 完成核验

- **Git 状态**：无未合并项；无本次遗留 merge/rebase 状态和锁；快进路径下 HEAD 等于固定目标。fetch 后的远端未再变化时，`HEAD...origin/main` 为 `0 / 0`。
- **本机内容**：逐路径核对备份。非共改内容保持原字节；共改内容等于已审查的合并结果；原有未跟踪文件、删除状态及部分暂存边界正确。文件数量相同不能代替内容核验。
- **远端增量**：非共改路径符合目标版本；共改文件含应保留的远端更新。区分 Git 规范化内容和工作区换行，不能把换行变化误报为业务变化。
- **文档**：检查实际内容中的冲突标记、相关文件／锚点引用及 `git diff --check`；不因手册示例或已有排版误判冲突。已有问题只记录，不扩大修复范围。
- **收尾**：更新本机设备 Daily，报告目标 SHA、保留范围、备份位置和限制；不自动 commit/push。
