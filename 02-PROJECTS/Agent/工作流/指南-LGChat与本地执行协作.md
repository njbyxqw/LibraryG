# LG、Chat 与本地执行协作实用指南

> [!info] 已整合
> 本文保留为 2026-09-15 的试行记录，不再作为执行入口。当前任务、Context、Worktree 和 Artifact 规则见 [[02-PROJECTS/Agent/工作流/规范-多Agent任务上下文与交接|多 Agent 任务上下文与交接规范]]。

> [!warning] 草案状态
> 本文用于试行“讨论—事实核实—执行—沉淀”的协作方式。入库、Daily、MOC、跨项目复现与项目写入边界仍以 [[02-PROJECTS/Agent/工作流/规范-任务产出入库与维护|任务产出入库与维护规范]] 和 [[02-PROJECTS/Agent/工作流/规范-本机项目执行与LG知识库桥接|本机项目执行与 LG 知识库桥接规范]] 为准。

## 一句话模型

> Chat 负责讨论与收敛决策；LG 负责保存可追溯知识；MT / TS 负责证明当前事实；本地执行任务负责核实、实施与验证。

## 名词与边界

| 名词 | 含义 | 不能替代什么 |
|---|---|---|
| Chat | 普通对话：澄清需求、推演方案、比较取舍、形成结论。 | 当前代码、运行配置或本地 Git 事实。 |
| LG | LibraryG：长期背景、已确认决策、规范、索引、Daily 与历史追溯。 | 当前项目的真实实现。 |
| MT / TS | TileMatch / TileScape 本地项目仓库。 | 长期规范和历史决策库。 |
| Codex | 面向本地仓库、Git、终端、代码、配置和验证的执行任务。 | 产品方案的唯一决策者。 |
| Work | ChatGPT 的研究与交付任务入口；适合资料、文档和非代码交付。 | 不等同于 Codex；不以“省 Codex 额度”为选择理由。 |

> [!note] Chat 记忆
> Chat 已有记忆只用于快速理解、提出检索线索和形成初步判断；它不是路径、版本、参数、当前行为或已确认规则的事实依据。

## 先判断问题属于哪一类

| 要回答的问题 | 主依据 | 建议入口 |
|---|---|---|
| 应该做什么、为何取舍 | 最新用户确认与当前需求 | Chat；必要时 `LG` 查历史原因。 |
| 现在做成了什么 | 当前本地 checkout、配置和必要运行证据 | `LG + MT` 或 `LG + TS`；以项目现场核实。 |
| 过去为何这么定 | LG 稳定结论、任务档案、Daily / Archive | `LG`。 |
| 文档是否已经落后 | LG 与当前项目现场 | `对比 LG 和 MT/TS`。 |

代码与需求不一致时，不选一方“覆盖”另一方：应报告为偏差，并说明它是待实施需求、代码缺陷、半完成迁移、运行配置差异还是 LG 文档过期。

## 快捷指令

| 指令 | 意图 | 默认边界 |
|---|---|---|
| `直接分析` | 讨论、方案、文案、数据思路或低风险判断。 | 不宣称当前实现细节。 |
| `LG，分析这个问题` | 查长期背景、稳定规则和历史决策。 | 从 MOC 逐级定位，不全库盲搜。 |
| `LG，查下之前怎么定的` | 追溯旧方案、原因和适用范围。 | 区分 current、historical、draft 与 needs-review。 |
| `LG + MT，查下这个逻辑` | 用 LG 解释背景，用 MT 核实当前实现。 | 报告分支、脏工作区和验证边界。 |
| `LG + TS，查下这个逻辑` | 用 LG 解释背景，用 TS 核实当前实现。 | Unity 任务还要区分源码、运行数据、覆盖与真机验证。 |
| `以当前实现为准，LG 只作背景` | 明确本次只确认实现状态。 | 不把历史设计静默改写成当前事实。 |
| `对比 LG 和 MT/TS` | 审计知识与实现偏差。 | 默认只读、输出差异，不自动回写。 |
| `把这次结论沉淀到 LG` | 将稳定结论整理入库。 | 仅入库可复用结论、来源、范围和验证状态。 |

## 任务等级：只用足够重的流程

| 等级 | 典型任务 | 最小产物 | 是否需要 Codex |
|---|---|---|---|
| L0 讨论 | 产品方向、机制取舍、文案、参数假设。 | Chat 结论。 | 否，除非结论依赖当前实现。 |
| L1 定位 | 查历史、查路径、确认单点规则或状态。 | 结论与来源；可复用时补 LG 索引。 | 仅当前项目事实需要本地核实时。 |
| L2 实施 | 有限代码、配置、资源或 SQL 修改。 | 实施包、前提核实、验证报告。 | 是。 |
| L3 持续任务 | 重构、跨项目迁移、DDA、DLC、跨天设计/实施。 | LG `任务-主题.md` 主档、分阶段计划、Daily。 | 是；按已批准阶段执行。 |

L0/L1 不应因为“有 AI”而强制建立计划或任务档案。L3 才需要把执行计划作为跨会话主线；每个阶段都应能独立实施、验证和停止。

## 两条日常流程

### A. 不依赖当前代码的决策

```text
Chat 讨论 → 明确目标、取舍与验收 → 形成结论 → 必要时沉淀 LG
```

适用：产品讨论、机制方向、文案、数据分析思路、参数假设和不依赖实现细节的技术判断。

### B. 会影响项目实现的决策

```text
Chat 初步方案 → 本地只读核实 → Chat 定案 → Codex 实施/验证 → 稳定结论回写 LG
```

适用：代码逻辑、Unity 配置、资源加载、运行数据、SQL 字段口径、当前功能状态与项目修改。

“本地只读核实”会使用执行额度，但它用于确认方案前提；不能因节省额度而用未经核实的 Chat 假设直接驱动实现。

## INBOX 任务池（试行设计）

本节所称“任务池”用于承接值得继续推进的 Chat 结论；它不是执行授权，也不是完整聊天记录库。

> [!info] 统一入口
> 任务卡直接放入 `00-INBOX/` 根目录；原始对话材料仍可按日期主题保留为文件夹，附件仍在 `00-INBOX/attachments/`。两者通过任务卡的 `type: inbox-task` 属性区分，不另建第二个任务目录，也不移动既有内容。详见 [[02-PROJECTS/Agent/工作流/INBOX对话工作区工作流|INBOX 对话工作区工作流]]。

### 何时创建

默认由用户主动触发，例如：`整理进 INBOX`、`转成待办`、`把方案留档`。Chat 可以在以下条件同时满足时建议一次，但不得自动创建：

1. 已形成明确结论或待选方案；
2. 存在下一步负责人或明确待核实事项；
3. 未来大概率需要继续、复用或回溯理由。

纯聊天、一次性问答和没有下一步的临时想法默认仍留在对话。

### 状态：少而清楚

```text
讨论 → 方案 → 待办 → 进行中 → 完成
                 ↘
                  阻塞
```

| 状态 | 含义 |
|---|---|
| `讨论` | 有价值的问题、背景或想法，尚未形成方案。 |
| `方案` | 已有可讨论的方案，尚未决定推进。 |
| `待办` | 已决定推进；下一步可以是事实核实、补设计或实施。 |
| `进行中` | Chat、Codex 或用户正在实际推进。 |
| `阻塞` | 等待用户决定、外部资料或前置条件；恢复后回原状态。 |
| `完成` | 已形成最终结论或已有实施产物与回链。 |

`不做`、`被替代`不再新增状态：移出活跃任务池，并在任务正文记录结果与替代去向。

### 任务卡：状态不承载细节

建议每张任务笔记只保留少量可汇总属性：

```yaml
state: 方案
target: LG | MT | TS | 跨项目
next_owner: Chat | Codex | 用户
next_action: 查当前实现，确认方案是否仍适用
updated: 2026-09-15
```

正文固定为：`当前结论`、`已知事实 / 待核实`、`下一步`、`关联`。`待事实核实`、`可直接执行`、`等待用户决定`等细节用 `next_owner` 与 `next_action` 表达，不膨胀为额外状态。

### Obsidian 使用方式

推荐“一张任务一篇 Markdown 笔记 + 一个原生 Base 总览”。Base 只读取 `00-INBOX/` 中 `type: inbox-task` 的笔记属性，不另建数据库或复制内容；日常最多维护两个视图：

| 视图 | 状态 | 用途 |
|---|---|---|
| 现在要看 | `待办`、`进行中`、`阻塞` | 日常推进与排障。 |
| 讨论池 | `讨论`、`方案` | 回顾想法和等待决策，不干扰执行。 |

`完成`任务不占主视图，但保留其最终结论、LG 链接、实现或验证证据，以便追溯。

### Chat 如何交给任务池

个人 ChatGPT Plus 的日常目标是：用户在 Chat 里说“整理进 INBOX”后，由 Chat 输出一份短的固定任务包；用户将该任务包交给 Codex，Codex 才在 `00-INBOX/` 新建一张任务卡。不能把 Chat 的单句指令误解为可直接写入本机文件。

> [!info] 当前可用路线
> 完整写入型 MCP 当前不适用于个人 Plus；因此默认采用“Chat 任务包 → 用户明确交给 Codex → 本地 writer 新建卡”。先完成 3–5 张真实任务卡试用，再决定是否值得加一个显式触发的本机快捷方式。详见 [[02-PROJECTS/Agent/工作流/方案-ChatGPTPlus环境INBOX收件与交接|Plus 环境 INBOX 收件与交接方案]]。

#### 任务包的权限边界

| 环节 | 可访问范围 | 允许能力 | 不允许能力 |
|---|---|---|---|
| Chat | 对话本身。 | 生成结构化任务包。 | 假定拥有本机文件、LG 或项目状态；创建本机文件。 |
| Codex 收件 | `00-INBOX/`；任务模板。 | 校验任务包、新建任务卡。 | 编辑/移动/删除已有文件；执行任务卡；读取 MT / TS。 |
| 项目实施（后续） | 用户明确指定的 LG / MT / TS 范围。 | 按单独实施授权核实、修改和验证。 | 从建卡动作推导出实施授权。 |

项目实施、Git 操作、终端、Unity、批量改动和需要验证的工作仍优先交给 Codex；建卡只创造一个可审阅的后续入口。

#### 未来快捷方式的准入条件

1. 先有 3–5 张真实任务卡的操作证据，证明复制到 Codex 的摩擦值得优化。
2. 只允许用户显式触发的剪贴板读取和 `00-INBOX/` 排他新建；不批准 MT / TS、网络监听或后台记录。
3. 不启用浏览器自动化、第三方高权限桥接、终端、桌面、插件、worker 或会话记录。
4. 快捷方式仍只创建符合模板的任务卡，不执行其中列出的下一步。

在这些条件被真实试用证明前，维持任务包 + Codex 收件路线，不为省一步交接放宽权限。

## Chat 到 Codex 的交接

普通 Chat 不会原生把完整历史自动移交到 Codex。不要粘贴整段对话；在 Chat 收敛后，交付一份短的实施包。

```md
# 实施包：<任务名>

## 已确认目标
- <待填写>

## 不在本次范围
- <待填写>

## 已确认方案与约束
- <待填写>

## 验收标准
- <待填写>

## 风险与回滚
- <待填写>

## 需先核实的项目事实
- <待填写>

## 执行边界
- 前提冲突、影响范围扩大或出现新决策时，停止修改并报告。
```

交给 Codex 时，先要求其只读核实“需先核实的项目事实”；确认一致后再实施。小任务可直接在任务消息中携带该实施包；跨日或跨项目任务按现有规范放入 LG 对应任务档案。

## 持续整理的触发条件

不按聊天轮次重复归档。出现以下任一变化时，才对本指南、协议、任务主档或 Daily 做增量整理：

- 用户确认了新的长期协作规则，或否定了旧规则；
- 真实任务暴露出交接丢失、错误路由、重复检索、权限或验证问题；
- 本地项目核实推翻或修正了 LG 中的历史结论；
- 外部实践带来可验证、且适合 LG 边界的新机制；
- L3 任务完成一个阶段、变更范围或形成新的可复用入口。

每次整理只记录新增结论、来源、适用范围和待验证项；先更新已有主档或索引，避免为同一规则创建平行文档。连续试行 3–5 个真实任务后，再决定是否把草案升级为 `current`。

## 何时沉淀 LG

值得沉淀：已确认决策、长期背景、术语、机制、可复用代码/配置入口、验证边界与重要偏差。

不应直接成为正式知识：临时想法、未确认方案、完整聊天记录、一次性排查过程和已失效尝试。它们可留在对话、Daily、任务档案或 INBOX，并标明状态。
