## 1. 知识库架构策略

### 1.1 现有架构诊断

目前 LibraryG 采用改良版 PARA 结构：

```
00-INBOX/   → 捕获层（暂存未经处理的中间产物）
01-DAILY/   → 时序层（以日期为轴的工作记录）
02-PROJECTS/ → 项目层（按项目/模块组织）
03-KNOWLEDGE/ → 知识层（领域知识沉淀）
04-TEMPLATES/ → 模板层（可复用的结构化模板）
05-ARCHIVE/  → 归档层（过期但不删除的内容）
```

**优点**：时间线—项目—知识三层分离清晰，INBOX 捕获机制健康，MOC 导航体系成熟。
**缺口**：缺少「参考层」与「流程层」的显式划分；知识更新依赖人工，缺乏版本化机制。

### 1.2 分层策略：五层 + 两横

建议将知识库扩展为 **5 个纵向层级 + 2 个横向维度**：

```
纵向层级（按生命周期和结构化程度递增）：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

层级 0: 捕获层 (00-INBOX)
  特征：非结构化、临时、未经处理
  管理策略：每周整理，过期未处理自动移入 05-ARCHIVE
  现有覆盖：✅ 已完善

层级 1: 时序记录层 (01-DAILY)
  特征：按时间线性排列，天然不可变
  管理策略：只追加不修改，周度/月度汇总后可在 DAILY 内保留摘要指针
  现有覆盖：✅ 已完善，可补充「月报摘要」机制

层级 2: 项目与流程层 (02-PROJECTS + 03-KNOWLEDGE/工作流)
  特征：有明确边界和状态的生命周期文档
  子分类建议：
  ├─ 项目文档 (02-PROJECTS/) — 与项目绑定，随项目生命周期变化
  │   ├─ analysis/  技术分析
  │   ├─ report/    工作报告
  │   ├─ spec/      项目内规范
  │   └─ _MOC.md   项目导航
  └─ 流程文档 (03-KNOWLEDGE/工作流/) — 跨项目、可复用的操作规程
      现有：INBOX工作流、日志同步规范
      建议新增：知识库更新流程、Agent 行为规范、记忆蒸馏 SOP
  现有覆盖：⚠️ 项目和流程未显式分离，可通过 frontmatter 区分

层级 3: 知识层 (03-KNOWLEDGE/)
  特征：跨项目、稳定、高度结构化
  子分类建议：
  ├─ 工作流/      操作规程（已少量）
  ├─ Unity/       引擎知识（已有）
  ├─ TileV2-Editor/ 编辑器知识（已有）
  ├─ Game-Logic/  游戏逻辑（已有）
  ├─ 参考/        外部参考资料、术语表、标准化文档
  └─ FAQ/         高频问答集（新增建议）
  现有覆盖：✅ 结构初步形成，可补充 FAQ 和参考层

层级 4: 模板与范式层 (04-TEMPLATES/)
  特征：最高结构化度，直接可复制使用
  现有覆盖：✅ 5 个模板已完善
  优化建议：为模板添加 frontmatter 说明适用场景与使用条件

横向维度 A — 知识状态管理：
  draft → review → finalized → deprecated
  （通过 frontmatter status 字段实现，现有 draft/finalized 两个状态，
   建议增补 review 和 deprecated，形成完整生命周期）

横向维度 B — 来源追踪：
  每个知识文档标记 source: conversation | manual | extracted | external
  便于追溯知识来源和更新时机
```

### 1.3 知识分类体系优化

在当前 `type` 体系（spec/analysis/report/reference/note/index）基础上：

| 现有 type | 优化方向 | 新增建议 |
|-----------|---------|---------|
| `spec` | 保持不变 | 补充 review 状态前需经过 peer review |
| `analysis` | 保持不变 | 增加 version 管理（已实施） |
| `report` | 保持不变 | 增加关联决策链接字段 `decisions: [...]` |
| `reference` | 保持不变 | — |
| `note` | 保持 | 建议设定过期检查周期（如 90 天） |
| `index` | 保持不变 | — |
| — | **新增 `faq`** | 高频问答，按主题组织，支持全文检索 |
| — | **新增 `workflow`** | 工作流文档（与流程层对齐，区别于 spec） |
| — | **新增 `decision`** | 关键决策记录（谁、何时、为何、后果） |

### 1.4 知识更新与维护机制

**被动更新（触发式）：**
- **对话中发现过时**：Agent 在引用旧文档时，通过 frontmatter date 判断时效性，标记提醒
- **项目状态变更**：项目进入新阶段时，关联的 analysis/report 需同步检视
- **错误修正**：发现错误立即修正，同时更新 `date` 字段

**主动更新（周期式）：**
- **周度检查**（结合现有健康检查流程）：扫描所有 `status: draft` 文档，超过 14 天未更新则标记过时
- **月度蒸馏**：合并 INBOX 中相似主题的草稿，删除重复内容
- **季度归档**：将不再活跃的项目文档从 02-PROJECTS 移至 05-ARCHIVE

**版本化策略：**
- `analysis` 类使用显式版本号（v1/v2...），已实施
- `spec` 类在发生不兼容变更时更新版本号
- 其余类型不强制版本化，通过 `date` 字段判断时效
- 关键文档在文件头标注 `supersedes: [旧文档路径]` 和 `superseded_by: [新文档路径]`

## 2. Agent 与知识库交互策略

### 2.1 检索策略（三层漏斗）

```
用户提问
  │
  ▼
第一层：Memory 层（0 latency）
  工作记忆（当前对话上下文）+ 项目记忆（MEMORY.md）
  → 快速判断：这个问题是否已有答案？
  → 命中 → 直接回答，不查知识库
  → 未命中 →
  │
  ▼
第二层：索引层（Obsidian MOC + 全文搜索）
  通过 vault 搜索、MOC 导航、标签过滤缩小范围
  → 使用场景：需要引用具体知识文档
  → 检索方式：
    ├─ 关键词搜索（Obsidian search / Grep）
    ├─ 标签过滤（tags 字段筛选）
    ├─ MOC 导航（MOC 文件作为"目录"快速定位）
    └─ 链接追踪（反向链接发现关联文档）
  │
  ▼
第三层：深度检索层（多文档综合分析）
  当问题涉及多个知识点或需要交叉验证时
  → 同时加载多个文档，综合分析后输出
  → 使用场景：对比分析、方案设计、问题排查
```

### 2.2 RAG 策略（针对 WorkBuddy 的定制化方案）

WorkBuddy 不是传统 RAG 系统（没有独立的向量数据库），而是**基于文件系统 + Agent 工具**的检索架构：

| RAG 组件 | WorkBuddy 实现 | 优化建议 |
|----------|---------------|---------|
| 文档分块 | 以 markdown 文件为自然单元 | 单个文件不宜超过 500 行；长文档拆分为多个文件 + MOC 索引 |
| 嵌入/向量化 | 不适用（无向量库） | 通过 Obsidian 搜索和 Grep 实现全文检索，依赖关键词命中 |
| 检索 | Read/Grep/Glob 组合 | 先 Grep 搜索相关内容，再 Read 全文，避免一次性加载过多文档 |
| 排序 | 无显式排序 | 通过 frontmatter 的 `status` 和 `date` 字段在 Agent 端做后过滤 |
| 引用 | 直接引用文件路径 | 在回答中标注来源文件路径，便于回溯验证 |

**关键优化建议：**

1. **Search-First, Read-Second 模式**：Agent 收到知识库相关问题时，先通过 Grep 或 vault search 定位相关文档，再选择性读取。避免"一股脑读完"。

2. **MOC 作为路由导航**：对于跨领域问题，先读取 MOC 文件获取模块地图，再定向读取具体文档。这相当于"索引优先"策略。

3. **Frontmatter 过滤**：检索结果中按 `status: finalized` 过滤掉草稿，按 `date` 优先选择较新版本。这个过滤逻辑应在 Agent 行为规范中固化。

4. **上下文窗口管理**：
   - 引用文档片段时优先输出结论性章节（如摘要、结论、关联）
   - 完整原文存于文件，Agent 倾向于摘要而非全文复述
   - 跨多个文档时，优先整合 MOC 指向的核心文档

5. **元数据增强**：在 frontmatter 增加 `keywords` 字段作为 Grep 精确匹配的辅助索引，弥补无向量检索的语义盲区。

### 2.3 知识库写入策略

Agent 对知识库的写入应有明确边界：

| 操作 | 允许条件 | 规则 |
|------|---------|------|
| 创建新文档 | 对话中形成明确结论 | 使用对应模板，填写完整 frontmatter，关联 MOC |
| 更新现有文档 | 修正错误或补充信息 | 先 Read 再 Edit，更新 `date`，标注修改原因 |
| 移动文件 | INBOX 整理阶段 | 按分类标准移动到目标目录，更新 MOC 引用 |
| 删除文件 | 仅在确认不再需要时 | 优先用归档替代删除（移动到 ARCHIVE） |
| 修改 MOC | 新增/移动/删除文档时 | 同步更新，不可遗漏 |

**写入规范（已部分实施，建议固化到 Skill 中）：**
- 新建文档必须使用模板
- 必须更新对应 MOC
- 必须填写完整的 frontmatter
- 必须维护 `## 关联` 章节（双向链接）

## 3. Memory 架构设计

### 3.1 现有 Memory 架构分析

目前已有三层记忆系统：

```
Layer 1: 云记忆（WorkBuddy 云端，只读）
  - 自动注入的用户长期画像
  - 跨会话的 Conversation Search

Layer 2: 用户级本地记忆 (~/.workbuddy/MEMORY.md)
  - 跨项目的用户偏好和硬规则
  - 上限 4000 字符/会话

Layer 3: 工作空间记忆 (D:\LibraryG\.workbuddy/memory/)
  ├─ MEMORY.md (项目级长期笔记，上限 3000 字符/会话)
  └─ YYYY-MM-DD.md (每日工作日志，append-only)
```

**现有设计的优势**：三层分离合理，短期-长期边界清晰，append-only 日志天然防丢失。
**缺口**：缺乏显式的遗忘机制、跨会话检索依赖 Conversation Search（非本地）、状态与实体缺乏结构化。

### 3.2 优化后的四层记忆模型

建议扩展为四层，在现有三层基础上增加一层「结构记忆」：

```
第 0 层（最快）  [对话上下文]         → 当前会话，不持久化
  范围：当前对话的所有交互内容
  生命周期：一次对话
  存储：Agent 上下文窗口
  管理：无（自然消失）

第 1 层（快速）  [工作记忆]            → 当日状态，append-only 日志
  当前实现：D:\LibraryG\.workbuddy/memory/YYYY-MM-DD.md
  范围：当日工作记录、临时决策、完成情况
  生命周期：最长 30 天（之后蒸馏到项目记忆）
  存储：纯文本文件，append-only
  检索：按日期读取
  现有覆盖：✅ 已实现

第 2 层（中速）  [项目长期记忆]         → 核心知识，curated
  当前实现：D:\LibraryG\.workbuddy/memory/MEMORY.md（有字符限制）
  优化建议：在 Obsidian vault 中建立显式的「结构化项目记忆」
  范围：项目约定、架构决策、关键经验、踩坑记录
  生命周期：永久（除非主动废弃）
  存储：
    ├─ .workbuddy/memory/MEMORY.md      — Agent 快速参考（精简版，3000 字符）
    └─ 02-PROJECTS/WorkBuddy/MEMORY/    — 完整版（无字符限制，MOC 索引）
  > 这样：Agent 在对话中快速读取 MEMORY.md；深度检索时走 Obsidian MOC
  > 两条路线，各司其职
  检索：Agent 启动时自动读入短版；按需加载完整版

第 3 层（慢速）  [知识库记忆]           → 结构化知识，非 Memory
  范围：03-KNOWLEDGE/、02-PROJECTS/ 下的所有文档
  生命周期：永久（遵循知识库更新机制）
  存储：Obsidian Markdown 文件
  检索：MOC 导航 + 全文搜索
  现有覆盖：✅ 已实现（但这层应视为知识库，非传统 Memory）
```

### 3.3 记忆的存储格式优化

**当前 MEMORY.md 的问题**：纯文本摘要，缺乏结构化，Agent 读取后难以精确提取信息。

**优化建议**：

```markdown
# LibraryG 项目记忆

## 项目约定
- 日常开发：Unity C# 在 D:\meatloaf_client01\Claw
- 规范文档：参考 TileMatch 知识库分类标准
- ...

## 踩坑记录
- 2026-07-03: 知识库污染事故 — 根因：Python 脚本批量写文件未展示 diff
  教训：禁止私自用 Python 脚本批量改文件
  关联：规范-知识库健康检查.md

## 重要决策
- 2026-07-06: 禁止自动 commit 仅针对 meatloaf_client01 公用 git
  私人 git 在授权下可 commit
- 2026-07-08: workbuddy_sync frontmatter 废弃，全 vault 清理

## 当前活跃事项
- [WIP] 知识库架构优化设计（2026-07-13）
```

这种格式让 Agent 可以在 MEMORY.md 中按节 grep 提取信息，而不是整块读取。

### 3.4 遗忘与蒸馏机制

当前的蒸馏规则（30 天以上 daily logs 蒸馏到 MEMORY.md 后删除）可以进一步细化：

```
┌───────────────────────────────────────────┐
│ 每日日志 (YYYY-MM-DD.md)                    │
│ Append-only，记录"做了什么 + 关键结论"       │
└──────────────┬────────────────────────────┘
               │ 每 30 天
               ▼
┌───────────────────────────────────────────┐
│ 蒸馏阶段（由 Agent 执行）                    │
│                                           │
│ 1. 扫描过去 30 天的所有 daily logs          │
│ 2. 提取三类内容：                            │
│    ├─ 关键决策 → 写入 MEMORY.md「决策」节    │
│    ├─ 踩坑经验 → 写入 MEMORY.md「踩坑」节    │
│    └─ 项目产出 → 创建/更新知识库文档         │
│ 3. 纯日志性内容（开会、日常沟通）→ 丢弃       │
└──────────────┬────────────────────────────┘
               │
               ▼
┌───────────────────────────────────────────┐
│ 蒸馏后操作                                  │
│ 1. MEMORY.md 超限 → 保守合并，不删仍相关内容  │
│ 2. 关键长期事实 → 写入 Obsidian（单一源）     │
│ 3. 删除 30 天前的 daily logs（确认已蒸馏）    │
└───────────────────────────────────────────┘
```

**遗忘规则**：
- 对话上下文（第 0 层）：每次会话自然清除
- 工作记忆（第 1 层）：蒸馏后删除，不保留原始日志
- 项目记忆（第 2 层）：被动遗忘——仅在 MEMORY.md 超限时压缩；用户主动标记 `deprecated` 的内容可删除
- 知识库（第 3 层）：不遗忘，只标记 `deprecated` 或移至 ARCHIVE

## 4. 三者协同模式

### 4.1 核心协作模型

```
      用户需求 / 触发事件
            │
            ▼
    ┌───────────────────┐
    │   工作流 (Workflow)  │  ← 流程编排层
    │   Skill / SOP      │     定义"怎么做"
    └────────┬──────────┘
            │ 调度
            ▼
    ┌───────────────────┐
    │    Agent           │  ← 执行引擎
    │   WorkBuddy        │     做"具体操作"
    └──┬─────────────┬──┘
       │             │
       ▼             ▼
┌──────────┐   ┌──────────┐
│ 知识库    │   │ Memory  │  ← 知识与记忆
│ Obsidian │   │ .workbuddy│   存储"已知道什么"
└──────────┘   └──────────┘
```

**三者的职责边界**：

| 组件 | 定位 | 核心产出 | 不可做什么 |
|------|------|---------|-----------|
| 工作流（Skill） | 流程编排 | 操作手册、SOP、检查清单 | 不能执行具体操作，不能决策 |
| Agent | 执行引擎 | 搜索、读写、分析、产出 | 不能跳过工作流中的步骤，不能违反知识库规范 |
| 知识库 | 知识存储 | 文档、规范、参考、索引 | 不能调度执行，不包含流程步骤逻辑 |
| Memory | 记忆存储 | 工作经验、决策、习惯 | 不能存储需要结构化的知识（应在知识库中） |

### 4.2 典型协作场景

**场景 A：新任务 → 知识检索 → 执行 → 记录**

```
1. 用户："分析火箭牌的碰撞逻辑"
2. Agent 检查 MEMORY.md → 找到「火箭牌 V2 分析已完成」
3. Agent 通过 MOC 定位到 02-PROJECTS/TileMatch/游戏逻辑/Rocket/
4. Agent 读取分析文档 → 理解现有逻辑
5. Agent 执行分析（读代码 + 写分析文档）
6. Agent 写入 03-KNOWLEDGE/ → 更新 MOC
7. Agent 在今日 daily log 记录完成事项
8. Agent 蒸馏关键结论到 MEMORY.md
```

**场景 B：工作流驱动的规范维护**

```
1. 用户："归档今天的工作"
2. Agent 触发 inbox-organizer Skill（工作流）
3. 工作流定义步骤：扫描 INBOX → 分类 → 展示建议 → 等待确认 → 执行
4. Agent 按步骤执行：
   a. 读取 INBOX 对话文件夹
   b. 按知识库分类标准判断去向
   c. 展示建议给用户确认
   d. 执行移动/删除/更新 MOC
   e. 写入 daily log 记录
```

**场景 C：知识库过时检查**

```
1. 周度健康检查 Skill 被触发（自动化或手动）
2. Skill 定义检查项：frontmatter 完整性 / 断链 /status 陈旧度
3. Agent 执行：扫描所有文档 → 生成报告 → 展示给用户
4. 用户确认处理方案后，Agent 执行更新
5. 知识库文档更新 → MOC 同步更新
6. 操作记录写入 daily log
```

### 4.3 多 Agent 场景下的知识共享

当前是单 Agent 架构，但未来可能扩展到多 Agent。规划建议：

| 场景 | 知识共享策略 | 实现方式 |
|------|-------------|---------|
| 同项目多 Agent | 共享知识库 + 共享 MEMORY.md | 所有 Agent 读同一个 vault、同一个 memory |
| 跨项目 Agent | 知识库各自独立，通过引用链接 | 一个 Agent 可在授权后 vault search 另一个项目的文档 |
| 专用 Agent（如 Code Review） | 访问特定子集 | 通过 Skill 限定的读取权限和路径白名单 |

**关键原则**：
- **Obsidian vault 是单一源**：所有 Agent 的知识来源统一为 LibraryG vault
- **Memory 按项目隔离**：不同项目的 Agent 读写各自的 `.workbuddy/memory/MEMORY.md`
- **跨 Agent 通信不经过 Memory**：短期协作信息通过工作流传递，非 Memory
- **知识同步方向**：Agent 写入 → 知识库持久化 → 其他 Agent 读取。不允许多 Agent 同时写入同一文档

### 4.4 冲突检测

当多个来源对同一知识产生不同版本时：

1. **时间优先**：以最新 `date` 为准
2. **类型优先**：`spec`（规范）> `analysis`（分析）> `note`（笔记）
3. **人工裁决**：Agent 检测到冲突时，先标记 `conflict`，展示差异给用户确认
4. **版本化**：冲突的分支版本可以共存，在文档中注明分歧点并存档

## 5. 可扩展性与治理

### 5.1 随着规模增长保持可维护性

**文档规模增长应对策略：**

| 规模区间 | 策略 | 检查点 |
|---------|------|-------|
| < 100 文件 | 当前结构直接可用 | 无需额外操作 |
| 100-500 文件 | 引入子 MOC 层级、分类内 cat_order 管理 | 健康检查纳入周度规范 |
| 500-2000 文件 | 考虑按模块拆分 MOC、引入标签分类索引 | 年度架构审计 |
| > 2000 文件 | 引入知识库搜索引擎（而非纯文件搜索） | 按需决策 |

**关键瓶颈预警**：
- 单文件夹超过 50 个文件 → 拆分子文件夹
- 单个 MOC 超过 30 个链接 → 拆分子 MOC
- 全文搜索响应变慢 → 启用 Obsidian 搜索缓存或第三方索引工具

### 5.2 知识质量管控体系

**质量门禁（3 级检查）：**

```
新建文档时（Agent 自动检查）：
  ┌─ 格式检查：frontmatter 必填字段完整性
  ├─ 命名检查：符合分类命名规范
  ├─ 链接检查：内容中引用的文档是否存在
  └─ 模板检查：必须使用对应模板创建

────── 强制通过 ──────

周度健康检查（Skill 执行）：
  ┌─ 断链检查：无 unresolved links
  ├─ 属性检查：frontmatter 六字段 + 值域合法性
  ├─ MOC 覆盖率检查：所有文档都在 MOC 中
  ├─ cat_order 合规性：连续编号，无重复
  ├─ 链接路径风格：项目内用基名，跨项目用全路径
  ├─ 命名规范：无中文命名冲突
  └─ 零污染：无意外创建的文件

────── 人工处理 ──────

季度架构审计：
  ┌─ 陈旧度检查：查找 90 天未更新的文档
  ├─ 冗余检测：内容重复的文档合并
  ├─ 结构审计：目录层级是否合理
  └─ 分类迁移：需要调整分类的知识迁移
```

### 5.3 权限与安全

个人知识库场景下权限相对简单，但仍有几个要点：

| 维度 | 策略 | 实现方式 |
|------|------|---------|
| 文件访问 | Agent 可读所有文件，写入遵循规范 | 通过 Skill 约束 Agent 的写操作 |
| 敏感信息 | 密钥/token 存于 vault 外 | 环境变量或专用配置文件 |
| Agent 行为 | Memory 写操作限定在 `.workbuddy/memory/` | 禁止 Agent 修改 Obsidian 配置目录 |
| 破坏恢复 | 知识库污染恢复机制 | 现有经验（2026-07-03 事故已有恢复方案） |

### 5.4 技能（Skill）作为治理单元

Skill 是 WorkBuddy 生态中的关键治理单元。建议固化以下原则：

```
┌────────────────────────────────────────┐
│           治理层级                      │
│                                        │
│  原则层 (Principles)                    │
│  → 硬规则，不可绕过                     │
│  → 存储：用户级 MEMORY.md              │
│    例：禁止私自 Python 批量改文件        │
│                                        │
│  规范层 (Policies)                      │
│  → 可执行的规则                         │
│  → 存储：03-KNOWLEDGE/工作流/           │
│    例：知识库文档分类标准                │
│                                        │
│  流程层 (Procedures)                    │
│  → 具体操作步骤                         │
│  → 存储：Skill (SKILL.md)              │
│    例：inbox-organizer 的整理流程        │
│                                        │
│  执行层 (Execution)                     │
│  → 一次性的具体操作                      │
│  → 由 Agent 在对话中完成                │
└────────────────────────────────────────┘
```

**Skill 的治理规则**：
- 每个 Skill 必须明确「触发条件」和「边界条件」
- Skill 应引用知识库中的规范文档作为依据，而非在 Skill 内部重复规范内容
- Skill 的更新应通知所有依赖该 Skill 的工作流
- Skill 的安装需经过安全检查（skill-vetter）

### 5.5 自动化与 Cron 建议

基于当前架构，建议设立以下自动化任务：

| 任务 | 频率 | 触发方式 | 职责 |
|------|------|---------|------|
| 知识库健康检查 | 周度 | 自动化 | 扫描断链/属性/MOC 覆盖率 |
| Memory 蒸馏 | 月度 | 自动化 | 30 天以上 daily logs 蒸馏 |
| INBOX 清理提醒 | 每周 | 自动化 | 检查 INBOX 是否有 7 天以上未整理内容 |
| 知识库格式审计 | 季度 | 手动 | 分类迁移、冗余检测 |
| 技能更新检查 | 每月 | 手动 | Skill 是否有过时指令 |
