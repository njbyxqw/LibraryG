## P2：MOC 使用情景验收样例

WorkBuddy 只按下列情景走链接并记录结果，不根据文件名全库搜索，不改文件。

| 情景 | 预期路径 |
|---|---|
| 查 TileMatch 障碍机制 | `AI总MOC → TileMatch MOC → 局内障碍知识库 MOC → 具体障碍文档` |
| 查 TileScape GM 工具 | `AI总MOC → TileScape MOC → GM 工具 MOC → 具体工具/规则` |
| 查 TileScape 文档或资源位置 | `AI总MOC → TileScape MOC → Docs 索引或快速定位索引` |
| 查可迁移 Unity / 编辑器方法 | `AI总MOC → 通用知识 MOC → 对应 Knowledge 条目 → 来源项目 MOC` |
| 查 LG 维护或 INBOX 规则 | `AI总MOC → Agent 工作流 MOC → 对应 current 规范` |

验收报告必须列出：实际经过的文件、未能继续的位置、链接是否存在、是否误入项目/历史资料；不要求 Obsidian Dataview 或 Canvas 动态渲染验证。

## 后续任务包硬边界

- 不移动、删除、重命名或覆盖历史文档，除非用户已确认具体文件和目标路径。
- 不创建没有真实内容的专题 MOC。
- 不将项目专属类、路径、配置值、功能实现和任务进度复制到 `03-KNOWLEDGE`。
- 任何可迁移知识都标明来源项目、适用范围、验证状态，并回链项目事实。
- 不 commit / push；不修改 MT / TS 代码仓库。
- 执行反馈和验收记录默认留在任务 INBOX，不视为待清理垃圾。

## 每个任务的最小文件结构

```text
00-INBOX/YYYY-MM-DD-主题/
├─ 规划-主题.md          # AI：目标、范围、风险、任务包和验收标准

```
